# Business Specification: FEAT-015 — интероп с мета-оркестратором (МО) в плагинной модели

status: approved (пользователь, 2026-10-04; открытые вопросы 1–2 — как в тексте, 3 — DESIGN)

## Контекст и Цели

Над стендами систем, разрабатываемых под SDX, появляется мета-оркестратор (МО). Принцип — генотип/фенотип: репозиторий системы описывает её и о стендах не знает, стенды ведёт МО; канал связи — файловый почтовый ящик `.mesh/` в репозитории системы (вне git, создаёт узел МО). Единственный признак «над проектом есть МО» — файл `.mesh/endpoint.yaml` (`MO-INTEROP.md` §0, стр. 8–13). Запись в каталоги исполнения стендов (`exec_paths`) допустима только под арендой МО; лист-сессия узнаёт аренду из своего inbox. Протокол и инструменты лист-сессии выпущены как sim-kit 0.7.3 (`sim-kit/VERSION`; файлы `core/MO-INTEROP.md`, `core/mesh_endpoint.py`, `core/devagent_hook.py`), а `MO-INTEROP.md` уже переписан под плагинную модель (ADR-013): инструменты живут в `${CLAUDE_PLUGIN_ROOT}/sdx/mo/`, в репозитории системы остаётся только `.mesh/`.

Цель поставки — выполнить обязательства SDX из `MO-INTEROP.md` (§1, §3, §4, §6) так, чтобы плагин оставался безопасным по умолчанию (REQ-PLUGIN-4): в проекте без `.mesh/endpoint.yaml` ничего не меняется и python не запускается; зависимость от `python3`/PyYAML возникает только у проекта под МО, не у плагина. Ожидаемый результат — вендорённая копия sim-kit в плагине, хук-обёртка в проводке, SessionStart-показ ящика, переключатель в агенте `devops`, две нормы в протоколе и обновление поверхностей состава плагина. Политика вендоринга (PROC-028, `sdx/protocol.md`, «Вендорённые компоненты (`sdx/mo/`)») и сторож `sdx/hooks/test-mo-inventory.sh` уже действуют; сторож правится только в части [6] (отсутствие каталога — регресс), политика не переписывается; спека опирается на них.

Обозначения: `DH` = `devagent_hook.py`, `ME` = `mesh_endpoint.py`, `MI` = `MO-INTEROP.md` (все в `sim-kit/core/`); ссылки `DH:N`/`ME:N`/`MI:N` — номера строк по `context_report.md`.

## Требования

### Вендоринг (REQ-MO-VEND)

- [ADDED] **REQ-MO-VEND-1.** В плагине появляется каталог `sdx/mo/` с тремя файлами `mesh_endpoint.py`, `devagent_hook.py`, `MO-INTEROP.md` — байт-в-байт копия `sim-kit/core/` версии 0.7.3, и файлами фиксации `SIMKIT_VERSION` (`0.7.3`) и `SIMKIT_SHA256` (формат `sha256sum`) в соответствии с политикой PROC-028. Локальные правки вендорённых файлов запрещены (политика PROC-028).
- [ADDED] **REQ-MO-VEND-2.** В проекты ничего из `sdx/mo/` не копируется; в репозитории системы под МО остаётся только `.mesh/` (`MI:4–6`).
- [ADDED] **REQ-MO-VEND-3.** Каталог `sdx/mo/` в чекауте не содержит `__pycache__` и иных неперечисленных файлов (сторож `test-mo-inventory.sh`, проверка (г)); сторож после появления каталога переходит из состояния «пропуск (INFO)» в реальную проверку и должен быть зелёным. Сторож правится только в части [6]: отсутствие каталога `sdx/mo/` — регресс (FAIL), а не пропуск.
- [ADDED] **REQ-MO-VEND-4.** Нигде в поставке (в проводке, обёртке, SessionStart-части, агентах, командах) инструменты `sdx/mo/` не вызываются без `PYTHONDONTWRITEBYTECODE=1`, чтобы импорт `mesh_endpoint` не создавал `sdx/mo/__pycache__/` в корне плагина (инвариант ADR-013 «плагин не пишет в свой корень в рантайме»; по `context_report.md` §3 это единственная нарушающая запись в корень плагина). Исключение — внешние вызовы вне контроля SDX, см. «Границы».

### Хук-обёртка (REQ-MO-HOOK)

- [ADDED] **REQ-MO-HOOK-1 (проводка).** В `hooks/hooks.json` добавляется запись `PreToolUse` с matcher `Bash|Write|Edit|MultiEdit|NotebookEdit`, вызывающая `bash "${CLAUDE_PLUGIN_ROOT}"/sdx/hooks/mo-hook.sh` (инвариант формы вызова BUG-008: интерпретатор указан явно, не зависит от бита `x`). В записи нет `timeout`-обёртки (BUG-010: на macOS `timeout` отсутствует, и `timeout … ; exit 0` для PreToolUse превратился бы в тихое «защиты нет»). Запись `prod-guard` (matcher `Bash`) сохраняется без изменений.
- [ADDED] **REQ-MO-HOOK-2 (порядок проверок).** Обёртка выполняет проверки строго в таком порядке: (1) наличие `${CLAUDE_PROJECT_DIR}/.mesh/endpoint.yaml`; (2) режим `on_write`; (3) наличие `jq`, `python3` и файла хука `sdx/mo/devagent_hook.py`. Наличие PyYAML обёртка **не** предпроверяет: хук sim-kit сам превращает «нет PyYAML» в `cannot_check` по режиму (`DH:51–55`, `DH:43–48`) — `deny` → `exit 2` с причиной в stderr, `notice` → `exit 0` и одна строка; наблюдаемое поведение для критериев 4–5 то же, а второй запуск python на каждый вызов инструмента не нужен (решение пользователя на коллизии SPEC ↔ DESIGN, `decisions_log.md`). Отсутствие любой из зависимостей из п.3 не может повлиять на проект без `.mesh/endpoint.yaml` (образец — BUG-002).
- [ADDED] **REQ-MO-HOOK-3 (проект без МО).** Если `.mesh/endpoint.yaml` отсутствует, обёртка завершается `exit 0` без вывода в stdout и stderr; `python3` не запускается, `jq` не требуется. Это не зависит от текущей ветки и наличия сессии/`.claude/sdx` (МО-хук привязан к `.mesh/endpoint.yaml`, а не к ветке `sdx/<id>`: запись в `exec_paths` мимо сессии — как раз целевой случай).
- [ADDED] **REQ-MO-HOOK-4 (чтение режима).** Режим берётся из `.mesh/endpoint.yaml` без PyYAML, по правилу, дословно совпадающему с `DH:35–40` (`^\s*on_write\s*:\s*['"]?(\w+)`, регистр значения не учитывается, берётся первое совпадение, при отсутствии совпадения или ошибке чтения — `notice`). Любое иное значение, кроме `deny`, трактуется как `notice`, как у хука sim-kit. Совпадение трактовки обёртки и `DH` на общих фикстурах `endpoint.yaml` проверяется тестом.
- [ADDED] **REQ-MO-HOOK-5 (политика отказа: невозможность проверить цель).** Если `endpoint.yaml` есть, а проверить цель записи нельзя (нет `python3`; python3 есть, но нет PyYAML — этот случай обрабатывает сам хук sim-kit, обёртка лишь транслирует его исход; нет `jq`, необходимого обёртке; нечитаемый вход; хук sim-kit завершился кодом, отличным от 0 и 2, — traceback, сигнал, 126/127), то: в режиме `notice` — ровно одна строка в stderr и `exit 0` (fail-open); в режиме `deny` — JSON `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"…"}}` на stdout и `exit 0` (fail-closed; не `exit 2`). Это воспроизводит политику 0.7.3 (`MI:68–71`, `DH:12–14,43–48`); для случая «иной код выхода хука» это расширение политики на ситуацию, прямо не названную в `MI`, по тому же принципу.
- [ADDED] **REQ-MO-HOOK-6 (передача хуку sim-kit).** Во всех остальных случаях обёртка запускает `python3 "${CLAUDE_PLUGIN_ROOT}/sdx/mo/devagent_hook.py"` с тем же stdin, который получила сама (однократный поток не теряется), с `CLAUDE_PROJECT_DIR` проекта и `PYTHONDONTWRITEBYTECODE=1`. Содержательную проверку цели записи (аренда, `exec_paths`, конверт `notice`, окно подавления) выполняет только хук sim-kit; обёртка её не дублирует.
- [ADDED] **REQ-MO-HOOK-7 (трансляция блока).** Если хук sim-kit завершился `exit 2` (его конвенция блока, `DH:11,14,184`, `MI:70`), обёртка наблюдаемо для харнесса: печатает на stdout JSON `permissionDecision: "deny"` с `permissionDecisionReason` = stderr хука и завершается `exit 0`. stderr хука при этом не дублируется на выход обёртки и `exit 2` обёртки не возвращается (механизм блокировки PreToolUse по `sdx/protocol.md`, «Механизм блокировки PreToolUse»). При `exit 0` хука его stderr (одна строка `devagent_hook: …` режима `notice`) пробрасывается.
- [ADDED] **REQ-MO-HOOK-8 (охрана ящика).** Обёртка сама отказывает (JSON deny, `exit 0`) инструментам `Write`/`Edit`/`MultiEdit`/`NotebookEdit`, целью которых является `.mesh/endpoint.yaml` или `.mesh/cursors.json` проекта, независимо от режима `on_write` и от наличия `exec_paths` (хук sim-kit эти записи пропускает — `DH:145–146`, прогнано в `context_report.md` §2.1). Для `Bash` обёртка такой охраны не обеспечивает; это названная граница (см. «Границы»). Основание: файл пишет узел МО, dev-agent его не правит (`MI:12`).
- [ADDED] **REQ-MO-HOOK-9 (независимость хуков на `Bash`).** На вызов `Bash` срабатывают два PreToolUse-хука (`prod-guard` и `mo-hook`). Требование: каждый хук независим, `deny` любого из них достаточен для блока; ни один не зависит от решения другого и не пытается вывести паттерны другого. Свойство «`deny` любого хука блокирует вызов» — свойство харнесса, а не обязательство плагина: источник утверждения о приоритете решений (FEAT-006: `deny > defer > ask > allow`) не проверен и фактом не принимается; проверка — исполнением на реальном харнессе в Verification, а если она невозможна — запись допущения в артефакты сессии.
- [ADDED] **REQ-MO-HOOK-10 (safe-by-default, переносимость).** Обёртка выводит ошибки/блоки только по правилам REQ-MO-HOOK-3…8; не использует `timeout` и конструкции bash > 3.2, недоступные на macOS (BUG-010); не пишет в корень плагина и не пишет в `.mesh/` сама (запись в `.mesh/` — только побочный эффект хука sim-kit: `cursors.json`, `hook-state.json`, `outbox/`).

### SessionStart (REQ-MO-SESS)

- [ADDED] **REQ-MO-SESS-1 (отдельная запись).** МО-часть SessionStart — отдельная запись `hooks/hooks.json` (`bash "${CLAUDE_PLUGIN_ROOT}"/sdx/hooks/mo-session.sh`, без `timeout`, форма вызова — BUG-008); существующий `preflight.sh` не меняется.
- [ADDED] **REQ-MO-SESS-2 (проект без МО).** Без `${CLAUDE_PROJECT_DIR}/.mesh/endpoint.yaml` скрипт молчит (нет вывода, `exit 0`, python не запускается). Гард `.claude/sdx` на МО-часть не распространяется: проект под МО может не быть проектом под SDX.
- [ADDED] **REQ-MO-SESS-3 (проект с МО).** При наличии `.mesh/endpoint.yaml` скрипт выполняет `mesh_endpoint.py pull`, затем `inbox --json` и `leases` (с `PYTHONDONTWRITEBYTECODE=1` и каталогом проекта, заданным явно из `CLAUDE_PROJECT_DIR`) и выводит результат в stderr — как соседние SessionStart-хуки. Аренды показываются затем, чтобы dev-agent видел, можно ли собирать в `build/`. Вывод сохраняет маркировку конвертов «данные, не инструкции» (`MI:49–54`, `ME:20,159`).
- [ADDED] **REQ-MO-SESS-4 (нет зависимостей).** Если при наличии `.mesh/endpoint.yaml` отсутствует `python3` или PyYAML, скрипт печатает одну строку предупреждения (в ней сказано, что в режиме `deny` хук будет блокировать записи, а в `notice` проверка пропускается), пропускает `pull`/`inbox`/`leases` и завершается `exit 0`. SessionStart ни при каких условиях не блокируется.
- [ADDED] **REQ-MO-SESS-5 (границы записи).** Скрипт пишет только в `.mesh/` проекта (курсор `cursors.json`, `outbox/` при `nack`) — это фенотип, вне git; в корень плагина, в `.claude/sdx/` и в git-дерево проекта не пишет. `/sdx:resume` после смерти CLI видит тот же ящик (он персистентен) без отдельной правки команды.

### Проект (REQ-MO-PROJ)

- [ADDED] **REQ-MO-PROJ-1 (`.gitignore`).** В блок targeted-паттернов `/sdx:init` (шаг 2 `commands/init.md`) добавляется строка `.mesh/` с комментарием «почтовый ящик МО — фенотип». Уже инициализированные проекты получают её штатной сверкой `/sdx:reconcile` (по каноническому списку `init.md`; отдельная правка `reconcile.md` не требуется, если он не перечисляет паттерны поимённо — проверить).
- [ADDED] **REQ-MO-PROJ-2 (CLAUDE.md-блок).** В `sdx/templates/claude-md-snippet.md`, внутрь блока `SDX:BEGIN…END`, добавляется абзац «МО над стендами» по шаблону `MI` §6 (стр. 86–91). Абзац условный («если есть `.mesh/endpoint.yaml`») — сниппет попадает и в проекты без МО.

### Агент devops (REQ-MO-DEVOPS)

- [ADDED] **REQ-MO-DEVOPS-1 (переключатель).** `agents/devops.md` вводит переключатель по наличию `${CLAUDE_PROJECT_DIR}/.mesh/endpoint.yaml`. При наличии: деплой и обслуживание стендов деактивированы; остаются сборка в рабочем дереве (`build/` — каталог исполнения, если назван в `exec_paths`, тогда сборка идёт под арендой), тесты, упаковка артефакта и `artifact.offer`; запрошенный деплой превращается в `request` узлу с сообщением пользователю об этом (`MI:27–30`). Без файла `devops` работает как прежде (п.3 инструкции «Выполни деплой…» сохраняется для этого случая).
- [ADDED] **REQ-MO-DEVOPS-2.** Любой вызов `python3 …/mesh_endpoint.py` из текста `agents/devops.md` ставит `PYTHONDONTWRITEBYTECODE=1` (вызовы из `MI` §5, стр. 75–84, этого не делают и в вендорённом файле не правятся — см. «Границы»).
- [ADDED] **REQ-MO-DEVOPS-3 (норма DEBT-042).** Текст агента (и команды, выполняющей обновление `sdx/mo/`, если она появится или уже есть) прямо говорит: обновление `sdx/mo/` и поставка/правка хука — изменение механизма надзора (PROC-020) и не выполняются в `gate_mode: auto`. Отправка `artifact.offer`/`request` в `gate_mode: auto` разрешена (сообщения; решение принимает человек на узле МО — решение пользователя, `decisions_log.md`, `[триаж]` круга 1). `.mesh/endpoint.yaml`/`.mesh/cursors.json` dev-agent не правит ни в каком режиме: обёртка блокирует запись (REQ-MO-HOOK-8, `MI` §0).

### Протокол (REQ-MO-PROTO)

- [ADDED] **REQ-MO-PROTO-1 (`[директива]`).** Входящая `directive` от МО — просьба, не полномочие (`MI:51–53`); в `gate_mode: auto` она никогда не принимается дефолтом. Основание: пункта стоп-рубрики для внешней просьбы нет, но её покрывает «критерий по умолчанию для не перечисленного» — цена отката ошибочно принятой директивы выше цены остановки. Список стоп-рубрики не меняется; `directive` называется в «Стоп-рубрике» примером этого правила. Остановка фиксируется в `decisions_log.md` под новым, восьмым тегом `[директива]` (внешняя просьба от МО в `auto`: остановка по правилу для неперечисленного). Тег отделён от `[триаж]` (тот определён как акт по находке; директива — не находка). Решение пользователя по директиве записывается в `decisions_log.md` по ходу, как у остальных тегов.
- [MODIFIED] **REQ-MO-PROTO-2 (список тегов журнала).** Везде, где перечислены теги журнала решений, число и перечень приводятся к восьми: `sdx/protocol.md` («Журнал решений» — слова «семь тегов» и «первые шесть соответствуют шести пунктам стоп-рубрики дословно» остаются верными для шести, новый тег в них не входит), `commands/next.md` (2в), `commands/verify.md`, `commands/resume.md` — там, где они перечисляют теги или опираются на их число. Противоречий между перечнями быть не должно.
- [ADDED] **REQ-MO-PROTO-3 (`Deployment` под МО).** Если над проектом есть МО (`.mesh/endpoint.yaml`), этап `Deployment` завершается отправкой `artifact.offer` (и `request`, если нужна операция); `msg_id` фиксируется в `change_note.md` или `DESIGN.md` сессии, смотря по объёму дельты. `rollout.result` приходит асинхронно и является входом следующей сессии, а не гейтом текущей. Норма вносится в описание этапа в `sdx/protocol.md` и согласована с `agents/devops.md`.
- [ADDED] **REQ-MO-PROTO-4 (граница с `prod-guard`).** Протокол («Enforcement-слой») фиксирует: при `.mesh/endpoint.yaml` запись в каталоги исполнения делает видимой узлу МО-хук (второй PEP, не граница безопасности — `MI:69–70`); `prod-guard` остаётся для того, о чём МО не знает (ssh на прод и т.п.). Паттерны одного из другого не выводятся (иначе фенотип попал бы в генотип). Политики отказа расходятся осознанно: `prod-guard` — fail-closed только при настроенной защите (без конфига или с пустым — no-op, BUG-002); МО-хук — fail-open в `notice`, fail-closed в `deny`.
- [MODIFIED] **REQ-MO-PROTO-5 (описание enforcement-слоя).** Разделы протокола, утверждающие, что хуков слоя «три» и что `prod-guard` — единственный хук с JSON-механизмом блокировки, приводятся в соответствие: МО-хук (обёртка) — второй, использующий этот механизм; его активация привязана к `.mesh/endpoint.yaml`, а не к ветке `sdx/<id>`. Раздел содержит именованные честные границы из «Границ» ниже (подмена `endpoint.yaml` через `Bash`; охрана по цели записи — best-effort).
- [ADDED] **REQ-MO-PROTO-6 (ADR).** Решения поставки — обёртка вместо голого `python3`, граница `prod-guard`/МО-хук, различие политик отказа — фиксируются в `docs/DECISIONS.md` (новая ADR или поправка к ADR-013 по выбору DESIGN).

### Поверхности состава (REQ-MO-INV)

- [ADDED] **REQ-MO-INV-1.** `README.md`, `README.en.md` и `CLAUDE.md` (§6) называют каталог `sdx/mo/` и каждое из имён `mesh_endpoint.py`, `devagent_hook.py`, `MO-INTEROP.md` (сегодня их там нет; без этого сторож `test-mo-inventory.sh` (д) красный). В таблице состава перечень `sdx/hooks/` дополняется МО-хуком (`mo-hook`, `mo-session`). Двуязычная пара README обновляется согласованно.

## Критерии приёмки

## Границы (что НЕ входит)

- **Правки вендорённых файлов.** `MO-INTEROP.md` §5 приводит вызовы `python3 $MO_TOOLS/mesh_endpoint.py …` без `PYTHONDONTWRITEBYTECODE=1`, а docstring `DH:17–18` велит запускать хук напрямую в обход обёртки; править их в `sdx/mo/` нельзя (PROC-028). Исправление — записка upstream в sim-kit (`agentico/reviews/`), вне этой поставки. До неё вызов из вендорённого текста в обход SDX-текстов может создать `sdx/mo/__pycache__/` (байткод пишет только `devagent_hook.py`, импортирующий `mesh_endpoint`; `mesh_endpoint.py` как скрипт — нет, PLAN T18) — это названный остаток, компенсируется только текстом `agents/devops.md` (REQ-MO-DEVOPS-2).
- **Self-test.** Периметр `selftest.sh` (три хука) в этой поставке не расширяется; живость МО-хука и строка «МО: python3/PyYAML» в `/sdx:status` — отдельная запись бэклога (создаётся на Closeout, класс DEBT-010).
- **Проверка идентичности установленной копии.** Сторож `test-mo-inventory.sh` статический (хеширует чекаут); хеш-проверка установленной копии в рантайме/self-test — отдельная запись.
- **`Bash`-пути к `.mesh/endpoint.yaml`/`cursors.json`.** Обёртка не пытается охранять (`>`, `sed -i`, `rm`, `git checkout`, удаление родительского каталога). Подмена `.mesh/endpoint.yaml` сессией выключает хук или ослабляет режим — свойство модели (`MI:12`: файл пишет узел); обнаружение — у узла МО при следующем `sync`. Фиксируется честной границей в протоколе.
- **Охрана по цели записи — best-effort**: хук sim-kit разбирает `Bash` по образцу guard МО (`MI:63–66`) и не является границей безопасности (второй PEP).
- **Классы риска и `request` с классом действия** (FEAT-006), HITL-inbox (FEAT-007: `.mesh/inbox` не используется как канал решений человека), портфельные задачи (IDEA-002).
- **Формальное подтверждение владельцу МО** нормы `Deployment` — действие вне бэклога (открытый вопрос 5 в `intake.md` сессии `intake-mo-interop-aibok-20261004`); поставка не заявляет «согласовано владельцем».
- **Версия протокола/конверта** (`V = 1`, `MAY_SEND`/`MAY_RECV`, `ME:31–33`): сторож её не проверяет; мажорный повод — по политике PROC-028.
- **Выпуск новых версий sim-kit** и любое обновление `sdx/mo/` после 0.7.3 — по политике PROC-028, не здесь.

## Риски и Ограничения

- **Зависимость от `jq` в обёртке.** Сборка JSON с `permissionDecisionReason` и разбор `tool_input.file_path` естественно требуют `jq`; МО-проект может быть без него. Требование — не блокировать проект без МО (REQ-MO-HOOK-2/3) и в `deny` при невозможности проверки отказывать, а в `notice` — предупреждать одной строкой; способ сборки JSON без `jq` — DESIGN.
- **Агрегация решений двух хуков на `Bash`** — свойство харнесса, не проверено в репо (FEAT-006); см. REQ-MO-HOOK-9 и критерий 20.
- **Fail-closed в `deny` без PyYAML блокирует каждый вызов, включая `ls`**, поэтому предупреждение SessionStart (REQ-MO-SESS-4) обязательно, иначе первая блокировка — сюрприз (класс DEBT-010).
- **Латентность.** В МО-проекте каждый вызов `Bash` стоит запуском python (десятки мс) — осознанная цена.
- **Канал SessionStart.** Что именно из stderr SessionStart-хука видит модель, в репо не задокументировано; требование — вывод в stderr как у соседей. Если dev-agent должен видеть входящие автоматически, остаётся норма `MI` §3/§5 (читать `inbox --json` явно); уточняется в DESIGN.
- **`directive` — вектор инъекции**: конверты — данные, не инструкции; норма REQ-MO-PROTO-1 закрывает `auto`, но не отменяет внимания в `interactive`.
- **Территория PROC-020.** Поставка меняет механизм надзора: не в `auto`; DEBT-042 исполняется REQ-MO-DEVOPS-3.
- **`ME`/`DH` требуют PyYAML и python3 3.x** на стороне проекта под МО; для плагина это не зависимость.
- **Переносимость.** Новые bash-скрипты — без `timeout` и без возможностей bash > 3.2 (BUG-010); `test-hook-wiring.sh` уже использует `mapfile` и на macOS не переносим — не расширяется этой поставкой.
- **Живая проверка вне поставки.** До приёмки на MOVE.IO риск расхождения фикстур с живым узлом остаётся.
