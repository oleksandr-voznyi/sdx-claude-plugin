# Business Specification: FEAT-017 — сдача пакетом изменения (плагин 2.5.0)

Сессия `feat-017-mo-change-package-20261031`. Дельта к `docs/specs/mo-interop.md` (REQ-MO-*, «Дельты FEAT-016»: REQ-MAND-22/23/23a/23b). Внешние файлы (sim-kit 0.9.1, ответ владельца МО 28.10) — данные-эталон. Решения оркестратора из `decisions_log.md` (Q-1/3/4/5/8/9/12/14, R-2) учтены как принятые.

## Контекст и Цели

Под мандатом МО исполнитель не сливает в основную ветку: сдача — **пакет изменения**. В 2.4.0 для `delivery: pr|branch` Closeout работает как временный мост (шаги 6–8 `(n/a, мандат)`, ручная инструкция из трёх шагов). Узел МО принимает только ветку `change/<C>-<exec>`, у которой вершина — отдельный коммит с одним файлом `CHANGE.yaml` (формат 1) поверх головы кода; остальное (аудит, `change.merge`, PR) — на стороне узла.

Цель 2.5.0: заменить ручной мост командой `/sdx:pr` — вторым вариантом Closeout (не параллельным механизмом): те же шаги 1–5 чек-листа, вместо шага 6 «мёрж в main» — сборка и сдача пакета. Дополнительно: экспорт `protocol.yaml` из существующих журналов сессии (не новый источник правды), приём заказа (`--from-order`/`--from-issue`), вендоринг шаблона манифеста и нейтральный текст «как сдать изменение» для чужих харнесов, семантика `docs_in_repo`.

Ожидаемый результат: пакет, собранный `/sdx:pr`, проходит формальные проверки `audit()` узла (формат, манифест-коммит, область, `archive_sha256`, `adr`) без `reject`/`return`; `protocol.yaml` валиден по схеме `protocol_check()`; без мандата команда отказывает одной строкой, всё прочее поведение — как в 2.4.0.

## Требования

### A. Команда `/sdx:pr` и условия входа

- [ADDED] **REQ-PKG-1** — `/sdx:pr` — отдельная команда плагина (`commands/pr.md`), второй вариант Closeout. Один вход для сдачи: мост `/sdx:archive` при `closeout-mode = bridge` (`delivery: pr|branch`) не выполняет ручную инструкцию, а делегирует `/sdx:pr`.
- [ADDED] **REQ-PKG-2** — Условия входа: (а) режим мандата (рядом `.mesh/endpoint.yaml` и `.mesh/mandate.yaml`); (б) `delivery` мандата — `pr` или `branch`; (в) сессия на этапе `Closeout` либо вызов из моста `/sdx:archive`. Нарушение любого условия — отказ без побочных эффектов; отсутствие мандата — отказ **одной строкой**. Для `delivery: artifact.offer` остаётся мост 2.4.0 (шаг 0 «оффер», REQ-MAND-23a); для `patch|worktree` — остановка по стоп-рубрике, как в 2.4.0.
- [ADDED] **REQ-PKG-3** — Конвейер `/sdx:pr` в строгом порядке: (1) шаги 1–4 Closeout (коммиты, перенос дельт по `docs_in_repo`, архив `PLAN.md`, бэклог); (2) экспорт `protocol.yaml` в каталог сессии (tracked на `sdx/<sid>`); (3) шаг 5 (`git rm -r` каталога сессии); (4) squash `sdx/<sid>` (без каталога сессии) в ветку `change/<C>-<exec>` от `base`; (5) `CHANGE.yaml` — отдельным последним коммитом; (6) `pr-check`; (7) подтверждение пользователя; (8) push (и PR, если применимо); (9) запись результата в сессию. Шаги 6–8 стандартного Closeout (мёрж в основную ветку, `archive-verify.sh`, финальный лог мёржа) для пакета `(n/a, пакет)`; ветка `sdx/<sid>` остаётся (не удаляется, не сливается).
- [ADDED] **REQ-PKG-4** — Данные заказа, нужные после шага 5 (`commitment`, `repo.base`, `repo.url`, `deliver.branch`, `title`), `/sdx:pr` считывает **до** шага 5 (либо из истории ветки `sdx/<sid>`); после удаления каталога сессии источником правды для них не служит ничто, кроме этих снимков.
- [ADDED] **REQ-PKG-5** — Имя ветки пакета: `change/<C>-<exec>`, где `<C>` — `commitment`, `<exec>` — `mandate.executor`. Значения проверяются по алфавиту `[A-Za-z0-9._-]`; при недопустимых символах (например `:` в идентификаторе исполнителя) — отказ с указанием поля, а не молчаливая подмена. Ветка строится от `base`: `repo.base` заказа, иначе основная ветка SDX (`lib/default-branch.sh`). Если `sdx/<sid>` вырезана не от `base`, `/sdx:pr` предупреждает о риске чужих изменений в пакете и требует подтверждения.
- [ADDED] **REQ-PKG-6** — Squash даёт **ровно один** коммит кода поверх `base`; его сообщение — `<C>: <заголовок заказа или цель сессии>`. Каталога сессии в пакете нет. История сессии остаётся только в `sdx/<sid>`.
- [ADDED] **REQ-PKG-7** — `/sdx:pr` без `commitment` (ручной режим `delivery: branch` без заказа) принимает `<C>` аргументом команды; без него — отказ с подсказкой.

### B. Манифест `CHANGE.yaml` (формат 1)

- [ADDED] **REQ-PKG-8** — `CHANGE.yaml` создаётся по шаблону `CHANGE.template.yaml` (вендорённый sim-kit 0.9.1), корневой ключ `change:`, и вносится **отдельным последним коммитом**: `tip^ == head`, а разница `head..tip` — ровно файл `CHANGE.yaml`. Файл создаётся средствами git-plumbing (`hash-object`/`update-index --cacheinfo`/`commit-tree`) **без записи в рабочее дерево** (R-2: хук области мандата не должен срабатывать на корневой `CHANGE.yaml`); рабочее дерево до и после сборки остаётся чистым и на ветке `sdx/<sid>`.
- [ADDED] **REQ-PKG-9** — Поля и их вычисление:
  - `format: 1`;
  - `commitment` — из заказа/аргумента;
  - `executor` — `mandate.executor`;
  - `mandate_digest` — `mandate.digest` (12 hex) из `.mesh/mandate.yaml`;
  - `base` — коммит, от которого построена ветка (merge-base с `base`-веткой);
  - `head` — коммит кода (до манифеста);
  - `archive_sha256 = sha256(git archive --format=tar <head>)`;
  - `scope_touched` — `git diff --name-only base..head`, включая сгенерированные файлы;
  - `touches_shared: true`, если хотя бы один изменённый путь попал в `shared_paths` мандата (по семантике `glob_any` узла), иначе `false`;
  - `spec` — `docs/specs/<module>.md@<sha>` перенесённой спецификации (если стадия `spec` была и перенос не `(n/a)`);
  - `verify {tests: pass, report: <путь|url>}` — по итогу stop-gate / `verification_report.md`;
  - `adr` — список ссылок на файл реестра решений, изменённый в пакете (`docs/DECISIONS.md#…`);
  - `docs` — файлы из `docs_paths`, изменённые в пакете;
  - `history_ref: executor:sdx/<sid>`;
  - `notes` — краткая сводка (необязательно).
  Необязательные поля шаблона (`module{}`, `contracts_changed`, `migrations{}`, `layer`) не заполняются.
- [ADDED] **REQ-PKG-10** — Значения, происходящие из заказа/issue (чужие данные), экранируются при генерации YAML, коммит-сообщений и командной строки `gh`; в манифест и в тело PR не попадают секреты.

### C. `pr-check` (проверка перед публикацией)

- [ADDED] **REQ-PKG-11** — `pr-check` — детерминированная проверка (аналог `closeout-check` моста), блокирующая push при любом провале. Проверяет: (а) рабочее дерево чистое (кроме `.mesh`); (б) в ветке пакета поверх `head` ровно один коммит и в нём только `CHANGE.yaml`; (в) `diff base..head ⊆ scope.paths ∪ shared_paths ∪ docs_paths` (кроме `CHANGE.yaml`); (г) в пакете нет каталога сессии; (д) `archive_sha256` в манифесте совпадает с пересчётом от `head`; (е) имя ветки допустимо и входит в `scope.branches` мандата; (ж) срок мандата не истёк; (з) stop-gate зелёный (повторный прогон тестовой команды проекта; кеш каталога сессии недоступен после шага 5); (и) для `docs_in_repo: final` — условие по `adr` (REQ-PKG-26). Проверки зеркалят формальные проверки `audit()` узла (`manifest.commit`, `scope`, `archive_sha256`, `adr`, `branch`, `mandate.valid`); живой `audit()` узла плагин не вызывает.
- [ADDED] **REQ-PKG-12** — Дифф `base..head` не пуст (зеркало `nonempty`); `touches_shared: true` при непустом пересечении с `shared_paths` дополнительно показывается пользователю («слияние такого пакета — человек»).

### D. Публикация

- [ADDED] **REQ-PKG-13** — Push — внешний эффект: подтверждение пользователя **в любом `gate_mode`** (в `auto` — стоп-рубрика `[контракт]`, запись в `decisions_log.md`). Перед подтверждением показываются: имя ветки, remote/URL, сводка манифеста, результат `pr-check`.
- [ADDED] **REQ-PKG-14** — Push отправляет **только** `change/<C>-<exec>` (явный refspec); ветки `sdx/*` на хостинг не уходят; `--all`, `--mirror`, `--follow-tags` не используются. Перезапись существующей `change/<C>-<exec>` (force) — деструктив, `[деструктив]`, отдельное подтверждение; по умолчанию отказ.
- [ADDED] **REQ-PKG-15** — Хостинг `bare`: push в `repo.url` заказа, а при его отсутствии — в `origin`. Готовность пакета = ветка в репозитории + `CHANGE.yaml` в корне вершины.
- [ADDED] **REQ-PKG-16** — Хостинг `github`: push ветки + `gh pr create` против `repo.base` (head — `change/<C>-<exec>`), заголовок `<C>: <title>`, тело строится из манифеста (обязательство, область, `verify`, `adr`, `touches_shared`). Если `gh` отсутствует или не авторизован — деградация до `bare`: push выполняется, пользователю печатается инструкция открыть PR вручную (одна строка), это не отказ. `gh` — не зависимость плагина.
- [ADDED] **REQ-PKG-17** — Результат сдачи (имя ветки, `head`, `tip`, remote, URL PR при наличии, `msg_id` при отправке сообщения) записывается в сессию (`change_note.md`/`session.log`, без удаляемого каталога — в ветку `sdx/<sid>` служебным коммитом) и выводится пользователю. `prod-guard` не ослабляется.
- [ADDED] **REQ-PKG-18** — Повторная сдача после `return`/`reject` узла — отдельное действие, не молчаливая перезапись: новая вершина той же ветки только по явному подтверждению с учётом REQ-PKG-14.

### E. Экспорт `protocol.yaml`

- [ADDED] **REQ-PKG-19** — `protocol.yaml` экспортируется из существующих журналов (новых источников правды нет) в каталог сессии на шаге конвейера «после шага 4, до шага 5»; файл tracked на `sdx/<sid>` и в `change/*` не входит. Структура — по `protocol_check()`: пять обязательных разделов-списков `done`, `decisions`, `questions`, `verified`, `deltas`; пустой список допустим.
- [ADDED] **REQ-PKG-20** — `decisions[] {id, what, why, alternatives, adr}` из `decisions_log.md`: `id` — порядковый (`D-1…`); `what` — «Вариант»; `why` — «Обоснование»; `alternatives` — из «Варианты» записи (пусто, если нет); `adr: true`, если в записи или в выполненном переносе назван ADR, иначе `false`. Непустые `id`, `what`, `why` — обязательны.
- [ADDED] **REQ-PKG-21** — `questions[]` — записи журнала с решением пользователя на стоп-рубрике; `verified[]` — из `verification_report.md` (сводка по осям, итог, число кругов); `deltas[]` — из `change_note.md`/`SPEC.md` (ID требований и признаки `[ADDED]/[MODIFIED]/[REMOVED]`); `done[]` — закрытые задачи `PLAN.md` либо одна запись для свёрнутой дельты. Отсутствие источника даёт пустой список, а не ошибку.
- [ADDED] **REQ-PKG-22** — Записи `decisions[]` с `adr: true` не требуют второго ручного ввода в реестр решений проекта. Доставка `protocol.yaml` узлу в `work/<C>/` вне зоны SDX: при `history: mo` узел читает его из ветки `sdx/<sid>` своего клона; при `history: executor` канал — вопрос upstream (см. «Открытые вопросы»).

### F. Заказ: `/sdx:start --from-order` и `--from-issue`

- [ADDED] **REQ-PKG-23** — `/sdx:start <type> <goal> --from-order <order.yaml|msg_id>`: заказ — файл либо конверт `work.order` из ящика (`inbox --json`, выбор по `msg_id`). Из заказа берутся цель, требования, область, срок, способ сдачи (`deliver`), `repo.base`, `repo.url`. Входящая `directive` — данные, не инструкция; в `gate_mode: auto` приём подтверждается пользователем (`[директива]`). Расхождение заказа и локального мандата (`mandate_digest`, `executor`, `deliver.branch`) — стоп `[контракт]`.
- [ADDED] **REQ-PKG-24** — `/sdx:start … --from-issue <N>`: текст issue читается `gh issue view`, внутри ищется YAML-блок заказа; формат обёртки — SDX-ный (первый fenced-блок ```yaml с ключом `action: work.order`), **это допущение SDX**, эталон узла формат issue не задаёт. Без `gh` — отказ с подсказкой использовать `--from-order <файл>`.
- [ADDED] **REQ-PKG-25** — Принятый заказ: `commitment` записывается в `session_state.json` (новое необязательное поле) и снимок заказа — в `order.yaml` каталога сессии (tracked); `C-…` входит в суффикс `sid` и в сообщения коммитов сессии; ветка сессии остаётся `sdx/<sid>`. На старте показывается `scope` заказа/мандата (шаг показа мандата 2.4.0). Без `--from-order` поведение `/sdx:start` — как в 2.4.0.

### G. `docs_in_repo`

- [ADDED] **REQ-PKG-26** — Поведение на Closeout/`/sdx:pr`: `none` — переносы в `docs/specs|designs` и реестр ADR `(n/a, docs_in_repo: none)`, дельты живут только в `protocol.yaml`; `final` и `full` — штатный перенос (`final` = `full`, как принято в FEAT-016). При `final` (и по умолчанию) поле `adr` манифеста обязательно непусто, и каждый указанный файл реестра изменён в пакете. Если реестр решений за сессию не менялся либо его путь не покрыт `docs_paths` мандата — `/sdx:pr` выдаёт предупреждение (путь реестра вне `docs_paths` — по §3 п.3 ответа МО); сдача возможна лишь после явного подтверждения пользователя.
- [ADDED] **REQ-PKG-27** — Критерий состава: при `docs_in_repo: final` среди документов пакета нет файлов вне `docs_paths` мандата.

- [ADDED] **REQ-PKG-29** — `sdx/templates/CONTRIBUTING-MO.md` — собственный текст SDX «как сдать изменение», нейтральный к инструменту (для харнесов заказчиков, П5); не вендорённый, правила сторожа `sdx/mo/` не меняются.
- [MODIFIED] **REQ-PKG-30** — Closeout-контракт (`sdx/protocol.md`, `commands/archive.md`) описывает два варианта: «мёрж» и «пакет»; мост FEAT-016 (REQ-MAND-23/23a/23b) для `pr|branch` заменяется делегированием `/sdx:pr`; ручная инструкция моста снимается. Для `artifact.offer` и `patch|worktree` поведение 2.4.0 сохраняется; поле `change` в `artifact.offer` **не** добавляется.

### I. Безопасность и совместимость

- [ADDED] **REQ-PKG-34** — Без мандата `/sdx:pr` отказывает одной строкой; вне мандата все команды работают как в 2.4.0 (обратная совместимость).
- [ADDED] **REQ-PKG-35** — `/sdx:pr` не создаёт и не сливает PR от имени узла, не вызывает `audit()` узла, не отправляет `protocol.yaml` узлу, не пушит `sdx/*`, не выполняет force-push без подтверждения.

## Критерии приемки

- [ ] Фикстурный репозиторий (мандат `delivery: pr`, `bare`): пакет, собранный `/sdx:pr`, удовлетворяет проверкам, зеркальным формальным проверкам `audit()` sim-kit 0.9.1: `format`, `manifest.commit` (`tip^ == head`, разница — только `CHANGE.yaml`), `scope`, `archive_sha256`, `adr`, `branch`, `mandate.valid` — без `reject`/`return` (REQ-PKG-8, 9, 11).
- [ ] Красные стороны `pr-check`: лишний коммит поверх `head`, посторонний файл в манифест-коммите, путь вне `scope`, неверный `archive_sha256`, каталог сессии в пакете, грязное дерево, имя ветки вне `scope.branches`, истёкший мандат, красный stop-gate — каждая блокирует push (REQ-PKG-11).
- [ ] Сборка манифеста не пишет `CHANGE.yaml` в рабочее дерево; дерево чистое после `/sdx:pr`, текущая ветка — `sdx/<sid>` (REQ-PKG-8).
- [ ] `archive_sha256` равен `sha256(git archive --format=tar <head>)` и воспроизводим в независимом клоне фикстуры (REQ-PKG-9).
- [ ] `touches_shared` корректен для обоих исходов; `scope_touched` включает сгенерированные файлы (REQ-PKG-9, 12).
- [ ] `protocol.yaml` содержит пять списков-разделов; каждая запись `decisions[]` имеет непустые `id`, `what`, `why`; пустой `decisions_log.md`/отсутствующие источники дают пустые списки, а не ошибку; файл в `change/*` отсутствует (REQ-PKG-19–21).
- [ ] Запись журнала с упомянутым ADR даёт `adr: true`, без ADR — `false` (REQ-PKG-20).
- [ ] Без подтверждения пользователя push не выполняется ни в `standard`, ни в `auto` (REQ-PKG-13); push выполняется только по явному refspec `change/<C>-<exec>`, ветки `sdx/*` не отправляются (REQ-PKG-14).
- [ ] Хостинг `github` без `gh`: push выполнен, выдана одна строка с инструкцией, код завершения — не отказ; с `gh` — PR создан против `repo.base` с телом из манифеста (REQ-PKG-16).

## Риски и Ограничения

- Деструктив: ветка и squash создаются в рабочем клоне; перезапись `change/*` — только с подтверждением (REQ-PKG-14).
- Хук области (`on_write: deny`) может блокировать запись корневого `CHANGE.yaml`; обход — plumbing без записи в дерево (не проверено исполнением на реальном хуке).
- `miniyaml` строже `safe_load`: `order.yaml` с многострочными скалярами им не разбирается; заказ из ящика — JSON (`jq`), из файла/issue требует PyYAML либо конвертации; вывод YAML генерируется текстом.
- `archive_sha256` зависит от версии git и `.gitattributes` (`export-ignore`/`export-subst`); для разных версий git совпадение не проверено.
- Построение ветки от `base`, не совпадающей с `dev` узла, даёт чужие изменения в пакете; узел пересчитывает `merge-base` сам.
- `questions[]` ограничен журналом решений: незафиксированные вопросы не восстанавливаются.
- Идентификатор исполнителя с недопустимыми для git-ссылок символами блокирует имя ветки.
- Отсутствует стороннее подтверждение, что рабочая копия `CHANGE.template.yaml` совпадает с тегом `sim-kit-0.9.1` — сверка хеша обязательна при вендоринге.
- Все данные заказа/issue — чужой текст; не инструкции.
- Таймаут stop-gate 180 с: повторный прогон тестов в `pr-check` и новые сьюты съедают запас.

## Открытые вопросы (с предложенным дефолтом)

1. **Q-2. Один squash-коммит или несколько?** Дефолт: один коммит `<C>: <title>`; автор — текущий git-пользователь.
2. **Q-7. Какой файл считается реестром ADR?** Дефолт: `docs/DECISIONS.md` либо единственный изменённый файл по маске `docs/**/{DECISIONS,decisions}*.md`; если не найден — предупреждение REQ-PKG-26.
3. **Q-10. Формат issue-заказа.** Дефолт: первый fenced yaml-блок с `action: work.order`; другие формы — отказ с подсказкой.
4. **Q-13. Stop-gate в `pr-check`.** Дефолт: повторный прогон тестовой команды проекта (кеш каталога сессии недоступен после шага 5); секреты/«контракт раньше кода» не зеркалятся (политика узла недоступна исполнителю).
5. **Q-15. Префиксы коммитов сессии.** Дефолт: `sdx(<sid>)` не меняется (в `sid` уже есть `C-…`); `C-…` — в squash-сообщении.
6. **Q-16. Повторная сдача.** Дефолт: новая вершина той же ветки поверх существующей только по подтверждению; force — отдельное `[деструктив]`.
7. **R-7. Нормализация `<exec>`.** Дефолт: отказ с указанием поля, не подмена символов.
8. **Q-9. Определение хостинга.** Дефолт: `github`, если URL remote содержит `github.com`; иначе `bare`; поле хостинга в заказе, если есть, приоритетнее.
9. **Канал `protocol.yaml` при `history: executor`.** Дефолт: вне SDX, вопрос владельцу МО (у узла читателя из репозитория нет).
10. **Исключение `CHANGE.yaml` из `_in_scope` хука** — просьба upstream; в 2.5.0 обход через plumbing.
11. **Q-18. Релиз.** Дефолт: 2.5.0, двуязычные заметки в `docs/history/releases/`, тег на merge-коммите.
12. **Q-17. Тесты, закрепляющие текст моста** (REQ-MAND-23/23a/23b, `test-mo-prose`): дефолт — обновляются вместе с REQ-PKG-30.
