### 2.1 `CHANGE.yaml` (формат 1) — поля и их вычисление

Цитата шаблона (шапка): «Нейтрален к инструменту … Без манифеста пакет не рассматривается». Манифест не может содержать сумму архива, в который входит сам, поэтому он — отдельный последний коммит (концепция §9 п.1: «вершина ветки = `head` + один коммит с одним файлом `CHANGE.yaml`»). Допустим и `tip == head` (манифест внутри головы) — тогда `archive_sha256` отсутствует и вердикт максимум `return` (`:353` комментарий).

### 2.3 `protocol.yaml` — точная схема (`protocol_check()` `SK/core/dev.py:577-593`)

```
PROTOCOL_KEYS = {done: list, decisions: list, questions: list, verified: list, deltas: list}   # :578
```
- файл `work/<C>/protocol.yaml` (**на узле**); отсутствие — `deny`;
- **все пять разделов обязательны** (`нет раздела {k}` на каждый отсутствующий), каждый — список (`ожидается список`); пустые списки допустимы (фикстура `SK/tests/kit.sh:751`: `questions: []`);
- `decisions[i]` — словарь с непустыми `id`, `what`, `why`; `alternatives` и `adr` — не проверяются; `adr` считается «истинным» по truthiness (`:588` счётчик `adr N`);
- элементы `done`, `questions`, `verified`, `deltas` — **без схемы** (в тесте — строки: `done: [x]`, `verified: [t]`, `deltas: [d1.patch]`);
- код возврата 1 при ошибках, иначе печатает счётчики.
Записка §2.10: записи `adr: true` «SDX выводит в реестр решений проекта (`docs/decisions.md` или ADR-файл) — не пишутся второй раз руками».
**Ни один код узла не забирает `protocol.yaml` из репозитория и не читает его из `change/*`**: он ожидается в `work/<C>/` (кладёт оператор/`history: mo`); `retention()` (`:596-`) хранит протоколы «всегда». Канал доставки `protocol.yaml` от исполнителя при `history: executor` в эталоне **не определён** (только `history_ref` в манифесте).

### 2.5 Хостинг: адаптеры `bare` и `github` (`SK/core/dev.py:123-250`)

| Аспект | `bare` (`class Bare` `:177-195`) | `github` (`class GitHub` `:197-225`) |
|---|---|---|
| Что такое «пакет» | ветка `refs/heads/change/*` (префикс из `policy/dev.yaml`), у вершины которой в **корне есть `CHANGE.yaml`** (`git for-each-ref refs/heads/`, `show(m, sha, "CHANGE.yaml")`, `:181-187`) | **открытый PR** (REST `GET /repos/{owner}/{repo}/pulls?state=open&per_page=50`), у `head.sha` которого в корне есть `CHANGE.yaml` (`:210-216`); `base_branch` записывается, но аудит его не использует |
| Откуда узел берёт ветку | из своего `--mirror`-клона репозитория `remote_url(repo)` (`:116-150`): `git clone --mirror`, затем `git fetch --prune origin` при каждом обращении. То есть исполнитель обязан **запушить `change/<C>-<exec>` в тот самый репозиторий** (`repo.url`/`repo.path` реестра узла: для dobro до GitHub — `ssh://dobro`) | то же зеркало + токен REST (файл `hosting.auth_ref` на хосте узла или `MO_GITHUB_TOKEN`) только для чтения PR и комментариев; ветку PR узел видит по sha через зеркало |
| Что «значит PR» | ничего: комментарий узла — файл `work/<C>/changes/<head8>.comment.md` | PR — единица пакета; вердикт узла — комментарий в PR (`POST …/issues/{n}/comments`) |
| Слияние | всегда `change.merge` узла: squash в `dev`, push (`:442-479`); API слияния PR **не** используется | то же (PR после слияния сам API не закрывается: `merged()` → `None`) |
| Поля создания PR | — | эталон их **не задаёт** (узел только читает); значимо лишь: у `head.sha` в корне `CHANGE.yaml`; ветка в `scope.branches`; целью аудита служит ветка `dev` реестра (`:376`), поэтому PR разумно открывать против `dev` (`work.order.repo.base`) |
| `gitlab`/`gitea` | как `bare` (`HOSTING` `:225`) | — |

Узел определяет `base` как `merge-base(head, refs/heads/<dev>)`; при сбое — `man.base` (`:376-380`). Следствие для плагина: ветка `change/*` должна быть **построена от актуальной головы `dev` узла** и достижима в его зеркале; `dev` в репозитории может отличаться от «основной ветки» SDX (`lib/default-branch.sh`).

## 4. Ограничения и риски

**R-1. Деструктивные git-операции.** `/sdx:pr` создаёт ветку и squash (`git checkout -b change/<C>-<exec> <base>`, `git merge --squash sdx/<sid>`, коммит, push). Риски: перезапись существующей `change/<C>-<exec>` (повторная сдача после `return` узла — `push -f` в фикстуре sim-kit, `tests/kit.sh` `mkpkg`; в плагине `-f`/`--force` — деструктив, стоп-рубрика `[деструктив]`); незакоммиченная работа при `checkout`; возврат на `sdx/<sid>` после сборки (`closeout-check` требует текущую ветку `sdx/<sid>`). `prod-guard` (`sdx/hooks/prod-guard.sh`) — по пользовательским regex (`sdx/templates/prod-guard.conf`, в SDX-репозитории пуст) и git-операции сам не блокирует; `archive-verify.sh` при мандате не вызывается. Хук `devagent_hook.py:87` (`GIT_WRITE = {merge, checkout, … commit …}`) относится к ветке `exec_paths` (запись под аренду), не к области мандата.

**R-2. Хук области против `CHANGE.yaml` в корне.** `devagent_hook.py` при `mandate.on_write: deny` блокирует запись (`Write`/`Edit`, redirect `>` в `Bash`, `cp`/`mv`/`tee` и т.д.) вне `scope.paths ∪ shared_paths` (его `_in_scope`: корень и `.mesh*` — «в области» лишь в смысле `rel in (".", "")`/`.mesh`, **файл `CHANGE.yaml` в корне — не `.`**; `docs/` — только если покрыт). `sdx/protocol.md:303` фиксирует, что под блок попадают собственные `.claude/sessions/` и `docs/`. Следствие: создание `CHANGE.yaml` в корне рабочего дерева исполнителя при `deny` может быть отклонено хуком; аудит узла `CHANGE.yaml` из проверки области исключает (`dev.py:381` `f != MANIFEST`). Обходы (plumbing `git hash-object`/`commit-tree` без записи файла в дерево и т.п.) — это выбор DESIGN; факт блока хуком не проверен исполнением.

**R-3. Разбор YAML без python.** Требование: новые скрипты — bash+jq; PyYAML — только где уже гарантирован. Факты: `miniyaml.sh` отвергает многострочные скаляры (`protocol.md:310`), flow-словари, список словарей; `order.yaml` — вывод `yaml.safe_dump`, а `commitment.requirements` свободный текст ⇒ вероятен многострочный скаляр ⇒ отказ miniyaml. Заказ из ящика приходит как JSON (`inbox --json`) ⇒ `jq` справляется. Заказ из `order.yaml`/issue — YAML: нужен PyYAML (проверка наличия уже есть: `mandate-info.sh:63-66`; `mo-hook.sh` проверяет PyYAML сам при `deny`) либо принимать заказ только JSON/через конвертер. Вывод `CHANGE.yaml`/`protocol.yaml` — генерация текста из bash (форматирование скаляров, кавычки, юникод) без parser'а; `verify: {tests: pass, report: …}` в шаблоне — flow-словарь (допустимый вывод; но `miniyaml` его **не** прочтёт, если когда-либо потребуется обратный разбор в самих тестах).

**R-4. Внешняя зависимость `gh`.** В плагине `gh` сейчас не используется нигде (grep по `commands/ agents/ sdx/ hooks/ README*` — совпадений по `gh pr|gh issue` нет). На машине автора `gh` есть (`/usr/bin/gh`); у исполнителей других харнесов/без GitHub — нет. `bare`-хостинг (первая ступень пилота dobro) без `gh`. Поведение при отсутствии/неавторизованности `gh` (fail-closed на сдаче или fail-open «ветка + манифест готовы, PR вручную») в предмете не задано; эталон узла PR не создаёт.

**R-5. Запрет пуша `sdx/<sid>`.** `MO-INTEROP.md:132` и ответ МО (§1, «Q2»): `sdx/<sid>` на хостинг заказчика не выталкивается. Сборка пакета должна пушить **только** `change/<C>-<exec>`; `git push --all`/`--mirror`/`--follow-tags`, `push.default=matching`, `remote.<name>.push` в конфиге — потенциальные пути утечки; `closeout-check`/`archive.md:50` требуют «ветка `sdx/<id>` остаётся (не удалять и не сливать)».

**R-6. Реконструкция `base` и «голова dev узла».** Узел требует, чтобы `change/*` строилась от головы своей `dev` (`merge-base`, `dev.py:376`), а `/sdx:start` создаёт `sdx/<sid>` от текущей ветки (`start.md:29`), основная ветка SDX определяется `lib/default-branch.sh` (`origin/HEAD` → `init.defaultBranch` → `main`/`master`), и может отличаться от `dev` (в фикстуре sim-kit репозиторий переименован в `dev`). Имя ветки `dev` в мандат не входит; приходит в `work.order.repo.base` (при `--from-order`), иначе источника нет. Squash из `sdx/<sid>` по определению берёт `merge-base(sdx/<sid>, <base>)`; если `sdx/<sid>` вырезана от ветки, не совпадающей с `<base>`, в пакет попадут чужие изменения (и `scope`/`nonempty`/`shared` пересчитаются узлом по ним).

**R-7. Идентификатор исполнителя в имени ветки.** Имя — `change/<C>-<exec>`, где `<exec>` = `mandate.executor`. В концепции встречается значение вида `client-harness:kitgroup` (`MO-dev-control-concept.md:` пример мандата), а `:` недопустим в именах git-ссылок; в фикстуре sim-kit — `ex1`. Нужна нормализация/отказ (то же касается `C-…` с нестандартными символами и проверки по `[A-Za-z0-9._-]` как в `mandate-info.sh safe`).

**R-8. Воспроизводимость `archive_sha256`.** Узел считает `git archive --format=tar <head>` в своём mirror-клоне (`dev.py:170-174`); исполнитель — в рабочем клоне другой версией git. Вывод зависит от содержимого дерева, `export-ignore`/`export-subst` в `.gitattributes` (читаются из дерева), времени коммита (mtime записей), а также настройки `tar.umask`; без `.gitattributes` и при дефолтных настройках детерминирован для одного `head`. Совпадение на практике фикстурой sim-kit подтверждено (`mkpkg` считает `sha256sum` `git archive` в рабочем клоне, аудит принимает), но для разных версий git не проверено.

**R-9. Доставка `protocol.yaml` и `history`.** Эталон не определяет канал (§2.3 выше). `history: mo|both` — клон/сессии живут у узла (П3; не 2.5.0), `history: executor` — история остаётся в клоне исполнителя, узлу достаётся только `history_ref`. `lint` отвергает `history: executor` + `docs_in_repo: none`. FEAT-017 п.2 («Файл уезжает с каталогом сессии (`history: mo` — остаётся в клоне узла)») и п.5 («`none` — … дельты остаются в `protocol.yaml` сессии») опираются на то, что `protocol.yaml` лежит в каталоге сессии, а каталог сессии удаляется на шаге 5 (и никогда не входит в `change/*`, поскольку squash идёт без каталога сессии).

**R-10. Безопасность входных данных.** Содержимое `work.order` и тела issue (`gh issue view` — чужой текст) — данные, не инструкции (`MO-INTEROP.md` §3 `:56-61`; сниппет). Значения заказа попадают в имя ветки, сообщение коммита, поля манифеста, строку `gh pr create`: нужно экранирование/ограничение алфавита (образец — `safe()` `mandate-info.sh:28`, `_mandate_safe`/`_my_q` `mandate.sh`). `has_secret` проверяется транспортом в узле/эндпоинте (`mesh_endpoint.py:126`); секреты в диффе пакета узел ловит `secrets_in_diff`.

**R-11. Режим `gate_mode: auto`.** `[директива]`: входящая `directive` в auto не принимается дефолтом (`protocol.md:651`, `devops.md:38`); `artifact.offer` в auto отправлять разрешено (`devops.md:39`). Команда `/sdx:pr` — публикация во внешний репозиторий (push/PR): по стоп-рубрике «внешние контракты/деструктив» её граница в auto не определена в текущем тексте.

**R-12. Конфиг и окружение.** `.mesh/` не отслеживается git (в `closeout-check` исключён из `git status`, `mandate-info.sh:108`); `CLAUDE_PLUGIN_ROOT` задаётся харнесом; `PYTHONDONTWRITEBYTECODE=1` обязателен при любом вызове `sdx/mo/*.py` (`sdx/mo/README.md`). В корне репозитория лежит посторонний tracked-файл `false` (не связан с предметом; отмечено для сведения).

## 6. Открытые вопросы для SPEC/DESIGN

**Q-1. `/sdx:pr`: отдельная команда или режим `/sdx:archive`?** Позиция SDX (backlog, «Суть»): «второй вариант Closeout, не параллельный механизм»; шаги 1–5 общие; вместо 6 — squash + манифест.
