# Записка владельцу МО (sim-kit): вопросы по итогам FEAT-017 (черновик, не отправлена)

> Сессия `feat-017-mo-change-package-20261031`, плагин SDX 2.5.0. Адресат — владелец sim-kit / узла МО. Это не работа плагина: репозиторий sim-kit из этой сессии не правится. Публикация — по решению пользователя (backlog `IDEA-` на Closeout, К-18).

SDX 2.5.0 собирает пакет изменения (`/sdx:pr`: ветка `change/<C>-<executor>` + корневой `CHANGE.yaml`, отдельным последним коммитом). Живой `audit()` узла плагин не вызывает; формальные проверки зеркалятся. Ниже — пять мест, где со стороны узла нужен ответ или решение.

1. **Канал доставки `protocol.yaml` при `history: executor`.** SDX кладёт файл в историю ветки `sdx/<id>` исполнителя (`.claude/sessions/<id>/protocol.yaml`, до удаления каталога сессии). При `history: mo` узел читает его из своего клона; при `history: executor` читателя из репозитория у узла нет (`protocol_check()` ждёт файл в `work/<C>/`). Вопрос: как файл должен попасть к узлу — отдельным сообщением, вложением в `artifact.offer`/`work.*`, чтением по `history_ref`? Пока SDX файл узлу не отправляет.
2. **Формат issue-заказа.** `--from-issue` ищет в тексте issue первый fenced-блок ```yaml с ключом `action: work.order` (формат SDX-ный). Нужно подтверждение, что узел (или человек на хостинге) может порождать issue в таком виде, либо спецификация формата со стороны узла.
3. **Корневой `CHANGE.yaml` и `_in_scope` хука.** Манифест лежит в корне репозитория (последний коммит пакета). В рабочем дереве исполнителя файла нет (создаётся через `hash-object` и временный индекс), но при ручной правке или другом харнесе запись корневого `CHANGE.yaml` попадёт под проверку области хука `devagent_hook.py`. Просьба исключить корневой `CHANGE.yaml` из `_in_scope` так же, как это сделано в `audit()`.
4. **Семантика `docs_in_repo: final|full`.** `MO-INTEROP.md` §7 различает значения неявно. SDX трактует `final` как `full` (перенос в `docs/` выполняется, реестр решений проверяется по `docs_paths`; документ вне `docs_paths` при `final` — `FAIL docs.final`), `none` — переносы пропускаются. Просьба подтвердить или уточнить разницу.
5. **Поле `change` в `artifact.offer`.** Узел его игнорирует (0.9.x не читает); SDX его **не добавляет**. Если планируется чтение — нужен формат; иначе пункт закрыт.

Дополнительно, к сведению: при повторной сдаче после `return`/`reject` SDX добавляет новый squash-коммит поверх прежней вершины `change/<C>-<executor>` (fast-forward, без force); `archive_sha256` считается как `sha256(git archive --format=tar <head>)` с `tar.umask=0002`, проверен на одной версии git.
