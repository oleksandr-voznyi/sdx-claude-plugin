# Технический дизайн: Агент-аудитор, команда `/sdx:audit` и тип сессии `audit`

Сессия: `feat-audit-agent-20260726` (feature, full). Вход: `.claude/sessions/feat-audit-agent-20260726/SPEC.md`
(REQ-AUDIT-1..16), `.claude/sessions/feat-audit-agent-20260726/context_report.md`.
Решение и инварианты — предлагаемый **ADR-019** (текст ниже, раздел «Архитектурное решение: ADR-019»).

## Архитектурный обзор

Поставка состоит из четырёх независимо стоящих на ногах частей и **ни одной строки нового
процедурного кода**:

1. **Новый субагент `agents/auditor.md`** — девятая роль фреймворка. Оценочное суждение о
   состоянии проекта целиком по девяти векторам (REQ-AUDIT-1/4). Тир модели — `fable`,
   формально вводимый ADR-019 четвёртым тиром (REQ-AUDIT-2). Набор инструментов —
   `Read, Write, Glob, Grep`, **без `Bash` и без `Edit`**: это не копия мотивации BUG-004, а
   самостоятельный вывод из REQ-AUDIT-3 (см. «Безопасность»).
2. **Новая команда `commands/audit.md`** — read-only, вне сессий, по образцу `/sdx:reconcile`
   (`commands/reconcile.md:6`) и `/sdx:backlog` (`commands/backlog.md:6`). Оркестрирует
   параллельный фан-аут по векторам, склеивает отчёт и пишет ровно один файл в
   `docs/history/audit/` (REQ-AUDIT-3/7/8).
3. **Новый тип сессии `audit` на существующем треке `doc`** — триаж уже готового отчёта в
   `docs/backlog/` (REQ-AUDIT-9..15). `SDX_STAGE_MATRIX` и `sdx-stage.sh` **не меняются вовсе**
   (см. «Что НЕ меняется в enforcement-слое»).
4. **ADR-019** — governance-часть: четвёртый тир `fable`, его граница с `opus`, и разграничение
   `audit` / `intake` / `grooming`.

Три архитектурных решения несут всю нагрузку дизайна:

**Решение 1 — фан-аут без единого разделяемого изменяемого состояния.** Девять векторов
исполняются параллельными вызовами `Task` одного и того же агента `auditor`. Каждый вызов
получает **общий read-only вход** (файл `manifest.txt`, путь) и **собственный write-only выход**
(файл `<CODE>.md`, путь). Общего изменяемого файла между параллельными вызовами нет ни одного —
в том числе нет общего счётчика (ID находок нумеруются локально внутри вектора, префиксом кода
вектора, поэтому глобальная уникальность достигается без координации). Это снимает класс риска
`PROC-010` (`docs/backlog/PROC-010-parallel-subagents-shared-session-files.md`) структурно, а не
дисциплиной: гонки нет, потому что нет разделяемой записи. Склейка — единственным внешним шагом
оркестратора (REQ-AUDIT-8).

**Решение 2 — детерминированный слой отделён от оценочного и вычислен один раз.** Всё, что
проверяется машинно (существование каталогов, наличие кода, наличие тестов, число записей
бэклога по статусам, `git rev-parse HEAD`, признаки CI/деплоя, применимость каждого вектора),
вычисляет **оркестратор** (у него есть `Bash`) один раз до фан-аута и материализует в
`manifest.txt` редиректом — тем же приёмом, что `verify.md:26` применяет к `delivery.diff`
(вывод не проходит через контекст). Отсюда три следствия: (а) девять агентов не
перевычисляют одни и те же факты; (б) все векторы видят *идентичную* картину формы проекта и не
могут разойтись в базовых утверждениях о ней; (в) агенту не нужен `Bash`, а значит read-only по
REQ-AUDIT-3 становится enforcement, а не обещанием.

**Решение 3 — отчёт аудита и документ разбора отчёта не сосуществуют.** Коллизия каталога
`docs/history/audit/` (см. следующий раздел) решена не переименованием, а **устранением одной из
двух сущностей**: тип сессии `audit` не производит постоянного документа разбора вовсе, ровно как
`grooming` (`docs/DECISIONS.md:511-514`, `sdx/protocol.md:311`). В каталоге живёт единственный род
файлов — отчёты прогонов.

## Коллизия `docs/history/audit/`: разведение

**Проверка констатации.** Коллизия реальна. По прецеденту ADR-017 сессия типа `<type>` ∈
{`retro`,`postmortem`,`intake`} переносит на Closeout свой постоянный документ в
`docs/history/<type>/<session_id>.md` (`sdx/protocol.md:311`, `commands/archive.md:59`,
`commands/init.md:17`). Для типа `audit` это дало бы `docs/history/audit/<session_id>.md`.
REQ-AUDIT-7 требует складывать в тот же каталог отчёты прогонов `/sdx:audit`. Две сущности с
разными авторами (агент `auditor` + оркестратор вне сессии vs. сессия-триаж), разным
жизненным циклом (создаётся вне сессии, коммитится пользователем vs. переносится на Closeout) и
разной семантикой (материал для разбора vs. разбор материала) в одном каталоге без различимого
имени — двусмысленность, которую не спасает даже разное имя файла: читатель каталога не может
сказать, что перед ним, не открыв файл.

**Решение: `docs/history/audit/` содержит ТОЛЬКО отчёты прогонов. Тип сессии `audit` постоянного
документа разбора не производит.**

Обоснование:
- **Предмет разбора уже является постоянным документом.** У `retro`/`postmortem`/`intake` вход
  эфемерен (выборка из лога сессий, интервью об инциденте, материал, поданный в диалог — у
  последнего нет структурированного места вовсе, `PROC-009`), поэтому документ разбора — это
  единственный способ сохранить и вход, и вывод. У `audit` вход **уже лежит в репозитории
  постоянно** и в известном формате. Второй документ был бы разбором разбора: пересказом
  находок, которые никуда не делись, плюс списком ID бэклога, который и так есть в бэклоге.
- **Прецедент существует и он ровно об этом.** ADR-017 уже сделал такое исключение для
  `grooming`: «для `grooming` отдельного документа нет, записи бэклога являются единственным и
  достаточным выходом» (`sdx/protocol.md:311`). `audit` становится **вторым** типом трека `doc`
  без постоянного документа. Это не новый паттерн, а второе применение существующего.
- **REQ-AUDIT-9 этим не нарушается.** Требование говорит: «Активные этапы, гейт-артефакт и
  Closeout-контракт для типа `audit` — те же, что действуют для трека `doc` в целом».
  Closeout-контракт трека `doc` **уже содержит развилку** по типу в п.4 (перенос документа для
  трёх типов, отсутствие переноса для `grooming`); выравнивание `audit` по ветке `grooming` — это
  исполнение контракта трека `doc`, а не отступление от него.
- **`docs/history/` остаётся read-only-архивом.** Отчёт после записи **никогда не правится**: ни
  триаж, ни повторные прогоны его не трогают, маркер `SDX-MIGRATED` в него не ставится (в отличие
  от прецедента `/sdx:reconcile`, `commands/reconcile.md:60`). Трассируемость односторонняя:
  запись бэклога ссылается на находку, находка на запись — нет. Это сохраняет инвариант
  «`docs/history/` — архив, read-only по смыслу» (`commands/reconcile.md:33`) и заодно делает
  ненужным исключение из него.

**Отклонения от SPEC здесь нет:** каталог `docs/history/audit/` используется буквально так, как
называет REQ-AUDIT-7.

**Имя файла отчёта и run-id.** `docs/history/audit/audit-<YYYY-MM-DD>.md`; при втором и
последующих прогонах в тот же день — `audit-<YYYY-MM-DD>-<N>.md`, `N` начиная с 2, определяется
прозаическим сканом существующих файлов (тот же приём, что выделение номера записи бэклога,
`commands/backlog.md:19`). **Run-id = основа имени файла** (`audit-2026-07-26`,
`audit-2026-07-26-2`). Это не новый формат: 23 записи бэклога уже несут ровно эту форму —
`source: audit-2026-07-01 (B1)` (`docs/backlog/DEBT-005-*.md:7`). Формализуется существующее
де-факто соглашение, миграция не требуется.

**Run-id и идентификатор каталога прогона — разные вещи, и их нельзя смешивать.** Каталог
прогона (`.sdx/audit-runs/<YYYY-MM-DD-HHMMSS>/`) несёт метку времени, потому что должен быть
уникален в момент создания и переживать несколько попыток; run-id несёт форму имени отчёта,
потому что на него ссылается поле `source` записей бэклога. Единственный источник run-id —
основа имени файла отчёта, известная уже на шаге записи манифеста (поле `report_target`);
`manifest.txt` и frontmatter отчёта обязаны нести именно её, а не идентификатор каталога.
Смешение форм ломает первый (детерминированный) слой дедупликации: `grep` по
`<run-id> (<CODE><N>)` искал бы строку, которой в бэклоге нет — то есть REQ-AUDIT-14 и
REQ-AUDIT-15 не исполнялись бы при формально корректном коде. Дефект допущен в первой редакции
поставки и обнаружен fresh-eyes ревью (FAIL-1); зафиксирован здесь как инвариант, чтобы не
воспроизвестись.

**Исторический отчёт не переносится.** `docs/audit-2026-07-01-recommendations.md` остаётся на
месте с его баннером исторического снапшота — по инварианту «исторические документы не
переписываются» (`docs/DECISIONS.md:79`). `/sdx:reconcile` его в `docs/history/audit/` не
перемещает; это явно названная граница, а не забытая миграция.

## Схема данных / API

### `session_state.json`

```
"type":  "feature | bug | refactor | init | import | grooming | retro | postmortem | intake | audit | proto"
"track": "patch | standard | full | doc | vibe"
```
`type` остаётся описательным: ни один enforcement-скрипт его не читает (инвариант ADR-017,
`docs/DECISIONS.md:487-491`). Позиция `audit` в enum — после `intake`, перед `proto`.

### Девять векторов и их коды (REQ-AUDIT-4)

Код вектора — префикс ID находок; ID = `<CODE><N>`, `N` нумеруется локально внутри вектора.
Локальность нумерации — то, что делает параллельный фан-аут безопасным без координации.

| Код | Вектор | Предикат применимости (вычисляет оркестратор) |
|---|---|---|
| `ARCH` | Архитектура | `has_code` |
| `TRIAD` | Целостность триады SPEC↔DESIGN↔Code | `specs_count ≥ 1` И `designs_count ≥ 1` |
| `TRACE` | Трассируемость требований | `TRIAD` применим И `req_id_files ≥ 1` И `has_code` |
| `CODE` | Качество кода | `has_code` |
| `TEST` | Тестовое покрытие | `has_code` (см. ниже — отсутствие тестов это находка, не «неприменимо») |
| `DOCS` | Качество документации | всегда |
| `DEPLOY` | Деплой | `deploy_evidence ≥ 1` |
| `SEC` | Безопасность | всегда (охват сужен REQ-AUDIT-16б, но это `## Охват`, не «неприменимо») |
| `PROC` | Процесс / экономика фреймворка | `is_sdx_project` |

Список — минимальный обязательный (REQ-AUDIT-4); расширение допустимо добавлением кода и
предиката, без правок enforcement-слоя.

### Детект применимости: определения предикатов

Каждый предикат — детерминированная проверка, результат которой (`applicable` / `n/a` + причина)
попадает в `manifest.txt` до фан-аута. Ключевой принцип, который предикаты обслуживают:
**«неприменимо» означает «у проверки нет предмета», а не «предмет проверки в плохом состоянии»**
(REQ-AUDIT-5). Отсюда несимметричность ниже — она не случайна.

- `specs_count` — число `docs/specs/*.md` за вычетом `README.md`. `designs_count` — то же для
  `docs/designs/`. Каталог, который существует и пуст, даёт `0` — «каталог есть» никогда не
  является признаком применимости, только непустота.
- `TRIAD` неприменим и при односторонней асимметрии (есть `docs/specs/`, пуст `docs/designs/`):
  сверять целостность двух сторон при отсутствии одной невозможно. Асимметрия при этом **не
  теряется**: она фиксируется как причина «неприменимо» в таблице покрытия отчёта. Она становится
  **находкой вектора `TRACE`** только при дополнительном условии — проект доказуемо прогонял
  full-сессии, которые обязаны были произвести обе стороны (`docs/history/plans/*.md` непусто ЛИБО
  `docs/history/sessions-log.md` содержит записи). Правило evidence-based; на проекте, где
  full-сессий не было, асимметрия не является находкой ничьей.
- `req_id_files` — число файлов `docs/specs/*.md`, содержащих паттерн `REQ-[A-Z]+-[0-9]`.
  Трассируемость предполагает идентифицированные требования: `docs/specs/` из сплошной прозы без
  ID трассировать не к чему → `TRACE` неприменим с причиной «требования не идентифицированы ID».
  Это второй случай, который каталог «существует и непуст» не покрывает.
- `has_code` — число файлов исходного кода по списку расширений (`*.py *.js *.ts *.tsx *.go *.rs
  *.java *.kt *.rb *.php *.cs *.c *.h *.cpp *.sh *.bash *.sql *.swift *.scala *.ex *.exs`) вне
  `docs/`, `.git/`, `node_modules/`, `vendor/`, `.sdx/`. Порог `≥ 1`. **Эвристика с честной
  границей:** экзотический стек может быть не распознан. Компенсация — число печатается в
  `manifest.txt` и в раздел «Границы прогона» отчёта, поэтому ошибочный `has_code=0` виден
  пользователю до и после прогона, а не тихо превращает четыре вектора в «неприменимо».
- `TEST` — предикат `has_code`, НЕ «наличие тестов». Проект с кодом и нулём тестов даёт исход
  «есть находки», а не «неприменимо»: тесты, в отличие от `docs/specs/`, не являются
  SDX-специфичным структурным артефактом, их отсутствие — состояние, а не отсутствие предмета
  проверки. Репозиторий без кода вовсе → `n/a`. Симметрично `DOCS`: репозиторий без документации
  даёт находку, не «неприменимо».
- `deploy_evidence` — наличие любого из: `.github/workflows/`, `.gitlab-ci.yml`, `Dockerfile`,
  `docker-compose*`, `*.tf`, `k8s/`, `charts/`, `Makefile` с целью `deploy|release|publish`,
  `package.json` со скриптом `publish`, `.claude-plugin/marketplace.json` (дистрибуция плагина —
  реальный релизный механизм), `.claude/sdx/prod-guard.conf` с хотя бы одной активной
  строкой-паттерном. Библиотека без механизма деплоя → `n/a`; отсутствие деплоя там, где его нет
  по построению, — не находка.
- `is_sdx_project` — существует любое из: `.claude/sdx/`, `.claude/sessions/`, `docs/backlog/`.
  Внутренняя оговорка: подскоуп «экономика самого фреймворка» осмыслен только в мета-репозитории
  (детект: `.claude-plugin/plugin.json` с `"name": "sdx"`). Сужение подскоупа **не создаёт
  четвёртого исхода**: вектор применим, если применим любой его подскоуп, а сужение объявляется в
  разделе `## Охват` файла вектора.

### `manifest.txt` — общий read-only вход фан-аута

Плоский `key: value` + блоки, ≤ 60 строк, пишется оркестратором одним редиректом. Состав:
run-id, целевой путь отчёта, timestamp, `git rev-parse HEAD` и имя основной ветки (через
`sdx/hooks/lib/default-branch.sh`), флаг is-git-repo, счётчики формы проекта (`has_code`,
`specs_count`, `designs_count`, `req_id_files`, тесты, записи бэклога по статусам, число
архивных планов), флаги `deploy_evidence`/`is_sdx_project`/`is_sdx_meta`, список путей и глобов
узкого входа для каждого вектора (что читать и что явно НЕ читать), и **вердикт применимости с
причиной по каждому из девяти векторов**. Файл иммутабелен с момента записи — ни один агент его
не правит (у `auditor` нет `Edit` и нет `Bash`).

### Контракт вызова вектора (REQ-AUDIT-8, ADR-005)

Каждому параллельному вызову `Task` агента `auditor` передаются **только пути и задача**, без
содержимого файлов (`sdx/protocol.md:105-106`):
1. код вектора (`ARCH`/`TRIAD`/…) — рубрика по этому коду живёт в `agents/auditor.md`, а не
   инлайнится оркестратором в промпт (иначе рубрика получила бы вторую точку дрейфа);
2. путь к `manifest.txt` — общий read-only вход; агент читает оттуда узкий вход своего вектора и
   факты о форме проекта, а не перевычисляет их;
3. путь к **своему и только своему** выходному файлу `<run-dir>/<CODE>.md`;
4. явный запрет: не читать файлы вне узкого входа своего вектора, не читать файлы других
   векторов, не писать ничего кроме своего файла.

**Разбиение на волны.** Волна 1 (пять векторов, узкий вход в `docs/`, конфиги, CI):
`TRIAD`, `TRACE`, `DOCS`, `DEPLOY`, `PROC`. Волна 2 (четыре вектора, читают исходный код):
`ARCH`, `CODE`, `TEST`, `SEC`. Обоснование именно такого разреза, а не произвольного: волна 1
дешёвая и её применимость полностью определена манифестом, поэтому ошибка манифеста (например
ложный `has_code=0` или неверный узкий вход) обнаруживается после пяти дешёвых вызовов, до траты
дорогой волны. Векторы, признанные неприменимыми, **не диспетчеризуются вовсе** — их файл
пишет оркестратор сам одной строкой-маркером плюс раздел `## Неприменимость` с причиной из
манифеста (уточнение REQ-AUDIT-8, см. «Отклонения от SPEC»).

### Машиночитаемый исход вектора (REQ-AUDIT-5)

Первая строка файла вектора И финальное сообщение агента — одна и та же строка строго формата:

```
AUDIT <CODE> <FINDINGS|CLEAN|N/A> findings=<N> strengths=<S> problems=<P> risks=<R> recommendations=<C> file=<path>
```

Дублирование в двух каналах намеренно: если финальное сообщение субагента потеряно или
переформулировано, оркестратор восстанавливает исход `grep -h '^AUDIT ' <run-dir>/*.md` — то есть
исход вектора определяется машинно, а не «на глаз» по прозе ответа.

**Счётчик на каждый из четырёх разделов обязателен, включая `problems=`.** Первая редакция
поставки его не содержала, и это выяснилось на первом же прогоне (`audit-2026-07-26`): число
проблем приходилось получать вычитанием `findings − strengths − risks − recommendations`, из-за
чего проверка суммы ниже была невыполнима, хотя выглядела выполнимой. Инвариант:
`findings = strengths + problems + risks + recommendations`.

Проверки консистентности, которые оркестратор выполняет перед склейкой (дешёвые, детерминированные):
- `CLEAN` ⇒ `findings=0`; `FINDINGS` ⇒ `findings ≥ 1`; `N/A` ⇒ `findings=0` И файл содержит
  раздел `## Неприменимость` с названной структурной причиной;
- **сумма сходится:** `findings = strengths + problems + risks + recommendations`, и число
  заголовков `### ` в каждом разделе файла равно своему счётчику;
- `<CODE>` совпадает с именем файла и присутствует в манифесте;
- ровно один файл на каждый вектор из манифеста, ни одного лишнего.

### Источник фактов для агента — только диск

Агент обязан читать каждый файл узкого входа инструментом `Read`/`Grep` непосредственно перед
суждением о нём и НЕ опираться на копии документов, уже присутствующие в его контексте. Часть
проектных файлов (в первую очередь `CLAUDE.md`) инжектируется в контекст субагента автоматически
и представляет собой **снимок на момент старта, а не текущее состояние файла**. Расхождение
снимка с диском даёт находку-фантом — уверенную, конкретную и полностью ложную, то есть худшую
из возможных: она выглядит достовернее многих настоящих.

Требование выведено не из общих соображений, а из наблюдения: на прогоне `audit-2026-07-26`
вектор `DOCS` сообщил, что в `CLAUDE.md` отсутствуют агент `auditor`, тир `fable` и тип `audit`,
тогда как все три там присутствовали. Соседняя находка того же вектора о `sdx/protocol.md`
оказалась верна — то есть протокол агент прочитал с диска, а `CLAUDE.md` взял из контекста.
После внесения правила вектор был перепрогнан: фантом исчез, число настоящих находок выросло
с 10 до 12. Правило добавлено в редакции после первого прогона (см. «Изменения контракта,
внесённые после первого прогона»).

Несоответствие = некорректный выход вектора: этот вектор перевызывается **один** раз, при
повторном несоответствии прогон объявляется незавершённым (см. «Обработка ошибок»).

**Строка `AUDIT ...` не является гейт-маркером и не может им стать случайно.** Литерал
`^### \[FAIL\]` (`sdx/hooks/sdx-stage.sh:115,261`) в отчёте аудита не используется намеренно.
Сверх этого действует **структурная** гарантия REQ-AUDIT-16в: `sdx-stage.sh` грепает
исключительно путь `.claude/sessions/<sid>/<artifact>`, где `<artifact>` берётся из
`SDX_STAGE_MATRIX` (`sdx-stage.sh:105-119, 255-283`). Отчёт лежит в `docs/history/audit/` и не
назван ни в одной строке матрицы, поэтому он неспособен повлиять на гейт даже если бы содержал
любой литерал. Это свойство конструкции, а не соглашение.

### Структура отчёта (REQ-AUDIT-6)

Минимальный YAML frontmatter (машиночитаемость прогона — по паттерну ADR-015: `run`, `date`,
`rev`, `project`, `findings_total`, `vectors` как отображение код → исход). Он и есть механизм
обещанного REQ-AUDIT-7 сравнения прогонов: тренд читается grep'ом по frontmatter'ам каталога, без
чтения тел отчётов.

Разделы: `## Сводка` (run-id, дата, rev, профиль проекта + **таблица покрытия**: вектор | код |
исход | число находок — единственное место, где все девять исходов видны сразу) → `## Сильные
стороны` → `## Проблемы` → `## Риски` → `## Рекомендации` → `## Неприменимые векторы` (код,
вектор, структурная причина) → `## Границы прогона` (что заведомо не проверялось: внешние сканеры
по REQ-AUDIT-16б, эвристичность `has_code`, прозаический характер оценочных векторов).

Внутри каждого из четырёх обязательных разделов находки сгруппированы **по вектору**
(REQ-AUDIT-6). Заголовок находки: `### [<CODE><N>] <заголовок>`. Поля: `Где` (`путь:строка`),
`Суть`, `Почему важно`. Дополнительно обязательны по разделу: в `## Риски` — `Реагирование`
(предложенное действие; риск без реагирования — дефект формата, REQ-AUDIT-6); в `## Сильные
стороны` — `Что нельзя сломать` (то, что делает раздел рабочим, а не декоративным).

### Промежуточные файлы прогона (REQ-AUDIT-8)

```
.sdx/audit-runs/<YYYY-MM-DD-HHMMSS>/
  manifest.txt        # общий read-only вход, пишет оркестратор
  ARCH.md TRIAD.md …  # по одному файлу на вектор; write-only для своего вызова
```

- **Расположение.** `.sdx/` — уже сложившаяся зона рабочих, не версионируемых данных проекта
  (`.sdx/bundles/`, `.sdx/worktrees/` — `.gitignore:3,13`). Каталог сессии не подходит: у
  `/sdx:audit` сессии нет по REQ-AUDIT-3. Системный `/tmp` не подходит: при обрыве прогона
  диагностика теряется, а файлы становятся невидимы пользователю.
- **Коммит.** Никогда. Новый паттерн `.sdx/audit-runs/` в `.gitignore`.
- **Идентификатор каталога — время с точностью до секунды**, а не имя отчёта: два конкурентных
  прогона в одном проекте физически не могут столкнуться каталогами. Целевой путь отчёта
  записан в манифесте, поэтому связь run-dir → отчёт не выводится из имени.
- **Удаление.** Оркестратор удаляет каталог прогона сразу после успешной записи отчёта в
  `docs/history/audit/`. При обрыве каталог остаётся — и это единственное состояние, в котором он
  существует после завершения команды.
- **Отличение мусора от актуального.** Следствие правила выше: **существование каталога прогона
  = прогон незавершён (обрван или выполняется прямо сейчас)**. Различить эти два случая
  оркестратор не пытается угадыванием: на старте `/sdx:audit` перечисляет найденные каталоги
  прогонов с их `started`/`rev` из манифеста и составом (какие векторы уже сдали файлы, каких по
  манифесту не хватает) и **спрашивает** пользователя — доснять недостающие векторы в этот же
  каталог (файлы уже сданных векторов переиспользуются), отбросить или оставить. Автоудаление не
  выполняется никогда: это чужие данные.
- **Частичный отчёт в `docs/` невозможен.** Отчёт пишется одним финальным действием оркестратора
  после того, как для каждого вектора манифеста есть корректный файл. Инвариант:
  `docs/history/audit/` никогда не содержит отчёт неполного прогона.

### Триаж: `source` как единственный канал трассируемости (REQ-AUDIT-14)

Формат — расширение уже существующей де-факто формы (`docs/backlog/DEBT-005-*.md:7`):

```yaml
source: audit-2026-07-26 (SEC1)
```

Для дополненной существующей записи `source` **накапливается списком через запятую** — это
делает канал полным для обоих случаев REQ-AUDIT-14 («порождённая ИЛИ дополненная») и
одновременно даёт точный слой дедупликации:

```yaml
source: audit-2026-07-01 (B1), audit-2026-07-26 (ARCH3)
```

Для записи о регрессе (REQ-AUDIT-13):

```yaml
source: audit-2026-07-26 (TEST2, регресс DEBT-013)
links: [DEBT-013]
```

Расширение аддитивное, схема ADR-015 не меняется (инвариант `docs/DECISIONS.md:292`); поле
свободнотекстовое.

### Триаж: три слоя дедупликации (REQ-AUDIT-12/13/15)

| Слой | Механизм | Что гарантирует |
|---|---|---|
| 1. Точный | `grep -l "<run-id> (<CODE><N>)" docs/backlog/*.md` — непусто ⇒ находка уже учтена, пропустить | Идемпотентность **повторного триажа того же отчёта** (REQ-AUDIT-15, первая половина). Детерминированный, не суждение |
| 2. Смысловой против открытых | Прозаическая сверка по смыслу с записями `status: open`/`in-progress` (приём `/sdx:reconcile`, `commands/reconcile.md:41`). Совпадение ⇒ не создавать; новая существенная деталь ⇒ дополнить `## Суть` + добавить прогон в `source` | REQ-AUDIT-12 и идемпотентность **нового прогона на неизменившемся проекте** (REQ-AUDIT-15, вторая половина): новый отчёт даёт новые ID находок, слой 1 бессилен — работает только слой 2 |
| 3. Смысловой против закрытых | Совпадение с `status: closed` ⇒ **новая** запись (обычно `BUG-`) с `links: [<closed-id>]`, `source` с пометкой «регресс», и первой строкой `## Суть`: «Регресс: `<closed-id>` закрыт сессией `<session>`, находка вернулась». В закрытую запись добавляется только обратная ссылка в `links` — `status` не меняется | REQ-AUDIT-13: регресс — самостоятельный случай, не тихий дубль и не пропуск |

Разделение слоёв 1 и 2 — содержательное: они закрывают **два разных** сценария REQ-AUDIT-15,
и ни один из них не покрывает оба.

## Что НЕ меняется в enforcement-слое (проверено по коду)

- **`SDX_STAGE_MATRIX` не меняется ни на одну строку.** Матрица параметризована **треком**:
  формат строки `track|stage|artifact|fail_marker` (`sdx/hooks/sdx-stage.sh:29,38-61`), все
  хелперы фильтруют по полю 1 = трек (`matrix_stages` :66-68, `matrix_row` :71-73,
  `matrix_index` :77-79). `audit` — тип, он использует существующий трек `doc`, чьи четыре
  строки (`sdx-stage.sh:56-59`) уже есть. Инвариант ADR-017 сформулирован буквально об этом:
  «тип как измерение не пересекается со скриптовым контрактом ни в одной точке»
  (`docs/DECISIONS.md:488-491`), и уже подтверждён прецедентом добавления `intake` («не меняет ни
  строки матрицы», :490).
- **`sdx/hooks/sdx-stage.sh` не меняется вовсе** — ни матрица, ни процедурная логика. В отличие
  от ADR-017, где новый **трек** вскрыл захардкоженную remediation-подсказку
  (`docs/DECISIONS.md:421-430`), новый **тип** не вскрывает ничего: подсказка уже сделана
  трек-зависимой, а трек `doc` не новый.
- **`sdx/hooks/test-sdx-stage.sh` не меняется, ни один сценарий не ломается.** Проверено грепом:
  значения `type` встречаются в тестах исключительно как **аргументы** `init`
  (`test-sdx-stage.sh:832,846` — `"grooming"`; `test-integration-stage-lifecycle.sh:219` —
  `"proto"`), никогда как перечисление, требующее расширения. Sanity-сценарий 34 итерирует
  `for track in full standard patch doc vibe` (`test-sdx-stage.sh:796`) — **треки**, не типы, и
  сравнивает поле 4 таблицы протокола (:798, `awk -F'|' '{print $4}'`) — столбец «Активные
  этапы». Правка столбца «Назначение» (поле 3) для перечисления типов сценарий 34 не затрагивает.
  **Ограничение реализации:** в ячейку «Назначение» нельзя вносить символ `|` (сдвинет поля) —
  единственный способ сломать сценарий 34 этой поставкой.
- **Остальные хуки и их проводка не меняются.** `stage-gate.sh` уже открывает запись в
  `docs/*`/`.claude/*`/`*.md` безусловно (`sdx/hooks/stage-gate.sh:62`), поэтому и отчёт, и
  файлы прогона (`.md`) записываются на любой стадии; вне ветки `sdx/<id>` все хуки no-op, что
  и есть штатный режим `/sdx:audit`. `hooks/hooks.json` — без изменений (нового хука нет).
- **Автотестов эта поставка не добавляет — и это названный пробел, а не упущение.** Поставка не
  содержит шелл-кода, а харнеса для тестирования прозаических команд/агентов во фреймворке нет
  (все `sdx/hooks/test-*.sh` тестируют скрипты). Прямое следствие для Verification: обязателен
  **фактический ручной прогон** `/sdx:audit` в двух конфигурациях — на этом мета-репозитории
  (полная триада) и на временном проекте без `docs/specs/`/`docs/designs/` (проверка исхода
  «неприменимо»). Если прогон не выполнен, покрытие остаётся видимым, и это обязано быть
  зафиксировано `DEBT-`записью на Closeout — прецедент невыполненного ручного прогона уже есть
  (`DEBT-025`), повторять его молча недопустимо.

## Граница `audit` vs `intake` (риск SPEC, требующий явного проговаривания)

Различия, наблюдаемые в поведении, а не в намерении:

1. **Форма входа.** `intake` принимает материал, поданный пользователем извне, для которого в
   репозитории нет структурированного места (`PROC-009` открыт, `sdx/protocol.md:70`);
   единственный след входа — прозаический. Вход `audit` — путь к файлу, **уже существующему в
   репозитории** до старта сессии, порождённому командой этого же проекта, с известным
   форматом (frontmatter прогона, девять векторов, ID находок). Наблюдаемо: `/sdx:start audit`
   может **детерминированно провалидировать свой вход** (файл существует, frontmatter парсится,
   run-id извлекается); `/sdx:start intake` не может по построению.
2. **Контракт дедупликации.** `intake` (как и `grooming`, и `/sdx:reconcile`) располагает только
   смысловой сверкой против открытых записей. У `audit` есть **точный** слой (слой 1 выше) и
   **обязательный класс «регресс»** против закрытых записей (REQ-AUDIT-13), которого нет ни у
   `intake`, ни у `grooming`, ни у `reconcile`. Наблюдаемо: повторный разбор одного и того же
   входа даёт у `audit` детерминированно нулевую дельту, у `intake` — нет.
3. **Постоянный документ.** `intake` производит `docs/history/intake/<session_id>.md`; `audit` не
   производит никакого (см. «Коллизия `docs/history/audit/`»). Наблюдаемо в Closeout-чек-листе.
4. **Обязательность НОВОЙ записи.** Closeout п.4 требует для `intake` минимум одну **новую** (не
   правку) запись (`sdx/protocol.md:311`, `commands/archive.md:59`). На `audit` это требование
   **не распространяется**: честный аудит зрелого проекта может дать ноль новых записей — все
   находки уже открыты — и это успешный триаж, а не пустая сессия. REQ-AUDIT-11 выполняется
   дополнением существующих записей (`source` + `## Суть`), как у `grooming`.

**Честная часть ответа.** Если бы различались только пункты 1 и 3, `audit` следовало бы
оформить не типом, а режимом `intake` с предзаданным входом — «источник материала другой» сам по
себе тип не оправдывает. Отдельный тип оправдывают пункты **2 и 4**: они меняют не вход, а
контракт операции над бэклогом и контракт Closeout, то есть ровно то измерение, по которому
ADR-017 уже развёл `intake` и `grooming` (create-путь vs update-путь). `audit` — третья точка на
той же оси: **verify-путь** (сверить свежую картину состояния с уже накопленным бэклогом,
включая обнаружение возврата закрытого).

**Как эта граница удерживается.** Так же, как граница `intake`/`grooming`: исключительно прозой
(`sdx/protocol.md:70` и :65-70, `commands/start.md:47`, ADR-019) — ни один хук её не проверяет и
не может (все три типа проходят через одну строку `doc|Update|change_note.md|no`). Компенсация:
ось когерентности лёгкой Verification трека `doc` расширяется — формулировка `sdx/protocol.md:290`
(«не подменила ли `intake`-сессия собой `grooming`») становится трёхсторонней, а `verify.md:12`
получает три audit-специфичных проверки: (а) каждая `source`-ссылка разрешается в реально
существующую находку названного отчёта; (б) каждая запись-регресс ссылается на реально закрытую
запись; (в) ни одна новая запись не дублирует открытую по смыслу.

## Обработка ошибок и Граничные случаи

### `/sdx:audit` в проекте-потребителе без SDX-структур (REQ-AUDIT-3)

Стратегия — **деградировать, а не отказывать**; ни одну структуру проекта, кроме контейнера
собственного вывода, не создавать:

- **Нет `docs/history/audit/`** → создать (`mkdir -p`) вместе с файлом-заглушкой. Это часть
  записи отчёта, а не навязывание раскладки: без каталога отчёт физически некуда положить.
  Формально это единственная запись за пределами самого файла отчёта — названа явно, чтобы
  `reviewer` не читал её как нарушение REQ-AUDIT-3.
- **Нет `.claude/sdx/` (проект не инициализирован SDX)** → не создавать. `PROC` получает
  «неприменимо», `TRIAD`/`TRACE` — по своим предикатам. Прогон выполняется на универсальных
  векторах и полезен (REQ-AUDIT-3). Одна информационная строка про `/sdx:init` допустима, гейтом
  не является.
- **Нет `docs/backlog/`** → `/sdx:audit` он не нужен вовсе (команда бэклог не пишет). Отчёт
  формируется штатно.
- **Не git-репозиторий** → `rev` в манифесте и frontmatter = `n/a`; векторы, опирающиеся на
  историю (churn в `ARCH`/`CODE`), теряют часть входа, что фиксируется в `## Границы прогона`.
  Прогон не отменяется.
- **Грязное рабочее дерево** → гарда нет (в отличие от `reconcile --auto`,
  `commands/reconcile.md:20`): команда read-only, откатывать нечего.
- **Коммит отчёта.** По образцу `commands/reconcile.md:74`: на ветке `sdx/<id>` — закоммитить
  инкрементально в ветку сессии; иначе — **напомнить** пользователю закоммитить отдельной веткой,
  самой коммит вне сессии не делать (основная ветка получает только merge-коммиты, ADR-009).
- **Вызов внутри активной сессии** разрешён (состояние не читается и не пишется, в `session.log`
  не пишется — по образцу `commands/backlog.md:6`), но одной строкой сообщается, что отчёт ляжет
  на ветку сессии и вольётся вместе с ней.

### Незавершённый прогон и сбой отдельного вектора

Прогон объявляется незавершённым (отчёт НЕ пишется, каталог прогона сохраняется, пользователю
называется, каких векторов не хватает), если после однократного перевызова хотя бы один вектор
манифеста не имеет корректного файла. **Осознанно не вводится четвёртый исход вектора** вида
«не выполнен»: REQ-AUDIT-5 требует ровно одного из трёх исходов для каждого вектора, а выдать
сбой вызова за «чисто» — дефект, за «неприменимо» — ровно то смешение, которое REQ-AUDIT-5
называет дефектом поставки. Неполнота — свойство **прогона**, а не статус вектора; в
опубликованном отчёте три исхода выполняются для всех девяти векторов всегда.

### `/sdx:start audit` — предусловия входа

Проверяются **до** создания сессии (образец: `commands/start.md:16`, где согласие на
реконсиляцию останавливает команду без создания сессии):
- аргумент — путь к существующему файлу в `docs/history/audit/` с парсящимся frontmatter
  (`run:`); иначе стоп с перечислением доступных отчётов. Discovery-lite **не порождает** новый
  аудит и не пересканирует проект (REQ-AUDIT-10) — при отсутствии отчётов направление на
  `/sdx:audit`, а не автозапуск;
- `docs/backlog/` существует; иначе стоп с направлением на `/sdx:init`/`/sdx:reconcile`.
  Причина отказа, а не создания структуры на ходу: гейт-выход трека `doc` — изменение бэклога
  (REQ-AUDIT-11), и сессия, начатая без бэклога, не может его выполнить, а разворачивание
  раскладки проекта — зона `/sdx:init`, не сессии;
- предупреждение (не блокировка), если по слою 1 все находки отчёта уже отражены в `source`
  записей бэклога: отчёт, вероятно, уже разобран.

### Шаблон сессии для типа `audit` не создаётся

`sdx/templates/audit.md` не добавляется. `commands/start.md:47-50` содержит обобщённую строку
`cp "${CLAUDE_PLUGIN_ROOT}/sdx/templates/<type>.md"` для `retro`/`postmortem`/`intake` — правка
должна **явно** отнести `audit` к ветке `grooming` («шаблона не получает»), иначе обобщение будет
прочитано как отсылка к несуществующему файлу.

### Статус `deferred` — молчание SPEC

REQ-AUDIT-12 называет `open`/`in-progress`, REQ-AUDIT-13 — `closed`; `deferred` не назван.
Решение: смысловое совпадение с `deferred` трактуется **как с открытой** (дубль не создаётся),
но факт повторного обнаружения фиксируется — прогон добавляется в `source`, в `## Суть`
дописывается строка «аудит `<run-id>` подтвердил актуальность отложенного». Разотложение
(`deferred → open`) **не выполняется**: это перераспределение атрибута существующей записи, то
есть зона `grooming` (ADR-017, `docs/DECISIONS.md:437-438`). Кандидат передаётся пользователю
одной строкой в `change_note.md`.

### Верификация и Closeout сессии `audit`

- `verification_report.md` — штатный лёгкий прогон трека `doc`: `reviewer` через Task, `qa` не
  вызывается (`commands/verify.md:12,15`). Оговорка ADR-017 про `stop-gate` на `doc|Verification`
  действует без изменений (`sdx/protocol.md:290`).
- Closeout: п.2 — как правило `(n/a)`, с тем же исключением, что у трека `doc` (если сессия
  привела к правке протокола/`CLAUDE.md`/новому ADR); п.3 — всегда `(n/a)`; п.4 — основная точка
  выхода, **без** переноса постоянного документа (его нет) и **без** требования новой записи.
- Отчёт аудита в Closeout **не переносится и не правится**: он уже лежит в постоянном
  хранилище и попал туда вне сессии.

### `/sdx:reconcile` и отчёты аудита

`docs/history/` исключён из скана целиком (`commands/reconcile.md:33`), поэтому отчёты аудита
`reconcile` кандидатами не считает — и это желаемое поведение: у них есть штатный путь разбора
(`/sdx:start audit`), а двойной триаж породил бы дубли двумя механизмами с разными правилами
дедупликации. Поскольку документ, полный actionable-находок в `docs/`, читатель ожидал бы увидеть
источником скана, исключение фиксируется **явной** оговоркой в тексте команды, а не остаётся
следствием общего правила.

## Безопасность

- **Read-only как enforcement, а не обещание (REQ-AUDIT-3/16а).** У `auditor` нет `Bash` и нет
  `Edit`. Мотивация выведена независимо, а не скопирована из BUG-004 (`context_report.md:62-70`
  прямо предупреждает не переносить её по аналогии): read-only здесь — **требование поставки**, а
  `Bash` — единственный инструмент, чьи мутации не покрыты хуками `Write|Edit|MultiEdit`
  (известная граница `DEBT-003`, `sdx/protocol.md:243-246`). Девять параллельных агентов с
  `Bash` в read-only команде были бы главным риском поставки. Совпадение набора инструментов с
  `reviewer.md:5` — следствие, не заимствование.
- **Цена решения названа честно.** Без `Bash` агент не может прогнать линтер/coverage/`git log`.
  Компенсация — детерминированный слой вычисляет оркестратор один раз в `manifest.txt`; то, что
  требует внешних инструментов, вне скоупа по REQ-AUDIT-16б и объявлено в `## Границы прогона`.
- **Отчёт не гейтит ничего (REQ-AUDIT-16в)** — гарантия структурная, см. «Машиночитаемый исход
  вектора»: путь `docs/history/audit/` не назван ни в одной строке `SDX_STAGE_MATRIX`, а
  `sdx-stage.sh` грепает только артефакты матрицы внутри каталога сессии. Литерал
  `^### \[FAIL\]` в отчёте не используется дополнительно — на уровне соглашения, поверх
  структурной гарантии.
- **Вектор `SEC` без внешних инструментов и без сети (REQ-AUDIT-16б).** Ограничен тем, что видно
  прозаическому анализу репозитория: паттерны похожих на секреты строк, права/режимы,
  небезопасные конструкции в шелл-скриптах, отсутствие пиннинга версий, конфиги с секретами в
  tracked-файлах. Классы, требующие сигнатурных инструментов (актуальные CVE), объявляются
  ненайденными в `## Границы прогона` — не выдаются за проверенные.
- **Значение `model` не валидируется ничем** (подтверждено грепом `sdx/hooks/test-*.sh`,
  `context_report.md:126-129`). Введение четвёртого тира расширяет пространство тихого сбоя от
  опечатки. SPEC сознательно оставляет пробел вне скоупа (раздел «Риски и Ограничения») —
  дизайн его не закрывает, но обязывает оформить `DEBT-`запись на Closeout.
- **`archive-verify.sh`, `stage-write-guard.sh`, `prod-guard.sh`** трек- и тип-агностичны —
  поведение на сессии `audit` не меняется.

## Архитектурное решение: ADR-019 (предлагаемый текст)

Следующий свободный номер — **019** (последний существующий ADR-018, `docs/DECISIONS.md:541`).

> ## ADR-019. Агент-аудитор, команда `/sdx:audit`, тип сессии `audit` и четвёртый тир модели `fable`
>
> - **Контекст.** Во фреймворке не было механизма целостной оценки состояния проекта «как есть».
>   `reviewer` оценивает **дельту одной сессии** против её же контракта и никогда не смотрит на
>   проект целиком (`sdx/protocol.md:283-290`). `/sdx:reconcile` переносит в бэклог **уже
>   написанные людьми** находки и приводит структуры к формату — он не порождает новых находок
>   оценочным суждением (`commands/reconcile.md:37`). Разовая ручная ревизия
>   `docs/audit-2026-07-01-recommendations.md` доказала ценность такой оценки — 23 находки легли
>   в бэклог и породили ADR-008/011/014/015/017/018 — но производилась без выделенной роли и без
>   повторяемой процедуры. Отдельно: пользователь эмпирически подтвердил живым вызовом субагента,
>   что значение `model: fable` резолвится реальным тиром (Fable 5), тогда как ADR-008 фиксирует
>   ровно три тира с инвариантом «пересмотр привязки — новый ADR» (`docs/DECISIONS.md:76`).
>   Использование `fable` без ADR было бы прямым нарушением этого инварианта.
>
> - **Решение.**
>   1. **Четвёртый тир `fable`** признаётся наравне с `opus`/`sonnet`/`haiku` и получает
>      закреплённую роль: **ревизионное суждение** — оценка состояния объекта целиком при
>      отсутствии эталона, с информационным (негейтящим) выходом. Единственный носитель тира на
>      момент решения — `auditor`.
>   2. **Новый субагент `auditor`** (`model: fable`, `tools: Read, Write, Glob, Grep` — без
>      `Bash` и `Edit`): многовекторная оценка проекта целиком, девять векторов, три исхода на
>      вектор, файл на вектор.
>   3. **Новая read-only команда `/sdx:audit`** вне сессий: детерминированный precheck →
>      `manifest.txt` → параллельный фан-аут двумя волнами (5+4) → склейка оркестратором → один
>      файл в `docs/history/audit/audit-<дата>[-N].md`. Единственная запись в проект — отчёт (и
>      каталог под него).
>   4. **Новый тип сессии `audit`**, жёстко и безусловно привязанный к треку `doc` на
>      `/sdx:start` (по образцу `grooming`/`retro`/`postmortem`/`intake` — ADR-017 — и `proto` —
>      ADR-018): триаж готового отчёта в `docs/backlog/`. `SDX_STAGE_MATRIX` и `sdx-stage.sh`
>      **не меняются ни на строку** — тип не является параметром матрицы (инвариант ADR-017).
>   5. **`audit` — второй тип трека `doc` без постоянного документа разбора**, наравне с
>      `grooming`: предмет его разбора уже является постоянным документом. Этим устраняется
>      двусмысленность каталога `docs/history/audit/`.
>   6. **Дедупликация в три слоя**: точный (`source` содержит `<run-id> (<CODE><N>)`) →
>      смысловой против открытых → смысловой против закрытых как **регресс** с отдельной
>      записью и ссылкой на источник регресса.
>
> - **Граница `fable` vs `opus` (то, что этот ADR обязан закрыть).** ADR-008 закрепил за `opus`
>   «оценочное суждение». Аудит — тоже оценочное суждение, поэтому без явной границы два тира
>   становятся неразличимы, а карта тир→ответственность — неоднозначной. Граница проводится по
>   **трём наблюдаемым признакам роли**, а не по ощущению «сложности задачи»:
>
>   | Признак | `opus` — верификационное суждение | `fable` — ревизионное суждение |
>   |---|---|---|
>   | Эталон | Задан извне и материализован (`SPEC`/`DESIGN`/`change_note` + diff). Правильный ответ определён контрактом; вопрос лишь в том, найдено ли расхождение | Эталона нет. Критерий качества — часть самого суждения; находка формулирует то, что нигде не записано требованием |
>   | Отношение к гейту | Вердикт **гейтит машинно**: `^### [FAIL]` в `verification_report.md`, `fail_marker=yes` в матрице | Вердикт **информационный**: не участвует ни в одном гейте (REQ-AUDIT-16в), не блокирует ни одну сессию |
>   | Охват | Дельта одной сессии; границы заданы diff'ом извне | Проект целиком; границы охвата агент определяет сам в рамках вектора |
>
>   Правило назначения для будущих ролей: **есть эталон и вердикт блокирует → `opus`; эталона
>   нет, охват — целое, вердикт информационный → `fable`.** Роли `sonnet` (производство
>   артефактов по заданию) и `haiku` (механика) правилом не затрагиваются.
>
> - **Обоснование.** (а) Роль не укладывалась ни в один существующий агент: `reviewer` определён
>   через дельту и контракт, `architect` — через проектирование нового, и его нельзя было
>   переиспользовать режимом (как Import/Export), потому что режим агента не может нести другой
>   тир модели. (б) Отдельная команда, а не этап сессии — потому что аудит по постановке
>   производится «как есть», вне и независимо от любой задачи; сессия для него была бы церемонией
>   без предмета. (в) Тип на существующем треке `doc`, а не новый трек — потому что
>   последовательность этапов триажа буквально совпадает с `doc` (`Discovery-lite → Update →
>   лёгкая Verification → Closeout`), а новый трек по прецедентам ADR-017/018 оправдан только
>   **другим набором активных этапов**. (г) Накопительное хранение вместо перезаписываемого
>   снапшота (`docs/sdx-reconcile-report.md`) — потому что сравнение прогонов во времени объявлено
>   ценностью (REQ-AUDIT-7), а не побочным эффектом. (д) Параллельность признана безопасной именно
>   потому, что общего изменяемого файла между вызовами нет: `PROC-010` описывает конкурентную
>   запись в **общие** файлы сессии и на схему «общий read-only вход + файл-на-вызов» не
>   переносится.
>
> - **Инварианты.**
>   - Раскладка тир→ответственность: `opus` — верификационное суждение с гейтящим вердиктом;
>     `fable` — ревизионное суждение без эталона с информационным вердиктом; `sonnet` — рабочая
>     роль; `haiku` — механика. Источник истины раскладки — frontmatter агентов
>     (инвариант ADR-008 сохраняется); конкретные model ID в документах не дублируются.
>     Пересмотр раскладки — новый ADR.
>   - Отчёт аудита **не участвует ни в одном стадийном гейте** ни на одном треке. Гарантия
>     структурная: путь `docs/history/audit/` не назван ни в одной строке `SDX_STAGE_MATRIX`, а
>     `sdx-stage.sh` проверяет только артефакты матрицы внутри каталога сессии. Подключение
>     отчёта к гейту — отдельное решение отдельным ADR.
>   - `/sdx:audit` не создаёт сессию, не пишет `session_state.json`/`session.log` и не изменяет
>     ни один файл проекта, кроме файла отчёта и каталога под него.
>   - `SDX_STAGE_MATRIX` и `sdx-stage.sh` этим решением не изменяются; `type` по-прежнему не
>     валидируется enforcement-скриптами (ADR-017, REQ-COMPAT-1).
>   - `audit`/`intake`/`grooming` — три разных пути над `docs/backlog/`: verify / create /
>     update. Различие держится **исключительно прозой** и не проверяется ни одним хуком;
>     компенсация — ось когерентности лёгкой Verification трека `doc`.
>   - Отчёт после записи иммутабелен: триаж его не помечает и не правит; трассируемость
>     односторонняя (запись бэклога → находка) через поле `source`.
>   - Промежуточные файлы прогона (`.sdx/audit-runs/`) никогда не версионируются;
>     `docs/history/audit/` никогда не содержит отчёт неполного прогона.
>
> - **Границы (не решается этим ADR, названо явно).**
>   - **Значение `model` не валидируется ни одним тестом фреймворка** — недокументированное
>     значение или опечатка проваливаются тихо при первом вызове через Task. Введение четвёртого
>     тира расширяет это пространство. Вне скоупа по SPEC; оформляется записью бэклога.
>   - Разграничение `fable`/`opus` — **нормативная классификация ролей, не измеренная разница
>     способностей**: бенчмарка нет и в рамках этой поставки быть не могло. ADR фиксирует
>     правило, делающее карту тиров однозначной, а не эмпирический факт превосходства тира на
>     классе задач. Ревизия — новым ADR при появлении данных.
>   - Внешние сканеры безопасности/зависимостей — вне скоупа (REQ-AUDIT-16б).
>   - Индекс каталога `docs/history/audit/` не заводится (класс `DEBT-020`); заглушка каталога
>     явно названа заглушкой, а не индексом, чтобы не повторить расхождение буквы ADR-017 и
>     факта.
>   - Достаточность зерна «один вектор = один вызов» для монорепозиториев промышленного размера
>     не гарантируется: дальнейшее дробление внутри вектора — отдельное решение.
>   - Общее правило записи в разделяемые файлы при параллельном исполнении (`PROC-010`) не
>     закрывается; поставка даёт первый работающий прецедент безопасной схемы.
>
> - **Связь.** Расширяет ADR-008 (четвёртый тир + граница ролей), не отменяя его инвариантов.
>   Расширяет ADR-017 (пятый тип трека `doc`; второе применение ветки «без постоянного документа»,
>   ранее только `grooming`; трёхсторонняя граница типов). Использует прецедент жёсткой привязки
>   тип→трек из ADR-017/018. Опирается на ADR-015 (аддитивное расширение семантики поля `source`
>   без правки схемы). Не пересматривает ADR-016 (единственный писатель `stage`). Родственно
>   `IDEA-002` (fanout-контур: та же идея декомпозиции на самодостаточные элементы, но
>   внутрипроектная, а не по портфелю репозиториев) и `IDEA-005` (процедура lean-аудита) — ни то,
>   ни другое этим решением не закрывается.

## Отклонения от SPEC

**Отклонений от требований SPEC нет** — ни одно требование REQ-AUDIT-1..16 не реализуется иначе,
чем записано, и ни один буквально названный путь (`docs/history/audit/`) не заменён другим. Но
**контракт, описанный в этом документе, изменился по ходу Execution** — см. отдельный раздел
«Изменения контракта, внесённые после первого прогона» ниже; первая редакция этого раздела
утверждала «содержательных отклонений нет» и тем самым скрывала эти изменения, что было
справедливо отмечено fresh-eyes ревью (FAIL-2). Ниже — четыре **уточнения** там, где SPEC
недоопределён или молчит; каждое названо, чтобы `reviewer` не принял его ни за тихое отклонение,
ни за пробел.

1. **Тип `audit` не производит постоянного документа разбора** (уточнение REQ-AUDIT-9).
   Closeout-контракт трека `doc` уже содержит развилку по типу (`sdx/protocol.md:311`:
   `retro`/`postmortem`/`intake` переносят документ, `grooming` — нет); `audit` выравнивается по
   ветке `grooming`. Это исполнение контракта трека, а не отступление от него; альтернатива —
   два рода файлов в одном каталоге с неразличимой семантикой.
2. **Векторы, признанные неприменимыми, не диспетчеризуются** (уточнение REQ-AUDIT-8). Их файл
   пишет оркестратор из уже вычисленного вердикта манифеста. REQ-AUDIT-8 регулирует параллельное
   исполнение аудита **по векторам**; у структурно неприменимого вектора исполнять нечего, а
   вердикт детерминирован — вызов агента ради пересказа причины был бы чистой стоимостью.
   Формальное требование «файл на вектор» соблюдено: файл существует у всех девяти.
3. **Неполнота прогона — свойство прогона, а не четвёртый исход вектора** (уточнение
   REQ-AUDIT-5). Сбой вызова не попадает ни в один из трёх исходов честно, поэтому отчёт с
   недостающим вектором **не публикуется** вовсе. Это усиливает REQ-AUDIT-5, а не ослабляет:
   в каждом опубликованном отчёте три исхода выполняются для всех девяти векторов.
4. **Статус `deferred` в SPEC не назван** (REQ-AUDIT-12 — про `open`/`in-progress`,
   REQ-AUDIT-13 — про `closed`). Решение: трактовать как открытый (дубль не создаётся), но
   зафиксировать повторное обнаружение (`source` + строка в `## Суть`) и не разотлагать запись —
   изменение атрибута существующей записи является зоной `grooming` (ADR-017). Заполнение
   молчания, не противоречие тексту.

Дополнительно, для устранения возможного разночтения REQ-AUDIT-3: команда создаёт каталог
`docs/history/audit/` при его отсутствии. Это часть записи собственного отчёта (положить файл
некуда иначе), а не изменение артефактов проекта.

## Изменения контракта, внесённые после первого прогона

Первый фактический прогон механизма (`audit-2026-07-26`, задача T-18) и деградационный прогон в
проекте-потребителе (T-19) нашли четыре дефекта поставки, невидимых при чтении. Все четыре
исправлены внутри сессии; здесь они перечислены явно, потому что три из них меняют контракт,
описанный выше, а этот документ уезжает в `docs/designs/` навсегда.

1. **Правило «источник фактов — только диск»** добавлено в `agents/auditor.md` (см. одноимённый
   раздел выше). Причина — фантомная находка по инжектированной копии `CLAUDE.md`. Доказательство
   действенности: перепрогон того же вектора с тем же манифестом и той же моделью — фантом исчез.
2. **Обязательный счётчик `problems=`** в строке-маркере (см. «Машиночитаемый исход вектора»).
   Без него проверка суммы была невыполнима при видимости выполнимой.
3. **Единая форма run-id** (см. «Run-id и идентификатор каталога прогона»). Первая редакция
   писала в манифест и отчёт идентификатор каталога с метк‌ой времени, тогда как `source` записей
   бэклога и протокол предписывают форму имени отчёта — детерминированный слой дедупликации
   искал бы несуществующую строку.
4. **`.sdx/audit-runs/` в блоке `.gitignore`, который `/sdx:init` кладёт в проект-потребителя.**
   Паттерн был добавлен только в `.gitignore` самого плагина; у проектов-потребителей источник
   паттернов другой файл (`commands/init.md`), и каталог прогона остался бы untracked — с риском
   уехать в коммит первым же `git add -A`. Контракт этим не менялся, дефект чисто реализационный.

Отдельно, не дефект, но снятие лишней записи: шаг 7 `commands/audit.md` предписывал создавать
файл-заглушку `README.md` рядом с отчётом. Это противоречит REQ-AUDIT-3 («единственная запись —
файл отчёта и каталог под него») и бессмысленно: каталог непуст, потому что в нём лежит отчёт.
Заглушка нужна только `/sdx:init`, создающему каталог заранее пустым, — там она и остаётся.

## Отложено за пределы поставки

1. **Валидация значения `model` во frontmatter агентов.** SPEC явно оставляет пробел вне скоупа
   («Эта поставка данный пробел не закрывает»), поэтому дизайн его не закрывает даже при низкой
   цене реализации — это был бы scope creep против прямого текста SPEC. Введение четвёртого тира
   пространство тихого сбоя расширяет ⇒ **обязательная `DEBT-`запись на Closeout**.
2. **Внешние сканеры безопасности/зависимостей/CVE** (REQ-AUDIT-16б) — отдельное решение.
3. **Инструмент сравнения прогонов** (`/sdx:audit --diff <run-a> <run-b>` или отчёт о тренде).
   REQ-AUDIT-7 объявляет сравнимость ценностью; дизайн обеспечивает её **данными** (frontmatter
   прогона + иммутабельность отчётов), но инструмента не даёт → `IDEA-`.
4. **Индекс каталога `docs/history/audit/`** — класс `DEBT-020`; заводится заглушка с явной
   оговоркой, что она не индекс.
5. **Автотесты прозаических команд/агентов.** Харнеса нет; поставка шелл-кода не содержит.
   Компенсация — обязательный ручной прогон на Verification в двух конфигурациях; при
   невыполнении — `DEBT-`запись (не повторять `DEBT-025`).
6. **Дробление внутри вектора** для монорепозиториев промышленного размера (риск SPEC
   «Масштаб охвата») — зерно фиксируется на уровне вектора, достаточность для любого размера не
   гарантируется.
7. **Общее правило параллельной записи в разделяемые файлы** (`PROC-010`) не закрывается;
   поставка даёт первый прецедент безопасной схемы, который стоит дописать в запись.
8. **Селективный и авторежимный прогон** (`/sdx:audit --vector <CODE>`, `--auto`) — не вводятся:
   `gate_mode` относится к сессиям, а у команды сессии нет; селективность добавит поверхность до
   того, как полный прогон обкатан.
9. ~~**`BUG-007`** (каталоги разборов создаются без заглушек) не исправляется~~ — **пересмотрено
   решением пользователя на гейте Technical Design: `BUG-007` закрывается этой поставкой.**
   Обоснование пересмотра: правка приходится на ту же строку `commands/init.md:17`, которую
   поставка и так меняет, а добавление `docs/history/audit/` с заглушкой при трёх соседних
   каталогах без неё оставило бы в коде необъяснённую асимметрию. Объём — три заглушки по
   образцу `docs/history/intake/README.md`. Область: `commands/init.md` (создание заглушек для
   `retro`/`postmortem`/`intake` наравне с `audit`); на Closeout `BUG-007` получает
   `status: closed` и `session: feat-audit-agent-20260726`. Это единственное расширение скоупа
   против исходного дизайна, и оно санкционировано явно.
10. **`IDEA-002` (fanout-контур по портфелю репозиториев)** и **`IDEA-005` (процедура
    lean-аудита)** остаются отложенными; поставка внутрипроектная и их не закрывает.
