# Context Report: feat-audit-agent-20260726

## Задача

Дословно (см. постановку Discovery): добавить новый тип субагента-аудитора (заявленная
модель `fable`) и новую команду комплексного аудита проекта по векторам (архитектура,
целостность триады, трассируемость, качество кода, тестовое покрытие, качество
документации, деплой, безопасность и т.п.), формирующую детальный отчёт (сильные стороны /
проблемы / риски / рекомендации), плюс отдельную последующую процедуру разбора отчёта и
наполнения `docs/backlog/`.

Это чисто исследовательский отчёт: развилки называются, не выбираются. Ниже — по пунктам
постановки.

## 1. Анатомия агента

Все 8 агентов (`agents/*.md`) имеют одинаковую форму: YAML frontmatter
(`name`/`description`/`tools`/`model`) + Markdown-тело. Ключевые наблюдения:

- **Значения `tools`.** Комбинации: `Read, Write, Edit, Glob, Grep, Bash` (`architect`,
  `developer`, `devops`, `qa` — все, кто пишет код/конфиги и должен уметь их запускать);
  `Read, Write, Edit, Glob, Grep` без `Bash` (`ba`, `lead-dev` — чистые prose-артефакты, не
  требуют исполнения); `Read, Write, Edit, Glob, Grep` без `Bash` (`tech-writer`, тот же
  набор); и минимальный набор `Read, Write, Glob, Grep` у `reviewer.md:5` — единственный
  агент вообще без `Edit` (не правит существующие файлы, создаёт только один новый —
  `verification_report.md`) и без `Bash`.
- **Значения `model`.** Ровно три алиаса тира встречаются во всём репозитории:
  `model: opus` (только `reviewer.md:4`), `model: haiku` (только `tech-writer.md:4`),
  `model: sonnet` (все остальные шесть — `architect.md:4`, `ba.md:4`, `lead-dev.md:4`,
  `qa.md:4`, `devops.md:4`, `developer.md:4`). Других значений (`inherit`, конкретные
  `claude-*-N` ID) в текущей версии репозитория не осталось — это было принято сознательным
  переходом от полных ID к алиасам (ADR-008, `docs/DECISIONS.md:71-79`), закрывшим
  DEBT-005/006. До ADR-008 поле принимало полные model ID (`claude-sonnet-4-6` и т.п.) —
  значит формально поле `model` — свободная строка, не enum, но **конвенция проекта**
  (CLAUDE.md §2, `docs/DECISIONS.md:76`) требует именно тир-алиаса.
- **Структура инструкций.** Единый шаблон по всем восьми файлам: `## Описание` →
  `## Ответственность` → (опционально `## Формат <артефакт>.md` с шаблоном) →
  `## Контекст трека` (как меняется поведение/выход агента по `patch/standard/full/doc/vibe`)
  → `## Инструкции` (пронумерованный алгоритм). `architect.md` и `reviewer.md` — единственные
  с дополнительными секциями (`## Режимы Import/Export` у architect, `## Контракт изоляции` +
  `## Рубрика: три оси` + `## Статусы находок` у reviewer) — оба agent'а несут не строго
  сессионную, а «сквозную» роль поверх обычного трек-контекста.

### `reviewer.md` как ближайший родственник аудитора

`reviewer` (`agents/reviewer.md`) — ролевая модель ближе всего к запрошенному аудитору:
оценочное суждение, работа по трём осям, `model: opus`, контракт изоляции контекста как
**enforcement**, а не договорённость (BUG-004, `agents/reviewer.md:17`, `sdx/protocol.md:286`)
— у ревьюера физически нет `Bash`, поэтому он не может пересчитать diff сам или дотянуться до
`session.log`/произвольного git.

**Чем аудитор принципиально отличается от reviewer:**
1. **Предмет проверки.** `reviewer` сверяет **контракт vs поставку** — что обещано в
   `SPEC.md`/`DESIGN.md`/`change_note.md` конкретной сессии против **diff** этой сессии
   (`sdx/protocol.md:283-290`). Он никогда не смотрит на проект целиком, только на дельту.
   Аудитор, судя по постановке пользователя, смотрит **на весь проект целиком** (архитектура,
   тестовое покрытие, деплой, безопасность «и т.п.») — у него по определению нет «поставки»,
   с которой сверяться, и часто нет одного `SPEC.md`/`DESIGN.md`, покрывающего всю кодовую
   базу (особенно на проекте, не полностью прошедшем через SDX).
2. **Изоляция контекста.** Контракт изоляции reviewer'а (нет `session.log`, нет истории
   рассуждений) существует, чтобы поймать рационализацию **автора текущих изменений**. У
   аудитора нет «автора этой сессии», которого нужно обмануть отсутствием памяти — сканирует
   он застывшее состояние репозитория, а не чью-то текущую работу. Это значит: мотивация для
   изъятия `Bash` у reviewer'а (BUG-004) **не переносится автоматически** на аудитора — там,
   где reviewer'у `Bash` не нужен (diff уже материализован оркестратором файлом), аудитору он
   может быть содержательно нужен (прогнать линтер/coverage-тул, `git log --stat` для
   трассируемости, поиск секретов, проверка версий зависимостей) — это отдельная развилка, не
   копия решения BUG-004, и её нужно решать по существу, а не по аналогии.
3. **Что переиспользимо буквально.** Формат находок `FAIL`/`WARN`/`OK` с секциями `### [FAIL]
   [Ось] Заголовок` (`reviewer.md:29-34, 51-58`) — удобный, уже отработанный паттерн для
   отчёта с находками; можно позаимствовать структуру (не обязательно теми же статусами —
   `FAIL` в `verification_report.md` семантически привязан к **гейту** через
   `^### \[FAIL\]`-маркер `sdx-stage.sh:33,115,261` — если `audit_report.md` не участвует ни в
   каком гейте (см. §5 ниже), заимствовать сам маркер буквально может быть избыточно/вводить в
   заблуждение).

## 2. Развилка по модели `fable` (требует явного решения пользователя)

CLAUDE.md §2 формулирует правило буквально: «Каждый субагент объявляет `model` во frontmatter
**алиасом тира**, а не конкретным model ID... Источник истины раскладки — frontmatter
агентов; конкретные ID в документах фреймворка не дублируются». ADR-008
(`docs/DECISIONS.md:71-79`) фиксирует ровно три тира и их закреплённые роли: `opus` —
оценочное суждение, `haiku` — механика, `sonnet` — рабочая роль; «Пересмотр привязки — новый
ADR» (инвариант, `docs/DECISIONS.md:76`).

**Факт, установленный по репозиторию:** во всём проекте (frontmatter восьми агентов, ADR-008,
DEBT-005, `docs/specs/phase1-enforcement-routing.md:88` и историческая таблица) встречаются
**только** три значения `model`: `opus`, `sonnet`, `haiku`. `fable` не встречается нигде —
ни как алиас тира, ни как исторический полный model ID (грепнул весь репозиторий и не нашёл ни
одного упоминания вне этой сессии).

**Чего я НЕ смог проверить (честно называю границу).** У меня нет доступа к живой схеме
frontmatter субагентов Claude Code вне этого репозитория (нет сети, нет установленной
документации продукта в файловой системе) — я не вызывал реальный рантайм с `model: fable`,
чтобы увидеть, резолвится оно или падает. Всё, что ниже, — сопоставление с тем, что
зафиксировано в этом репозитории и с общими знаниями о продукте на момент обучения, не
эмпирическая проверка.

**Наблюдение по формату слова.** Три существующих тира (`opus`/`sonnet`/`haiku`) — общие
нарицательные слова, обозначающие именно **класс модели** (Claude 5 Opus/Sonnet/Haiku).
Исторические полные ID следовали паттерну `claude-<семейство>-<версия>`
(`claude-sonnet-4-6`, `claude-opus-4-8`, `claude-haiku-4-5` — `docs/DECISIONS.md:72`,
`docs/specs/phase1-enforcement-routing.md:134-136`). `fable` не соответствует ни одному из
двух паттернов: это не одно из трёх задокументированных имён тира и не похоже на
`claude-<family>-<version>`. Мне известно (из общих знаний, не из этого репозитория), что
`fable` — узнаваемое имя голоса text-to-speech у другого поставщика (OpenAI), а не имя модели
или тира Claude/Anthropic — это может объяснять происхождение слова у пользователя (путаница
имён между продуктами), но это только гипотеза, не установленный факт.

**Развилка (называю варианты, не выбираю):**
1. **`fable` — опечатка/подмена и пользователь имел в виду один из трёх существующих тиров.**
   Если так — по аналогии с `reviewer` (оценочное суждение, множество осей аудита, широкий
   охват репозитория) логичный кандидат по роли — `opus`, но это тоже решение пользователя,
   не решение архитектора: `sonnet` тоже валиден, если аудит трактовать как в основном
   механический обход + чтение (см. §8 про масштаб, где предлагается разбиение по векторам —
   не все векторы одинаково требуют фронтир-суждения).
2. **`fable` — реальное, но не задокументированное здесь имя модели/тира**, поддерживаемое
   текущей версией Claude Code у пользователя (например, новое поколение или экспериментальный
   алиас, появившийся после последнего ADR). В этом случае нужна **эмпирическая проверка**
   (тестовый вызов агента с этим значением `model`) до того, как оно попадёт во frontmatter —
   раскладка тиров не валидируется ни одним тестом фреймворка (грепнул `sdx/hooks/test-*.sh` —
   ни один сценарий не проверяет значения `model:` ни у одного агента), т.е. невалидное
   значение **не будет поймано enforcement-слоем** и провалится тихо в рантайме при первом
   вызове через Task — тот же класс тихой деградации, что и у DEBT-010, но для нового
   измерения (frontmatter агента, а не хук).
3. **Принять `fable` буквально как явный per-agent пин**, аналогично тому, как ADR-008
   допускает «проект-потребитель вправе запиннить конкретный ID per-project override'ом — это
   не нарушение инварианта» (`docs/DECISIONS.md:78`). Но это исключение сформулировано для
   **project-level override** конкретного ID существующего тира, а не для введения **четвёртого
   тира** в самом фреймворке — если `fable` окажется четвёртым тиром на уровне самого
   `agents/*.md` (а не project override), это прямо противоречит инварианту ADR-008
   («Привязка ролей к тирам фиксирована... Пересмотр привязки — новый ADR») и требует **нового
   ADR**, а не тихого добавления значения.
4. **Оформить решение отдельным ADR**, который явно вводит `fable` как признанный тир/алиас
   (если он реален и подтверждён эмпирически) и обновляет карту тир→роль. Это явно предусмотрено
   постановкой Discovery как один из вариантов и согласуется с прецедентом ADR-008 (единственный
   ADR, который уже один раз менял состав/форму значения `model`).

Рекомендация Technical Design (не выбор, а то, что стоит сделать первым шагом): проверить
эмпирически, резолвится ли `model: fable` в реальном вызове субагента, прежде чем фиксировать
что-либо в `DESIGN.md`/ADR.

## 3. Анатомия команды

Все 15 команд (`commands/*.md`) — двухчастная форма: YAML frontmatter (`argument-hint`
опционален, `description` обязателен — **нет `model`/`tools`**, потому что команда исполняется
не отдельным агентом, а самой основной сессией в роли Session Manager, `commands/verify.md:5`,
`commands/backlog.md:6` и т.д. — «Ты выполняешь роль Session Manager») + прозаический алгоритм
пронумерованными шагами.

**Разделение read-only / state-changing:**
- **Read-only, без сессии.** `/sdx:backlog` без аргументов и с фильтрами/`<ID>` —
  «команда НЕ требует активной SDX-сессии... является чисто читающей: не пиши в лог сессии и
  не меняй её состояние» (`commands/backlog.md:6`). `/sdx:export` — «read-only операция:
  проект-источник НЕ модифицируется, отдельная сессия не создаётся»
  (`commands/export.md:6`). `/sdx:status` упомянут в протоколе как «чисто читающая операция,
  не мутирует состояние» (`sdx/protocol.md:95`, ADR-005 `docs/DECISIONS.md:48`).
  `/sdx:reconcile --scan-only` — тоже read-only с одним признанным исключением (сам отчёт,
  `commands/reconcile.md:8-10`).
- **State-changing.** `/sdx:next`, `/sdx:verify`, `/sdx:archive`, `/sdx:retrack`,
  `/sdx:backtrack`, `/sdx:start` — все пишут `session_state.json`/`session.log` через
  единственный писатель `sdx-stage.sh` (`sdx/protocol.md:111-143`) и коммитят на ветку сессии.
  `/sdx:backlog add` — единственный пишущий режим read-мостовой команды
  (`commands/backlog.md:17-23`), тоже коммитит, но не создаёт сессию и не трогает `stage`.

**Как команда вызывает субагента.** Единообразно через инструмент `Task`, с **путями к
артефактам и краткой задачей**, а не содержимым файлов — экономия на двойной токенизации
(`sdx/protocol.md:105-106`, ADR-005 `docs/DECISIONS.md:49`). Единственное явное исключение —
`reviewer`, которому подаётся **путь** к материализованному diff-файлу
(`commands/verify.md:29-33`). Пример вызова видно по описанию, а не по литеральному
коду — Markdown-команды не содержат самого `Task`-вызова императивно (это прерогатива
оркестрирующей модели, читающей инструкцию), но контракт входа задан явно текстом: например
`/sdx:export` шаг 2 — «Передавай субагенту пути и задачу, а не содержимое файлов»
(`commands/export.md:19`).

**Как резолвятся пути плагина.** `${CLAUDE_PLUGIN_ROOT}` — переменная, подставляемая рантаймом
в markdown команд/агентов и `hooks.json` (ADR-013, `docs/DECISIONS.md:200-201`), используется
для ссылок на `sdx/protocol.md`, `sdx/hooks/*.sh`, `sdx/templates/*` из любой команды/агента,
независимо от того, где физически установлен плагин у конкретного пользователя. Per-project
данные (сессии, `docs/`, `.claude/sdx/`) резолвятся относительно корня проекта
(`$CLAUDE_PROJECT_DIR`, неявно — команды просто используют относительные пути от корня рабочего
дерева, т.к. вся модель ADR-012 — один CLI, один рабочий каталог).

## 4. Куда встраивается аудит — ключевая развилка

Три обозначенных варианта — с тем, что каждый ломает/переиспользует:

### (a) Отдельная read-only команда вне сессий (образец `/sdx:export`, ближе — `/sdx:reconcile`)

`/sdx:export` — плохой прямой образец: он **read-only по построению**, потому что фича уже
полностью описана в `SPEC`/`DESIGN`/коде — извлечение механическое (посчитать замыкание уже
существующих артефактов), не оценочное. Аудит по постановке пользователя — оценочное суждение
(сильные/слабые стороны, риски, рекомендации), а не механическое извлечение.

**Гораздо более близкий и уже существующий образец — `/sdx:reconcile`** (не был назван в
постановке явно, но структурно ближе всего): не требует активной сессии
(`commands/reconcile.md:6`), имеет режимы `--scan-only`/интерактив/`--auto`
(`commands/reconcile.md:8`), сканирует источники и **сам порождает записи `docs/backlog/`**
с дедупликацией по смыслу против уже существующих записей (`commands/reconcile.md:41,55-58`),
пишет постоянный отчёт `docs/sdx-reconcile-report.md`, **перезаписываемый на каждом прогоне**
(`commands/reconcile.md:66`, `docs/sdx-reconcile-report.md:1-8`). Это ровно тот класс команды,
который умеет и «просканировать и оценить», и «породить бэклог-записи с дедупликацией» — два
из трёх больших кусков функциональности, которые нужны аудитору.

Что ломает/чего не хватает в этом варианте: `reconcile` — **read-only по данным, которые уже
кем-то написаны** (легаси-заметки, TODO, roadmap-блоки) — это перенос уже существующих находок
в новый формат, а не **порождение новых находок оценочным суждением** («не написано, но должно
быть найдено» — например «в этом модуле нет тестов» или «архитектурное решение X создаёт
скрытую связность»). Для этого куска (собственно аудит) прямого прецедента-команды нет —
это генерация нового контента через анализ, что ближе к работе `architect`/`reviewer`, чем к
`reconcile`.

### (b) Новый тип сессии + новый трек (образцы: `doc`/ADR-017, `vibe`/ADR-018)

Оба прецедента вводили **новый трек**, потому что реальный жизненный цикл требовал новых
активных этапов, которых не было ни в одном существующем треке: `doc` — потому что
процессная работа не производит кода и не нуждается в Design/Planning/Execution/Deployment
(`sdx/protocol.md:64-70`); `vibe` — потому что прототипирование требует единственного этапа
без Closeout вовсе, со снятием нормы инкрементальных коммитов (`sdx/protocol.md:72`,
ADR-018 `docs/DECISIONS.md:541-647`).

Введение нового трека — тяжёлая операция по прецеденту: правка `SDX_STAGE_MATRIX` в
`sdx-stage.sh` (единственный машиночитаемый источник истины,
`sdx/protocol.md:141-143`), расширение sanity-теста (`test-sdx-stage.sh` сценарии 34/49,
`docs/DECISIONS.md:485-486,610`), правка таблицы «Профили флоу» в протоколе, `CLAUDE.md`,
минимум трёх-шести команд (`start.md`, `archive.md`, `verify.md`, `retrack.md` и др.), новый
ADR. ADR-017 прямо говорит: «SDX_STAGE_MATRIX расширяется... логика переходов `sdx-stage.sh`
не меняется — `doc` полностью укладывается в существующий формат» — то есть даже «лёгкое»
добавление трека `doc` было оправдано только потому, что **набор активных этапов был
буквально другим**. Вопрос к аудиту как кандидату в новый трек: производит ли комплексный
аудит принципиально другую последовательность этапов, которой нет ни в одном из пяти
существующих треков? По содержанию постановки — нет: «исследовать → сформировать отчёт →
разобрать отчёт → наполнить бэклог» почти буквально совпадает с `doc`-треком
(`Discovery-lite → Update → Verification → Closeout`), см. пункт (c) ниже.

### (c) Тип на существующем треке `doc`

Это прямое попадание по структуре, и постановка Discovery явно просит проверить это. `doc`
уже имеет:
- **`Discovery` (лёгкий, инлайн)** — точка входа, куда естественно ложится «собрать вход для
  аудита» (какие векторы, какой охват, какие каталоги/модули).
- **`Update`** — этап, который производит правки `docs/backlog/` как **обязательный выход**
  (`sdx/protocol.md:71`: «Правки `docs/backlog/` выполняются НА этом этапе, а не откладываются
  до Closeout»). Единственный гейт-артефакт — `change_note.md`.
- **`Verification` (лёгкая, обязательная)** — уже требует fresh-eyes `reviewer` против
  `change_note.md`, ось когерентности буквально сформулирована как «не противоречит ли
  новая/изменённая запись бэклога уже существующим» (`sdx/protocol.md:290`, ADR-017
  `docs/DECISIONS.md:462-471`) — это **дословно** совпадает с требованием дедупликации из
  постановки пользователя.
- **`Closeout`** — уже требует «минимум одно изменение `docs/backlog/`... помечено
  `session: <session_id>`» (`sdx/protocol.md:311`).

**Прямое совпадение, которое постановка просит явно проверить и назвать:** процедура «разбора
аудита и наполнения бэклога соответствующим списком задач» — это, по факту устройства
протокола, **уже описанный** тип операции: `intake` (создаёт записи из НОВОГО внешнего
материала, «create-путь», `sdx/protocol.md:69-70,431-446`) в сочетании с `grooming`
(перераспределяет приоритеты уже существующих записей, куда попадут переоткрытые находки по
уже известным открытым `BUG-`/`DEBT-`). Пограничный вопрос: является ли `audit_report.md`,
сгенерированный **своим же** SDX-агентом по итогам сканирования **этого же** проекта,
«внешним материалом» в смысле, вложенном в определение `intake` («эпик, пачка багрепортов,
продуктовый материал» — `sdx/protocol.md:69`)? Формально он не внешний (не привнесён извне
пользователем), но механически операция идентична: документ с находками → записи бэклога,
дедупликация по смыслу против уже существующих (у аудита это особенно актуально: в бэклоге
уже 27 открытых записей, `docs/backlog/README.md:26-36`, часть из них аудит почти наверняка
переоткроет — например DEBT-003/007/009/010, которые прямо перечисляют пробелы enforcement,
которые дотошный аудит скорее всего снова найдёт).

**Прецедент того, что это уже происходило вручную, один в один.** Исторический
`docs/audit-2026-07-01-recommendations.md` — это ровно то, что просит пользователь: сплошной
аудит фреймворка по векторам A (enforcement-дыры) / B (дрейф документов) / C (процесс) / D
(экономика) / E (предложения по развитию), с находками, приоритетом и рекомендациями. Он был
сделан **вручную** (без выделенного агента-аудитора), а затем **разобран и перенесён в
бэклог** отдельной сессией `fw-backlog-20260719` (ADR-015) — механизм переноса (сопоставление
находка → новый ID, сохранение маппинга в поле `source`, дедупликация) уже один раз применён
на практике именно к аудиторскому документу и задокументирован в
`docs/sdx-reconcile-report.md:28-39` (полный маппинг всех 23 находок на ID бэклога). Это
сильный сигнал: **вторая часть постановки («разбор аудита и наполнение бэклога») скорее всего
не требует новой сущности вообще** — она уже один раз выполнена как штатная doc-сессия
(`fw-backlog-20260719`, тип, судя по времени, предшествующий введению ADR-017 — сейчас это
естественно легло бы в `intake` или новый специализированный тип на треке `doc`).

**Вывод по риску дублирования (прошу отнестись как к главному найденному риску сессии, как и
просит постановка).** Компонент 2 из постановки пользователя («отдельная процедура разбора
аудита и наполнения бэклога») с высокой вероятностью **не требует новой механики** — он
почти покрывается существующим треком `doc` (либо буквально типом `intake`, либо
специализированным типом-побратимом на том же треке). Единственный содержательный новый кусок
всей задачи — **компонент 1**: собственно генерация `audit_report.md` через многовекторное
оценочное исследование существующего состояния проекта (архитектура/качество кода/покрытие/
безопасность/деплой/…). Это именно то, для чего нет прямого прецедента ни в одной из
существующих команд/агентов, и то, что оправдывает новый агент (аудитор) — но необязательно
новый трек/тип сессии для **разбора** его результата.

## 5. Отчёт как артефакт

`verification_report.md` — единственный существующий пример «отчёта с находками» в протоколе.
Структура (`agents/reviewer.md:38-59`): `## Сводка` (трек, итог PASS/FAIL, счётчики находок) →
`## Матрица трассируемости` (требование → файл реализации → тест → когерентность → статус) →
`## Находки` (`### [FAIL|WARN] [Ось] Заголовок` + Где/Суть/Ожидалось-Фактически).

**`^### \[FAIL\]` как машиночитаемый гейт.** Это не просто форматирование — `sdx-stage.sh`
буквально грепает эту строку (`sdx/hooks/sdx-stage.sh:115,261`, `grep -q '^### \[FAIL\]'`) как
часть проверки гейта для `verification_report.md` конкретно (единственный артефакт с
`fail_marker=yes` в матрице, `sdx-stage.sh:45,51,54,58`). Это означает: если `audit_report.md`
захочет участвовать в каком-либо гейте (например «нельзя закрыть Closeout, пока в отчёте есть
критичная находка») — потребуется **явное расширение матрицы** (новая строка с
`fail_marker=yes` для нужного трека/этапа), а не просто копирование формата заголовков —
маркер сам по себе ничего не гейтит без явной проводки в скрипте.

**Кто читает `verification_report.md`.** `/sdx:verify` шаг 6 (`commands/verify.md:34`) —
сводит находки; `/sdx:archive` (гейт входа в Closeout для `patch`/`doc`,
`sdx/protocol.md:302`) — проверяет отсутствие FAIL как предусловие входа; `sdx-stage.sh`
(гейт этапа Verification на всех треках, где он есть, `SDX_STAGE_MATRIX`).

**Где мог бы жить `audit_report.md` — три конкурирующих прецедента:**
1. **Каталог сессии** (`.claude/sessions/<id>/`) — как `context_report.md`,
   `verification_report.md`: эфемерно, удаляется на Closeout (Closeout п.5,
   `sdx/protocol.md:312`), если не перенесено явно в постоянное хранилище на п.2/п.4
   чек-листа.
2. **`docs/history/<type>/<session_id>.md`** — прецедент ADR-017 (`retro`/`postmortem`/
   `intake`): «первый прецедент шаблона сессионного, а не per-project, артефакта»
   (`docs/DECISIONS.md:414-415`), с переносом из каталога сессии в постоянное хранилище на
   Closeout п.4 (`sdx/protocol.md:311`), **без собственного индекса** (в отличие от
   `docs/backlog/README.md`) — это явно названная граница ADR-017
   (`docs/DECISIONS.md:519-520`, кандидат в будущий `IDEA-`). Модель — **накопительная
   история**: один файл на сессию, аудитов может накопиться много со временем.
3. **Плоский `docs/*.md`, перезаписываемый на каждом прогоне** — прецедент
   `docs/sdx-reconcile-report.md` (`commands/reconcile.md:66`: «Запиши (перезаписывая
   предыдущий прогон)»), а также исторический (уже устаревший, но показательный)
   `docs/audit-2026-07-01-recommendations.md`, который жил как одиночный корневой doc-файл
   **до** введения `docs/backlog/`/`docs/history/` и был явно помечен баннером как
   «исторический снапшот» после миграции (`docs/audit-2026-07-01-recommendations.md:7-11`).
   Модель — **только последнее состояние**, без истории прогонов в файловой системе (история
   доступна через `git log` по этому одному пути).

Эти три модели дают разный ответ на вопрос «нужна ли история аудитов во времени (тренд
находок между прогонами) или достаточно последнего состояния» — это открытый вопрос, не
решённый ни одним существующим прецедентом однозначно (первые два — история, третий — только
текущий срез).

## 6. Бэклог как приёмник

Схема (`docs/backlog/README.md:1-13`, ADR-015 `docs/DECISIONS.md:266-301`): один файл на
запись, YAML frontmatter (`id`/`type`/`status`/`priority`/`wave`/`source`/`session`/`links`),
префиксы `FEAT-`/`BUG-`/`DEBT-`/`IDEA-`/`PROC-` со сквозной нумерацией **внутри** префикса,
статусы `open|in-progress|closed|deferred`, индекс `docs/backlog/README.md` (таблицы
Открытые/Закрытые). `id` неизменяем после создания (`docs/DECISIONS.md:294`).

**Как `/sdx:backlog add` выделяет номер:** «Определи следующий свободный номер внутри
префикса (скан существующих `<PREFIX>-NNN`, ведущие нули до трёх знаков)»
(`commands/backlog.md:19`) — то же правило буквально повторено в `/sdx:reconcile` шаг 8
(`commands/reconcile.md:56`: «ровно так же, как в режиме `add`»). Это **прозаический скан**
файловой системы на момент операции, не централизованный счётчик — при пачечном создании
записей из отчёта аудита (много кандидатов за один проход) это создаёт риск гонки только при
параллельном исполнении (не актуально для одного агента, последовательно создающего записи
за один ход, но актуально, если разбор аудита будет распараллелен по векторам — см. PROC-010
ниже).

**Что уже решено для пачечного порождения записей — почти всё нужное есть в `/sdx:reconcile`:**
- **Дедупликация по смыслу.** Шаг 5: «Каждого оставшегося кандидата сверь ПО СМЫСЛУ (не по
  буквальному совпадению строки) с уже существующими записями... При совпадении — не создавай
  дубль; если кандидат добавляет новую деталь — предложи дополнить `## Суть`, не создавая
  новый `id`» (`commands/reconcile.md:41`). Ровно то, что нужно для аудита: он **переоткроет**
  часть уже открытых записей (например архитектурные/enforcement-пробелы, уже описанные в
  DEBT-003/007/009/010/014/015 — см. `docs/backlog/README.md:26-33`) — без дедупликации
  аудит нарастит дубли при каждом повторном прогоне.
- **Идемпотентность повторных прогонов.** Маркер `<!-- SDX-MIGRATED: → <ID> (<дата>) -->`
  (`commands/reconcile.md:39,60`) — актуален для маркировки **источника находки** (файла), но
  не имеет прямого аналога для «находки, обнаруженной живым сканированием кода/архитектуры»
  (нет постоянного файла-источника рядом с находкой, который можно было бы пометить —
  находка живёт только внутри `audit_report.md` очередного прогона). Дедупликация здесь
  целиком ложится на шаг «сверка по смыслу с существующими записями бэклога»
  (как в reconcile), без опоры на маркер.
- **Трассируемость «находка → запись».** У `docs/backlog/*.md` уже есть поле `source`
  (например `source: audit-2026-07-01 (B1)` — `docs/backlog/DEBT-005-*.md:7`) — готовый канал
  для указания, что запись породил именно аудит (например `source: audit <session_id>
  (<vector>, <id находки в отчёте>)`), без изменения схемы (аддитивное расширение уже
  предусмотрено инвариантом ADR-015, `docs/DECISIONS.md:292`).

**Чего нет и придётся спроектировать отдельно:** дедупликация против уже **закрытых**
(`status: closed`) записей — нужна ли она? Аудит может обнаружить **регресс** уже решённой
проблемы (закрытая запись описывала риск, который вернулся) — ни `reconcile`, ни `backlog add`
сейчас не рассматривают этот случай явно (оба ориентированы на дедупликацию против **открытых**
записей, по крайней мере по тексту команд).

## 7. Векторы аудита: что уже покрыто, чего нет

Сопоставление перечисленных пользователем векторов с существующими механизмами:

| Вектор | Уже покрыто чем | Насколько | Применимо только к SDX-проекту? |
|---|---|---|---|
| Целостность триады SPEC↔DESIGN↔Code | Ось когерентности `reviewer` (`sdx/protocol.md:271-273`, ADR-004) | Только **внутри одной сессии** (diff vs контракт этой сессии), не по всему репозиторию сразу | Да — требует `docs/specs/`+`docs/designs/`, т.е. проекта, прошедшего через SDX |
| Трассируемость | Матрица трассируемости `reviewer` (`agents/reviewer.md:46-49`) | Та же граница — по одной поставке, не по всему бэклогу/истории | Да |
| Архитектура | `architect` на Technical Design — но только **для новых фич**, не периодический пересмотр существующей архитектуры целиком | Нет прецедента «ревизии» существующей архитектуры как таковой — ближайшее по духу: сама ревизия 2026-07-01 (`docs/audit-2026-07-01-recommendations.md`), сделанная вручную, разово | Нет — применимо к любому кодовому проекту |
| Качество кода | Ничего структурного — `developer`/`qa` пишут код с TDD, но нет отдельного шага «оценить существующее качество кода» | Не покрыто | Нет |
| Тестовое покрытие | `qa` упоминает «при необходимости — coverage» (`agents/qa.md:16`), но не обязательный количественный порог; `stop-gate` гарантирует только зелёный прогон, не покрытие (`sdx/protocol.md:195-209`) | Слабо, необязательно | Нет |
| Качество документации | `tech-writer` **обновляет** документацию под изменения, но не оценивает её полноту/устаревание как отдельная задача | Не покрыто | Нет (хотя связано с триадой у SDX-проектов) |
| Деплой | `prod-guard` блокирует **опасные команды** по паттерну (`sdx/protocol.md:210-216`) — узкая защита от случайности, не оценка зрелости деплой-процесса; `devops`-агент реализует деплой, не аудирует его | Узко, не оценочно | Нет |
| Безопасность | Ничего целенаправленного — нет сканирования зависимостей/секретов/CVE ни в одном хуке или агенте | Не покрыто вовсе | Нет |
| «и т.п.» (экономика, процесс) | Ревизия 2026-07-01 включала разделы C (процесс) и D (экономика) — прецедент того, что вектор аудита фреймворка/процесса тоже осмыслен, не только кода | Разово, вручную | И то, и другое — для SDX-специфичных находок (D-раздел был об экономии токенов самого SDX) нужен SDX-проект; для процессных находок общего типа — нет |

**Ключевое наблюдение по применимости.** Аудит должен работать «и в проекте-потребителе
плагина, не только здесь» (условие постановки). Часть векторов (архитектура, качество кода,
тестовое покрытие, безопасность, деплой) — универсальны, не требуют присутствия SDX вообще.
Часть (целостность триады, трассируемость требований) **структурно требует** `docs/specs/` +
`docs/designs/` — на проекте, где SDX только что подключён (`/sdx:init` без `--existing`,
или вообще без предшествующих full-сессий), эти два вектора **пусты по построению**, а не
проваливаются с находками — отчёту нужно уметь честно сказать «неприменимо» вместо того чтобы
трактовать отсутствие спек как находку.

## 8. Масштабируемость и контекст

Комплексный аудит по 8+ векторам на репозитории сравнимого с этим (только на этот момент — 15
команд, 8 агентов, 17 hook-скриптов+тестов, 27+47 записей бэклога, полный ADR-журнал) уже
не помещается в чтение «одним проходом» без риска деградации контекста; на прикладном проекте
промышленного размера — тем более.

**Что уже есть во фреймворке для этого класса проблемы:**
- **`/sdx:checkpoint` + `/clear`.** Механизм сброса контекста с восстановлением через чтение
  `.md`-файлов состояния (`sdx/protocol.md:434-435`) — применим **внутри одной длинной
  сессии** аудита (между векторами), но не решает исходную проблему поместить весь охват в
  один вызов одного агента.
- **Делегирование через Task с изоляцией.** Уже используемый паттерн — оркестратор вызывает
  субагента с узким входом (пути, не содержимое), получает узкий выход. Прямо намекает на
  архитектуру «один Task-вызов на вектор (или на группу векторов)», а не один агент,
  читающий весь репозиторий целиком за один проход.
- **Контракт изоляции reviewer'а** (§1 выше) — прецедент того, что узкий, специально
  скроенный вход **обязателен** для качества оценочного суждения, а не просто экономии
  токенов — усиливает аргумент за декомпозицию по вектору (каждый под-аудит получает только
  релевантный себе срез: код-качество не должно читать историю ADR, деплой не должен читать
  весь исходный код).
- **`IDEA-002` («fanout-контур», `docs/backlog/IDEA-002-fanout-contour.md`) — отложенный
  roadmap-пункт, который **дословно называет аудиты** как пример использования**:
  «stateless-задачи по N репозиториям (регенерация доков, **аудиты**, массовый `/sdx:init
  --existing`)... элемент = самодостаточный промпт» (`docs/backlog/IDEA-002-*.md:14-18`).
  Это отложено (`status: deferred`, Фаза 4) и рассчитано на **межпроектный** fanout (N
  репозиториев), но та же идея декомпозиции на независимые самодостаточные элементы прямо
  переносится на **внутрипроектный** fanout по векторам одного аудита (N векторов вместо N
  репозиториев) — концептуально родственная, ещё не реализованная инфраструктура.
- **`PROC-010`** (`docs/backlog/PROC-010-parallel-subagents-shared-session-files.md`) —
  **предостережение**, не решение: реально наблюдавшаяся гонка при параллельном запуске двух
  субагентов, дописывающих в общие файлы сессии без протокола разрешения конфликтов. Если
  форма аудита — «параллельный Task на вектор, каждый пишет в общий `audit_report.md`» — это
  тот же класс риска, уже зафиксированный как открытая находка (`status: open`, приоритет
  normal, `docs/backlog/PROC-010-*.md`), не абстрактный.

**Что это диктует форме команды (называю альтернативы, не выбираю):**
1. Один агент-аудитор, один Task-вызов, весь репозиторий и все векторы за один проход — не
   масштабируется на реальный размер, самый простой в реализации.
2. Один агент-аудитор, вызываемый оркестратором **последовательно, по вектору** (N Task-вызовов
   с узким входом на каждый), каждый дописывает свою секцию в `audit_report.md` **через
   оркестратора** (не параллельно) — избегает риска PROC-010, совместимо с текущей
   архитектурой команд (все они последовательны).
3. Несколько специализированных под-агентов (или один агент с разными «режимами», как у
   `architect` уже есть режимы Import/Export) на разные векторы, с параллельным Task —
   быстрее, но напрямую наследует нерешённый риск PROC-010 без явного протокола записи (нужно
   либо «пишет только оркестратор после сбора ответов», предложенное как предпочтительный
   вариант в самом PROC-010, либо файл-на-вектор со склейкой).

## 9. Риски и открытые вопросы

### Требуют решения пользователя на гейте (Business Spec / Technical Design)
- **Развилка модели `fable`** (§2) — факт, что значение не входит ни в один
  задокументированный тир и не встречается нигде в репозитории, требует либо подтверждения
  (это реальный, эмпирически проверенный тир) и, если он новый, — отдельного ADR, либо
  замены на один из трёх существующих тиров. Без ответа `DESIGN.md` не может корректно
  специфицировать frontmatter нового агента.
- **Где встраивается аудит** (§4) — команда вне сессии (a) vs новый тип на `doc` (c) vs
  новый трек (b, вероятно избыточен по установленному выше сравнению с ADR-017/018). Это
  форма всей поставки, определяющая, сколько файлов правится (от одной команды+агента до
  правок `sdx-stage.sh`, протокола, ADR).
- **Нужна ли отдельная процедура разбора аудита вообще** (§4, §6) — сильный сигнал, что
  существующий `doc`-трек (в частности `intake`, возможно с уточнением семантики «внешний
  материал») уже покрывает эту часть постановки почти буквально; решение — расширять ли
  существующий тип, вводить новый тип на том же треке, или всё-таки строить отдельный
  механизм — стратегическое, не техническое.
- **Модель хранения отчёта** (§5) — накопительная история (`docs/history/audit/<session_id>.md`,
  по образцу ADR-017) vs перезаписываемый снапшот (по образцу `/sdx:reconcile`) — меняет,
  нужен ли пользователю тренд находок между прогонами.
- **Участвует ли `audit_report.md` в каком-либо гейте** (§5) — если да, требуется явное
  расширение `SDX_STAGE_MATRIX`/`fail_marker`; если нет — отчёт чисто информационный, и это
  тоже нужно явно зафиксировать, чтобы не создавалось ложного впечатления машинного гейта там,
  где его нет.
- **Форма распараллеливания по векторам** (§8) — последовательные Task-вызовы (просто, ADR-005
  «экономный режим логирования» этому не противоречит) vs параллельные (быстрее, но требует
  решения PROC-010 хотя бы для этого частного случая, если не для всего фреймворка).
- **Дедупликация против закрытых записей бэклога** (§6) — регресс уже решённой проблемы:
  нужно ли аудиту переоткрывать `closed`-записи, если находка похожа семантически.

### Можно закрыть на Technical Design (без участия пользователя)
- Точный список tools для нового агента (по аналогии с `reviewer`/`architect` — вероятно
  `Read, Glob, Grep` обязательно, `Bash` и `Write` — по итогам решения §1.2 про необходимость
  прогонять внешние тулы).
- Точный формат секций `audit_report.md` (по аналогии с `verification_report.md`, но без
  привязки к гейт-маркеру, если решение §5/9 о негейтящем характере отчёта принято).
- Конкретная схема поля `source`/`links` для порождаемых бэклог-записей (аддитивное
  расширение, не требует ADR по инварианту ADR-015).
- Технический механизм скана «применимых» векторов (детект наличия `docs/specs/`+
  `docs/designs/` для условной активации триад-векторов, §7).

### Не проверено / требует эмпирической проверки (честно называю)
- Резолвится ли `model: fable` вообще в текущей установленной версии Claude Code — не
  проверял (нет сетевого доступа и живого вызова).
- Нет ни одного теста в `sdx/hooks/test-*.sh`, который бы проверял допустимость значений
  `model:` во frontmatter агентов — подтверждено грепом, но не проверял, есть ли такая
  валидация на стороне самого Claude Code (вне этого репозитория) при загрузке плагина.
