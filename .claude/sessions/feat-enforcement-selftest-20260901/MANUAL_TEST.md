# Manual Testing Guide: Self-test enforcement-слоя и блок здоровья в /sdx:status

Контекст: `commands/status.md` — прозаическая инструкция, исполняемая агентом Claude Code, а не
bash-скрипт. Автотест `[T24]` в `sdx/hooks/test-selftest.sh` проверяет её текст статически
(grep-структура), но не может доказать поведенчески, что реальный вызов `/sdx:status` (а) ничего
не меняет на диске и (б) действительно выводит блок здоровья с корректными значениями. Это разрыв
между тем, что доказуемо автотестом, и тем, что требует критерий приёмки SPEC.md («Вызов
`/sdx:status` не инициирует новый прогон self-test и не изменяет никакое состояние»,
REQ-HEALTH-3). Ниже — атомарные шаги для интерактивного прогона через `/sdx:manual`.

Каждый шаг предполагает рабочую директорию `/home/archi/Code/sdx-claude-plugin`, ветку
`sdx/feat-enforcement-selftest-20260901` (или актуальную ветку сессии).

---

### Шаг 1: Зафиксировать контрольные суммы конфигов enforcement-слоя до вызова

**Действие**: выполнить в терминале:
```bash
find .claude/sdx -type f -exec md5sum {} \; | sort > /tmp/before_status.txt
cat /tmp/before_status.txt
```

**Предусловия**: репозиторий — рабочая копия проекта, `.claude/sdx/` существует (создаётся
`/sdx:init`, уже присутствует в этом репозитории).

**Ожидаемый результат**: выведен список файлов `.claude/sdx/prod-guard.conf`,
`.claude/sdx/verify-cmd.sh` и, если self-test уже когда-либо запускался в этом проекте,
`.claude/sdx/.cache/selftest.json` — с их md5-суммами. Список сохранён в `/tmp/before_status.txt`
для сравнения на Шаге 4.

---

### Шаг 2: Вызвать `/sdx:status` в реальной CLI-сессии

**Действие**: в интерактивной сессии Claude Code (не через подагента) выполнить команду
`/sdx:status`.

**Предусловия**: Шаг 1 выполнен. Плагин `sdx` установлен (`/plugin install sdx@sdx --scope user`)
и обновлён до версии, включающей `commands/status.md` из этой сессии (если сессия ещё не
смёржена/не обновлена в установленной копии плагина — см. ограничение DESIGN.md «Ограничение
среды исполнения» — команда всё равно резолвится из установленной копии плагина, не из рабочего
дерева; для проверки именно ЭТОЙ правки может потребоваться временно скопировать
`commands/status.md` в установленную копию плагина или дождаться `/plugin marketplace update
sdx` после мёржа).

**Ожидаемый результат**: команда выполняется без ошибок и выводит стандартный отчёт (Session ID,
Stage, Artifacts, Progress, листинг активных сессий), ПОСЛЕ которого следует новый блок «Здоровье
enforcement» (шаг 5 `commands/status.md`).

---

### Шаг 3: Проверить содержимое блока «Здоровье enforcement»

**Действие**: изучить вывод `/sdx:status` из Шага 2, раздел «Здоровье enforcement».

**Предусловия**: Шаг 2 выполнен, вывод команды доступен.

**Ожидаемый результат**: блок содержит ровно четыре структурных факта: наличие `jq` в `PATH`
(present/MISSING), наличие и непустоту `prod-guard.conf`, наличие и исполняемость
`verify-cmd.sh`, соответствие текущей git-ветки активной сессии — и результат последнего
self-test: если `.claude/sdx/.cache/selftest.json` отсутствует — фраза «self-test ещё не
выполнялся»; если присутствует — `selftest_status` (`ok`/`degraded`/`broken`), результат по
каждому из трёх хуков, `duration_ms`/`budget_exceeded` и явная метка возраста результата
(например, «прогонялся N назад»). Текст НЕ содержит формулировок «блокирует
автономию»/«отключает автономию»/«понижает уровень доступа» — только диагностику со ссылкой на
`FEAT-010`/`FEAT-006`/`FEAT-004` как будущих потребителей.

---

### Шаг 4: Подтвердить отсутствие побочных эффектов после `/sdx:status`

**Действие**: выполнить в терминале:
```bash
find .claude/sdx -type f -exec md5sum {} \; | sort > /tmp/after_status.txt
diff /tmp/before_status.txt /tmp/after_status.txt && echo "NO CHANGES" || echo "CHANGED"
```

**Предусловия**: Шаги 1–2 выполнены в этом порядке (без вызовов `/sdx:status` между ними, помимо
проверяемого).

**Ожидаемый результат**: `diff` не выводит различий, скрипт печатает `NO CHANGES` — контрольные
суммы всех файлов `.claude/sdx/` (включая `.cache/selftest.json`, если он существовал) идентичны
до и после вызова `/sdx:status`. Если появился НОВЫЙ файл `.claude/sdx/.cache/selftest.json`,
которого не было на Шаге 1, — это провал критерия REQ-HEALTH-3 (`/sdx:status` не должен запускать
`selftest.sh`).

---

### Шаг 5: Убедиться, что self-test реально исполняется на `SessionStart` установленной копии плагина

**Действие**: после `/plugin marketplace update sdx` (когда эта сессия смёржена и плагин
обновлён) начать НОВУЮ CLI-сессию Claude Code в любом проекте с `.claude/sdx/`, затем сразу
выполнить `/sdx:status` и проверить, что блок здоровья показывает `selftest_status` со свежей
меткой времени (секунды/минуты назад, не «не выполнялся»).

**Предусловия**: плагин обновлён (`sdx-version` актуален), `.claude/sdx/.cache/selftest.json`
отсутствовал или имел устаревший отпечаток (версия плагина/конфиги менялись) перед стартом новой
сессии.

**Ожидаемый результат**: `.claude/sdx/.cache/selftest.json` создан/обновлён автоматически без
ручного запуска `selftest.sh` — подтверждает, что проводка `SessionStart` в установленной копии
плагина реально работает (это единственная точка, которую дев-сьют `test-selftest.sh` в принципе
не может проверить — см. DESIGN.md «Ограничение среды исполнения»: тесты вызывают `selftest.sh`
напрямую, минуя `hooks.json`/установленную копию плагина).
