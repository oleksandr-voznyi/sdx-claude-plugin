# Context Report: Self-test enforcement-слоя (FEAT-014 + DEBT-010)

## Предмет исследования
Две сцепленные записи бэклога, обе волна 1, обе open:
- `FEAT-014` — `sdx/hooks/selftest.sh`: синтетическое событие каждому хуку слоя, сверка
  фактического ответа с ожидаемым, прогон на `SessionStart` + после смены версии плагина/конфигов,
  результат — «запись в журнал прогона», контракт «отсутствие доказанной живости = автономия
  недоступна, но надзорный режим, а не падение».
- `DEBT-010` — тихая деградация хуков в no-op не видна пользователю; рекомендация — блок «здоровье
  enforcement» в `/sdx:status`. Груминг 2026-08-31 объявил обе записи одним механизмом закрытия:
  `FEAT-014` — машинное доказательство, `DEBT-010` — предъявление человеку.

## 1. Контракт входа каждого хука слоя

Три хука, три разных контракта ответа — единого «синтетическое событие → сравнить ответ»
интерфейса в коде НЕТ, его придётся построить по трём разным осям:

| Хук | Событие | Вход | Побеждающий сигнал | Проваленный сигнал | Транспарентный/no-op |
|---|---|---|---|---|---|
| `preflight.sh` | `SessionStart` | ничего не читает (ни stdin, ни `CLAUDE_PROJECT_DIR`) | `exit 0`, stderr пуст | `exit 0` + предупреждение в stderr (жёсткий отказ `exit 2` закомментирован) | нет ветки no-op вообще — либо тихо, либо громко в stderr, код возврата не различает |
| `prod-guard.sh` | `PreToolUse` (matcher `Bash`) | stdin JSON `{"tool_input":{"command":"..."}}`, `CLAUDE_PROJECT_DIR` | JSON `{"hookSpecificOutput":{...,"permissionDecision":"deny",...}}` на stdout, `exit 0` | то же, не `exit 2` | `exit 0` + пустой stdout — нет `.claude/sdx/prod-guard.conf`, conf пуст/только комментарии, нет паттерна-совпадения |
| `stop-gate.sh` | `Stop` | ничего на stdin; `CLAUDE_PROJECT_DIR`, git-ветка, `.claude/sessions/<sid>/session_state.json`, опционально `SDX_STOP_GATE=1` | `exit 0` (зелёный прогон или транспарентность) | `exit 2` + хвост лога на stderr | `exit 0` без побочных файлов — не SDX-ветка, стадия вне `Execution/Verification`, `no_gates=true`, нет тест-команды |

Ключевое наблюдение: у хуков **разная семантика «правильного ответа»**. У `prod-guard` это
содержимое JSON на stdout при неизменном `exit 0` — то есть «deny» и «allow» неразличимы по коду
возврата, только по телу ответа. У `stop-gate` наоборот — decision целиком в коде возврата (0/2),
тела ответа нет вообще, есть лишь happens-to-write side-эффекты (`.stopgate.ok`, `.stopgate.count`,
`.stopgate.out`). У `preflight` ни то ни другое не формализовано: единственный наблюдаемый канал —
текст в stderr, код возврата всегда 0 в текущей конфигурации. Единый селфтест-раннер не сможет
использовать один и тот же компаратор «ответ == ожидание» для всех трёх — нужна per-hook стратегия
проверки, а не общий шаблон.

`hooks/hooks.json` регистрирует ровно эти три события с ровно этими скриптами
(`preflight.sh`→`SessionStart`, `prod-guard.sh`→`PreToolUse[Bash]`, `stop-gate.sh`→`Stop`); других
активных хуков в проводке нет (`stage-gate.sh`/`stage-write-guard.sh` сняты ADR-020 без замены —
см. §5). `sdx-stage.sh` — не хук в терминах `hooks.json`, а CLI, вызываемый командами через `Bash`;
формально вне периметра «хуков слоя», но по факту тоже fail-closed без `jq` (`exit 2`) и тоже
единственный писатель `.stage` — граница «входит ли `sdx-stage.sh` в self-test» решается на
Technical Design, не факт, что она очевидна из FEAT-014 (текст говорит «каждому хуку слоя»,
`sdx-stage.sh` хуком не является).

## 2. Пригодные фикстуры — насколько self-test переиспользует уже написанное

Три из четырёх скриптов слоя уже имеют dev-юнит-тесты, построенные на одном и том же паттерне:
`TMPPROJ=$(mktemp -d)`, синтетический git-репозиторий/конфиг внутри него,
`CLAUDE_PROJECT_DIR="$TMPPROJ" bash "$HOOK" <вход>`, проверка `exit`/stdout/файлов. Это ровно та же
механика, которую предлагает FEAT-014 («подать синтетическое событие, сверить ответ») — то есть
self-test не изобретает новый способ подачи события, а формализует уже существующий паттерн
инвокации в постоянный рантайм-скрипт.

- `test-prod-guard.sh` (9 сценариев, ~0.4с прогона) — не требует git, дёшев.
- `test-stop-gate.sh` (20 сценариев, **5.9с прогона на этой машине**) — каждый сценарий поднимает
  полноценный git-репозиторий (`git init` + коммит), сценарий loop-guard (`[4]`) прогоняет
  verify-команду 4 раза подряд. Сценарии `[15]`/`[16]` — уже готовый кейс DEBT-026 (`verify-cmd.sh`
  с режимом `0600` обязан держать пол) — прямое попадание в то, что self-test должен ловить
  (см. §8).
- `test-hook-wiring.sh` (4 сценария) — НЕ вызывает хуки поведенчески; это статический парсинг
  `hooks/hooks.json` (валидный JSON → все команды идут через `bash <путь>` → все referenced-пути
  существуют) плюс демонстрационный сценарий `[4]` (0600-скрипт: `bash <path>` работает, прямой
  запуск даёт `exit 126`). Это другой класс проверки, чем «подать событие хуку» — она про форму
  вызова в проводке, а не про поведение самого хука.
- `preflight.sh` тестов не имеет вообще (аудит `audit-2026-07-26`, находка `[TEST7]`: «единственный
  хук без единого теста» — актуально по сей день, `ls sdx/hooks/test-*.sh` подтверждает). Значит
  ровно для одного из трёх хуков слоя self-test строит фикстуру с нуля, без образца для
  переиспользования, и упирается в то, что единственный наблюдаемый канал `preflight` (отсутствие
  `jq`) искусственно не создать без манипуляции `PATH` — сам хук не принимает никакого входа для
  инъекции отсутствия зависимости.

**Граница «тест разработчика» vs «проверка живости в рантайме» — реальная, не бумажная.**
Замеренная стоимость: полный прогон `test-*.sh` (используется как `verify-cmd.sh` этого же
репозитория, дословно «no --fast mode: full suite runs in ~9s») — не тот бюджет, который приемлем
на каждый `SessionStart` (событие, которое срабатывает на каждый старт/резюм CLI-сессии, а не
только на вход в SDX-сессию). Даже один `test-stop-gate.sh` (5.9с, git init на сценарий) — тяжелее,
чем разумно вызывать безусловно при каждом открытии окна. Прямое переиспользование файлов
`test-*.sh` как есть для рантайм-self-test не годится по бюджету; годится сам паттерн инвокации
(`TMPPROJ` + `CLAUDE_PROJECT_DIR` override), в облегчённом варианте — по одному представительному
сценарию на хук (deny-кейс + no-op-кейс для `prod-guard`; красный+зелёный или хотя бы один
дискриминирующий кейс для `stop-gate`, без 20 сценариев и без реального `git init`, если возможно
сконструировать fixture дешевле). Побочные зависимости у dev-тестов тоже разные: `test-stop-gate.sh`
требует git и, для веток автодетекта, потенциально `npm`/`composer` в `PATH` (эта ветка сама не
покрыта тестами — `DEBT-036`, см. §8) — self-test не должен наследовать эту зависимость от внешних
тулов.

## 3. Побочные эффекты и изоляция

Наблюдаемые побочные файлы у `stop-gate.sh`, все под `.claude/sessions/<sid>/`:
- `.stopgate.ok` — кэш отпечатка зелёного прогона (`HEAD:md5(porcelain status)`);
- `.stopgate.count` — счётчик loop-guard (сбрасывается на зелёном прогоне, снимается после 3);
- `.stopgate.out` — хвост лога последнего прогона verify-команды.

Все три — per-session (путь включает `${sid}`), gitignored точечным паттерном
`.claude/sessions/*/.stopgate.*`. Реальный прогон verify-команды в `stop-gate.sh` **фактически
выполняет тест-сьют проекта** (`timeout ... bash -c "$cmd"` / раннер) — синтетический вызов из
self-test обязан НЕ довести исполнение до `run_verify()`, иначе self-test-на-`SessionStart` начнёт
незапланированно гонять реальный тест-сьют проекта при каждом старте CLI, что и дорого, и не то,
что синтетический пробник обязан делать.

Существующие dev-тесты избегают этой проблемы, полностью изолируя контекст: `TMPPROJ` — отдельный
временный git-репозиторий вне реального проекта, `CLAUDE_PROJECT_DIR` переопределён на него, поэтому
хук ни разу не касается `.claude/sessions/<реальный-sid>/` реальной сессии. Тот же приём —
единственный чистый способ подать `stop-gate.sh` синтетическое событие без риска затронуть
`.stopgate.*` реальной активной сессии или спровоцировать реальный прогон тестов: self-test обязан
строить собственный одноразовый `TMPPROJ`-фикстур (с уже готовым «красным» или «зелёным»
`verify-cmd.sh`, который ничего не делает, кроме `exit 0`/`exit 1`) и указывать
`CLAUDE_PROJECT_DIR` на него — не на реальный `$CLAUDE_PROJECT_DIR` сессии. Прямой вызов с реальным
`CLAUDE_PROJECT_DIR` (без подмены) либо ничего не докажет (транспарентность на реальном стейте —
ожидаемое поведение вне `Execution/Verification`), либо, если случайно попадёт на реальную
`Execution/Verification`-сессию, действительно погонит реальный тест-сьют — недопустимо для
`SessionStart`-пробника.

`prod-guard.sh` синтетически безопаснее — не пишет на диск ничего, только читает `conf` и печатает
JSON; но по той же причине (не задеть реальный `prod-guard.conf` реального проекта синтетическим
deny-паттерном) self-test обязан подавать ему тоже изолированный `CLAUDE_PROJECT_DIR`, а не реальный
(иначе позитивный/негативный кейс зависит от того, что реально лежит в `.claude/sdx/prod-guard.conf`
проекта, а не от контролируемого фикстура).

`preflight.sh` без входа и без файловых эффектов — изолировать нечего, но и просигналить «работает»
кроме факта успешного `exit 0` нечем (см. §1).

## 4. Отпечаток для кэширования — что реально доступно

- `${CLAUDE_PLUGIN_ROOT}` — доступен как переменная окружения в командах хуков (используется в
  `hooks/hooks.json` и во всех `commands/*.md`), путь к развёрнутой копии плагина.
- `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json` — есть, содержит `"version": "2.1.0"`, читаемо
  `jq -r .version` (при наличии `jq` — циклическая зависимость: preflight существует именно потому,
  что `jq` не гарантирован, значит отпечаток-механизм self-test не может безусловно требовать `jq`
  для собственной работы без деградации).
- `.claude/sdx/prod-guard.conf`, `.claude/sdx/verify-cmd.sh` — per-project конфиги, tracked в git (НЕ
  gitignored), живут в целевом проекте. Их содержимое/mtime/hash — валидные компоненты отпечатка.
- `.claude/sdx/sdx-version` — маркер версии плагина, но **в этом самом репозитории отсутствует**
  (`test -f` → MISSING): пишется исключительно `/sdx:reconcile`, а он в этом дереве ни разу не
  запускался (или запускался до появления маркера). Отпечаток-механизм не может полагаться на его
  наличие как на данность — обязан работать и при отсутствующем маркере.

**Где хранить результат, если активной сессии может не быть** — реальная развилка, не техническая
деталь. `SessionStart` срабатывает на каждый старт/резюм CLI-сессии Claude Code, включая случаи вне
SDX-сессии вовсе (нет ветки `sdx/<id>`, `.claude/sessions/` пуст) — `preflight.sh` сегодня уже
работает именно в этом безусловном режиме (не проверяет ветку/сессию). Кандидаты на место хранения
кэша self-test:
- `.claude/sessions/<sid>/` — недоступно, когда сессии нет (частый случай: пользователь просто
  открыл проект).
- `.claude/sdx/` — существует независимо от сессии (это per-project конфиг-каталог), но сегодня
  ПОЛНОСТЬЮ tracked (`prod-guard.conf`, `verify-cmd.sh` — оба в git). Файл кэша self-test,
  меняющийся на каждый прогон/версию, либо надо тоже трекать (шум в diff, коммиты кэша — плохая
  практика), либо заводить для него новый точечный gitignore-паттерн (прецедент есть:
  `.stopgate.*` — но это первый случай точечного паттерна ВНЕ `.claude/sessions/`).
- Новый нетрекаемый каталог (`.claude/sdx/.cache/` или аналог) — чистое решение, но раньше в
  проекте такого каталога не было, это новая структура хранения.

Все три — легитимные развилки, ни одна не выбрана кодом или протоколом; протокол молчит про кэш
self-test вообще (не найдено ни строки в `sdx/protocol.md`).

## 5. «Надзорный режим, а не падение» — честная граница сегодня

`FEAT-014` формулирует контракт как «отсутствие доказанной живости слоя = автономия недоступна».
Проверено по коду: **модели автономии, которая могла бы читать этот факт, в репозитории нет**.

- `FEAT-009` (карта освоенности, `declared`/`observed`) — статус `open`, волна 4.
- `FEAT-010` (асимметричная выдача полномочий, `effective = min(declared, observed)`, «провал
  self-test → уровень падает») — статус `open`, волна 4. Именно этот пункт FEAT-010 и есть
  единственное место в бэклоге, где self-test что-то реально блокирует — и оно не реализовано.
- `FEAT-006` (классы риска, `allow/ask/defer/deny`) — статус `open`, волна 2. Сегодня
  `permissionDecision` в репозитории используется **ровно с одним значением — `deny`**
  (подтверждено и провенанс-примечанием самой записи FEAT-006, и грепом кода: `prod-guard.sh` —
  единственный источник JSON-решений, только `deny`). Значения `ask`/`allow`/`defer` нигде не
  эмитируются.
- `FEAT-004` (журнал прогона, append-only JSONL, пишут хуки) — статус `open`, волна 1, **в эту
  сессию не входит** (не входит в заявленный предмет). Сегодня журнала, которому «self-test — первый
  факт», не существует. Есть только `session.log` с четырьмя прозаическими категориями
  (`START`/`STAGE_CHANGE`/`CHECKPOINT`/`ERROR`, `ADR-005`) — это не append-only машиночитаемый
  журнал прогонов, а сильно урезанный лог смены состояния, который явно не пишется хуками сегодня
  (только оркестратором вручную, по протоколу).
- `authority.conf` (обобщение `prod-guard.conf`, FEAT-006) — не существует в коде вообще, только
  упоминается в бэклоге и в `intake`-документе разбора.
- `PROC-020` (инвариант «не автономен при правке слоя надзора») — статус `open`, волна 3, ни строки
  в `sdx/protocol.md` (грепом не найдено).

**Вывод, который дизайн обязан констатировать явно, а не подразумевать.** Сегодня self-test технически
реализуем как самостоятельный диагностический механизм («живы ли хуки»), но у него **нет потребителя**,
способного превратить провал в ограничение чего бы то ни было — ни автономии (нет самой автономии),
ни классов риска (нет `ask`/`allow`), ни журнала (`FEAT-004` не в этой сессии). Единственные
РЕАЛЬНО доступные сегодня каналы, куда self-test может что-то положить:
1. stderr-предупреждение (по образцу `preflight.sh`) — читается человеком, ничего не блокирует;
2. запись категории `ERROR` в `session.log` (существующий формат, но по протоколу пишется
   оркестратором в момент правки `session_state.json`, не хуком напрямую — self-test как отдельный
   скрипт, пишущий в `session.log` из `SessionStart`, был бы новым классом писателя этого файла,
   не описанным в §«Логирование» протокола);
3. блок «здоровье enforcement» в `/sdx:status` (то, что просит `DEBT-010`) — читается человеком по
   явному запросу, тоже ничего не блокирует.

То есть «надзорный режим, а не падение» сегодня — не осознанный компромисс между двумя работающими
режимами, а единственно возможное поведение, потому что режима «падение» (отказ автономии) не к
чему подключить. Дизайн обязан не выдавать эту диагностическую заготовку за работающий gate — и
явно зафиксировать, что путь к реальному gate лежит через `FEAT-010`/`FEAT-006`/`FEAT-004`
(волна 2/4), которые в объём текущей сессии не входят.

## 6. `/sdx:status` и здоровье enforcement

`commands/status.md`, шаг 4 (уже реализован): «Активные сессии» — листинг `git branch --list
'sdx/*'`. Это ровно половина рекомендации `DEBT-010` («Туда же — перечисление всех сессий...») —
**уже сделано, вне объёма этой сессии**, подтверждено чтением файла (пронумерованный шаг 4,
отдельный от блока «здоровье enforcement»).

Вторая половина — сам блок «здоровье enforcement» (jq есть? conf заполнен? verify-cmd активен?
ветка соответствует сессии?) — в `status.md` сегодня отсутствует полностью. Файл читает только
`session_state.json`, `PLAN.md`, git-статус артефактов; ничего не проверяет из состава хуков.

`/sdx:status` — «чисто читающая операция», явно помечено в файле как не мутирующая состояние.
Отсюда прямая развилка: если self-test пишет кэш-файл при `SessionStart` (см. §4), `/sdx:status`
технически МОЖЕТ его просто прочитать (не мутируя ничего) — это дешевле и не требует повторного
прогона хуков. Но: `status.md` может быть вызван в любой момент, необязательно сразу после
`SessionStart` — если кэш просрочен (например, `prod-guard.conf` отредактирован руками посреди
сессии, а `SessionStart` не перезапускался), показ устаревшего результата вводит в заблуждение
ровно в том духе, который критикует сам `DEBT-010` («пользователь думает — работает, а не работает»).
Альтернатива — `/sdx:status` перепрогоняет свою лёгкую версию проверок сам (не self-test целиком,
а те же дешёвые статические факты: `command -v jq`, `[ -f prod-guard.conf ]`, `[ -f
verify-cmd.sh ]`, соответствие ветки — то, что уже перечислено в самой рекомендации DEBT-010 как
самостоятельный список, независимый от self-test). Это не то же самое, что self-test (self-test
поведенчески подаёт событие и сверяет ответ; DEBT-010 просит структурные факты присутствия) — то
есть DEBT-010 и FEAT-014 закрывают смежные, но не идентичные проверки, и решение «должен ли
`/sdx:status` дублировать вычисление или доверять кэшу self-test» — отдельная развилка Technical
Design, не предрешённая ни одной из двух записей дословно.

## 7. Ограничение PROC-020 и путь исполнения этой сессии

`PROC-020` перечисляет территорию инварианта «агент не автономен в прогоне, меняющем механизм
собственного надзора» явно: «...`hooks.json` и hook-скриптов...» — **self-test, как новый
hook-скрипт слоя, сам попадает в объявляемую им же территорию**. Это не парадокс, а прямое
следствие: то, что self-test доказывает живость слоя, не освобождает работу НАД self-test'ом от
того же класса риска, что и работа над `prod-guard.sh`/`stop-gate.sh`. `PROC-020` статус `open`,
волна 3, ни строки enforcement в протоколе или коде — сегодня это прозаическая, не enforced
рекомендация; но раз бэклог явно называет её условием для `PROC-018` (инверсия дефолта
`gate_mode`), дизайн self-test обязан как минимум НЕ противоречить этому будущему инварианту
(не проектировать self-test так, чтобы его нельзя было позже вписать в надзорный периметр
`PROC-020`).

**Практическое следствие для ЭТОЙ сессии, проверено эмпирически.** Команды `/sdx:*` резолвятся из
установленной копии плагина (`~/.claude/plugins/marketplaces/sdx/`), не из рабочего дерева
(`/home/archi/Code/sdx-claude-plugin`). Сверка `diff` показала, что `stop-gate.sh` в установленной
копии и в рабочем дереве **идентичны** (репозиторий синхронизирован — вероятно, marketplace update
после недавнего мёржа `fix-stop-gate-exec-bit-20260901`), но это совпадение состояния на данный
момент, не гарантия: любая правка `sdx/hooks/*.sh` в рабочем дереве В ЭТОЙ сессии **не** повлияет на
поведение хуков, которые реально исполняются в этой же CLI-сессии, пока не будет выполнено
`/plugin marketplace update sdx` (согласно CLAUDE.md §0/preamble). Это касается и самого self-test
скрипта: если он будет вызываться из `hooks.json` на `SessionStart`, до обновления установленной
копии плагина изменения не подействуют «на живую» — их придётся проверять либо прямым вызовом
`bash sdx/hooks/selftest.sh` из рабочего дерева (как делают `test-*.sh`), либо после
`marketplace update`.

## 8. Прецеденты в бэклоге — поймал бы self-test каждый?

**BUG-008 (потеря бита `x` при установке плагина).** Проверено гредом по всем точкам вызова:
`hooks.json` (все три хука), `commands/archive.md`, `commands/verify.md`, `commands/audit.md`,
`archive-verify.sh` → `lib/default-branch.sh`, `stop-gate.sh` → `lib/resolve-session.sh` — **все**
сегодня вызываются либо через `bash <путь>`, либо через `. <путь>` (source), ни одного прямого
исполнения не осталось. Это значит: инвариант формы вызова, из-за нарушения которого возник
BUG-008, уже структурно закрыт и охраняется статическим тестом `test-hook-wiring.sh` (сценарии
`[2]`/`[3]`), а не поведенческим. **Важный нюанс: self-test, если он (по буквальному прочтению
FEAT-014) ограничивается «подать синтетическое событие, сверить ответ», сам будет звать хуки через
`bash <путь>`** (тот же паттерн, что и `test-*.sh`) — а `bash <путь>` **не чувствителен к биту `x`**
(источник самого бага был в форме вызова, а не в поведении хука). Значит поведенческий self-test,
вызывающий хуки через `bash`, **никогда не воспроизведёт условия BUG-008** и физически не сможет
его поймать заново — не потому что недостаточно тщателен, а потому что синтетическая инвокация тем
же способом, что и правильный вызов, структурно не в состоянии обнаружить регресс формы вызова.
Ловит его сегодня только статический разбор `hooks.json` (`test-hook-wiring.sh` — уже существующий
механизм, отдельный от self-test). **Честный вывод: self-test, спроектированный буквально по
FEAT-014, BUG-008-класс не поймает; для его повторного покрытия в рантайме потребовалось бы
отдельно инкорпорировать статическую проверку wiring — открытый вопрос для Technical Design,
не предрешённый записью.**

**DEBT-026 (`stop-gate` определял тест-команду по биту).** Прямо противоположный случай — это ровно
класс, для которого поведенческая проверка создана: сценарии `[15]`/`[16]` в `test-stop-gate.sh`
(0600 `verify-cmd.sh` обязан всё равно держать пол) — это уже написанный, зелёный сегодня
регрессионный тест именно того типа, который self-test обязан инкорпорировать. Синтетическое
событие «дай стоп-гейту красный 0600-раннер, проверь `exit 2`» — точное попадание в контракт
FEAT-014. **Поймал бы: да**, при условии, что self-test включает этот сценарий (или эквивалентный)
в свой набор проб для `stop-gate`.

**DEBT-010 (тихая деградация не видна пользователю)** — это не отдельный технический баг, который
self-test либо ловит, либо нет: это ровно предмет self-test'а целиком (сделать деградацию видимой).
Единственный нюанс — self-test делает деградацию видимой МАШИННО (в кэше/логе), а не пользователю
напрямую; предъявление человеку — работа `/sdx:status` (§6), не самого self-test.

## Развилки, требующие решения на Technical Design

1. **Периметр self-test.** Три хука `hooks.json` (`preflight`/`prod-guard`/`stop-gate`) — бесспорно
   в периметре. Входит ли `sdx-stage.sh` (не hook в терминах `hooks.json`, но единственный писатель
   `.stage`, тоже fail-closed без `jq`)? Входит ли повторно статическая проверка формы вызова
   `hooks.json` (сегодня — вотчина `test-hook-wiring.sh`), учитывая вывод §8 про BUG-008?
2. **Стратегия сравнения ответа — не единая.** `prod-guard` сверяется по телу JSON-ответа при
   неизменном `exit 0`; `stop-gate` — по коду возврата (0/2) плюс побочным файлам; `preflight` —
   только по каналу stderr, входа для инъекции синтетического «плохого» состояния у него нет вообще
   (нет способа синтетически сымитировать отсутствие `jq`, не трогая реальный `PATH` окружения).
   Нужно решение: либо `preflight.sh` дорабатывается, чтобы принимать инъекцию (usable для
   self-test), либо self-test признаёт его непроверяемым поведенчески и довольствуется фактом
   «скрипт исполнился и вернул 0» — это не то же самое, что «предупреждение реально сработало бы
   при отсутствии jq».
3. **Изоляция от реального состояния проекта (§3).** Self-test обязан строить собственный
   одноразовый `TMPPROJ`-фикстур с подменой `CLAUDE_PROJECT_DIR`, а не бить по реальному
   `$CLAUDE_PROJECT_DIR` — иначе риск (а) утечки в реальные `.stopgate.*` активной сессии, (б)
   незапланированного реального прогона тест-сьюта проекта из `stop-gate`, (в) зависимости позитив/
   негатив-кейса `prod-guard` от содержимого реального `prod-guard.conf`, а не от контролируемого
   фикстура. Нужно решение по устройству фикстура (постоянный шаблон в `sdx/`? генерируется на
   лету? переиспользует `mktemp -d`, как `test-*.sh`, каждый раз заново — с какой ценой в
   быстродействии на `SessionStart`?).
4. **Бюджет времени на `SessionStart`.** Замерено: полный `test-stop-gate.sh` — 5.9с (git init на
   сценарий, 20 сценариев), `test-prod-guard.sh` — 0.37с. Прямое переиспользование существующих
   `test-*.sh` как self-test-раннера не проходит по бюджету события, которое срабатывает на КАЖДЫЙ
   старт/резюм CLI-сессии (не только вход в SDX-сессию). Нужно решение об облегчённом подмножестве
   проб (сколько сценариев на хук, нужен ли реальный `git init` для `stop-gate`-пробы или можно
   обойтись без git вовсе — `resolve_sid` при отсутствии git-репозитория просто вернёт пусто и хук
   останется транспарентным, то есть проба стоп-гейта БЕЗ git-репозитория не сможет проверить
   Execution/Verification-ветку вообще).
5. **Место хранения кэша/результата (§4).** Три кандидата (`.claude/sessions/<sid>/`, `.claude/sdx/`
   как есть — но он tracked, новый нетрекаемый каталог) — ни один не выбран ни кодом, ни протоколом.
   Выбор влияет на: (а) поведение вне активной сессии (SessionStart без sdx-ветки), (б) нужен ли
   новый gitignore-паттерн (прецедент точечных паттернов есть, но только внутри
   `.claude/sessions/*`), (в) может ли `/sdx:status` читать кэш без повторного прогона.
6. **Куда фактически пишется «доказательство» сегодня (§5).** Целевой «журнал прогона» (`FEAT-004`)
   не существует и не в объёме сессии. Промежуточное решение — писать в `session.log` (новый класс
   писателя, не описанный в текущем разделе «Логирование» протокола), в отдельный
   self-test-специфичный файл (наименьшее вмешательство в существующий формат, но новая структура),
   или только в свежесозданный кэш (§5) без интеграции в `session.log` вообще. От этого зависит,
   можно ли говорить, что self-test выполнил свою заявленную роль «первого факта для проекции
   `observed`», или честнее описать это как задел, ожидающий `FEAT-004`.
7. **Реакция `/sdx:status` (§6).** Дублировать дешёвые структурные проверки DEBT-010
   (jq/conf/verify-cmd/branch) самостоятельно при каждом вызове, или доверять кэшу self-test с
   риском показать устаревший результат между запусками `SessionStart`.
8. **Что означает «после любого изменения версии плагина или per-project конфигов» операционально.**
   Отпечаток должен реагировать на смену `.claude-plugin/plugin.json` (доступно), но также на смену
   содержимого `prod-guard.conf`/`verify-cmd.sh` (доступно, но требует хэша содержимого, не только
   mtime, если конфиг правится руками без смены версии) — вычисление отпечатка не должно требовать
   `jq` безусловно (см. циклическую зависимость preflight/jq выше), иначе self-test унаследует ту же
   деградацию, которую призван обнаруживать.

## Риски и ограничения, которые дизайн обязан назвать явно

- **Self-test — сам часть надзорного механизма (PROC-020), и правки над ним в этой сессии не
  подпадают ни под один enforced-контроль сегодня** (окно ADR-020: два бывших процессных хука сняты
  без замены; `PROC-020` не enforced). Единственная страховка — прозаическая дисциплина
  оркестратора и обязательный fresh-eyes `reviewer` на Verification.
- **«Автономия недоступна» в контракте FEAT-014 сегодня не подключена ни к чему** (§5) — дизайн не
  должен формулировать реализацию так, будто self-test уже гейтит что-либо реальное; честная
  формулировка — диагностика + видимость, задел на `FEAT-010`, явным текстом.
- **BUG-008-класс регрессии self-test поведенчески не поймает** (§8) — если Technical Design хочет
  реального покрытия этого класса в рантайме (не только в dev-test-сьюте), потребуется либо
  инкорпорировать статический разбор `hooks.json`, либо явно принять, что это не входит в self-test
  и остаётся зоной `test-hook-wiring.sh`.
- **Изоляция обязательна, не опциональна** (§3) — синтетический вызов `stop-gate.sh` без подмены
  `CLAUDE_PROJECT_DIR` на изолированный фикстур рискует либо смешаться с `.stopgate.*` реальной
  сессии, либо запустить реальный тест-сьют проекта на каждом `SessionStart`.
- **preflight.sh непроверяем поведенчески без доработки** (§1, §2) — единственный хук из трёх без
  входа для инъекции синтетического состояния; self-test для него в лучшем случае проверит «скрипт
  исполнился и вернул 0», не «предупреждение сработало бы».
- **Бюджет времени на `SessionStart`** (§2, §4) — полное переиспользование `test-*.sh` неприемлемо
  дорого (5.9с только для stop-gate-сьюта) для события, срабатывающего на каждый старт CLI-сессии,
  включая случаи вне SDX вообще.
- **Циклическая зависимость от `jq`** (§4, §8-п.8) — и отпечаток для кэширования, и сама механика
  сравнения JSON-ответа `prod-guard` естественно тянутся к `jq`; self-test не должен ломаться/
  деградировать некрасиво именно тогда, когда `jq` отсутствует — том самом случае, ради которого
  существует `preflight.sh`.
- **`sdx-stage.sh` в текущем виде уже fail-closed без `jq` (`exit 2`)** — если он войдёт в периметр
  self-test, синтетический вызов CLI-скрипта, а не hooks.json-хука, потребует отдельной модели
  инвокации (аргумент `<sid>`, не событие).

## Расхождения записей бэклога с фактическим кодом

- **FEAT-014 называет «deny-кейс, allow-кейс, ask-кейс» как три синтетических события.** Проверено
  кодом и подтверждено провенанс-примечанием самой записи `FEAT-006`: `permissionDecision` в
  репозитории используется ровно с одним значением — `deny`. `ask` (и `allow` как явный JSON-ответ,
  не молчаливая транспарентность) не эмitируются НИГДЕ в текущем коде — это словарь будущей модели
  полномочий `FEAT-006` (волна 2, `open`), спроецированный назад на сегодняшний прод-гард, у
  которого фактически два исхода: `deny` (JSON) и молчаливый no-op (пустой stdout, `exit 0`, не
  «allow»-ответ). Technical Design не должен закладывать пробу «ask-кейса» как проверку СУЩЕСТВУЮЩЕГО
  поведения — сегодня проверять нечего, это задел.
- **BUG-008 упоминается в FEAT-014 как живой прецедент того класса, который self-test обязан
  ловить**, но структурно (форма вызова через `bash <путь>`/`source` везде, инвариант закрыт и
  охраняется отдельным статическим тестом) поведенческий self-test его не поймает — см. §8. Запись
  не формулирует это неверно (BUG-008 остаётся валидным мотивирующим прецедентом класса «тихая
  смерть хука»), но дизайну нужно явно разграничить, что из трёх названных прецедентов
  (`BUG-008`/`DEBT-026`/`DEBT-010`) self-test реально закрывает поведенческой пробой (`DEBT-026`,
  `DEBT-010`), а что остаётся закрытым другим, уже существующим механизмом (`BUG-008` →
  `test-hook-wiring.sh`).
- **DEBT-010's рекомендация «туда же — перечисление всех сессий» в `/sdx:status` уже реализована**
  (шаг 4 `commands/status.md`, `git branch --list 'sdx/*'`) — сверено и подтверждено чтением файла;
  задача явно исключает это из скоупа, отмечаю для полноты сверки триады.
- Запись `.claude/sdx/sdx-version` (маркер версии плагина, на который опирается идея отпечатка
  FEAT-014) **отсутствует в этом самом репозитории** — не расхождение записи с кодом как таковое, но
  показывает, что предположение «маркер версии всегда доступен» не выполняется даже в
  dogfood-проекте самого фреймворка; отпечаток-механизм должен корректно работать и без него.
