# change_note — proc-028-simkit-vendoring-20261004

**Запись бэклога:** `PROC-028` — политика вендоринга sim-kit в плагин. Условие входа для `FEAT-015`.

**Что.** Политика для первого фрагмента плагина, у которого источник истины — другой репозиторий
(`aibok/agentico/meta-orchestrator/sim-kit`, выпуск 0.7.3): где фиксируется версия, как сверяется
идентичность копии, кто и как обновляет, что запрещено, что считается мажорным поводом.

**Зачем.** `FEAT-015` вносит в `sdx/mo/` чужой python-код, исполняемый хуком. Без политики две копии
(sim-kit и плагин) разъедутся по версиям — ровно то, от чего ушёл ADR-013, — а дефект, найденный в
плагине, будет починен локально и потерян для upstream. Прецедент: семь находок по 0.7.2 SDX исправить у
себя не мог и не должен был — только запиской (`SDX-MO-interop-reply-2026-10-04.md`).

## Решения (Business Spec + Technical Design, свёрнуто — REQ-SCALE-3)

1. **Источник истины для `sdx/mo/` — sim-kit.** Плагин вендорит ровно файлы выпуска. Локальные правки
   вендорённого кода запрещены; дефект уходит запиской в `agentico/reviews/`, плагин ждёт выпуска.
   Это **именованное исключение** из инварианта ADR-013 «источник истины фреймворка — этот репозиторий».
   Оформление: датированная поправка внутри ADR-013 (по образцу поправки 2026-09-02 к ADR-014), не новый
   ADR — инвариант остаётся, у него появляется одно исключение с границами.
2. **Два файла фиксации, оба в `sdx/mo/`:**
   - `SIMKIT_VERSION` — одна строка, версия sim-kit (`0.7.3`); единственное место, где число названо;
     документы плагина ссылаются на файл, не дублируют число (`DEBT-006`/ADR-008).
   - `SIMKIT_SHA256` — вывод `sha256sum` по вендорённым файлам (формат `<sha256>  <имя>`), чтобы сверка
     была одной командой `sha256sum -c` без парсинга. `RELEASES` sim-kit для сверки непригоден: хеширует
     только `core/mo.py`, который не вендорится.
3. **Сторож инвентаря** (`PROC-027`, прецедент `test-init-patterns.sh`) — новый сьют
   `sdx/hooks/test-mo-inventory.sh`, статический: (а) каждый файл `sdx/mo/`, кроме двух файлов фиксации
   и `README.md`, перечислен в `SIMKIT_SHA256` и совпадает по хешу; (б) каждый перечисленный файл
   существует; (в) `SIMKIT_VERSION` — одна непустая строка вида `X.Y[.Z]`; (г) каталог плоский — любой
   подкаталог, включая `__pycache__`, находка (исключений нет; `FEAT-015` п.2 обязана запускать python с
   `PYTHONDONTWRITEBYTECODE=1`); (д) **поверхности состава** — каждое вендорённое имя упомянуто в
   `README.md`, `README.en.md`, `sdx/protocol.md`, `docs/DECISIONS.md` (п.5 записи `PROC-028`, класс
   `PROC-027`; сверка состава, не описания). Логика доказывается на временной фикстуре: зелёная сторона,
   `sha256sum -c`-совместимость, красные стороны для (а)–(д) и для `SIMKIT_SHA256` с коротким хешем и
   путём со слэшем, эквивалентность fallback `shasum`; реальный `sdx/mo/` и поверхности проверяются теми
   же функциями, когда каталог существует — сегодня его нет и сьют это явно печатает, не считая
   отсутствие ни успехом, ни провалом.
   **`sdx/mo/` этой сессией не создаётся**: пустой вендоринговый каталог в поставке плагина — шум; его
   заводит `FEAT-015` вместе с файлами.
4. **Обновление — осознанный шаг** отдельной сессией `feature`/`refactor`, **не в `gate_mode: auto`**
   (`PROC-020`: меняется механизм надзора). Состав шага: копия файлов выпуска → `SIMKIT_VERSION`/
   `SIMKIT_SHA256` → `tests/kit.sh` sim-kit (часть лист-сессии) против вендорённой копии → собственные
   сьюты плагина → релизные заметки с номером версии sim-kit (файла `CHANGELOG` в репозитории нет —
   заметки ведутся в GitHub Releases). Автообновления нет.
5. **Мажорный повод:** смена `v` конверта или списков `MAY_SEND`/`MAY_RECV` в sim-kit — повод для
   мажорного обновления плагина, не минорного; фиксируется в протоколе.
6. **Где живёт политика:** `sdx/protocol.md`, новый подраздел «Вендорённые компоненты (`sdx/mo/`)» в
   «Enforcement-слой (хуки)» — рядом с описанием зависимости от `jq`; ADR-013 — поправка; `README.md`/
   `README.en.md` — строка `sdx/mo/` в «Состав плагина» **не добавляется** (каталога нет; добавит
   `FEAT-015`, и с этого момента проверка (д) этого же сторожа сверяет обе README, протокол и ADR с
   фактическим составом — до появления каталога сверять нечего).

## Границы (названы, не скрыты)
- «Не в авторежиме» — норма протокола, хуком не enforced: нет детерминированного признака «сессия
  обновляет `sdx/mo/`» в enforcement-слое; в текстах команд её тоже нет. Кандидат на `DEBT`, если
  `FEAT-015` не закроет попутно.
- Сторож сверяет **состав, хеши и упоминания**, не семантику: совместимость `v`/`MAY_*` (п.5) — суждение
  при обновлении, не тест; поверхность, назвавшая файл, но описавшая его неверно, не ловится.
- Проверка (д) активируется только с каталогом: два прозаических перечня, добавленных этой поставкой
  (поправка ADR-013, подраздел протокола), до `FEAT-015` никем не сверяются — ровно до того момента,
  когда появится предмет сверки.
- Запрет локальных правок — конвенция текста + сторож (любая правка меняет хеш и роняет сьют, пока
  `SIMKIT_SHA256` не переписан осознанно); переписать его втихую можно — защита от этого ревью diff.

## QA

**Прогоны.** `bash sdx/hooks/test-mo-inventory.sh` -> 6 passed, 0 failed, rc=0 (`[6]` печатает INFO: `sdx/mo/` отсутствует). Полный `bash .claude/sdx/verify-cmd.sh` -> 12/12 сьютов.

**Покрытие против контракта п.3.** Красную сторону на фикстуре имеют: (г) unlisted file `[2]`, (а→в) hash mismatch `[3]`, (б) listed but missing `[4]`, форма `SIMKIT_VERSION` `[5]` (две строки и префикс `v`). Тавтологии нет: фикстура хеширует той же `sha256_of`, что и проверка, но `[3]` красный именно потому, что хеш после правки расходится; подмена `sha256_of` константой уронила бы `[3]`.

**Ветки без красной стороны (мутация -> сьют остаётся 6/0).** Все — реальные ветки `check_inventory`, отключённые во временной копии:
1. `SIMKIT_SHA256 malformed line` — отключена, зелёный. Нужен сценарий: дописать в `SIMKIT_SHA256` строку `deadbeef  foo` (и вариант с `../x`, абсолютным путём) -> ожидается `SIMKIT_SHA256 malformed line: 'deadbeef  foo'`.
2. `unexpected subdirectory` — отключена, зелёный. Сценарий: `mkdir $fx/sub` -> `unexpected subdirectory: sub`.
3. `SIMKIT_SHA256 missing` — отключена, зелёный. Сценарий: `rm SIMKIT_SHA256` -> `SIMKIT_SHA256 missing`.
4. `SIMKIT_VERSION missing` — отключена, зелёный. Сценарий: `rm SIMKIT_VERSION` -> `SIMKIT_VERSION missing`.
5. Скрытые файлы (глоб `.[!.]*`) — убран из цикла, зелёный. Сценарий: `printf x > $fx/.hidden.py` -> `unlisted file: .hidden.py`.
Также не покрыты: ветка `no-sha256-tool` (недостижима без подмены PATH; сценарий: `PATH` без sha256sum/shasum -> `FAIL: sha256 tool`, rc=1) и отсутствие проверки, что формат фикстуры совпадает с реальным выводом `sha256sum` (прозa протокола обещает `sha256sum -c`; предложение: сценарий, где `SIMKIT_SHA256` порождён самим `sha256sum` и проходит `sha256sum -c`).

**Мутации сторожа** (копии в scratch, не в репозитории):
- ветка hash mismatch -> `elif false` -> `[3]` красный (5/1).
- ветка listed-but-missing -> `if false` -> `[4]` красный (5/1): файл ловится как `hash mismatch: MO-INTEROP.md`, а не «missing» — проверка различает причины.
- проверка формы `X.Y[.Z]` -> `[5]` (случай с `v`) красный; проверка «одна строка» -> `[5]` (двустрочный) красный.
- ветка unlisted (замена сопоставления на no-op) -> `[2]` красный.
Все четыре ключевые мутации красные. Зелёными остались только мутации пунктов 1–5 выше — это находка (WARN: ветки без доказательства, не дефект поставки).
Слабое место: проверка `[5]` для `v0.7.3` сопоставляет подстроку `malformed` — достаточно слабо, но на текущей фикстуре однозначно (других «malformed» нет).

**Переносимость (класс BUG-010).** Fallback `sha256sum` -> `shasum -a 256` -> sentinel `no-sha256-tool` корректен по чтению: ранний выход с FAIL и rc=1 в начале сьюта; внутри `check_inventory` sentinel не совпадёт с хешем (дал бы ложный mismatch, но туда исполнение не доходит). Проверка идёт по `$0`, оба инструмента выдают `<hex>  <name>`. GNU-зависимостей не найдено: `mktemp -d` без шаблона работает на GNU и современном macOS (на старом BSD нужен `-t`/шаблон — единственное сомнение, рекомендуется `mktemp -d "${TMPDIR:-/tmp}/mo-inv.XXXXXX"`); `grep -E` с `{64}` и `-c`, `.[!.]*` (POSIX), `${var%%  *}`, `cut`, `head -1` — переносимы. CRLF в `SIMKIT_VERSION` фиксируется как malformed (желательное поведение).

**Вердикт QA:** поставка корректна, ключевой класс (локальная правка вендорённого файла) доказан мутацией; рекомендуется добавить 5 красных сторон (пп.1–5) и сценарий `no-sha256-tool` — несущественно для гейта, но без них пять веток проверки держатся без доказательства.
