# Ручное тестирование — `PROC-019`, журнал решений `decisions_log.md`

**Приёмочный критерий #1 поставки** (DESIGN.md, «Шесть категорий стоп-рубрики + акты триажа»):
для КАЖДОЙ из семи категорий стоп-рубрики решение человека, принятое на остановке, порождает
корректную запись в `.claude/sessions/<id>/decisions_log.md`.

Юнит-тестом это не покрывается по природе события: запись порождает **прозаическая инструкция**,
исполняемая моделью, а не bash-код (тот же предел, по которому `auto_decisions.md` сегодня не
покрыт ни одним `sdx/hooks/test-*.sh`). Структурные проверки `sdx/hooks/test-resume-contract.sh`
(секции `[T19]`-`[T24]`) доказывают лишь **присутствие** load-bearing формулировок в тексте
команд — не то, что их исполнение даёт корректную запись. Этот файл закрывает вторую половину.

Сценарии **синтетические** (DESIGN.md разрешает: «может быть синтетическим на scratch-сессии, не
обязательно живым»). Причина — `PROC-020`: слэш-команды резолвятся из установленной копии
плагина, поэтому прогон «по-настоящему» проверял бы предыдущую версию текста, а не поставляемую.
Оператор в шагах 1-7 читает **рабочие копии** `commands/*.md` и `sdx/protocol.md` из дерева
и применяет их к scratch-сессии вручную.

## Шаг 0 — Подготовка фикстуры (не измеряется, предусловие остальных)

**Действие.**
```bash
scratch=$(mktemp -d)
cd "$scratch" && git init -q && git config user.email t@e && git config user.name t
mkdir -p .claude/sessions/manual-dec-01
cat > .claude/sessions/manual-dec-01/session_state.json <<'JSON'
{
  "session_id": "manual-dec-01",
  "type": "feature",
  "stage": "Execution",
  "gate_mode": "interactive",
  "git_branch": "sdx/manual-dec-01",
  "no_code": false,
  "no_gates": false
}
JSON
: > .claude/sessions/manual-dec-01/session.log
git add -A && git commit -qm "fixture"
echo "$scratch"
```

**Предусловие.** Установлены `git`, `jq`, `awk`. Рабочее дерево репозитория SDX доступно на чтение
(оператор читает из него `commands/*.md` и `sdx/protocol.md` — тексты ПОСТАВКИ, не установленной
копии плагина).

**Ожидаемый результат.** Каталог `$scratch/.claude/sessions/manual-dec-01/` создан,
`decisions_log.md` в нём **отсутствует** (файл ленивый — REQ-DEC-5, отсутствие не ошибка).

**Проверка помощника измерения.** Определи функцию — она используется в шагах 1-7 без изменений:
```bash
check_dec() {  # $1 = тег категории без скобок, $2 = путь к decisions_log.md
  h="### Развилка: [$1]"
  blk=$(awk -v h="$h" 'index($0,h)==1{i=1;print;next} i&&index($0,"### ")==1{exit} i{print}' "$2" 2>/dev/null)
  [ -n "$blk" ] || { echo "FAIL [$1]: записи нет"; return 1; }
  printf '%s\n' "$blk" | grep -qE "^### Развилка: \[$1\] +[^[:space:]].*\(этап: *[^[:space:])]+ *\)$" \
    || { echo "FAIL [$1]: пустое название развилки или пустой этап в заголовке"; return 1; }
  printf '%s\n' "$blk" | grep -qE "^- Вариант: *[^[:space:]]"     || { echo "FAIL [$1]: поле «Вариант» пусто"; return 1; }
  printf '%s\n' "$blk" | grep -qE "^- Обоснование: *[^[:space:]]" || { echo "FAIL [$1]: поле «Обоснование» пусто"; return 1; }
  echo "PASS [$1]: запись найдена, все четыре поля непусты"
}
```
Функция измеряет ровно то, что требует REQ-DEC-2: тег категории, непустое название развилки,
непустой этап (оба — в заголовке), непустые «Вариант» и «Обоснование». Пятого поля нет и быть
не должно — тег живёт внутри поля «развилка».

**Действие.** Предъяви оркестратору синтетический `verification_report.md` с одной находкой

**Критерий измерения.**

Дополнительно (человеческое суждение, не грепается): «Вариант» читается как **инструкция к

## Шаг 7а — Симметрия `auto` ↔ `interactive` на одной и той же развилке

**Источник инструкции:** `commands/verify.md`, шаг 7 (два подпункта записи в журнал решений);
`commands/next.md`, шаг 2а; `sdx/protocol.md`, «Журнал решений».

**Почему отдельным шагом.** Шаги 1-7 все идут на `gate_mode: "interactive"`. Критерий приёмки
SPEC требует не формулировки правила, а **демонстрации**: одна и та же по смыслу развилка не
остаётся незафиксированной ни в одном из двух режимов. Структурные проверки `[T21]`/`[T22]`
доказывают лишь присутствие текста правила в командах — не его исполнение.

**Развилка берётся стоп-рубричная — FAIL-триаж, не WARN.** Это не деталь оформления: `WARN` в
стоп-рубрику не входит, и в `auto` он штатно уходит в `auto_decisions.md` БЕЗ остановки. Сценарий,
построенный на WARN, требовал бы от корректной системы остановки, которой она не должна делать, и
давал бы `Failed` на правильном поведении. (Именно такой дефект был у первой редакции этого шага —
найден fresh-eyes ревью как `FAIL`, см. `verification_report.md`.)

**Действие.** Переведи scratch-сессию в `gate_mode: "auto"` (`jq '.gate_mode = "auto"'`) и повтори
развилку **Шага 2** (FAIL-триаж) дословно, теми же словами. Затем — контрольная развилка НЕ
стоп-рубричного класса в том же режиме: `WARN`-находка верификации. Она обязана уйти в
`auto_decisions.md` без остановки.

**Предусловие.** Шаги 0 и 2 выполнены; запись `[FAIL]` от Шага 2 уже в журнале.

**Ожидаемый результат.** Три утверждения одновременно:
1. FAIL-триаж в `auto` ОСТАНАВЛИВАЕТ сессию так же, как в `interactive`, и его решение уходит в
   `decisions_log.md` — **второй** записью `[FAIL]`.
2. `WARN` в `auto` не останавливает и уходит строкой в `auto_decisions.md`.
3. Ни одно решение не задвоено: `WARN` в `decisions_log.md` не появляется, FAIL-триаж в
   `auto_decisions.md` не появляется.

**Критерий измерения.**
```bash
d=.claude/sessions/manual-dec-01/decisions_log.md
a=.claude/sessions/manual-dec-01/auto_decisions.md
grep -c '^### Развилка: \[FAIL\]' "$d"     # ожидается 2 (interactive + auto) — симметрия
check_dec FAIL "$d"                         # форма записи корректна
[ -s "$a" ] && echo "PASS: auto_decisions.md непуст (WARN автоквитирован)"
grep -ci 'warn' "$d"                        # ожидается 0 — WARN не течёт в журнал решений
grep -ci 'FAIL-триаж\|триаж находк' "$a"    # ожидается 0 — стоп-рубрика не течёт в auto-журнал
```
Расхождение в любую сторону — `Failed`: либо `auto` проглотил стоп-рубричное решение дефолтом
(нарушение симметрии), либо границы между двумя журналами размылись.

## Шаг 8 — Живой прогон (рекомендация DESIGN.md, не синтетика)

**Действие.** Как минимум одно стоп-рубричное решение **этой** сессии
(`proc-run-as-durable-unit-20260902`) провести живьём — наиболее вероятная точка — WARN/FAIL от
`reviewer` на `/sdx:verify`, то есть категория `[FAIL]` или `[триаж]`. Оркестратор читает
рабочие копии `commands/verify.md` из дерева (не установленную копию плагина) и пишет запись в
`.claude/sessions/proc-run-as-durable-unit-20260902/decisions_log.md`.

**Предусловие.** `/sdx:verify` этой сессии дал хотя бы одну находку, требующую решения человека.
Если ревью вернулось полностью чистым — шаг помечается `Blocked` (не `Failed`): предмета не
возникло, синтетические шаги 1-7 остаются единственным каналом доказательства.

**Ожидаемый результат.** Живая, а не сконструированная запись в журнале решений реальной сессии;
предъявляется на Closeout как дополнительное подтверждение поверх фикстур `[T14]`-`[T24]`.

**Критерий измерения.**
```bash
check_dec FAIL  .claude/sessions/proc-run-as-durable-unit-20260902/decisions_log.md || \
check_dec триаж .claude/sessions/proc-run-as-durable-unit-20260902/decisions_log.md
```

## Границы этого прогона (честно, REQ-BOUND-1)

Прогон **не** доказывает, что запись переживёт смерть CLI в окне между принятием решения и
ближайшим коммитом — это окно названо границей поставки и сознательно не закрыто. Он не
доказывает и подлинности записи: писателем является модель, независимого наблюдателя решений в
этой поставке нет (REQ-BOUND-2). Проверяется ровно одно — что инструкция, исполненная
оркестратором, даёт корректную по форме и содержательно осмысленную запись.
