## Принятые решения Task Planning

- **Находка 2 DESIGN (генерализация `foldable` на `Discovery`/`Task Planning`) — принята.**
  `SDX_STAGE_TABLE` в T-2 реализуется с `foldable=yes` для всех четырёх «планировочных» этапов
  (`Discovery`, `Business Spec`, `Technical Design`, `Task Planning`), не только для двух, которые
  SPEC называет буквально (REQ-SCALE-3). Обоснование DESIGN («единственный способ пройти `next`
  через эти четыре имени без нового скип-механизма, который SPEC явно не заказывает») принимается
  без изменений; отдельного возврата на Business Spec это не требует.
- **Тестовый разрыв REQ-TEST-1 — устранён декомпозицией, не принят как красное окно.** Требование
  DESIGN «Порядок исполнения» (п.2: `sdx-stage.sh` пишется раньше `sdx/protocol.md`) сталкивается с
  требованием «сьют остаётся зелёным после каждой задачи»: sanity-сценарий REQ-TEST-1 по
  определению сверяет ДВА артефакта (канонический список в коде и его прозаическую проекцию в
  `protocol.md`), а второй артефакт в новой форме не существует до T-26. Решение — не писать этот
  ОДИН сценарий внутри T-2 вместе с остальными ~27, а вынести его в отдельную маленькую задачу T-27
  сразу после T-26, когда оба сравниваемых артефакта существуют в финальной форме. Это не нарушает
  правило «один файл — одна задача целиком, если файл не является признанной атомарной парой»:
  `test-sdx-stage.sh` правится дважды ПОСЛЕДОВАТЕЛЬНО (T-2 → T-27), не параллельно двумя
  исполнителями — гонки `PROC-010` здесь нет. Это единственная пара задач во всей поставке, где
  наивное слияние в одну задачу было бы невозможным (нельзя проверить коэренцию с документом,
  которого ещё нет в целевой форме); ни одна другая пара соседних задач такого разрыва не создаёт
  (см. «Тестовый цикл» ниже — счётчик сьютов приведён после каждой кодовой задачи).
- **REQ-COMPAT-3 (скан легаси-имён этапов по всем сессиям репозитория) — не задача Execution.**
  Механизм добавляется в `commands/archive.md` задачей T-9 (новый пункт чек-листа), но сам скан —
  действие, выполняемое живым `/sdx:archive` этой сессии на Closeout, а не артефакт, который можно
  предъявить на Verification этого PLAN. Вынесено в раздел «Не входит в план» ниже.
- **Особенность исполнения (риск DESIGN «Сессия исполняется под установленным плагином 1.7.0»)
  учтена явно двумя способами**: (а) автоматический тестовый сьют (`verify-cmd.sh`) резолвит
  `sdx-stage.sh` релятивно к рабочему дереву — ему это не мешает, задачи T-2/T-27/T-33 опираются
  именно на него; (б) отдельная задача T-34 прямыми вызовами скрипта репозитория (не через
  `/sdx:*`) доказывает то, что автотест не проверяет по построению (полный жизненный цикл флагов в
  свежесозданной фикстуре), и явно фиксирует, что живые `/sdx:next` ЭТОЙ сессии до
  `/plugin marketplace update sdx` продолжат идти через старый скрипт — это не дефект реализации.

## Принцип группировки и порядка задач

- **Один файл — одна задача целиком**, за исключением двух явно названных DESIGN атомарных пар,
  где раздельное исполнение оставило бы промежуточный коммит в заведомо нерабочем состоянии:
  `sdx-stage.sh` + его тесты (T-2) и `stop-gate.sh` + `test-stop-gate.sh` (T-4). Обе пары
  фигурируют как единые задачи с типом `[CODE][TEST]`, что одновременно удовлетворяет правилу
  «каждая `[CODE]`-задача сопровождается `[TEST]`» — сопровождение здесь не отдельной задачей, а
  тем же неделимым шагом, ровно как предписывает DESIGN «Порядок исполнения», пп. 3 и 8.
- **Удаление / переписывание / правка прозы разведены явно** (см. типы задач и критерии готовности
  ниже): T-3, T-6 — чистое удаление (критерий — отсутствие файла + зелёный прогон); T-2, T-4 —
  переписывание (критерий — новые сценарии проходят); T-5, T-7…T-31 — правка прозы (критерий —
  `grep`-проверка остаточных упоминаний по каждому файлу).
- **`sdx/protocol.md` (68 упоминаний «трек», задет почти каждым разделом карты документации) —
  ОДНА задача (T-26), не дробится по разделам**, выполняется после того, как весь код (T-2…T-4) и
  все команды (T-5…T-16) уже стабильны, по прямой рекомендации DESIGN «Класс `PROC-010`».
- **`hooks/hooks.json` — одна задача (T-3, объединена с удалением файлов хуков)**, не пересекается
  по времени ни с одной задачей, тестирующей проводку (`test-hook-wiring.sh` читает файл с диска на
  каждый прогон — она встроена в тот же прогон `verify-cmd.sh`, что и T-3, не отдельная задача).
- **`commands/proto.md` — одна задача (T-5)**, внутри которой сначала переносится текст легализации
  из `retrack.md` дословно, затем вносятся точечные замены условий (`track != "vibe"` →
  `no_gates != true`) — порядок внутри задачи, не порядок задач, по прямой рекомендации DESIGN.
- **`docs/backlog/*.md` (7 закрываемых записей) + `docs/backlog/README.md` (общий индекс) — одна
  задача (T-32)**, не семь параллельных — тот же риск гонки на общем индексе, что и `protocol.md`.
- **`agents/*.md` (9 файлов, включая `auditor.md`) — девять отдельных задач (T-17…T-25)**, по
  одному агенту на задачу: разные файлы, гонки нет, DESIGN прямо называет это безопасным для
  параллелизации.
- **`commands/*.md` (10 файлов помимо `proto.md`/`retrack.md`/`backtrack.md`) — по одной задаче на
  файл (T-7…T-16)**: каждый файл упомянут DESIGN как отдельная точка правки, ни один не пересекается
  с другим по содержанию.
