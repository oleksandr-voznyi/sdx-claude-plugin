---
description: Многовекторный аудит проекта «как есть» (read-only, вне сессий) — параллельный фан-аут по девяти векторам, накопительный отчёт в docs/history/audit/.
---

Ты выполняешь роль Session Manager. Твоя задача — провести ревизионную оценку проекта целиком по
девяти векторам рубрики (полный состав и описание векторов — `${CLAUDE_PLUGIN_ROOT}/agents/auditor.md`,
раздел «Рубрика: девять векторов»; здесь эта рубрика НЕ дублируется) и записать один накопительный
отчёт. Это **read-only относительно проекта** операция: она НЕ создаёт сессию, НЕ читает и НЕ пишет
`session_state.json`/`session.log`, НЕ вызывает `sdx-stage.sh` и НЕ создаёт ветку. Единственная
запись в проект — файл отчёта (и каталог под него, если отсутствует).

Алгоритм:

1. **Precheck незавершённых прогонов.** Перечисли каталоги `.sdx/audit-runs/*/` (если каталог
   `.sdx/audit-runs/` не существует — пропусти шаг, прогонов нет). Для каждого найденного каталога
   прочитай его `manifest.txt` (если файл отсутствует — прогон оборвался до записи манифеста,
   назови это явно) и вычисли состав: `started`/`rev` из манифеста, какие векторы из девяти уже
   сдали корректный файл (`<CODE>.md`), каких по манифесту не хватает. Покажи это пользователю по
   каждому найденному каталогу и спроси (`AskUserQuestion`): доснять недостающие векторы **в этот
   же каталог** (файлы уже сданных векторов переиспользуются, не перевычисляются), отбросить
   (`rm -r` каталога — только по явному согласию пользователя на КАЖДЫЙ каталог отдельно) или
   оставить как есть (пропустить, не трогать). **Автоудаление не выполняется никогда** — это чужие
   данные, ты не можешь знать, обрыв это или параллельно выполняющийся прогон. Если пользователь
   выбрал «доснять» для какого-то каталога — этот каталог становится run-dir шага 2 (пропусти в
   нём создание нового каталога и уже готовый детерминированный слой, если манифест уже валиден;
   пересчитай его заново, если манифест отсутствует или повреждён). Иначе — переходи к шагу 2 с
   новым run-dir.

2. **Детерминированный слой.** Вычисли форму проекта командами `Bash` (без вызова субагентов —
   это единственный шаг с прогоном скриптов, всё дальнейшее делают субагенты `auditor` без
   `Bash`):
   - `is_git_repo` (наличие `.git/`); если да — `rev = git rev-parse HEAD`, `default_branch` через
     `bash "${CLAUDE_PLUGIN_ROOT}/sdx/hooks/lib/default-branch.sh"`; если нет — `rev: n/a`,
     `default_branch: n/a` (см. «Граничные случаи», п. «Не git-репозиторий»);
   - `specs_count` = число `docs/specs/*.md` за вычетом `README.md`; `designs_count` — то же для
     `docs/designs/`; каталог, который существует и пуст, даёт `0`;
   - `req_id_files` = число файлов `docs/specs/*.md`, содержащих паттерн `REQ-[A-Z]+-[0-9]`
     (`grep -l`);
   - `has_code` = число файлов исходного кода по расширениям `*.py *.js *.ts *.tsx *.go *.rs
     *.java *.kt *.rb *.php *.cs *.c *.h *.cpp *.sh *.bash *.sql *.swift *.scala *.ex *.exs` вне
     `docs/`, `.git/`, `node_modules/`, `vendor/`, `.sdx/`;
   - `tests_count` — эвристический счёт файлов/каталогов с `test`/`spec` в имени вне тех же
     исключённых путей (входит в манифест как факт формы, а не как предикат применимости — `TEST`
     применим по `has_code`, не по наличию тестов);
   - счётчики бэклога по статусам (`open`/`in-progress`/`closed`/`deferred`) из frontmatter
     `docs/backlog/*.md`, если каталог существует;
   - `archived_plans` = число файлов `docs/history/plans/*.md`, если каталог существует;
   - `deploy_evidence` — наличие любого из: `.github/workflows/`, `.gitlab-ci.yml`, `Dockerfile`,
     `docker-compose*`, `*.tf`, `k8s/`, `charts/`, `Makefile` с целью `deploy|release|publish`,
     `package.json` со скриптом `publish`, `.claude-plugin/marketplace.json`,
     `.claude/sdx/prod-guard.conf` с хотя бы одной активной строкой-паттерном;
   - `is_sdx_project` — существование любого из `.claude/sdx/`, `.claude/sessions/`,
     `docs/backlog/`; `is_sdx_meta` — `.claude-plugin/plugin.json` с `"name": "sdx"`.

   По этим фактам вычисли применимость (`applicable`/`n/a` + причина) для каждого из девяти
   векторов:
   - `ARCH`, `CODE` — применимы при `has_code ≥ 1`;
   - `TRIAD` — применим при `specs_count ≥ 1` И `designs_count ≥ 1`; при односторонней асимметрии
     (одна сторона пуста, другая нет) — `n/a` с причиной «односторонняя асимметрия триады», даже
     если это само по себе кандидат в находку `TRACE` (см. ниже);
   - `TRACE` — применим при (`TRIAD` применим) И `req_id_files ≥ 1` И `has_code ≥ 1`; при
     `docs/specs/` без идентифицированных ID — `n/a` с причиной «требования не идентифицированы
     ID»;
   - `TEST` — применим при `has_code ≥ 1` (НЕ при `tests_count ≥ 1` — код без единого теста даёт
     вектору исход «есть находки», а не «неприменимо»); при `has_code = 0` — `n/a`;
   - `DOCS`, `SEC` — применимы всегда;
   - `DEPLOY` — применим при `deploy_evidence = yes`;
   - `PROC` — применим при `is_sdx_project = yes`; при `is_sdx_meta = yes` подскоуп «экономика
     самого фреймворка» расширяет предмет вектора, но не создаёт отдельного исхода — это
     объявляется в `## Охват` файла вектора самим агентом.

   Запиши `manifest.txt` в run-dir `.sdx/audit-runs/<YYYY-MM-DD-HHMMSS>/` (создай каталог, если
   шаг 1 не переиспользует существующий) ОДНИМ редиректом — плоский `key: value` плюс девять
   блоков `[vector:<CODE>]`, не более ~60 строк:
   ```
   run: audit-<YYYY-MM-DD-HHMMSS>
   report_target: docs/history/audit/audit-<YYYY-MM-DD>[-N].md
   started: <ISO-8601>
   rev: <sha | n/a>
   default_branch: <name | n/a>
   is_git_repo: yes|no
   is_sdx_project: yes|no
   is_sdx_meta: yes|no
   has_code: <N>
   specs_count: <N>
   designs_count: <N>
   req_id_files: <N>
   tests_count: <N>
   backlog_open: <N>
   backlog_in_progress: <N>
   backlog_closed: <N>
   backlog_deferred: <N>
   archived_plans: <N>
   deploy_evidence: yes|no

   [vector:ARCH]
   applicable: yes|no
   reason: <текст, обязателен при no>
   scope_include:
     - <путь/глоб>
   scope_exclude:
     - <путь/глоб>
   ```
   (и так по одному блоку `[vector:<CODE>]` на каждый из девяти кодов — `ARCH`, `TRIAD`, `TRACE`,
   `CODE`, `TEST`, `DOCS`, `DEPLOY`, `SEC`, `PROC`). `scope_include`/`scope_exclude` — узкий вход
   вектора (что читать и что явно НЕ читать); для `n/a`-векторов оставь их пустыми. Файл
   иммутабелен с момента записи — дальше его никто не правит.

3. **Фан-аут двумя волнами.** Векторы, признанные `n/a` на шаге 2, **не диспетчеризуются вовсе** —
   для каждого из них СРАЗУ напиши `<run-dir>/<CODE>.md` сам (без вызова `Task`): строка-маркер
   `AUDIT <CODE> N/A findings=0 strengths=0 problems=0 risks=0 recommendations=0 file=<path>` первой строкой,
   затем раздел `## Неприменимость` с причиной из манифеста.

   Для оставшихся (применимых) векторов вызови субагента `auditor` (`Task`) — **один вызов на
   вектор**, все вызовы одной волны параллельно. Каждому вызову передай СТРОГО: (а) код вектора;
   (б) путь к `manifest.txt`; (в) путь к его единственному выходному файлу `<run-dir>/<CODE>.md`.
   Никакого содержимого файлов в промпте — только пути и задача.

   - **Волна 1** (пять векторов, узкий вход — документация/конфиги/CI, дешёвая): `TRIAD`, `TRACE`,
     `DOCS`, `DEPLOY`, `PROC` (из применимых в этом списке).
   - **Волна 2** (четыре вектора, узкий вход — исходный код): `ARCH`, `CODE`, `TEST`, `SEC` (из
     применимых в этом списке).

   Запускай волну 2 только после завершения волны 1 — это даёт шанс обнаружить ошибку манифеста
   (например ложный `has_code=0`) на пяти дешёвых вызовах до траты дорогой волны.

4. **Проверки консистентности.** Для каждого полученного `<run-dir>/<CODE>.md` (включая файлы,
   написанные тобой на шаге 3 для `n/a`-векторов) проверь:
   - `CLEAN` ⇒ `findings=0`; `FINDINGS` ⇒ `findings≥1`; `N/A` ⇒ `findings=0` И файл содержит
     раздел `## Неприменимость` с названной причиной;
   - **сумма сходится:** `findings = strengths + problems + risks + recommendations`, и число
     заголовков `### ` в каждом из четырёх разделов файла равно соответствующему счётчику. Без
     поля `problems=` эта проверка невозможна — счётчик обязателен (см. `agents/auditor.md`,
     «Формат файла вектора»);
   - `<CODE>` в строке-маркере совпадает с именем файла и присутствует в манифесте;
   - ровно один файл на каждый вектор из манифеста, ни одного лишнего.

   Несоответствие = некорректный выход вектора. Перевызови ТОЛЬКО этот вектор **один раз**
   (тем же контрактом, что в шаге 3). Если после повторного вызова несоответствие сохраняется —
   прогон объявляется **незавершённым**: отчёт НЕ пишется, каталог прогона `.sdx/audit-runs/…`
   сохраняется как есть, пользователю называется, какой вектор не сдал корректный файл. Не вводи
   четвёртый исход вектора («не выполнен») — несоответствие описывает прогон, а не вектор.

5. **Склейка.** Только если для всех девяти векторов манифеста есть корректный файл — собери
   отчёт `docs/history/audit/audit-<YYYY-MM-DD>[-N].md` (текущая дата запуска; если файл на эту
   дату уже существует — прозаически просканируй `docs/history/audit/audit-<YYYY-MM-DD>*.md` и
   возьми следующий свободный `-N` начиная с `2`, тот же приём, что выделение номера записи
   бэклога, `commands/backlog.md:19`). Frontmatter:
   ```yaml
   run: <run-id>
   date: <YYYY-MM-DD>
   rev: <sha | n/a>
   project: <имя каталога проекта>
   findings_total: <сумма findings по всем девяти файлам>
   vectors:
     ARCH: FINDINGS|CLEAN|N/A
     TRIAD: FINDINGS|CLEAN|N/A
     TRACE: FINDINGS|CLEAN|N/A
     CODE: FINDINGS|CLEAN|N/A
     TEST: FINDINGS|CLEAN|N/A
     DOCS: FINDINGS|CLEAN|N/A
     DEPLOY: FINDINGS|CLEAN|N/A
     SEC: FINDINGS|CLEAN|N/A
     PROC: FINDINGS|CLEAN|N/A
   ```
   Разделы (в этом порядке):
   - `## Сводка` — run-id, дата, rev, краткий профиль проекта (счётчики из манифеста) и
     **таблица покрытия**: `вектор | код | исход | число находок` — все девять строк, единственное
     место отчёта, где все девять исходов видны сразу.
   - `## Сильные стороны`, `## Проблемы`, `## Риски`, `## Рекомендации` — собери находки всех
     векторов из соответствующих разделов их файлов, сгруппированные по вектору (не разбивай
     находки одного вектора между разными местами раздела); ID находок оставь как есть
     (`<CODE><N>`, глобальный счётчик не нужен — коды уже дают уникальность). Каждая находка в
     `## Риски` обязана нести «Реагирование», каждая в `## Сильные стороны` — «Что нельзя
     сломать»; если в файле вектора поле отсутствует — это дефект выхода вектора уровня шага 4
     (не должно было пройти проверки консистентности; если всё же обнаружено на склейке —
     остановись и не публикуй раздел без исправления, обработай как несоответствие шага 4).
   - `## Неприменимые векторы` — код, вектор, структурная причина (из `## Неприменимость` файлов
     `N/A`).
   - `## Границы прогона` — что заведомо не проверялось: внешние сканеры безопасности/CVE
     (REQ-AUDIT-16б), эвристичность `has_code` (число печатается здесь же, чтобы ошибочный `0` был
     виден), прозаический характер оценочных векторов, `rev: n/a`/деградация функций, зависящих от
     git-истории, если проект не git-репозиторий.

   Запись — **одним финальным действием** (`Write` целиком собранного текста): частичный отчёт в
   `docs/` невозможен — до этого момента файл отчёта не существует и не создаётся по частям.

6. **Удаление каталога прогона.** Сразу после успешной записи отчёта удали `.sdx/audit-runs/<run-id>/`
   целиком (`rm -r`). Это единственный момент, когда команда удаляет каталог прогона сама — при
   обрыве (шаг 4, повторное несоответствие) каталог остаётся.

7. **Граничные случаи проекта-потребителя.**
   - **Нет `docs/history/audit/`** → создай (`mkdir -p`) вместе с файлом-заглушкой `README.md` (по
     образцу `docs/history/intake/README.md`: «заглушка для версионирования каталога, не индекс
     прогонов»). Это часть записи собственного отчёта — класть его больше некуда — а не
     навязывание раскладки проекту; это ЕДИНСТВЕННАЯ запись за пределами самого файла отчёта.
   - **Нет `.claude/sdx/`** (проект не инициализирован SDX) → НЕ создавай ничего. `PROC` получает
     `N/A`, `TRIAD`/`TRACE` — по своим предикатам. Прогон на универсальных векторах (`ARCH`,
     `CODE`, `TEST`, `DOCS`, `SEC`, при наличии `deploy_evidence` — `DEPLOY`) выполняется и
     полезен. Одна информационная строка про `/sdx:init` допустима, гейтом не является.
   - **Нет `docs/backlog/`** → ничего не создавай; отчёт формируется штатно (`/sdx:audit` бэклог
     не пишет никогда — это работа `/sdx:start audit`, а не этой команды).
   - **Не git-репозиторий** → `rev`/`default_branch` в манифесте и во frontmatter отчёта = `n/a`;
     это фиксируется в `## Границы прогона`; прогон НЕ отменяется.
   - **Грязное рабочее дерево** → гарды нет (в отличие от `/sdx:reconcile --auto`): команда
     read-only относительно кода проекта, откатывать нечего.
   - **Коммит отчёта.** Если текущая ветка — `sdx/<id>` (команда вызвана внутри активной
     SDX-сессии — это допустимо, состояние сессии при этом не читается и не пишется): напомни, что
     отчёт ляжет на ветку сессии и закоммитится вместе с ней штатным циклом сессии — сама эта
     команда коммит не делает. Иначе (обычный случай) — по образцу `commands/reconcile.md:74`:
     НАПОМНИ пользователю закоммитить отдельной веткой (`git checkout -b chore/sdx-audit-<дата>`
     перед коммитом), а не в основную — основная ветка получает только merge-коммиты (ADR-009);
     сама команда коммит вне сессии не делает.

8. **Финальная подсказка.** Выведи путь к записанному отчёту и одной строкой предложи
   `/sdx:start audit <путь к отчёту>` — штатный путь триажа находок в `docs/backlog/`.

Протокол сессий, контракт `/sdx:audit` и его триажа, формат `source`, три слоя дедупликации:
прочитай (Read) `${CLAUDE_PLUGIN_ROOT}/sdx/protocol.md`.
