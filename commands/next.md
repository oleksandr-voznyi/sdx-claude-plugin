---
argument-hint: [--to <stage>]
description: Переход на следующий этап жизненного цикла SDX.
---

Ты выполняешь роль Session Manager. Твоя задача — проверить готовность текущего этапа и перевести сессию на следующий **активный** этап (без аргумента), либо вернуть её на уже пройденный этап (`--to <stage>`).

Аргументы: $ARGUMENTS (без аргумента — обычный форвард; `--to <stage>` — откат на более ранний, уже пройденный или ранее пропущенный этап, см. шаг 4а)

Алгоритм:
1. Прочитай `session_state.json`: определи `no_code`, `no_gates` и текущий `stage`. Набор активных этапов определяется каноническим порядком девяти имён (`sdx/protocol.md`) плюс флагами (REQ-SCALE-1/4/5) — гейт уже учитывает это внутри `sdx-stage.sh`, здесь пересказывать его прозой не нужно.
2. **Scope-check (пересмотр объёма).** Прежде чем двигаться дальше, оцени, не вышла ли задача за рамки того объёма, что предполагался на уже пройденных планировочных этапах:
   - Затронуты бизнес-логика, публичные контракты, схемы данных или архитектура, которых лёгкий `change_note.md` уже пройденного этапа не предполагал → предложи создать для него полноценный артефакт (`SPEC.md`/`DESIGN.md`, через `ba`/`architect`) вместо `change_note.md`, затем `/sdx:next --to <тот этап>` (REQ-SCALE-9, REQ-NAV-1).
   - Церемония оказалась явно избыточной → предложи ограничиться `change_note.md` дальше, без создания дополнительных полноформатных артефактов.
   Не меняй объём молча — сообщи пользователю и дождись решения, если масштаб изменился существенно.
2а. **Авторежим (по протоколу, ADR-014).** Прочитай `gate_mode` из state:
   - Если `"auto"`: гейт-подтверждения, обычно запрашиваемые у пользователя, принимай дефолтом без остановки; каждый дефолт — одна строка в `auto_decisions.md` (коммить вместе со сменой состояния). Остановка ОБЯЗАТЕЛЬНА на стоп-рубрике протокола: коллизии триады, FAIL/красный тест-пол, внешние контракты/схемы данных, деструктив/prod-guard, эскалация объёма — переход к более тяжёлому артефакту для уже пройденного этапа (сбрасывает `gate_mode → interactive`), ручные шаги. **Стоп-рубрика останавливает `auto`-сессию так же, как `interactive`** — на её пунктах решение всегда принимает человек, а не дефолт модели; такое решение идёт в `decisions_log.md` (`PROC-019`, `sdx/protocol.md` «Журнал решений»), НЕ в `auto_decisions.md` — последний фиксирует только то, что было принято дефолтом БЕЗ остановки.
   - Если `"interactive"` и это первый содержательный гейт сессии (`Discovery`/`Business Spec`): при тривиальном масштабе задачи предложи пользователю включить авторежим (AskUserQuestion); решение зафиксируй в `gate_mode`.
   - При `no_gates == true` предложение включить авторежим не делается.
2б. **Соблюдение записанных решений (REQ-RESUME-3, `PROC-019`).** Перед любым `AskUserQuestion` на этом гейте (шаги 2/2а/3 выше и ниже) — сверь текст развилки с записями `decisions_log.md` по тому же алгоритму, что шаг 6 `commands/resume.md` (текстовое сопоставление по ключевым терминам развилки): найдено совпадение → примени зафиксированный вариант молча, без повторного вопроса по этой же развилке; не найдено → веди себя как обычно. Применимо не только после `/sdx:resume` — для ЛЮБОГО живого хода сессии с памятью о ранее принятых решениях.
3. **Гейт текущего этапа.** Объективно проверяемая часть гейта (существование/непустота требуемого артефакта или `change_note.md`-эквивалента для планировочных этапов, отсутствие `FAIL` в `verification_report.md`) проверяется автоматически вызовом `sdx-stage.sh next` (шаг 4) — не описывай её прозой заново. Смысловые условия («решение согласовано», `SPEC.md` подтверждён по смыслу — `status: approved`, декомпозиция `PLAN.md` адекватна) остаются твоим суждением **до** вызова — скрипт их не проверяет (DEBT-007, ограничение унаследовано).
4. Вызови единственный писатель `stage` — режим определяется наличием `--to`:
   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/sdx/hooks/sdx-stage.sh" next "<session_id>"
   # либо, для отката:
   bash "${CLAUDE_PLUGIN_ROOT}/sdx/hooks/sdx-stage.sh" next "<session_id>" --to "<stage>"
   ```

   **Ограничение цели по флагу.** `--to` отклоняется кодом `1`, если целевой этап исключён из
   активного набора флагом `no_code` (`Task Planning`, `Execution`, `Documentation`, `Deployment`).
   Это тот же безусловный запрет, что на `init` и на форвардном `next` (REQ-SCALE-4).

   **Снятие `no_code` (эскалация объёма).** Если по ходу выяснилось, что процессная сессия
   переросла в работу с кодом — сними флаг прямой правкой `session_state.json`
   (`no_code: true -> false`), закоммить её отдельным коммитом с явным сообщением и продолжай
   обычным `/sdx:next`. Эскалация одноразовая: обратная установка `no_code: false -> true`
   посреди идущей сессии запрещена (REQ-FLAG-4), как и прежде запрещалась деэскалация из трека
   `doc`. Флаг `no_gates` так не снимается — его снимает только легализация через `/sdx:proto`.
   ```bash
   ```
   - **Код `0`** (включая no-op `OK no-op <stage>`, когда текущий этап уже терминальный (`Closeout`), либо когда сессия с `no_gates == true` возвращает `OK no-op Execution` (REQ-LEGAL-1 — приоритетно над всем остальным, единственный выход — легализация через `/sdx:proto`), либо когда `--to` целится в текущий же этап — файл не тронут): `stage` уже переведён (форвард) или возвращён (`--to`), и `[STAGE_CHANGE]` уже записан в лог скриптом атомарно; используй `OK <old> -> <new>` из stdout как текст коммита. Закоммить смену состояния на ветку `sdx/<id>` (REQ-SESS-1), включая пути, помеченные строками `OUTDATED: <path>` в stdout (только для `--to`), И `decisions_log.md`, ЕСЛИ в рамках текущего хода в него была добавлена запись (та же дисциплина, что уже для `PLAN.md`/`OUTDATED`-меток — коммитить только реально изменённые в этом ходе файлы):
     ```bash
     git add .claude/sessions/<id>/session_state.json .claude/sessions/<id>/session.log <помеченные файлы, если есть> <decisions_log.md, если он был изменён в этом ходе> && git commit -m "sdx(<id>): stage <old> -> <new>"
     ```
     (для `OK no-op` коммитить нечего — файл не менялся). Для форварда без `--to` — затем запусти работу нового этапа: вызови соответствующего субагента (architect, ba, lead-dev, developer, qa, tech-writer, devops через Task) либо выполни этап инлайн, если объём задачи это предполагает. Если новый этап — `Closeout`, направь пользователя на `/sdx:archive`. Если получен `OK no-op Execution` при `no_gates == true` — это легитимный no-op, не ошибка: направь пользователя на `/sdx:proto`; коммитить нечего. Для `--to` — сообщи пользователю ровно те пути, что перечислены строками `OUTDATED: <path>` в stdout, как файлы, требующие актуализации, и что сессия теперь на `<stage>`.
   - **Код `1`**:
     - без `--to` — гейт уходящего этапа отклонён (недостающий/пустой артефакт, включая `change_note.md`-эквивалент, или находка `FAIL`);
     - с `--to` — цель не распознана как имя этапа, либо цель позже текущего этапа в каноническом порядке (не откат — форвард мимо гейта делает только обычный `next` без `--to`), либо (при `no_gates == true`) цель отлична от `Execution` (REQ-LEGAL-1 приоритетнее навигации — выход только через легализацию).
     Во всех случаях сообщи пользователю текст stderr дословно (он уже называет проблему и команду для исправления — не формулируй заново), запиши в лог `[ERROR] Ошибка перехода: <текст stderr>`. `stage` не менялся, коммитить нечего.
   - **Код `2`** (ошибка окружения/аргументов — нет `jq`, нет `session_state.json`, состояние повреждено или использует нераспознанное/устаревшее имя этапа — REQ-COMPAT-3, требует ручной миграции): сообщи пользователю текст stderr дословно, запиши в лог `[ERROR] Ошибка перехода: <текст stderr>` и остановись.
