---
argument-hint: <type> <goal> [--auto]
description: Запуск новой сессии разработки SDX (Feature, Bug, Refactor, Grooming, Retro, Postmortem, Intake, Audit, Proto).
---

Ты выполняешь роль Session Manager в рамках SDX фреймворка (оркестрация в основной сессии). Твоя задача — запустить новую изолированную сессию, назначить стартовый этап и режимные флаги (`no_code`/`no_gates`).

Аргументы: $ARGUMENTS
(Ожидается: <type> <goal>, например: bug "Исправить падение при пустом вводе". Опциональный флаг `--auto` включает авторежим гейтов с самого старта — см. «Авторежим гейтов» в протоколе, ADR-014.)

Примечание: сессии типа `import` создаются отдельной командой `/sdx:import <bundle-path>` (нужен бандл, а не текстовая цель), а не через `/sdx:start`.

Алгоритм:
1. **Сверка версии плагина (предложение, не блокировка).** Если в проекте есть `.claude/sdx/` (проект уже инициализирован SDX) — сравни маркер `.claude/sdx/sdx-version` с текущей версией плагина (`jq -r .version "${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json"`). При расхождении версий ИЛИ отсутствии файла-маркера в уже инициализированном проекте — одной строкой предложи прогнать `/sdx:reconcile` до старта сессии (например: «Версия плагина изменилась с `<маркер>` на `<текущая>` — сверить формат бэклога/структуры командой `/sdx:reconcile` перед стартом? »).
   - **Отказ** — НЕ мешает старту сессии и НЕ запоминается глобально: продолжай к шагу 2. Предложение будет показано снова при следующей смене версии плагина (маркер не сдвинется без фактической реконсиляции — см. `commands/reconcile.md`, шаг 12).
   - **Согласие** — **остановись и НЕ создавай сессию**. `/sdx:start` реконсиляцию инлайн не выполняет: её результат (записи бэклога, пометки источников, приведение форматов) относится ко всему проекту, а не к задаче этой сессии, и должен пройти обычным путём правок репозитория — своя ветка, свой коммит по явному запросу пользователя (branch-first, процессные соглашения `docs/DECISIONS.md` и ADR-009: основная ветка получает только merge-коммиты). Выведи пользователю ровно две строки: «Запусти `/sdx:reconcile`, затем повтори `/sdx:start <аргументы>`» — с дословным повтором его исходных аргументов, чтобы перезапуск был копипастой. На этом выполнение команды заканчивается.
   - Если `.claude/sdx/` нет вовсе — проект не инициализирован SDX, сверять нечего, пропусти шаг без вопроса.
2. Сгенерируй уникальный `session_id`.
3. **Назначение флагов и стартового этапа.** Тип задачи определяет флаги `no_code`/`no_gates` — для пяти типов ниже ЖЁСТКО, без диалога об альтернативе (REQ-FLAG-2); для остальных типов флаги остаются `false`/`false`, а суждение выбирает только стартовый `stage`:
   - **`no_code = true`** — типы `grooming`/`retro`/`postmortem`/`intake`/`audit` жёстко задают `no_code = true`, `no_gates = false` (ADR-017/ADR-019): назначь это безусловно, БЕЗ диалога об альтернативе (в отличие от суждения по `feature`/`bug`/`refactor` ниже — здесь связь тип↔флаг жёсткая 1:1 по построению). Стартовый `stage` — `Discovery`. **Для типа `audit` дополнительно выполни предусловия входа ДО создания сессии** — стоп-условия, по образцу проверки реконсиляции на шаге 1: аргумент обязан быть путём к уже существующему файлу отчёта (ожидаемо в `docs/history/audit/`) с парсящимся YAML frontmatter, содержащим поле `run:` — если аргумент отсутствует, файл не существует или frontmatter не парсится, ОСТАНОВИСЬ, перечисли пользователю найденные отчёты в `docs/history/audit/` (если каталог есть и непуст) и направь на `/sdx:audit`, если отчётов нет вовсе (Discovery-lite для `audit` НЕ порождает новый аудит и не вызывает `/sdx:audit` автоматически — REQ-AUDIT-10); `docs/backlog/` обязан существовать — если его нет, ОСТАНОВИСЬ и направь на `/sdx:init`/`/sdx:reconcile` (сессия, начатая без бэклога, не сможет выполнить гейт-выход этапа `Business Spec`, где `no_code`-сессии типично фиксируют решение в `change_note.md`); если оба условия выполнены, но по точному слою дедупликации все находки отчёта (`source: <run-id> (<CODE><N>)`) уже отражены в записях `docs/backlog/` — предупреди пользователя одной строкой (отчёт, вероятно, уже разобран), это НЕ блокировка, сессию не останавливай. Только после прохождения предусловий продолжай к шагу 4.
   - **`no_gates = true`** — тип `proto` жёстко задаёт `no_gates = true`, `no_code = false` (ADR-018): назначай безусловно, БЕЗ диалога об альтернативе, по тому же принципу, что и `no_code` выше — связь тип↔флаг здесь тоже жёсткая 1:1 по построению. Стартовый `stage` ВСЕГДА `"Execution"` (REQ-LEGAL-3, REQ-SCALE-5) — единственный легитимный старт при `no_gates == true`; `sdx-stage.sh init` откажет на любом другом значении.
   - **`no_code = false`, `no_gates = false`** — типы `feature`/`bug`/`refactor` (и `import`, создаваемый отдельной командой — см. `commands/import.md`): суждение определяет ТОЛЬКО стартовый `stage`, не флаги. `Execution` сразу — если задача точечная (правка на 1–N строк, без изменения бизнес-логики, публичных контрактов, схем данных или архитектуры); `Discovery` — если задача крупнее (новая фича, рефакторинг, что-то затрагивающее контракты/архитектуру).
   Если по формулировке масштаб `feature`/`bug`/`refactor`-задачи неочевиден — задай уточняющий вопрос пользователю перед выбором стартового `stage`. Помни: активный набор этапов не фиксируется раз навсегда — он пересматривается на каждом `/sdx:next` по фактическому объёму создаваемых артефактов (REQ-SCALE-2/9); `no_code` может быть снят по ходу сессии при эскалации объёма (симметрично сегодняшнему `doc → {...}`), но не установлен заново; `no_gates` может быть снят РОВНО ОДИН РАЗ, легализацией через `/sdx:proto` (REQ-FLAG-4), и никогда не установлен повторно в этой же сессии.
4. Проверь, что рабочее дерево чистое (`git status --porcelain` пуст). Если нет — остановись и попроси пользователя закоммитить/стэшнуть изменения: сессия должна стартовать с чистой точки основной ветки. Для типа `proto` этот гард дополнительно служит основой baseline-снимка отката (REQ-VIBE-5): чистое дерево на входе означает, что любой untracked-файл, появившийся позже, либо порождён прототипом, либо явно записан в baseline попытки.
5. Создай ветку сессии в ТЕКУЩЕМ рабочем дереве (ADR-012, без worktree и без смены CLI):
   ```bash
   git checkout -b sdx/<session_id>
   mkdir -p .claude/sessions/<session_id>
   ```
6. Инициализируй `session_state.json`+`session.log` через единственный писатель `stage` (REQ-STAGE-1), позиционные аргументы РОВНО в этом порядке (`sid type stage gate_mode git_branch no_code no_gates`):
   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/sdx/hooks/sdx-stage.sh" init \
     "<session_id>" "<type>" "<стартовый stage>" "<gate_mode>" "sdx/<session_id>" "<no_code>" "<no_gates>"
   ```
   Стартовый `stage` и оба флага — назначены шагом 3 выше; `gate_mode`: `"auto"` при флаге `--auto`, иначе `"interactive"`. Код `0` — оба файла созданы (stdout `OK - -> <stage>`), продолжай к шагу 7. Ненулевой код (у `init` это всегда `2` — несовместимые флаги (REQ-FLAG-3), нераспознанный `stage`, `no_gates=true` не на `Execution` (REQ-SCALE-5), `no_code=true` на исключённом этапе (REQ-SCALE-4), сессия с таким `session_id` уже проинициализирована, аргументы некорректны или окружение сломано, например нет `jq`) — сообщи пользователю текст stderr дословно и остановись, коммит шага 7 не делай. При `--auto` заведи пустой `auto_decisions.md` и напомни пользователю правила авторежима одной строкой (дефолты по ходу + дисклоуз перед закрытием; стоп-рубрика протокола действует). При `--auto` для типа `proto` дополнительно выведи одну строку: «при `no_gates == true` до легализации авторежим не имеет поверхности применения: единственный содержательный гейт (`/sdx:proto`) безусловно интерактивен (REQ-VIBE-10), а легализация всё равно сбросит `gate_mode` в `interactive`». Флаг при этом принимается и пишется в state как есть — специальных веток в схеме не заводим.
7. Закоммить seed-состояние на ветку сессии (REQ-SESS-1):
   ```bash
   git add .claude/sessions/<session_id>
   git commit -m "sdx(<session_id>): init session state"
   ```
8. Запусти работу стартового этапа:
   - **Стартовый `stage == "Execution"`** (масштаб `feature`/`bug`/`refactor` оценён как точечный, оба флага `false`) — сразу переходи к доводке. Заведи `change_note.md` (что/зачем менялось, затронутые файлы, ссылка на коммит — заполняется по ходу; тот же файл станет доказательством гейта на `Verification`/`Closeout`). Реализуй правку в основной сессии или через субагента `developer` (режим прямой задачи, без `PLAN.md`).
   - **Стартовый `stage == "Discovery"`** (масштаб `feature`/`bug`/`refactor`/`import` оценён как полноценный цикл, оба флага `false`) — выполни Discovery (лёгкий инлайн без субагента `architect` для небольшой дельты, либо вызови субагента `architect` (Task) для `context_report.md` при более крупной). Глубина каждого следующего планировочного этапа (`Business Spec`/`Technical Design`/`Task Planning`) — прозаическое суждение оркестратора НА КАЖДОМ из них по отдельности, пересматриваемое `/sdx:next` (REQ-SCALE-2/9), а не решение, зафиксированное здесь раз навсегда: небольшая дельта — `change_note.md` инлайн, который одновременно закрывает гейт всех четырёх планировочных этапов (REQ-SCALE-3) — серия `/sdx:next` пройдёт их без остановки; крупная — полноценные `SPEC.md`/`DESIGN.md`/`PLAN.md` через `ba`/`architect`/`lead-dev` соответственно.
   - **`no_code == true`** (типы `grooming`/`retro`/`postmortem`/`intake`/`audit`) — выполни Discovery-lite инлайн (без субагента `architect`), вход зависит от типа — `grooming`: срез текущего бэклога (`docs/backlog/README.md` + записи); `retro`: выборка завершённых сессий из `docs/history/sessions-log.md` за период/список, заданный пользователем; `postmortem`: интервью пользователя об инциденте (что произошло, когда обнаружено, серьёзность); `intake`: приём внешнего материала, явно поданного пользователем (ссылки/пути/вложения — ограничение по `docs/backlog/PROC-009`), и его первичный обзор; `audit`: прочитай (Read) файл отчёта, уже провалидированный предусловиями шага 3 (путь-аргумент, frontmatter с `run:`), и срез текущего бэклога (`docs/backlog/README.md` + записи) — Discovery-lite здесь состоит в чтении УЖЕ существующего отчёта, никакой новый скан проекта не выполняется. Для типов `retro`/`postmortem`/`intake` скопируй соответствующий шаблон в каталог сессии (`grooming` и `audit` шаблона НЕ получают — `sdx/templates/audit.md` не существует и не создаётся этой поставкой; строка `cp` ниже относится только к `retro`/`postmortem`/`intake`):
     ```bash
     cp "${CLAUDE_PLUGIN_ROOT}/sdx/templates/<type>.md" ".claude/sessions/<session_id>/<type>.md"
     ```
     Затем заведи `change_note.md` и переходи `/sdx:next`: он одновременно закрывает гейт КАЖДОГО активного планировочного этапа (`Business Spec`/`Technical Design` — `Task Planning` при `no_code == true` безусловно исключён, REQ-SCALE-4) на пути к `Verification` (REQ-SCALE-3) — `Execution`/`Documentation`/`Deployment` тоже исключены `no_code`, поэтому следующая содержательная остановка после Discovery — именно `Verification`.
   - **`no_gates == true`** (тип `proto`) — НЕ вызывай Discovery/`architect`/`ba`, НЕ заводи `SPEC.md`/`DESIGN.md`/`PLAN.md`/`change_note.md`. Сначала зафиксируй baseline попытки (см. ниже), затем реализуй цель пользователя ОДНИМ непрерывным проходом — в основной сессии или через субагента `developer` (режим «Прототип»), без промежуточных подтверждений и БЕЗ коммитов кода (REQ-VIBE-3/9). По завершении реализации сообщи пользователю одной строкой, что прототип готов, и направь на `/sdx:proto`.

     **Захват baseline попытки.** Выполни дословно (тот же bash-блок используется в `commands/proto.md` шаг 6 — сверен построчно; `<id>` = `<session_id>`, при первом запуске `<N>` = 1):
     ```bash
     sdir=".claude/sessions/<id>"
     # Гард безопасности: путь с переводом строки сделал бы построчный формат неоднозначным.
     n_nul=$(git ls-files --others --exclude-standard -z | tr -dc '\0' | wc -c)
     n_ln=$(git ls-files --others --exclude-standard -z | tr '\0' '\n' | sed '/^$/d' | wc -l)
     if [ "$n_nul" != "$n_ln" ]; then
       echo "SDX proto: среди untracked-файлов есть путь с переводом строки — baseline не может быть записан безопасно." >&2
       exit 1
     fi
     {
       printf '# SDX vibe prototype baseline\n'
       printf 'attempt %s\n' "1"
       printf 'started %s\n' "$(date '+%Y-%m-%d %H:%M:%S')"
       printf 'rev %s\n' "$(git rev-parse HEAD)"
       git ls-files --others --exclude-standard -z | tr '\0' '\n' | sed '/^$/d' | sed 's|^|untracked |'
     } > "$sdir/prototype_baseline.txt"
     git add "$sdir/prototype_baseline.txt" && git commit -m "sdx(<id>): vibe baseline (attempt 1)"
     ```
     Блок совпадает с блоком повторного захвата baseline в `/sdx:proto` (шаг 6) с точностью до номера попытки: здесь это всегда первая попытка (`attempt 1`), там — `<N+1>`. При правке одного блока правь и второй.
     Если гард сработал (путь с переводом строки среди untracked) — baseline НЕ записывается: сообщи пользователю об ошибке и остановись; сессия не переходит к реализации, пока проблемный путь не будет убран/переименован. Это честный отказ, а не тихая деградация к `git clean`.
9. Дальнейшие переходы этапа (`stage`) в рамках сессии выполняются исключительно через `sdx-stage.sh` (`/sdx:next`, включая режим `--to`, и `/sdx:archive`) — здесь, в момент старта, больше писать `[STAGE_CHANGE]` вручную не нужно. Создание артефактов в лог тоже не пиши — вместо этого коммить созданные файлы сессии в ветку инкрементально (их история и состав выводятся из git).
10. Продолжай работу в ЭТОМ ЖЕ CLI — никакого хендоффа нет (ADR-012): ветка `sdx/<session_id>` checkout'нута в основном дереве, enforcement-хуки резолвят активную сессию по имени текущей ветки. Дальнейшие `/sdx:next|checkpoint|verify|archive` выполняются здесь же.

Протокол сессий, профили флоу и контракт закрытия: прочитай (Read) `${CLAUDE_PLUGIN_ROOT}/sdx/protocol.md`
