# DEBT-039. Поле `status` в схеме `session_state.json` объявлено без писателя

## Суть
После закрытия `DEBT-038` (удаление `artifacts`/`history`) в схеме состояния остался третий
случай того же класса: поле `status` объявлено в документации схемы, но `sdx-stage.sh` его не
пишет — ни `cmd_init`, ни `cmd_next`. `cmd_init` создаёт ровно семь ключей, `status` среди них
нет; при этом читатели в прозе команд на него ссылаются («`SPEC.md` подтверждён по смыслу —
`status: approved`», `commands/next.md` шаг 3), то есть у поля есть читатель и нет писателя —
зеркальное отражение `DEBT-038`, где не было ни того, ни другого.

Формально это делает `REQ-STATE-1` («нет полей без писателя и читателя») достигнутым лишь в той
части, что покрывала `DEBT-038`; в общей формулировке требование не выполнено.

## Рекомендация
Решить, чем `status` является, и привести схему в соответствие — оба варианта дёшевы, дорога
только неопределённость:
1. **Убрать из схемы**, а прозаическую проверку «`SPEC.md` подтверждён по смыслу» оставить
   суждением оркестратора, каким она фактически и является (это честнее: поле создаёт видимость
   машинной проверки там, где её нет — ср. `DEBT-007`).
2. **Завести писателя** — тогда назвать, кто и в какой момент его выставляет, и покрыть тестом,
   как покрыт состав ключей `cmd_init` сценарием `[31]` `sdx/hooks/test-sdx-stage.sh`.

Вариант 1 предпочтителен по тому же доводу, каким закрывался `DEBT-038`: заводить писателя под
уже написанное поле означает изобретать потребность задним числом.
