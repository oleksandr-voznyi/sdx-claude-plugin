# FEAT-015. Интероп с мета-оркестратором (МО) в плагинной модели: канал `.mesh/`, хук `exec_paths`, режим `devops`

## Суть
Над стендами систем, разрабатываемых под SDX, появляется мета-оркестратор (МО, `aibok/agentico/meta-orchestrator`).
Принцип разделения — **генотип и фенотип**: репозиторий системы описывает её и о стендах не знает; стенды ведёт МО.
Канал связи — файловый почтовый ящик `.mesh/` в репозитории системы (`endpoint.yaml` узла задаёт, среди прочего,
`exec_paths` — каталоги исполнения стенда, запись в которые допустима только под арендой МО) (вне git, создаёт узел МО командой
`register-endpoint`), конверты с цепью `seq`/`prev`, транспорт у верхней стороны при односторонней видимости.
Протокол и инструменты лист-сессии (`mesh_endpoint.py`, `devagent_hook.py`, `MO-INTEROP.md`) выпущены как
**sim-kit 0.7.3** после разбора ответа SDX: семь находок по 0.7.2 (чтение репозитория узла хуком, порядок проверок
при отсутствии PyYAML, усечение `inbox`, отсутствие авто-`nack`, глаголы записи без различения чтения, неназванная
политика отказа, место переключателя `on_write`) подтверждены по коду и закрыты в 0.7.3.

Записка владельца МО написана из модели «SDX скопирован в репозиторий» (`tools/mo/` в каждом проекте, хук в
`.claude/settings.json`). С ADR-013 плагин живёт иначе, и `MO-INTEROP.md` 0.7.3 уже переписан под плагинную модель:
инструменты — в `${CLAUDE_PLUGIN_ROOT}/sdx/mo/`, в репозитории системы остаётся только `.mesh/`.

## Рекомендация
Одна feature-сессия, после фиксации политики вендоринга (`PROC-028`). Состав поставки — обязательства SDX из
ответа §3, принятые разбором без возражений:

1. **Вендоринг** `sdx/mo/` из sim-kit 0.7.3 (`mesh_endpoint.py`, `devagent_hook.py`, `MO-INTEROP.md`) + файл
   `SIMKIT_VERSION`; в проекты ничего не копируется.
2. **Хук** в `hooks/hooks.json`: `PreToolUse`, matcher `Bash|Write|Edit|MultiEdit|NotebookEdit` →
   **bash-обёртка** `bash "${CLAUDE_PLUGIN_ROOT}/sdx/hooks/mo-hook.sh"`, а не голый `python3`: обёртка выходит
   `exit 0` до любого запуска python, если нет `${CLAUDE_PROJECT_DIR}/.mesh/endpoint.yaml`; при наличии файла и
   отсутствии `python3`/PyYAML воспроизводит политику отказа 0.7.3 сама (`notice` — строка в stderr, `exit 0`;
   `deny` — блок; режим читается `grep`'ом), иначе запускает `python3 …/sdx/mo/devagent_hook.py` **и
   переводит его исход в механизм блокировки SDX**: хук sim-kit блокирует `exit 2` (его конвенция), а протокол
   SDX для PreToolUse требует JSON `permissionDecision: "deny"` на stdout при `exit 0` (`sdx/protocol.md`,
   «Механизм блокировки PreToolUse», подтверждено на бинарнике) — обёртка ловит `exit 2`, печатает JSON с
   `permissionDecisionReason` из stderr хука и завершается `exit 0`. Это вторая причина, по которой обёртка
   обязательна, а не удобство. Так python не становится зависимостью плагина — только проекта под МО (ADR-013:
   хуки безопасны по умолчанию). Код обёртки исполняется из установленной копии (ADR-013), но **активация и режим
   читаются из `.mesh/endpoint.yaml` в рабочем дереве**: удалив или поправив файл, сессия выключит хук или
   ослабит режим. Это свойство модели (фенотип пишет узел, dev-agent его не правит — `MO-INTEROP.md` §0), и
   обнаружение подмены — у узла при следующем `sync`; на стороне SDX обёртка дополнительно отказывает `Write`/`Edit`
   в `.mesh/endpoint.yaml` и `.mesh/cursors.json` (для `Bash`-путей — best-effort, остаток названной границей).
   Поставка хука, правка `.mesh/` и каждое обновление `sdx/mo/` меняют механизм надзора — территория `PROC-020`:
   не в автономном режиме.
3. **`SessionStart`** (`preflight.sh`): при наличии `endpoint.yaml` — `pull`, `inbox --json`, `leases`
   (действующие аренды — чтобы dev-agent видел, можно ли собирать в `build/`); там же проверка
   `python3 -c 'import yaml'` **только когда `.mesh/endpoint.yaml` есть** — зависимость появляется у проекта,
   не у плагина.
   `/sdx:resume` после смерти CLI видит тот же ящик (персистентен).
4. **`.gitignore`**: строка `.mesh/` («почтовый ящик МО — фенотип») в блок targeted-паттернов `/sdx:init`;
   `/sdx:reconcile` доносит до уже инициализированных проектов.
5. **`agents/devops.md`**: переключатель по наличию `.mesh/endpoint.yaml` — деплой и обслуживание стендов
   деактивированы; остаются сборка в рабочем дереве, тесты, упаковка, `artifact.offer`; запрошенный деплой
   превращается в `request` с сообщением об этом. Сегодня п.3 инструкции («выполни деплой») оговорок не имеет.
6. **`claude-md-snippet.md`**: абзац «МО над стендами» (шаблон — `MO-INTEROP.md` §6) в блок `SDX:BEGIN…END`.
7. **Протокол, две нормы:**
   - `directive` от МО в `gate_mode: auto` **никогда не принимается дефолтом**. Среди шести пунктов
     стоп-рубрики (`sdx/protocol.md`, «Стоп-рубрика») внешней просьбы нет, но её покрывает правило для
     неперечисленного: цена отката ошибочно принятой директивы выше цены остановки — остановись. Список
     стоп-рубрики править не нужно — `directive` называется в протоколе примером этого правила. Но триггер
     записи в `decisions_log.md` (`PROC-019`) задан семью тегами, и остановка по правилу для неперечисленного
     ни в один не попадает: `[триаж]` определён как явный акт «принять/отложить сейчас» **по находке**, а
     директива — не находка. Поэтому поставка правит определение триггера: либо расширяет `[триаж]` на внешние
     просьбы, либо вводит отдельный тег — это список тегов журнала, отдельный от стоп-рубрики. Альтернатива без
     остановки —
     откладывать `directive` до ближайшего `interactive`-гейта — тоже допустима, но тогда это должно быть
     сказано явно.
   - Этап `Deployment` под МО завершается **отправкой** `artifact.offer` (и `request`, если нужна операция);
     `msg_id` фиксируется в `change_note.md`/`DESIGN.md` сессии. `rollout.result` приходит асинхронно и является
     входом следующей сессии, не гейтом текущей. Разбор согласился и записал это в `MO-INTEROP.md` §1;
     формальное подтверждение владельцу МО — действие вне бэклога (открытый вопрос 5 в `intake.md` сессии
     `intake-mo-interop-aibok-20261004`).
8. **Граница с `prod-guard`**: при наличии `.mesh/endpoint.yaml` запись в каталоги исполнения делает видимой узлу МО-хук
   (второй PEP, не граница — `MO-INTEROP.md` §4); `prod-guard` остаётся для того, о чём МО не знает (ssh на прод
   и т.п.). Паттерны одного из другого **не выводятся** — это протащило бы фенотип в генотип. Политики отказа
   расходятся осознанно: `prod-guard` — fail-closed только при настроенной защите, без конфига или с пустым —
   no-op (`BUG-002`, `prod-guard.sh`); МО-хук — fail-open в `notice`, fail-closed в `deny`.

**Критерии приёмки** (минимум): в проекте без `.mesh/endpoint.yaml` обёртка завершается до запуска python — ни
stderr, ни `python3` в дереве процессов (проверяемо подменой `python3` на заглушку, которая падает); в проекте
с `endpoint.yaml` и без python3 или PyYAML — одна строка в `notice`, в `deny` — JSON `permissionDecision: "deny"`
на stdout и `exit 0` (не `exit 2`); блок хука sim-kit (`exit 2`) наблюдается снаружи как тот же JSON;
`SessionStart` в проекте с `endpoint.yaml` показывает входящие и аренды; `devops` при наличии `endpoint.yaml` не выполняет деплой, а шлёт
`request`; `directive` в `auto` не исполняется без остановки (форма записи — по выбору п.7). Живая проверка — на репозитории ядра MOVE.IO
(пилот MO-I), где до выпуска плагина стоит ручная установка `tools/mo/`.

## Зависимости и порядок
После `PROC-028` (политика вендоринга — иначе нечем ответить, что делать при следующем выпуске sim-kit).

только форма «очередь входящих + курсор», не предмет), `FEAT-006` (`request` узлу сможет нести класс действия,
когда у SDX появятся классы риска), `IDEA-002` (МО — внешний актор над многими репозиториями, но его предмет —
стенды, а не stateless-задачи по портфелю; пересечение по охвату, не по предмету), `DEBT-031` (L6/L7 для стендов
живут у МО — см. дополнение там).
