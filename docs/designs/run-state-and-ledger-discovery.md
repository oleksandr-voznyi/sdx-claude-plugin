## 1. Что сегодня является состоянием сессии и кто его пишет

`.claude/sessions/<id>/` сегодня несёт:

- **`session_state.json`** — единственный детерминированный писатель `.stage` — CLI-скрипт
  `sdx/hooks/sdx-stage.sh` (`init`/`next`), вызываемый командами через `Bash`, не хук в терминах
  `hooks.json`. Схема (`sdx/protocol.md`): `session_id`, `type`, `stage`, `status`, `gate_mode`,
  `git_branch`, `no_code`, `no_gates`, `artifacts: []`, `history: []`.
  **Находка:** поля `artifacts` и `history` объявлены в схеме, но **нигде не пишутся и не
  читаются** — ни одним хуком, ни одной командой, ни одним агентом (`grep` по `\.history\b`,
  `\.artifacts\b`, `"history"`, `"artifacts"` по `sdx/hooks/*.sh`, `commands/*.md`, `sdx/protocol.md`
  даёт только сами строки объявления схемы). В реальном `session_state.json` этой сессии сейчас
  буквально `"artifacts": [], "history": []` — нетронутые пустые массивы. Это не абстрактный риск,
  а действующий прецедент «машиночитаемое поле без потребителя, спроектированное заранее» — тот же
  класс проблемы, который рамка сессии явно называет причиной вынести класс риска/компенсацию в
  точки расширения вместо полей. Прямое основание для п. 8 ниже.
- **`session.log`** — append-only, четыре прозаические категории (`ADR-005`, «ходы дороже строк»),
  пишет модель своим ходом. `FEAT-004` (вне скоупа) предлагает сменить писателя на хуки; сегодня
  это не так.
- **Эфемерные `.stopgate.*`** (`.stopgate.ok`, `.stopgate.count`, `.stopgate.out`) — пишет
  `sdx/hooks/stop-gate.sh`, гитигнорятся точечным паттерном (`.claude/sessions/*/.stopgate.*`),
  НЕ версионируются ни при каких условиях (REQ-SESS-2). Разобраны подробно в п. 7.
- **`delivery.diff`** — материализованный `git diff` для fresh-eyes ревью, тоже гитигнорится
  (`.claude/sessions/*/delivery.diff`), пересчитывается оркестратором в `/sdx:verify`.

**Инварианты, которые реестр обязан соблюсти** (по `sdx/hooks/archive-verify.sh`, вызывается на
Closeout):
- Инвариант 1: рабочее дерево основной ветки чистое — любой untracked-файл без targeted-паттерна
  `.gitignore` ловится здесь и блокирует Closeout.
- Инвариант 5: ветка `sdx/<id>` доказуемо слита.
- Инвариант 6: каталог сессии отсутствует в дереве основной ветки — то есть удалён коммитом
  `git rm -r` НА ВЕТКЕ до мёржа (вариант A, `ADR-012`).

Все три инварианта параметризованы **каталогом сессии целиком** (`$sdir`), а не именами файлов
внутри него — они уже сегодня одинаково обязывающи для любого нового файла состояния, добавленного
в `.claude/sessions/<id>/`, без единой правки `archive-verify.sh`. Это касается и реестра, если он
физически ляжет в этот каталог (см. п. 5).

**Инвариант, который к реестру НЕ относится напрямую:** REQ-SESS-1 («дисциплина инкрементальных
коммитов», содержательные артефакты сессии tracked и версионируются) — сформулирован для
артефактов типа `SPEC.md`/`DESIGN.md`/`PLAN.md`, естественно нечастых по частоте записи (один
коммит на существенный прогресс). Реестр по конструкции меняется **на каждую транзицию статуса
задачи** — потенциально многократно за один ход агента. Применение той же дисциплины «каждое
изменение коммитится» к реестру либо плодит коммит-шум несопоставимого масштаба с остальными
артефактами сессии, либо требует явного исключения/иной частоты коммитов. Норма не адресует этот
случай явно — это открытый вопрос для Technical Design, а не решённый прецедент.

## 2. `PLAN.md` как он есть: что механизируемо, а что прозаично

Прочитаны `feat-enforcement-selftest-20260901.md` (290 строк, 26+2 сверхплановых задачи),
`feat-audit-agent-20260726.md`, `refactor-tracks-collapse-20260901.md` (34 задачи). Во всех трёх —
устойчивая структура:

**Повторяется механически (кандидаты на поля реестра):**
- ID задачи (`T01`, `T-1` — форма ID уже расходится между планами, не унифицирована);
- тег типа (`[CODE]`/`[TEST]`/`[DOC]`/`[INFRA]`);
- статус чек-бокса `[x]`/`[ ]`;
- ссылка на `REQ-` (трассировка) — обычно инлайн в тексте DoD, не отдельное структурное поле;
- граф зависимостей между задачами — но оформлен как ASCII-диаграмма прозой в отдельном разделе
  «Зависимости между задачами», НЕ как атрибут отдельной задачи;
- итоговый раздел «Покрытие: требование → задачи» — тоже отдельная таблица-проекция, не поле
  задачи.

**Не механизируется, остаётся прозой по существу:**
- Definition of Done — каждая задача формулирует свой DoD текстом, включая для `[TEST]`-задач
  обязательный «красный» сценарий (явное правило: «тест зелёный» без предъявленного красного НЕ
  считается выполнением DoD) — это не булев предикат, а описание конкретной проверки, специфичной
  для задачи.
- «Эффект» задачи (что именно меняется) — по построению прозаичен: список файлов, семантика
  изменения, обоснование конкретных технических решений (пример: T02 требует именно
  `date +%s%N / 1000000`, а не `date +%s%3N`, со ссылкой на подтверждённую несовместимость на
  конкретной машине — это не сериализуется без потери содержания).
- **Ключевая находка о `verify`-команде.** В прочитанных планах НЕТ per-task `verify`-команды в
  смысле «команда, доказывающая именно эту задачу». Тестовый цикл — **один общий** прогон
  (`bash .claude/sdx/verify-cmd.sh`), гоняющий ВСЕ сьюты сразу («сплошной прогон, не выборочный»)
  и общий для всей поставки. DoD части задач (`T01` — `.gitignore`-паттерн, `T26` — документация)
  **явно выведены из-под `verify-cmd.sh`** («не входит в `verify-cmd.sh`, т.к. не является тестом
  кода») и проверяются вручную (`git check-ignore -v ...`) или не проверяются автоматически вовсе.
  Поле «`verify`-команда» на уровне отдельной задачи реестра сегодня почти всегда будет либо (а)
  идентичным для десятков задач одной поставки (тот же `verify-cmd.sh`), либо (б) `N/A`/ручной шаг
  для `[DOC]`/`[INFRA]`-задач. Гранулярность «одна проверяемая команда на одну задачу» не
  подтверждается практикой существующих планов этого репозитория.

**Ответ на вопрос сессии.** Механизируемая часть `PLAN.md` — это по сути то, что сегодня уже
полуструктурировано (`T-`ID, тег, чек-бокс, ссылка на `REQ-`, граф зависимостей) — она реальна, но
тонкая: одна строка на задачу плюс граф. DoD/эффект остаются прозой почти полностью. Это дословно
совпадает с выводом уже существующего дизайн-среза `docs/designs/spec-format-feasibility.md`
(закрывающего `PROC-023`, см. п. 8 ниже): «`PLAN` не формализуется — он **замещается** реестром,
оставаясь человекочитаемой проекцией; его нынешняя полуструктурность — прообраз реестра, а не его
отсутствие».

## 3. Прецедент «источник истины машиночитаем, проза — проекция» — переносится ли механизм

`SDX_STAGE_TABLE` в `sdx/hooks/sdx-stage.sh` работает как источник истины по трём одновременно
необходимым условиям:
1. **Единственный писатель** таблицы — правки скрипта, то есть человек/агент, редактирующий код
   в review-цикле. Не рантайм-запись.
2. **Проекция — статический текст** («Единая шкала этапов» в `sdx/protocol.md`), тоже правится
   вручную, синхронно с таблицей, в рамках одного и того же изменения кода.
3. **Sanity-тест** (`test-sdx-stage.sh`, REQ-TEST-1) сравнивает обе стороны **на момент прогона
   тестов** (CI-время), а не во время выполнения пользовательской сессии — обе стороны неизменны
   между прогонами теста.

Это работает, потому что таблица и её проекция **обе неизменны в рамках одной сессии
пользователя** — расхождение может возникнуть только между релизами плагина, и тест ловит его на
этапе разработки самого фреймворка.

**Реестр задач устроен принципиально иначе:** данные меняются **по ходу прогона**, много раз за
одну сессию, пишутся не человеком в код-ревью, а (потенциально) агентом/хуком в рантайме. Прямой
перенос механизма («реестр — источник истины, `PLAN.md` — проекция, sanity-тест сверяет») не
работает как есть: sanity-тест по построению статичен (сравнивает две фиксированные строки), а
здесь обе стороны — движущаяся цель. Если `PLAN.md` остаётся человекочитаемой проекцией реестра
(как предлагает запись), связка «источник/проекция» держится не тестом, а **живой синхронизацией
на запись** (кто-то/что-то обязано обновлять `PLAN.md` при каждом изменении реестра, либо
`PLAN.md` рендерится реестром по запросу, а не поддерживается вручную). Это не мелкая деталь — это
структурно другой механизм устаревания, и он не покрыт существующим прецедентом. Развилка для
Technical Design.

## 4. Кто будет писателем реестра

Сегодня статус задач ведёт **сам действующий субагент** (`developer`, `agents/developer.md`:
«Зафиксируй изменения: обнови статус в `PLAN.md`... ») — не оркестратор прозой мимо агента, а сам
исполнитель через `Edit`, своим ходом, каждый раз когда решает, что задача завершена. Это дёшево
по инфраструктуре, но ненадёжно и неверифицируемо — ничто не проверяет, что чек-бокс отражает
реальность (тот же класс проблемы, который `ADR-005` называет причиной скудости `session.log`, и
тот же класс проблемы, который `FEAT-004` явно ставит в вину модели-писателю: «агент не может
подтасовать `observed`, не подделав журнал, если журнал пишут хуки»).

Варианты писателя реестра, найденные в коде как прецеденты:

- **Сам агент своим ходом** (статус-кво, аналог сегодняшней записи `PLAN.md`) — дёшево, но
  подделываемо и не даёт `PROC-019` то, что ему нужно (планировщик/kill-test не могут доверять
  самоотчёту исполнителя без независимой верификации).
- **CLI-скрипт по образцу `sdx-stage.sh`** — детерминированный писатель, вызываемый агентом/
  командой через `Bash` (не хук). Плюс: атомарность (`mktemp`+`mv` в той же ФС, как
  `write_stage()`), явная валидация переходов состояний. Минус: агент всё ещё сам решает, КОГДА
  вызвать скрипт (условное честности переносится с «правит ли агент JSON корректно» на «вызывает
  ли агент скрипт вообще») — то же ограничение, что и у статус-кво, просто на один слой ниже.
- **Хук.** Кандидаты событий, реально проводные в этом репозитории сегодня: `PreToolUse` (уже
  используется `prod-guard.sh`/`stage-gate`-класс, даёт `permissionDecision`), `Stop` (уже
  используется `stop-gate.sh`). `PostToolUse`/`SessionEnd`/`PreCompact` **упомянуты в `FEAT-004`
  как допущение из внешнего материала, непроверяемое из репозитория** — `hooks/hooks.json` в этом
  репозитории их не заводит нигде; единственные реально проводные хуки — `PreToolUse`, `Stop`,
  `SessionStart` (self-test, `FEAT-014`). Хук-писатель реестра по образу `stop-gate.sh` мог бы
  засчитывать переход задачи в `done` по факту зелёного `verify` на `Stop` — но, как показано в
  п. 2, `verify-cmd.sh` сегодня **не гранулярен по задаче**, гоняет всё сразу; хук не может
  однозначно определить, КАКАЯ задача из реестра сейчас была закрыта зелёным прогоном, без
  дополнительного протокола (например, явного объявления «сейчас исполняется задача N» до старта
  прогона — то есть агент всё равно пишет что-то до факта, разрывая чистоту схемы).

**Вывод для Technical Design:** ни один вариант не даёт «бесплатной» верификации без изменения
сегодняшнего одно-командного `verify-cmd.sh` в granular per-task форму (что прямо конфликтует с
находкой п. 2 — per-task verify не подтверждается практикой) либо без обязательного протокола
«агент объявляет намерение → хук подтверждает результат» (двухфазная запись, дороже, но честнее).
Решение — на Technical Design, не здесь.

## 5. Контейнер и грядущее переименование

`FEAT-003` говорит «в каталоге прогона»; понятие прогона вводит `PROC-019`, которая сама
опирается на `FEAT-003» («Опирается на `FEAT-003` (реестр) ... — без них восстанавливать
нечего»). Круговая ссылка внутри волны 1 подтверждается по тексту обеих записей.

**Что реально стоит за словом «прогон» сегодня в коде — ничего физического.** `PROC-019` вводит
понятие прогона (run) как оппозицию понятию сессии: «сессия остаётся тем, чем является физически —
одним инстансом CLI; прогон становится тем, что versioned на диске». Ключевое наблюдение: то, что
`PROC-019` называет диском для прогона («versioned на диске», переживающее смерть CLI-процесса),
**уже есть сегодня и называется каталогом сессии** — `.claude/sessions/<id>/` — это git-ветка
`sdx/<id>`, checkout'нутая в основном дереве, с инкрементально коммитящимися артефактами
(`ADR-012`). Она физически переживает убийство CLI уже сейчас (данные лежат в git, не в контексте
модели) — единственное, чего не хватает для kill-test `PROC-019`, это не новый контейнер, а
процедура `/sdx:resume`, реконструирующая **из уже существующего каталога**. Нет находки в коде,
подтверждающей, что «прогон» должен быть отдельным физическим каталогом, отличным от
`.claude/sessions/<id>/` — само `PROC-019` такого не требует явно, а лишь переопределяет понятия.

**Во что реально упирается выбор контейнера, если он всё же станет отдельным каталогом:**
- `.gitignore` — новые targeted-паттерны потребуются, только если новый каталог содержит
  ЭФЕМЕРНЫЕ файлы (по образцу `.stopgate.*`/`delivery.diff`/`.claude/sdx/.cache/`); если реестр
  версионируется как содержательный артефакт (see REQ-SESS-1 логика) — паттерн не нужен, инвариант
  1 `archive-verify.sh` его и так примет как tracked.
- `archive-verify.sh` — инварианты 1/5/6 параметризованы **каталогом сессии целиком** (`$sdir`),
  не отдельными путями внутри. Если новый каталог прогона — ПОДкаталог `.claude/sessions/<id>/`,
  ничего не меняется вовсе (см. п. 1). Если это каталог ВНЕ `.claude/sessions/<id>/` (например,
  параллельный `.claude/runs/<id>/`), инвариант 1/6 не увидит его автоматически — потребуется
  явная правка `archive-verify.sh` (плюс `resolve-session.sh`, если по этому каталогу тоже нужно
  резолвить активность) и Closeout-чек-листа (`sdx/protocol.md`, п.5).
- `resolve-session.sh` — резолвит `sid` **по имени git-ветки** (`sdx/<id>`), не по каталогу.
  Абсолютно не завязан на путь `.claude/sessions/` буквально — эта функция сама по себе устойчива
  к переименованию контейнера. Дешёвая часть.
- Closeout-удаление (`git rm -r .claude/sessions/<id>`, `sdx/protocol.md` п.5 чек-листа) —
  хардкодит путь текстом инструкции; при переносе контейнера потребует правки текста команды
  `/sdx:archive`, но это одна прозаическая правка, не код.

**Рекомендация для Technical Design (не решение, наблюдение):** самый дешёвый путь — трактовать
«каталог прогона» как **тот же `.claude/sessions/<id>/`**, переименование — вопрос словаря
(«прогон» = логическое понятие поверх уже существующего физического контейнера), а не миграции
файловой системы. Любой другой выбор явно платит инфраструктурной ценой, перечисленной выше, ради
терминологической чистоты, которая сама пока не оформлена ни одним принятым ADR — `PROC-019`
открыта (`status: open`), физическая раскладка не зафиксирована нигде.

## 6. Kill-test `PROC-019` — что из реестра реально необходимо

Приёмочный критерий `PROC-019`: убить CLI, запустить с пустым контекстом, `/sdx:resume`
восстанавливает прогон **с диска, без человека и без чтения истории чата**.

Пройдено по полям, предложенным `FEAT-003` (`id`, статус, счётчик попыток, `verify`-команда,
предусловия, эффект):

- **`id` + статус** — необходимы буквально: без них `/sdx:resume` не знает, какие задачи уже
  сделаны, какие в процессе, какие ещё не начаты. Это ядро kill-test.
- **проверяемые предусловия** — необходимы для восстановления БЕЗ человека: агент, воскресший с
  пустым контекстом, обязан уметь заново вычислить «какая задача сейчас runnable», не читая
  историю чата и не спрашивая пользователя, что происходило. Предусловия — единственный
  механический способ дать этот ответ (граф зависимостей, п. 2, служит тем же целям — по сути
  предусловие «задача X» = «задачи Y, Z в статусе done»).
- **эффект** — частично необходим: без описания эффекта агент, восстанавливающий контекст, не
  узнает, ЧТО должна была сделать незавершённая задача, и рискует либо повторить работу, либо
  пропустить её незавершённой. Но природа поля прозаична (п. 2) — вопрос для Technical Design в
  том, достаточно ли ссылки на исходный текст задачи `PLAN.md`/`SPEC.md` вместо дублирования
  эффекта в реестре.
- **`verify`-команда** — необходима для восстановления доверия к статусу `done`: без неё
  `/sdx:resume` обязан верить чек-боксу без независимой проверки — то же самое доверие-без-
  верификации, которое сегодня и есть проблема (п. 4). Но, как показано в п. 2, granular per-task
  verify не подтверждён практикой репозитория — велик риск, что поле окажется одинаковой строкой
  `bash .claude/sdx/verify-cmd.sh` почти у каждой задачи, что даёт restart-сценарию МЕНЬШЕ
  гранулярности, чем кажется на бумаге: перезапуск не может доказать «задача N сделана», может
  только доказать «дерево в целом зелёное».
- **счётчик попыток** — необходим для решения «эскалировать в HITL или пробовать снова» ПОСЛЕ
  restart без участия человека — иначе restart сбрасывает историю ретраев и превращает
  предохранитель `FEAT-003` («N попыток, на N+1 — эскалация») в вечный цикл N попыток на каждый
  новый CLI-инстанс. Прямое следствие п. 7 ниже.

**Вывод:** пять из шести названных полей проходят kill-test как необходимые буквально (не
избыточные); `verify`-команда проходит с оговоркой — её полезность для kill-test упирается в ту же
проблему гранулярности, что и для писателя (п. 4). Рамка сессии не называет поле, отсутствие
которого сломало бы kill-test — критических пропусков в предложенной минимальной схеме не найдено.

## 7. Идемпотентность и ретраи — что уже проявляется в коде

`.stopgate.count` — работающий, но **сессионный** (не задачный) прецедент: loop-guard в
`stop-gate.sh` считает подряд идущие КРАСНЫЕ прогоны ЕДИНОГО `verify-cmd.sh` на весь Stop-гейт
сессии («после 3 попыток — возврат человеку»), сбрасывается на первом зелёном прогоне. Он НЕ
считает попытки конкретной задачи — он не знает о задачах вообще, оперирует только состоянием
дерева (`git rev-parse HEAD` + хэш `git status --porcelain`).

Здесь же — рабочий прецедент идемпотентности по факту, не по гарантии: green-run cache
(`.stopgate.ok`, отпечаток = HEAD + хэш porcelain-статуса). Повторный `Stop` на неизменном дереве
не перезапускает `verify` — это ровно форма «идемпотентности по договорённости», о которой
`FEAT-003` пишет в разделе «Границы»: движок не гарантирует exactly-once исполнения самой
проверки, но избегает повторной работы там, где состояние доказуемо не изменилось.

**Следствие для схемы реестра:** счётчик попыток задачи — НОВАЯ единица учёта, для которой в
репозитории пока нет прямого прецедента (существующий счётчик — на уровень выше, про сессию
целиком, а не про отдельную задачу). Технический дизайн должен решить это заново, а не
переиспользовать `.stopgate.count` буквально; максимум — заимствовать форму (файл-счётчик,
инкремент/сброс по фингерпринту), не сам счётчик.

## 8. Стоимость и риск отказа

**Реестр — новый файл состояния**, живущий в каталоге, который удаляется на Closeout (Closeout
чек-лист п.5, `git rm -r`) и версионируется инкрементально на ветке `sdx/<id>` (если не
исключён точечным `.gitignore`-паттерном по аналогии с `.stopgate.*`).

**Прецедент дорогого расхождения уже есть в этом же файле состояния.** `artifacts`/`history` в
`session_state.json` — поля, спроектированные заранее без активного потребителя, сегодня мёртвые
(п. 1). Это прямое, уже случившееся воплощение риска «второй `session_state.json` с теми же
проблемами»: минимальная схема `FEAT-003` намеренно защищается от ЭТОГО риска, исключая класс
риска/компенсацию как поля до появления потребителя (`FEAT-006`/`FEAT-008`) — но тот же принцип
стоит применить и к вопросу «а есть ли у `verify`-команды и `эффекта` реальный потребитель СЕГОДНЯ»,
не только у отложенных полей (см. честную оценку ниже).

**Кто прав при рассогласовании реестра и `PLAN.md`.** Запись предполагает «реестр — источник
истины, `PLAN.md` — проза-проекция» по аналогии с `SDX_STAGE_TABLE`. Но, как показано в п. 3, эта
аналогия структурно не переносится один в один (движущиеся данные, не статичный код). Если
`PLAN.md` не поддерживается синхронизацией на запись (рендер из реестра либо принудительная
регенерация), реестр и `PLAN.md` разойдутся так же, как сегодня расходятся требования спек и их
производные (см. независимо найденную метрику в `docs/designs/spec-format-feasibility.md`: 52 из
120 требований `REQ-` не упомянуты ни одним производным артефактом репозитория — тот же класс
дрейфа «источник объявлен, проекция не поддерживается»). Кто прав в момент расхождения —
открытый вопрос для Technical Design; аналогия со скриптом сама по себе ответа не даёт, потому что
там расхождение НЕВОЗМОЖНО между прогонами (проекция читается только вручную, при разработке
фреймворка), а не потому что есть арбитраж «кто прав».

## Расхождения записей бэклога с фактическим кодом

1. **`FEAT-003` ссылается на устаревшее имя конструкции.** Текст записи («тот же паттерн ...
   уже применён к `SDX_STAGE_MATRIX`») использует имя, которое было переименовано в
   `SDX_STAGE_TABLE` рефакторингом `refactor-tracks-collapse-20260901` (`ADR-020`), — сессия,
   более поздняя, чем источник `FEAT-003` (`intake sdx-runtime-rethink-20260830`). Записи об этом
   переименовании не последовало. Смысл аналогии не страдает (структура прецедента та же), но
   буквальная ссылка сейчас не резолвится ни в одном файле кода — только в исторических
   документах и `DECISIONS.md`.
2. **Круговая ссылка `FEAT-003` ↔ `PROC-019` на контейнер** (уже разобрана в п. 5) — не столько
   ошибка, сколько незакрытый вопрос: обе записи предполагают существование понятия «прогон» друг
   у друга, но ни одна не фиксирует его физическую раскладку. Технический дизайн обязан либо
   закрыть это здесь, либо явно передать вопрос в будущую сессию `PROC-019`.
3. **`PLAN.md` не «прозаический» в том смысле, в каком его описывает `FEAT-003`** («`PLAN.md` —
   проза») — на практике планы репозитория уже полуструктурированы (`T-`ID, теги типов, ссылки
   `REQ-`, разделы «Зависимости»/«Покрытие»), что подтверждается и независимо проведённым срезом
   `docs/designs/spec-format-feasibility.md`. Формулировка записи упрощает состояние сильнее, чем
   оно есть — не критично для решения, но стоит явно назвать на Technical Design, чтобы не
   спроектировать реестр так, будто он замещает голую прозу, а не уже частично структурированный
   документ.

## Развилки, требующие решения на Technical Design

1. **Механизм связи «реестр ↔ `PLAN.md`-проекция».** Живая синхронизация на запись (реестр
   рендерит `PLAN.md`) vs ручная поддержка человеком/агентом (риск дрейфа, как у `REQ-`
   покрытия) vs отказ от идеи проекции вовсе (реестр — единственный источник, `PLAN.md` умирает
   как артефакт или становится чисто вводным описанием без статусов). Прецедент
   `SDX_STAGE_TABLE`/протокол НЕ даёт готового ответа (п. 3).
2. **Писатель реестра.** Сам агент (дёшево, неверифицируемо) vs CLI-скрипт по образцу
   `sdx-stage.sh` (детерминированная запись, но агент всё ещё решает, когда её вызвать) vs
   хук на `Stop`/`PreToolUse` (верифицируемо, но требует решения проблемы гранулярности `verify`,
   п. 2/4) vs двухфазный протокол «намерение → подтверждение». Ни один вариант не бесплатен.
3. **Гранулярность `verify`-команды.** Оставить общий `verify-cmd.sh` на всю сессию (тогда поле
   почти не отличает задачи друг от друга) vs потребовать per-task granular verify (тогда план
   репозитория придётся писать иначе, чем пишется сегодня — сдвиг практики, не только схемы).
4. **Физический контейнер реестра.** Подкаталог существующего `.claude/sessions/<id>/` (дёшево,
   инварианты 1/5/6 не меняются) vs новый отдельный каталог «прогона» (правки `archive-verify.sh`,
   `.gitignore`, Closeout-текста, возможно `resolve-session.sh`) — см. п. 5.
5. **Счётчик попыток задачи vs счётчик попыток сессии.** Нужна ли отдельная задачная единица учёта
   при живом сессионном loop-guard (`.stopgate.count`), и как они соотносятся, если задача
   эскалирует в HITL, а сессионный loop-guard параллельно тоже считает красные прогоны того же
   `verify-cmd.sh` (риск двойного срабатывания предохранителя на одном и том же событии).
6. **Частота коммитов реестра.** Реестр меняется чаще, чем типичный сессионный артефакт —
   коммитить на КАЖДОЕ изменение статуса задачи (шум, но чистая история) vs батчить (проще, но
   создаёт окно, где diff и `git log` не отражают реальный прогресс — а именно `git log --stat`
   сегодня официальный способ узнавать историю артефактов сессии, `sdx/protocol.md` строка 126).

## Риски/ограничения, которые дизайн обязан назвать явно

- **Exactly-once недостижим** (граница из самой записи `FEAT-003`) — реестр не должен формулировать
  свои гарантии сильнее, чем «идемпотентность по договорённости в контракте задачи», иначе
  повторяет ошибку, которую собственный текст записи прямо запрещает («не выдавать за
  проверенное»).
- **Риск построить второй мёртвый `session_state.json`.** Прецедент `artifacts`/`history` (п. 1, 8)
  — конкретное, не гипотетическое основание отнестись серьёзно к вопросу «кто СЕГОДНЯ читает
  `verify`-команду и `эффект» помимо будущего непостроенного `PROC-019`».
- **`PLAN.md`-проекция как источник дрейфа**, если не поддержана механизмом синхронизации на
  запись — тот же класс проблемы, что и измеренный дрейф `REQ-` покрытия в
  `spec-format-feasibility.md` (52/120 без ссылки).
- **Двойной loop-guard.** Сессионный (`.stopgate.count`) и задачный (предлагаемый реестром) могут
  сработать на одном и том же красном прогоне общего `verify-cmd.sh`, если задачный ретрай тоже
  опирается на его результат — не названо явно нигде.
- **Норма REQ-SESS-1 не адресует высокочастотную запись** (п. 1, последний абзац) — реестр меняется
  на порядок чаще типичного артефакта сессии, для которого норма писалась.

## Окупаемость минимального реестра сегодня — честная оценка

Основания усомниться, что минимальный реестр окупается прямо сейчас, есть, и они не тривиальны:

1. **Единственный обозначенный потребитель (`PROC-019`) сам ещё не спроектирован** — открыта
   (`status: open`), не имеет `DESIGN.md`, физическая модель «прогона» не зафиксирована нигде
   (п. 5). Реестр проектируется под контракт, автора которого предстоит написать позже — обратная
   ситуация тому, что обычно проектируется сначала (сначала известен потребитель, потом контракт
   под него). Сама запись `FEAT-003` признаёт этот риск на своём примере («предыдущая сессия волны
   показала, чего стоит проектировать под отсутствующего потребителя») — и именно поэтому вывела
   класс риска/компенсацию в точки расширения. Но `verify`-команда и, отчасти, `эффект» находятся
   в ровно том же положении относительно `PROC-019` — они нужны в первую очередь ЕМУ (kill-test,
   п. 6), а не текущему коду. `id`/статус/предусловия ближе к текущей пользе (наблюдаемость
   прогресса без интерпретации прозы), но и они не имеют сегодня работающего читателя-планировщика
   (`FEAT-005`, вне скоупа этой сессии, волна 3).
2. **Механизируемая часть `PLAN.md` тонка** (п. 2) — по факту это уже почти то, что даёт реестр
   (ID, тег, статус, ссылка на REQ, граф зависимостей), плюс прозаический DoD/эффект, которые
   реестр либо дублирует текстом (без выигрыша структуры), либо не несёт вовсе (тогда он
   недостаточен как «единственный источник истины» для восстановления, п. 6). Разрыв между
   «сегодняшним полуструктурированным `PLAN.md`» и «полноценным реестром» уже сейчас закрыт
   независимым дизайн-срезом `docs/designs/spec-format-feasibility.md` — с прямым выводом «кандидат
   с названными пробелами, а не готовый вклад».
3. **Аналогия с `SDX_STAGE_TABLE`, на которую опирается сама рекомендация записи, структурно не
   переносится** (п. 3) — обосновывающий прецедент слабее, чем текст записи предполагает.
4. **С другой стороны** — `verify`-команда/предусловия/счётчик попыток нужны буквально для
   kill-test (п. 6), а kill-test — заявленный приёмочный критерий ВСЕЙ волны 1 (`PROC-019`:
   «Kill-test является приёмочным критерием для всей волны 1»). Если волна 1 признаётся ценной
   как целое (решение вне полномочий этого отчёта), реестр — предпосылка, без которой не из чего
   собирать `/sdx:resume`, и откладывать его — откладывать всю волну.

Решение, стоит ли строить минимальный реестр сейчас или дождаться, пока `PROC-019` определит
физическую модель прогона и конкретный контракт читателя, — не мой вызов; но основания для
сомнения реальны и не должны замалчиваться перед Technical Design.
