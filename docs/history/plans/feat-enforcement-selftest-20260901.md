## Чек-лист задач

Каждая задача несёт трассировку на `REQ-` в скобках. Для `[TEST]`-задач DoD сформулирован в форме
«тест зелёный И показано, что при <конкретная поломка> он краснеет» — формулировка «тест зелёный»
без предъявленного красного сценария НЕ считается выполнением DoD.

### Группа 1 — `sdx/hooks/selftest.sh`, ядро (CODE)

Реализуется строго по псевдокоду `DESIGN.md` («Псевдокод / структура `sdx/hooks/selftest.sh`»).
Каждая CODE-задача — самостоятельный, изолированно читаемый блок скрипта (≤30 строк).

- [x] **T02 [CODE]** Скелет + resolution путей + `now_ns()` + функции отпечатка
  (`plugin_version`, `file_component`, `compute_fingerprint`, `cached_fingerprint`). Использовать
  ИМЕННО `date +%s%N` с делением на `1000000` (НЕ `date +%s%3N` — см. DESIGN.md, развилка 4,
  подтверждённая на этой машине несовместимость). DoD: заголовочный комментарий файла явно
  фиксирует периметр self-test (три хука, `sdx-stage.sh` и `test-hook-wiring.sh` вне периметра —
  REQ-ST-1) и границу BUG-008 (REQ-LIMIT-1) — как в псевдокоде DESIGN.md, не переформулировать
  слабее. Никакого `jq` в этой функции (REQ-ST-10).
- [x] **T03 [CODE]** `write_cache()` — атомарная запись (`mktemp` + `mv` в той же ФС, best-effort:
  `mkdir -p ... || return 0`, `mktemp ... || return 0`) и итоговый формат `selftest.json` строго
  по схеме DESIGN.md (`schema/ts/fingerprint/selftest_status/preflight/prod_guard/stop_gate/
  duration_ms/budget_ms/budget_exceeded`). Никакого `jq`, только `printf` (REQ-ST-10). Зависит от
  T02 (использует `compute_fingerprint`/бюджет).
- [x] **T04 [CODE]** `probe_preflight()` — только факт `exit 0`, без инъекции состояния (REQ-ST-2).
  DoD включает комментарий в коде, дословно фиксирующий, что эта проба доказывает «скрипт
  исполнился и вернул 0», а не «предупреждение о `jq` сработало бы».
- [x] **T05 [CODE]** `probe_prod_guard()` — два вызова (deny-паттерн / непаттерновая команда) в
  изолированном `mktemp -d`-фикстуре со своим `CLAUDE_PROJECT_DIR`; сравнение по подстроке
  `"permissionDecision":"deny"` и по пустоте `out2` (REQ-ST-2, REQ-ST-5). Никакого `jq`. Зависит
  от T02 (использует `hooks_dir`).
- [x] **T06 [CODE]** `probe_stop_gate()` — изолированный `git init -q && git checkout -q -b
  sdx/selftest` БЕЗ коммита, синтетический `session_state.json` (`stage=Execution`),
  `verify-cmd.sh` в режиме `0600` с телом `exit 1` (форма `DEBT-026`), сравнение `$? -eq 2`
  (REQ-ST-3, REQ-ST-5, REQ-ST-6). Явная проверка кодов возврата `git init`/`checkout` → `skip`
  при сбое. Зависит от T02.
- [x] **T07 [CODE]** `main()` — кэш-хит по отпечатку (обход через `SDX_SELFTEST_FORCE=1`), замер
  `t0`/`t1`/`dur`, вызов трёх проб, классификация `overall` (`ok`/`degraded`/`broken` по
  `case "$r_pf $r_pg $r_sg" in *skip*) broken;; *fail*) degraded;; esac`), запись кэша, условные
  сообщения в stderr (только при `degraded`/`broken`/`budget_exceeded`, полная тишина при
  здоровом прогоне), плюс `main || write_cache broken skip skip skip ...` и финальный безусловный
  `exit 0`. Зависит от T02–T06 (использует все функции).
- [x] **T08 [INFRA]** `hooks/hooks.json` — новая независимая запись `SessionStart`:
  `timeout 10 bash "${CLAUDE_PLUGIN_ROOT}"/sdx/hooks/selftest.sh; exit 0`, ПОСЛЕ существующей
  записи `preflight.sh` (порядок значим — см. DESIGN.md «Проводка»); запись `preflight.sh` не

  изменены. Зависит от T02 (файл `selftest.sh` должен существовать на диске для последующей T09).

## Ограничение среды исполнения (`${CLAUDE_PLUGIN_ROOT}`)

Команды `/sdx:*` и хуки в реальном Claude Code резолвятся из установленной копии плагина, не из
рабочего дерева этой сессии — правки `sdx/hooks/selftest.sh`/`hooks/hooks.json` в этой сессии НЕ
повлияют на поведение реально исполняемого `SessionStart`, пока не будет `/plugin marketplace
update sdx`. План намеренно не пытается это обойти. Доказательство работоспособности нового
скрипта в условиях ЭТОЙ сессии даёт **исключительно прямой вызов** `bash sdx/hooks/selftest.sh`
из рабочего дерева тем же паттерном, что и все существующие `test-*.sh` (T09–T21, T25) — минуя
`hooks.json`/`${CLAUDE_PLUGIN_ROOT}`/установленную копию плагина полностью. Проверка ЖИВОЙ
проводки (`hooks.json` → установленная копия → реальный `SessionStart`) остаётся вне периметра
Verification этой сессии и доступна только после `marketplace update` — зафиксированное
ограничение среды (DESIGN.md), не задача этого плана.

## Тестовый цикл

Всё прогоняется одной командой из корня репозитория:

```bash
bash .claude/sdx/verify-cmd.sh
```

Она глобит `sdx/hooks/test-*.sh` (включая новый `test-selftest.sh`, без отдельной проводки) и
требует, чтобы КАЖДЫЙ сьют завершился `PASS`. Зелёным на выходе этой поставки считается:

- `bash sdx/hooks/test-selftest.sh` — все сценарии T09–T21, T25 зелёные (включая явно
  предъявленные красные ветки внутри самих сценариев — тест на T09–T21 логически состоит из пары
  прогонов «зелёный/красный» внутри одного файла, а не из отдельного файла на цвет);
- `bash sdx/hooks/test-hook-wiring.sh` — сценарии `[1]`–`[4]` зелёные С учётом новой записи
  `SessionStart` (T22);
- остальные существующие `test-*.sh` (`test-prod-guard.sh`, `test-stop-gate.sh`,
  `test-preflight`-покрытие внутри других сьютов, `test-sdx-stage.sh`,
  `test-integration-stage-lifecycle.sh`, `test-default-branch.sh`, `test-resolve-session.sh`,
  `test-archive-verify.sh`) остаются зелёными БЕЗ РЕГРЕССИЙ — ни один из них не трогается кодом
  этой поставки, но `verify-cmd.sh` всё равно перепрогоняет их все на каждом вызове (сплошной
  прогон, не выборочный);
- `Summary: N/N suites passed` в хвосте вывода, `exit 0` от `verify-cmd.sh`.

Отдельно от `verify-cmd.sh` (не автоматизируется в дев-сьюте, см. T24): ручная QA-проверка
`/sdx:status` — вызов вживую в CLI-сессии, подтверждение блока здоровья и отсутствия побочных
эффектов, зафиксированная как шаг Verification этой сессии.

`.gitignore`-паттерн (T01) проверяется вручную (`git check-ignore`) — не входит в
`verify-cmd.sh`, т.к. не является тестом кода.
