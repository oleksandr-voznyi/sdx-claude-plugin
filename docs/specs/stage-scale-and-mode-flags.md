# Business Specification: Треки → одна шкала этапов + два режима-флага

## Контекст и Цели

Сегодня SDX масштабирует церемонию через пять треков (`patch`/`standard`/`full`/`doc`/`vibe`),
каждый — свой набор имён этапов, зашитых в `SDX_STAGE_MATRIX` (`sdx/hooks/sdx-stage.sh`) и
защищённых машинерией `/sdx:retrack`, `/sdx:backtrack`, evidence-based forward-skip guard,
`stage-write-guard.sh`. `PROC-012`/`PROC-013` (`docs/backlog/`) фиксируют структурный аргумент:
десять записей бэклога простаивают именно из-за формы этой машинерии, а не из-за отдельных
дефектов в ней — снос предмета закрывает их без единой сессии починки.

Цель этой поставки — заменить «пять треков» на **одну линейную шкалу этапов с опциональными
артефактами** плюс **два ортогональных режима-флага** («без кода», «без гейтов»), убрав саму
форму данных, которая порождала находки. Одновременно: `stage-gate.sh` и `stage-write-guard.sh`
(enforcement порядка процесса — класс, который `PROC-013` считает избыточным для современной
модели) снимаются целиком; `prod-guard.sh`, `stop-gate.sh`, `archive-verify.sh` (enforcement
необратимого) не трогаются вовсе — граница проведена намеренно и это не побочный эффект.

Снятие `stage-gate`/`stage-write-guard` открывает окно: до появления модели полномочий по классу
риска (`FEAT-006`, отдельная будущая сессия) часть сегодняшних механических гарантий заменяется
дисциплиной оркестратора. Пользователь принял это окно осознанно (см. «Риски и Ограничения» и
`REQ-ENF-1`) — задача этой спеки сделать содержимое окна видимым, а не подразумеваемым.

Легализация экстремального прототипирования (`vibe`/`proto`) остаётся: инвариант «нельзя закрыть
сессию без легализации» (ADR-018) сохраняется, но выражается не отсутствием строки в
трек-параметризованной матрице (эта форма данных уходит), а приоритетным детерминированным
правилом над флагом `no_gates` — см. `REQ-LEGAL-1`.

## Требования

### Единая шкала этапов (REQ-SCALE)

- **[ADDED] REQ-SCALE-1.** Один канонический, не зависящий от типа/флагов сессии порядок имён
  этапов для ЛЮБОЙ SDX-сессии: `Discovery → Business Spec → Technical Design → Task Planning →
  Execution → Documentation → Verification → Deployment → Closeout`. Это уже сегодняшний список
  трека `full` (и уже сегодняшний список в `CLAUDE.md` §3 «Этапы (Stages)») — он становится
  единственным словарём имён. Имена `Change` (patch/standard), `Update` (doc), `Prototype` (vibe)
  выводятся из словаря этапов: они не появляются как `stage` ни у одной новой сессии.

- **[ADDED] REQ-SCALE-2.** Активность этапа для конкретной сессии определяется двумя независимыми
  факторами, применяемыми в порядке приоритета:
  1. **Флаги** (`no_code`, `no_gates`) — детерминированные правила (`REQ-SCALE-4`, `REQ-SCALE-5`),
     которые могут только СУЖАТЬ активный набор, никогда не расширять его сверх того, что
     определил бы объём дельты.
  2. **Объём дельты** — прозаическое суждение оркестратора, пересматриваемое на каждом гейте
     (`/sdx:next`), заменяющее сегодняшний триаж трека на `/sdx:start` и scope-check ADR-001.
     Минимально необходимый активный набор для любой сессии — `Execution → Verification →
     Closeout` (сегодняшний эквивалент `patch`).

- **[ADDED] REQ-SCALE-3.** Когда `Business Spec`/`Technical Design` не активны как отдельные этапы
  (малая дельта), их содержательное решение фиксируется слитно в `change_note.md` — сегодняшнее
  правило `patch`/`standard` (ADR-003) становится единственным правилом для любой сессии с такой
  дельтой, без зависимости от бывшего поля `track`.

- **[ADDED] REQ-SCALE-4.** `no_code == true` безусловно исключает из активного набора `Execution`,
  `Task Planning`, `Documentation`, `Deployment` — независимо от объёма дельты (замена трека
  `doc`, ADR-017). Планировать и исполнять нечего без кода; `Business Spec`/`Technical Design`
  (или их свёртка в `change_note.md` по `REQ-SCALE-3`) остаются активны — это ровно то место,
  где сегодня живёт этап `Update`.

- **[ADDED] REQ-SCALE-5.** `no_gates == true` безусловно ограничивает активный набор до `{Execution}`
  — единственного этапа — независимо от объёма дельты (замена трека `vibe`, ADR-018), пока флаг не
  снят легализацией (`REQ-LEGAL-1`).

- **[ADDED] REQ-SCALE-6.** `Documentation` активен только если дельта производит производные
  документы (Swagger/README/мануалы); `Deployment` активен только если дельта затрагивает
  инфраструктуру/конфиги деплоя. Правило генерализует сегодняшнюю практику «только у `full`» на
  любую сессию — определяется объёмом дельты (`REQ-SCALE-2.2`), не флагом.

- **[ADDED] REQ-SCALE-7.** `Verification` и `Closeout` активны ВСЕГДА для любой сессии, независимо
  от объёма дельты и от `no_code`, — за единственным временным исключением: пока `no_gates ==
  true`, `REQ-SCALE-5` временно перекрывает и их (см. `REQ-LEGAL-1`). Это генерализация
  сегодняшней «обязательной лёгкой верификации» (ADR-014 для `patch`, ADR-017 для `doc`) на все
  сессии без исключения — устраняет саму почву для `DEBT-009` (Discovery на `standard` без
  определённого артефакта, тот же класс неоднородности).

- **[ADDED] REQ-SCALE-8.** Глубина `Verification` (объём fresh-eyes ревью, вызывается ли `qa`)
  определяется тем же критерием объёма дельты, что и активность `Business Spec`/`Technical
  Design` (`REQ-SCALE-2.2`), а не отдельным правилом на бывший трек. При `no_code == true` `qa`
  не вызывается вовсе (нет кода для регрессионного прогона) — сегодняшнее поведение `doc`,
  обобщённое на флаг. Рубрика трёх осей (полнота/корректность/когерентность, ADR-004) и контракт
  изоляции `reviewer` этой поставкой не пересматриваются.

- **[ADDED] REQ-SCALE-9.** Оркестратор на каждом гейте (`/sdx:next`) переоценивает активный набор
  этапов по факту открывшегося объёма работы — замена «scope-check → предложи `/sdx:retrack`»
  (ADR-001, второй инвариант). Если по ходу выясняется, что нужен ранее неактивный этап (например,
  `Business Spec` для сессии, начатой как минимальная правка), оркестратор активирует его через
  навигационный механизм `REQ-NAV-1`; активность этапа не хранится отдельным полем состояния —
  вычисляется заново при каждом переходе.

### Два режима-флага (REQ-FLAG)

- **[ADDED] REQ-FLAG-1.** Схема `session_state.json`: поле `track` удаляется. Добавляются два
  булевых поля верхнего уровня — `no_code` и `no_gates`, оба по умолчанию `false`, записываются
  `sdx-stage.sh init` при создании сессии.

- **[ADDED] REQ-FLAG-2.** Жёсткая привязка на `/sdx:start`, без диалога о выборе (по прецеденту
  ADR-017/ADR-018): `type ∈ {grooming, retro, postmortem, intake, audit} → no_code = true`
  безусловно; `type == proto → no_gates = true` безусловно. Для остальных типов (`feature`, `bug`,
  `refactor`, `import`) оба флага стартуют `false`, а активный набор этапов — гипотеза,
  пересматриваемая по ходу (`REQ-SCALE-9`).

- **[ADDED] REQ-FLAG-3.** Флаги несовместимы одновременно: `no_code = true` и `no_gates = true` в
  одной сессии запрещены. Обоснование — предмет `no_gates` (`vibe`) специфично про код («один
  промпт без церемонии» с кодом на выходе), а `no_code` по определению исключает код: сочетание
  бессмысленно по содержанию задачи, не только по механике. `sdx-stage.sh init` отказывает при
  попытке установить оба флага сразу; попытка включить `no_gates` для сессии с `no_code = true`
  (или наоборот) на любом более позднем шаге запрещена тем же правилом.

- **[ADDED] REQ-FLAG-4.** `no_gates` — одноразовый в рамках сессии: после снятия флага (легализация,
  `REQ-LEGAL-1`/`REQ-LEGAL-2`) повторная установка `no_gates = true` в этой же сессии запрещена.
  `no_code`, напротив, может быть снят по ходу сессии при эскалации объёма (симметрично сегодняшней
  эскалации `doc → {patch,standard,full}`, ADR-017); обратная установка `no_code: false → true`
  посреди уже идущей сессии запрещена (симметрично сегодняшнему запрету деэскалации в `doc`).

### Инвариант легализации прототипа (REQ-LEGAL)

- **[ADDED] REQ-LEGAL-1.** Инвариант ADR-018 «сессия с активным прототипированием не может достичь
  `Closeout` без легализации» сохраняется МЕХАНИЧЕСКИ, не только прозой. Замена enforcement'а
  «отсутствием строки в матрице трека»: вычисление активного набора этапов обязано применять
  `no_gates == true → {Execution}` (`REQ-SCALE-5`) КАК ПЕРВОЕ, приоритетное условие — раньше
  любой другой логики набора активных этапов, включая `REQ-SCALE-7`. Пока флаг не снят,
  `Closeout` (и любой другой этап) физически не входит в активный набор ни для какого вызова
  `/sdx:next` — это то же свойство «нет пути», что и сегодня, выраженное условием над флагом
  вместо отсутствующей строки трек-параметризованной матрицы; детерминизм не ослабляется.

- **[ADDED] REQ-LEGAL-2.** Логика spec-after реверс-инжиниринга прототипа (сегодня —
  `commands/retrack.md`, шаг 3, «Легализация из `vibe`», ~120 строк: вычисление диффа от
  `prototype_baseline.txt`, реверс-инжиниринг требований ДО коммитов через `ba`/`architect`
  (и, при целевом объёме `full`, дополнительно `lead-dev`), коммит кода прототипа первым,
  коммит артефактов вторым, обязательная пост-проверка состоявшегося коммита) переносится ЦЕЛИКОМ,
  без потери содержания, в `commands/proto.md`, ветку «Принять» (сегодня она лишь ссылается на
  `retrack.md`). Понятие «целевой трек легализации» (`standard`/`full`) заменяется на «целевой
  объём последующей работы»: то же прозаическое решение пользователя («полный цикл» vs «лёгкий
  проход»), формулируемое и рекомендуемое тем же критерием, что и сегодня (задет ли контракт/
  архитектура/схема данных, крупный ли дифф) — управляет тем, какие этапы (`Business Spec`,
  `Technical Design`, `Task Planning`) активируются для сессии после легализации, а не выбором
  из перечня треков.

- **[ADDED] REQ-LEGAL-3.** Вход в `no_gates` разрешён ИСКЛЮЧИТЕЛЬНО как стартовая точка сессии
  типа `proto` через `/sdx:start proto "<цель>"` — вход `{no_code=false/true, no_gates=false} →
  no_gates=true` посреди уже идущей сессии запрещён прозаически (тот же класс принятого
  trade-off, что и сегодняшний запрет `{patch,standard,full,doc} → vibe`, не enforced хуком).

- **[ADDED] REQ-LEGAL-4.** `DEBT-023` («`/sdx:proto` не показывает содержимое новых файлов на
  шаге предъявления результата») этой поставкой НЕ закрывается автоматически: перенос гейта
  принятия/отклонения с условия «`track == vibe`» на условие «`no_gates == true`» не меняет
  поведение шага предъявления диффа (список путей + число строк, не содержимое) — дефект
  независим от формы хранения режима и остаётся открытым в `docs/backlog/`.

### Совместимость с сессиями, начатыми до сноса (REQ-COMPAT)

- **[ADDED] REQ-COMPAT-1.** Новый `sdx-stage.sh` и все команды `/sdx:*` толерантны к наличию
  legacy-поля `track` в `session_state.json` уже существующих сессий: поле не читается, не
  требуется, не проверяется, но и не удаляется проактивно (JSON терпит лишние ключи). Ошибки
  парсинга/отказа из-за одного лишь присутствия `track` быть не должно.

- **[ADDED] REQ-COMPAT-2.** Сессии, чей текущий `stage` уже совпадает с одним из девяти
  канонических имён (`REQ-SCALE-1|`) — сегодня это исключительно сессии бывшего трека `full`, в
  частности ЭТА сессия (`stage: "Business Spec"`) — продолжают работу без единого ручного шага:
  `no_code`/`no_gates` трактуются как отсутствующие ⇒ `false`/`false`, дальнейшие переходы идут
  по новому механизму как обычно.

- **[ADDED] REQ-COMPAT-3.** Сессии, чей `stage` использует имя, выводимое из словаря этой
  поставкой (`Change` — бывшие patch/standard, `Update` — бывший doc, `Prototype` — бывший
  vibe), автоматическим переходом не поддерживаются: перед `Closeout` этой сессии оркестратор
  обязан просканировать `.claude/sessions/*/session_state.json` на предмет таких `stage`-значений.
  Если такие сессии обнаружены — они получают одноразовый ручной перенос (`Change`/`Update` →
  `Execution` с сохранением уже накопленного `change_note.md` как доказательства; `Prototype` →
  `Execution` + `no_gates: true`) до слияния этой сессии в основную ветку; если не обнаружены —
  пункт закрывается как неприменимый, но проверка обязательна в любом случае (репозиторий не
  должен остаться с сессией в нераспознаваемом `stage`).

### Возврат на более ранний этап и recourse авторежима (REQ-NAV)

- **[ADDED] REQ-NAV-1.** Способность «переместить сессию на более ранний, уже пройденный этап,
  чтобы доработать артефакт» сохраняется как штатная детерминированная операция без выделенной
  команды `/sdx:backtrack`: доступна через явный целевой аргумент у `/sdx:next` (например,
  `/sdx:next --to <stage>`). Не проверяет гейт уходящего этапа (симметрично сегодняшнему
  `backtrack`); не может целить дальше текущего этапа в каноническом порядке — только назад или
  на месте (форвард мимо гейта остаётся исключительно за обычным `/sdx:next` без аргумента).

- **[ADDED] REQ-NAV-2.** Нередеструктивная маркировка «последующие артефакты устарели» (сегодня —
  HTML-баннер `<!-- SDX-OUTDATED -->`) сохраняется как бизнес-требование: перемещение назад не
  удаляет и не бэкапит артефакты, лишь сигнализирует человеку/агенту, что содержимое требует
  пересмотра. Баннер не блокирует ни один гейт (доказательность гейта остаётся фактом наличия
  файла, не его качеством — без изменений относительно сегодняшнего поведения).

- **[ADDED] REQ-NAV-3.** Recourse несогласия пользователя на дисклоузе `gate_mode: auto`
  (сегодня протокол и `archive.md` называют штатным путём `/sdx:backtrack`/`/sdx:retrack`)
  переформулируется: несогласие → сброс `gate_mode` в `interactive` + пересмотр решения через
  `/sdx:next --to <stage>` (`REQ-NAV-1`). Все места протокола и команд, ссылающиеся на удаляемые
  команды как способ несогласия, обновляются на эту формулировку.

### Что перестаёт проверяться до FEAT-006 (REQ-ENF)

- **[ADDED] REQ-ENF-1.** Явно, для фиксации принятого пользователем окна (см. «Риски и
  Ограничения»), перечислены классы, enforced сегодня хуками `stage-gate.sh`/
  `stage-write-guard.sh`, которые НЕ enforced ни одним детерминированным хуком после этой
  поставки и до отдельной будущей сессии `FEAT-006`:
  1. Запись НЕ-документационного, НЕ-тестового кода реализации ДО прохождения
     Discovery/Business Spec/Technical Design/Task Planning (при их активности) — механический
     блок исчезает; становится вопросом прозаической дисциплины оркестратора, того же класса, что
     сегодня уже составляют смысловые условия гейта («решение согласовано»).
  2. Прямая правка `stage` (и новых полей `no_code`/`no_gates`) в `session_state.json` через
     `Write`/`Edit`/`MultiEdit`, минуя `sdx-stage.sh` — раньше блокировалось
     `stage-write-guard.sh`, теперь доступно любому агенту штатными инструментами, не только
     через `Bash`.
  3. Обход через `Bash` (`sed -i`/`jq` in-place и т.п.) — не новая дыра сама по себе (уже была
     известна как `DEBT-003`, не enforced и раньше), но её относительное значение меняется: то,
     что раньше было единственным способом обхода, становится единственным способом входа вообще,
     потому что штатные инструменты (п. 2) больше тоже не проверяются.
  4. Ложные срабатывания и пробелы покрытия этих двух хуков (`BUG-001`, `BUG-006`, `DEBT-003`,
     `DEBT-014`, `DEBT-015`, `DEBT-016`) закрываются симметрично — их предмет исчезает вместе с
     хуками, не чинится отдельно.
  Единственный компенсирующий механизм на время окна — прозаическая дисциплина оркестратора
  (`sdx/protocol.md`) и fresh-eyes ревью `reviewer` на `Verification`, которое по-прежнему
  безусловно и не смягчается.

- **[ADDED] REQ-ENF-2.** `stop-gate.sh` получает **одно дополнительное условие**: при
  `no_gates == true` тест-пол прозрачен (no-op), как сегодня на этапе `Prototype`. Причина
  механическая, а не идейная: `stop-gate.sh` различает поведение исключительно по значению
  `stage`, а `REQ-SCALE-1` убирает имя `Prototype` из словаря — после чего `no_gates`-сессия
  проводит всю работу на `stage == "Execution"`, том же имени, на котором пол включается. Без
  этого условия снос **побочным эффектом отменил бы** решение ADR-018 («прототипирование одним
  непрерывным проходом без промежуточных подтверждений»), которое настоящая поставка нигде
  явно не пересматривает.

  Правка не является демонтажом слоя, охраняющего необратимое: она **адаптирует хук к новой схеме
  состояния**, вводимой этой же поставкой (`REQ-FLAG-1`), и сохраняет его поведение неизменным для
  всех остальных сессий. Дополнительной связанности не возникает — `stop-gate.sh` уже читает
  состояние сессии через `lib/resolve-session.sh`.

  Область правки ограничена: одно условие в `stop-gate.sh` и один новый сценарий в
  `test-stop-gate.sh`, проверяющий прозрачность пола при `no_gates == true`. Никакая другая часть
  хука, включая green-run cache (`ADR-011`) и loop-guard, не меняется.

### Замена sanity-тестам матрицы (REQ-TEST)

- **[ADDED] REQ-TEST-1.** Прямой эквивалент сценария `test-sdx-stage.sh [34]` («матрица
  соответствует таблице протокола») сохраняется в новой форме: sanity-тест сверяет упорядоченный
  канонический список имён этапов, зашитый в `sdx-stage.sh` (`REQ-SCALE-1`), с одноимённым
  списком, документированным в `sdx/protocol.md` — падает на любом расхождении (пропуск/
  добавление/перестановка имени в одном из двух мест). Модель «трек × этап» заменяется на
  «просто этап» — сверка по одному списку вместо пяти.

- **[ADDED] REQ-TEST-2.** Прямого эквивалента сценарию `[35]` («страховка от возврата
  `SDX_CANON_ORDER`/`canon_rank`») не требуется: предмет этого теста — регресс к межтрековой
  ранговой схеме внутри `retrack`, а сама подкоманда `retrack` и понятие «трек» уходят вместе с
  этой поставкой — классу дефекта, который тест страховал, больше не в что регрессировать.

## Границы

- **`PROC-017`** (автоматизация переноса дельт при Closeout, пп. 2/3/5 чек-листа) — вне скоупа.
  Правка `archive.md` в этой сессии ограничивается снятием track-условной ветвистости чек-листа;
  сами пункты 2/3/5 остаются ручными операциями оркестратора, как сегодня.
- **`FEAT-006`** (модель полномочий по классу риска действия) — вне скоупа, отдельная будущая
  сессия. Окно между снятием `stage-gate`/`stage-write-guard` и приходом `FEAT-006` (`REQ-ENF-1`)
  принято пользователем осознанно, не является упущением этой поставки.
- **`docs/specs/` и `docs/designs/`** — исторические записи прошлых поставок НЕ переписываются;
  ADR-001/016/017/018 не правятся на месте (по прецеденту ADR-012 относительно ADR-009) — новый
  ADR волны 2 их пересматривает, ссылаясь на них, а не заменяя текст задним числом.
- **`prod-guard.sh` и `archive-verify.sh`** и их тесты — не трогаются вовсе (охраняют необратимое,
  `PROC-013`). **`stop-gate.sh`** — не демонтируется и не переосмысливается, но получает одно
  условие адаптации к новой схеме состояния (`REQ-ENF-2`); это единственное исключение из правила
  «слой необратимого не трогается», и оно вынужденное, а не расширение скоупа.
- **Рубрика трёх осей верификации** (полнота/корректность/когерентность, ADR-004) и контракт
  изоляции `reviewer` — не пересматриваются; масштабируется только глубина, а не сама рубрика
  (`REQ-SCALE-8`).
- **`/sdx:export`/`/sdx:import`** — их триаж трека на входе (`import.md`) адаптируется под флаги
  тем же принципом, что `/sdx:start` (`REQ-FLAG-2`), но остальная логика import-сессии (реконсиляция
  покомпонентно `transplant`/`reimplement`/`gap`) этой спекой не пересматривается.
- **Точное итоговое число тестовых сценариев** в переписываемых сьютах — не фиксируется этой
  спекой числом; фиксируется факт (зелёный прогон, покрытие ключевых сценариев `REQ-NAV-1`,
  `REQ-LEGAL-1`, `REQ-TEST-1`) — точное число выводится на Technical Design/Task Planning.

## Риски и Ограничения

- **Окно enforcement (`REQ-ENF-1`).** Класс «код пишется до пройденного гейта» и класс «`stage`
  правится в обход `sdx-stage.sh`» перестают быть механически защищены до `FEAT-006`. Это не
  пробел этой поставки — это явное, принятое пользователем решение (см. «Границы»), но оно снижает
  фактическую детерминированность enforcement-слоя на время окна; `PROC-013` называет этот перенос
  «не уменьшением детерминизма, а его переносом» на другую границу (необратимость действия) —
  граница необратимости (`prod-guard`/`stop-gate`/`archive-verify`) не ослабляется этой поставкой
  ни на йоту, но граница «порядок процесса» временно держится только прозой.
- **Объём документационной правки.** 23 файла (без `docs/specs/`/`docs/designs/`) содержат
  содержательные упоминания `track`, включая источники правды `CLAUDE.md` и `sdx/protocol.md` —
  риск рассинхронизации прозы и кода на переходный период; частично компенсируется `REQ-TEST-1`.
- **Compat-скан (`REQ-COMPAT-3`) — ручной, не автоматизированный этой поставкой.** Если к моменту
  Closeout этой сессии в репозитории окажется активная сессия со `stage ∈ {Change, Update,
  Prototype}`, её перенос — ручная операция оркестратора, не покрытая тестом; риск человеческой
  ошибки при этом переносе признаётся и не устраняется этой спекой.
- **`DEBT-023` остаётся открытым** (`REQ-LEGAL-4`) — не регресс этой поставки, но и не закрытие,
  которое могло бы ожидаться «по инерции» от переписывания `/sdx:proto`.
