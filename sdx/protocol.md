# Протокол SDX-сессий

Этот документ описывает формат состояния и логирования сессий. Им руководствуется основная сессия Claude Code при выполнении команд `/sdx:*` (роль Session Manager). Оркестрация субагентов (architect, ba, lead-dev, developer, qa, reviewer, auditor, tech-writer, devops) выполняется только из основной сессии через инструмент Task — для `reviewer` это не деталь, а контракт изоляции (см. «Fresh-eyes ревью»), для `auditor` — единственный способ вызова из `/sdx:audit`. Субагенты не могут вызывать друг друга.

## Состояние сессии (session_state.json)
```json
{
  "session_id": "string",
  "type": "feature | bug | refactor | init | import | grooming | retro | postmortem | intake | audit | proto",
  "stage": "Discovery | Business Spec | Technical Design | Task Planning | Execution | Documentation | Verification | Deployment | Closeout",
  "status": "draft | review | approved | executing",
  "gate_mode": "interactive | auto",
  "git_branch": "sdx/...",
  "no_code": false,
  "no_gates": false
}
```

Поля `artifacts`/`history` из схемы УДАЛЕНЫ (`DEBT-038`, `PROC-019`, REQ-STATE-1/2): у обоих
не было ни одного писателя/читателя (объявлены «на будущее» и никогда не использовались) —
состав артефактов сессии остаётся выводимым из листинга каталога сессии/`git status`
(`commands/status.md`), история переходов этапов — из `session.log` (строки `[STAGE_CHANGE]`).
Существующие (созданные до этой правки) `session_state.json` могут ещё содержать эти поля —
`sdx-stage.sh` их не читает и не трогает (толерантность к лишним ключам, тот же прецедент, что
уже описан для legacy-поля `track`, REQ-COMPAT-1); они просто переживают до собственного
Closeout соответствующей сессии.

- **`type`** — исходная категория задачи. Для пяти типов (`grooming`/`retro`/`postmortem`/`intake`/`audit`) и для `proto` жёстко определяет стартовые флаги `no_code`/`no_gates` (REQ-FLAG-2, без диалога об альтернативе); для остальных типов (`feature`/`bug`/`refactor`/`import`) — лишь ориентир для стартового этапа, не жёсткая привязка.
- **`stage`** — текущий этап, один из девяти канонических имён (см. «Единая шкала этапов и режимы-флаги» ниже, REQ-SCALE-1). Поле `track` из схемы УДАЛЕНО (ADR-020): активный набор этапов вычисляется из канонического порядка плюс двух флагов, а не выбирается позицией в отдельной строке матрицы.
- **`no_code`** / **`no_gates`** — два независимых булевых режима-флага (REQ-FLAG-1), оба по умолчанию `false`, записываются `sdx-stage.sh init` при создании сессии. Сужают активный набор этапов — см. «Единая шкала этапов и режимы-флаги».
- **`gate_mode`** — режим прохождения прозаических гейтов: `interactive` (по умолчанию) или `auto` (opt-in, см. «Авторежим гейтов»). Отсутствие поля = `interactive`.

**Совместимость с сессиями, начатыми до ADR-020 (REQ-COMPAT-1..3).** Legacy-поле `track`, если оно присутствует в `session_state.json` уже существующей сессии, толерантно игнорируется всеми командами `/sdx:*` и `sdx-stage.sh` — не читается, не требуется и не удаляется проактивно (JSON терпит лишние ключи); парсинг из-за одного лишь присутствия `track` не отказывает (REQ-COMPAT-1). Сессии, чей `stage` уже совпадает с одним из девяти канонических имён (сегодня это все сессии бывшего трека `full`), продолжают работу без единого ручного шага: отсутствующие `no_code`/`no_gates` трактуются как `false`/`false` (REQ-COMPAT-2). Сессии, чей `stage` использует имя, выведенное из словаря этапов этой поставкой (`Change` — бывшие `patch`/`standard`, `Update` — бывший `doc`, `Prototype` — бывший `vibe`), автоматическим переходом не поддерживаются: `sdx-stage.sh` отказывает явной диагностикой (`exit 2`) вместо неопределённого результата — требуется одноразовый ручной перенос (`Change`/`Update` → `Execution` с сохранением накопленного `change_note.md` как доказательства; `Prototype` → `Execution` + `no_gates: true`, прямой `Edit` поля — легитимный путь, deny-хука на поля состояния больше нет) до слияния такой сессии в основную ветку. Обязательный сквозной скан репозитория на предмет таких сессий перед Closeout — см. «Контракт закрытия сессии» (REQ-COMPAT-3).

## Модель сессии = ветка в основном рабочем дереве (ADR-012)
Одна сессия = одна **git-ветка** `sdx/<id>`, checkout'нутая в ОСНОВНОМ рабочем дереве
репозитория. Весь жизненный цикл — от `/sdx:start` до `/sdx:archive` включительно — проходит
в **одном CLI-инстансе**, запущенном в корне репозитория; хендоффов на другой CLI нет.
Содержательные артефакты сессии (`.claude/sessions/<id>/session_state.json`, `session.log`,
`SPEC.md`/`DESIGN.md`/`PLAN.md`/`change_note.md` и т.д.) **версионируются** на этой ветке
инкрементальными коммитами; эфемерные `.stopgate.*` игнорируются точечным паттерном корневого
`.gitignore` (REQ-SESS-1/2). Основная ветка (автоопределяется, см. ниже) никогда не видит файлы
сессии в своём HEAD-дереве: удаление каталога сессии оформляется коммитом `git rm -r` НА ВЕТКЕ
`sdx/<id>` ДО мёржа (**вариант A**), после чего мёрж `--no-ff` вносит всю историю ветки в DAG
основной ветки, но не в её HEAD-дерево.

**Операционные следствия.** Enforcement-хуки резолвят активную сессию по имени текущей ветки
(`sdx/<id>`) — при работе в основном дереве `$CLAUDE_PROJECT_DIR` (корень репозитория) корректен
по построению, отдельный CLI не нужен. Переключение сессий (`/sdx:switch`) — обычный
`git checkout sdx/<id>` с гардом чистого дерева: при незакоммиченных изменениях — стоп и
инструкция закоммитить их в текущую сессию (слепой авто-коммит запрещён, ядро REQ-WT-2).
Физической изоляции параллельных «грязных» деревьев (бывший REQ-WT-3) больше нет — осознанный
трейд-офф в пользу непрерывности работы в одном CLI; дисциплина инкрементальных коммитов
(REQ-SESS-1) — штатная компенсация.

Обоснование и границы — ADR-012 в `docs/DECISIONS.md` (worktree-модель ADR-009 пересмотрена).

## Единая шкала этапов и режимы-флаги
Порядок этапов — **фиксированное свойство имени этапа** (REQ-SCALE-1), одно на любую SDX-сессию, не зависящее ни от типа задачи, ни от флагов. `/sdx:next` переводит сессию на следующий **активный** этап этого канонического порядка, пропуская неактивные (REQ-SCALE-9) — масштабирование церемонии под размер задачи выражается не выбором строки матрицы (ADR-020 отменяет прежнюю модель «трек × этап»), а тем, какой артефакт создаётся для каждого этапа и двумя ортогональными булевыми флагами.

| # | Этап | Гейт-артефакт | FAIL-маркер | Fold-credit (`change_note.md`) |
|---|------|----------------|-------------|----------------------------------|
| 1 | Discovery | `context_report.md` | нет | да |
| 2 | Business Spec | `SPEC.md` | нет | да |
| 3 | Technical Design | `DESIGN.md` | нет | да |
| 4 | Task Planning | `PLAN.md` | нет | да |
| 5 | Execution | — (нет объективного гейта) | — | — |
| 6 | Documentation | — (нет объективного гейта) | — | — |
| 7 | Verification | `verification_report.md` | да (`^### \[FAIL\]`) | нет |
| 8 | Deployment | — (нет объективного гейта) | — | — |
| 9 | Closeout | — (нет объективного гейта) | — | — |

**Машиночитаемый источник истины** этой таблицы — `SDX_STAGE_TABLE` внутри `sdx/hooks/sdx-stage.sh` (heredoc-строки `stage|artifact|fail_marker|foldable`, порядок = порядок исполнения). Таблица выше — человекочитаемая проекция для справки; она не используется скриптом. При расхождении прав скрипт. Sanity-тест `test-sdx-stage.sh` (REQ-TEST-1) сверяет **все четыре столбца** — имя этапа, гейт-артефакт, наличие проверки `^### [FAIL]` и признак складываемости — между этой таблицей и `SDX_STAGE_TABLE`, и краснеет на расхождении в любом из них, а не только в порядке имён.

### Активность этапа (REQ-SCALE-2)
Активность этапа для конкретной сессии определяется двумя факторами, применяемыми в порядке приоритета:
1. **Флаги** (`no_code`, `no_gates`) — детерминированные правила ниже, которые могут только СУЖАТЬ активный набор, никогда не расширять его сверх того, что определил бы объём дельты.
2. **Объём дельты** — прозаическое суждение оркестратора, пересматриваемое на каждом гейте `/sdx:next` (REQ-SCALE-9), заменяющее прежний триаж трека на `/sdx:start` и scope-check ADR-001. Минимально необходимый активный набор для ЛЮБОЙ сессии — `Execution → Verification → Closeout` (сегодняшний эквивалент бывшего трека `patch`).

**Fold-credit планировочных этапов (REQ-SCALE-3).** Когда `Discovery`/`Business Spec`/`Technical Design`/`Task Planning` не оправданы отдельным полноценным артефактом (малая дельта), их содержательное решение фиксируется слитно в `change_note.md` — гейт каждого из четырёх этапов удовлетворяется ЛИБО собственным артефактом, ЛИБО непустым `change_note.md` (столбец «Fold-credit» выше). Это генерализация уже существовавшего special-case'а бывшего этапа `Change` (ADR-016, W-6 fix) на все четыре планировочных этапа — не новый принцип, а расширение уже проверенного на одно дополнительное имя не единственного, а теперь всех четырёх.

**`no_code == true` (REQ-SCALE-4)** безусловно исключает из активного набора `Task Planning`, `Execution`, `Documentation`, `Deployment` — независимо от объёма дельты (замена бывшего трека `doc`, ADR-017/ADR-019). Планировать и исполнять нечего без кода; `Business Spec`/`Technical Design` (или их свёртка в `change_note.md` по REQ-SCALE-3) остаются активны — это ровно то место, где раньше жил отдельный этап `Update`.

**`no_gates == true` (REQ-SCALE-5)** безусловно ограничивает активный набор до `{Execution}` — единственного этапа — независимо от объёма дельты (замена бывшего трека `vibe`, ADR-018), пока флаг не снят легализацией (REQ-LEGAL-1, см. «Прототипирование» ниже). Эта проверка приоритетна НАД ВСЕМ остальным вычислением активного набора, включая REQ-SCALE-7 — единственный способ сохранить силу инварианта «нет Closeout без легализации» без структурной опоры на отсутствующую строку матрицы.

**`Documentation`/`Deployment` (REQ-SCALE-6)** активны, только если дельта производит производные документы (Swagger/README/мануалы) — для `Documentation`, либо затрагивает инфраструктуру/конфиги деплоя — для `Deployment`. Определяется объёмом дельты, не флагом (генерализация практики «только у бывшего трека `full`»).

**`Verification`/`Closeout` всегда активны (REQ-SCALE-7)** для ЛЮБОЙ сессии, независимо от объёма дельты и от `no_code`, — за единственным временным исключением: пока `no_gates == true`, REQ-SCALE-5 временно перекрывает и их (REQ-LEGAL-1). Это генерализация прежней «обязательной лёгкой верификации» (ADR-014 для бывшего `patch`, ADR-017 для бывшего `doc`) на все сессии без исключения.

**Глубина Verification (REQ-SCALE-8)** определяется тем же критерием объёма дельты, что и активность `Business Spec`/`Technical Design`, а не отдельным правилом на бывший трек. При `no_code == true` `qa` не вызывается вовсе (нет кода для регрессионного прогона) — см. «Верификация» ниже.

**Пересмотр на каждом `/sdx:next` (REQ-SCALE-9).** Оркестратор на каждом гейте переоценивает активный набор этапов по факту открывшегося объёма работы — замена прежнего «scope-check → предложи `/sdx:retrack`» (ADR-001). Если по ходу выясняется, что нужен ранее неактивный этап (например, `Business Spec` для сессии, начатой как минимальная правка), оркестратор активирует его через навигационный механизм `next --to` (REQ-NAV-1, см. «Механизм перехода этапов»); активность этапа не хранится отдельным полем состояния — вычисляется заново при каждом переходе.

### Два режима-флага (`no_code`, `no_gates`)
Схема `session_state.json`: два булевых поля верхнего уровня, оба по умолчанию `false`, записываются `sdx-stage.sh init` при создании сессии (REQ-FLAG-1).

**Жёсткая привязка на `/sdx:start` (REQ-FLAG-2).** Без диалога о выборе (по прецеденту ADR-017/ADR-018): `type ∈ {grooming, retro, postmortem, intake, audit} → no_code = true` безусловно; `type == proto → no_gates = true` безусловно. Для остальных типов (`feature`, `bug`, `refactor`, `import`) оба флага стартуют `false`, а активный набор этапов — гипотеза, пересматриваемая по ходу (REQ-SCALE-9).

**Взаимоисключение (REQ-FLAG-3).** `no_code = true` и `no_gates = true` в одной сессии запрещены — не просто нежелательное сочетание, а содержательное противоречие: предмет `no_gates` специфичен про код («один промпт без церемонии» с кодом на выходе), `no_code` по определению код исключает. `sdx-stage.sh init` отказывает при попытке установить оба флага одновременно; попытка включить один флаг для сессии с уже установленным другим на любом более позднем шаге запрещена тем же правилом.

**Однонаправленность (REQ-FLAG-4).** `no_gates` — одноразовый в рамках сессии: после снятия флага (легализация) повторная установка `no_gates = true` в этой же сессии запрещена. `no_code`, напротив, может быть снят по ходу сессии при эскалации объёма (симметрично прежней эскалации `doc → {patch,standard,full}`); обратная установка `no_code: false → true` посреди уже идущей сессии запрещена (симметрично прежнему запрету деэскалации в `doc`). Оба правила — прозаическая дисциплина, не enforced хуком (тот же класс trade-off, что и сегодняшние направленные запреты ADR-017/ADR-018).

### `no_code == true` — процессная работа без кода
Пять значений `type` жёстко и безусловно задают `no_code = true` на `/sdx:start` (без диалога об альтернативе, ADR-017/ADR-019):
- **grooming** — пересмотр ТЕКУЩЕГО состояния `docs/backlog/`: актуализация статусов/приоритетов/волн уже существующих записей (update-путь над бэклогом).
- **retro** — разбор набора уже ЗАВЕРШЁННЫХ SDX-сессий за период/список (`docs/history/sessions-log.md`), выводы оформляются новыми записями бэклога и постоянным документом `retro.md`.
- **postmortem** — разбор ОДНОГО конкретного инцидента (прод, процессный сбой, серьёзный дефект): хронология, корневая причина, план действий; постоянный документ `postmortem.md`.
- **intake** — разбор НОВОГО значительного блока внешних требований (эпик, пачка багрепортов, продуктовый материал), цель — **породить** записи бэклога из этого материала (create-путь); постоянный документ `intake.md`.
- **audit** — триаж уже готового отчёта `/sdx:audit` (`docs/history/audit/audit-<дата>[-N].md`) в `docs/backlog/`: вход — путь к существующему в репозитории отчёту, а не новый скан проекта и не прозаический материал (verify-путь, по аналогии с create-путём `intake` и update-путём `grooming`); выход — записи `docs/backlog/`, порождённые/дополненные/регрессные по трём слоям дедупликации (точный по `source`, смысловой против открытых, смысловой против закрытых как регресс). `audit` постоянного документа разбора не производит — второй тип `no_code`-семейства без него, наравне с `grooming` (предмет разбора уже является постоянным документом сам по себе). Подробнее — раздел «Аудит проекта (`/sdx:audit`) и его триаж» ниже, ADR-019.

**`audit`/`intake`/`grooming` — три разных пути над `docs/backlog/`, не синонимы и не альтернативные имена одного типа**, несмотря на то, что все три читают/пишут один и тот же `docs/backlog/` через один и тот же гейт-артефакт `change_note.md`. Разница — в направлении операции: `intake` **порождает** записи из внешнего материала (create), `grooming` **перераспределяет** атрибуты уже существующих записей и сам новых записей не создаёт (update), `audit` **сверяет** уже накопленный бэклог со свежим отчётом о состоянии проекта «как есть» — дополняет существующие записи, порождает новые под ранее не отражённые находки и заводит отдельную запись-регресс при совпадении находки с уже закрытой записью (verify). Наблюдаемо от `intake`: вход `audit` — путь к уже существующему файлу с известным парсящимся форматом (frontmatter `run:`), поэтому Discovery-lite может детерминированно провалидировать вход; вход `intake` — прозаический материал без структурированного места (`PROC-009`). Наблюдаемо от `grooming`: у `audit` есть точный слой дедупликации (`source` содержит `<run-id> (<CODE><N>)`) и обязательный класс «регресс» против закрытых записей, которого нет ни у `grooming`, ни у `intake`. Типичный порядок — сначала `audit` или `intake` (находки/материал → записи), затем, отдельной сессией, `grooming` (пересмотр приоритетов среди уже накопленного); порядок не enforced, все три типа доступны в любой момент. Ничто в enforcement-слое эту границу не проверяет — она держится исключительно текстом инструкций `/sdx:start` и, для `intake`, шаблоном `intake.md` (раздел «Открытые вопросы к дальнейшему груминг-циклу» как явная точка передачи эстафеты); для `audit` шаблона сессии нет вовсе. См. ADR-017, ADR-019.

**Что производит `change_note.md` при `no_code == true` (ADR-017/ADR-019).** `change_note.md` — единственный объективно проверяемый гейт-артефакт планировочных этапов (`Discovery`/`Business Spec`/`Technical Design` — `Task Planning` исключён безусловно, REQ-SCALE-4) для всех пяти типов; минимальный состав: краткое резюме сессии (что разобрано/поправлено и почему) + список ID затронутых/порождённых записей `docs/backlog/` +, для `retro`/`postmortem`/`intake`, ссылка на параллельно ведущийся содержательный документ `retro.md`/`postmortem.md`/`intake.md` в каталоге сессии + для `intake` дополнительно — состав внешнего материала, фактически взятого в разбор (ссылки/пути/описание вложений; единственный структурированный след входа, пока не закрыт `docs/backlog/PROC-009`) + для `audit` дополнительно — перечень созданных/дополненных/регрессных/отдедуплицированных ID записей бэклога и путь к разобранному отчёту (`docs/history/audit/audit-<дата>[-N].md`). **Правки `docs/backlog/` выполняются НА планировочных этапах, а не откладываются до Closeout** — п.4 чек-листа Closeout (см. ниже) — это финальная сверка/актуализация статусов, не первичная работа над бэклогом.

### `no_gates == true` — прототипирование без церемонии
Тип `proto` жёстко и безусловно задаёт `no_gates = true` на `/sdx:start`, без диалога об альтернативе (по образцу `no_code`, ADR-018); вход в `no_gates` посреди уже идущей сессии другого типа запрещён прозаически (REQ-LEGAL-3, тот же класс принятого trade-off, что и прежний запрет `{patch,standard,full,doc} → vibe`). Единственный активный этап — `Execution` (REQ-SCALE-5); собственного `Closeout` у такой сессии нет — это структурный инвариант вычисления активного набора (приоритет-0 проверка `no_gates == true` в `cmd_next`, REQ-LEGAL-1), а не пропуск пункта. Именованное исключение из нормы инкрементальных коммитов (REQ-SESS-1): пока `no_gates == true`, коммиты кода не делаются вовсе — единственное такое исключение во всём протоколе (REQ-VIBE-9). Гейт принятия/отклонения прототипа (`/sdx:proto`) безусловно интерактивен независимо от `gate_mode` — деструктивная операция отката попадает под стоп-рубрику протокола.

**Легализация (REQ-LEGAL-1..4).** Единственный выход из `no_gates == true` — команда `/sdx:proto`, ветка «Принять»: spec-after реверс-инжиниринг требований из уже написанного кода прототипа через `ba`/`architect`/опционально `lead-dev` (в объёме, выбранном пользователем на самой легализации — лёгкий проход или полный цикл), первый коммит кода прототипа с обязательной пост-проверкой, второй коммит артефактов, снятие `no_gates` прямым `Edit` поля (легитимный путь — deny-хука на поля состояния больше нет), затем обычный `next` без `--to` дальше по канонической шкале. Полный алгоритм — `commands/proto.md`, ветка «Принять» (перенесён туда дословно из прежнего `commands/retrack.md`, который вместе с `commands/backtrack.md` удалён этой поставкой — их функции поглощены `next --to` и `/sdx:proto`, REQ-LEGAL-2). Повторная установка `no_gates = true` в этой же сессии запрещена (REQ-FLAG-4). `DEBT-023` («`/sdx:proto` не показывает содержимое новых файлов на шаге предъявления результата») этой поставкой не закрывается — независим от формы хранения режима (REQ-LEGAL-4).

## Логирование (экономный режим)
В журнал `.claude/sessions/<session_id>/session.log` пишутся ТОЛЬКО durable-события смены состояния. Каждая отдельная запись в лог — это лишний ход агента (полный round-trip контекста), поэтому логирование намеренно минимально.

### Формат строки:
`[YYYY-MM-DD HH:mm:ss] [КАТЕГОРИЯ] [ЭТАП] Сообщение`

### Логируемые категории (только эти четыре):
- `START`: Инициализация сессии или переключение на неё.
- `STAGE_CHANGE`: Переход между этапами (форвард или `--to`).
- `CHECKPOINT`: Фиксация точки восстановления.
- `ERROR`: Ошибки команд или проваленные гейты.

### Что НЕ логируется (выводится иначе):
- **Артефакты (создание/изменение файлов)** — НЕ логируются. История изменений файлов выводится из git (`git log --stat`, `git diff --name-status`), а текущий состав артефактов — из `git status`/листинга папки сессии по запросу. Для этого артефакты коммитятся в ветку сессии **инкрементально** по ходу работы (это же поддерживает чек-лист Closeout).
- **INFO / просмотр статуса** — НЕ логируется вообще. Чтение состояния не должно мутировать его.

### Правила записи:
- **Время**: не выдумывай — получай `date '+%Y-%m-%d %H:%M:%S'`. Захватывай время и пиши запись в том же ходе, что и правку `session_state.json` (батч), а не отдельным вызовом.
- **ЭТАП**: текущее значение `stage`. **Сообщение**: кратко, на русском.
- Запись — в режиме **append** (`>>`):
```bash
echo "[$(date '+%Y-%m-%d %H:%M:%S')] [STAGE_CHANGE] [Execution] -> Verification" >> .claude/sessions/<session_id>/session.log
```

## Передача контекста субагентам (экономия токенов)
При вызове субагента через Task передавай **пути к артефактам и краткую задачу**, а не вставляй содержимое файлов в промпт. Субагент прочитает нужное сам. Вставка контента в промпт ведёт к двойной токенизации (в контексте оркестратора и заново в субагенте). Исключение — fresh-eyes `reviewer`, которому diff передаётся как данные по контракту изоляции.

## Гейты (Gates)
Перед переходом на следующий **активный** этап проверяется наличие необходимых артефактов (`SPEC.md`, `DESIGN.md`, `PLAN.md`, `change_note.md` и т.д.). Объективно проверяемая часть гейта (существование/непустота артефактов или `change_note.md`-эквивалента для планировочных этапов, отсутствие `FAIL` в `verification_report.md`) **enforced автоматически** скриптом `sdx-stage.sh` (см. ниже, раздел «Механизм перехода этапов»). Смысловые условия («решение согласовано», контракты подтверждены) остаются **прозаическим суждением оркестратора** (не проверяются скриптом). Гейт также включает scope-check (REQ-SCALE-9): оркестратор оценивает, не вышла ли задача за рамки объёма, предполагавшегося на уже пройденных планировочных этапах, и при необходимости предлагает создать для них полноценный артефакт (`SPEC.md`/`DESIGN.md`) вместо `change_note.md`, затем вернуться туда через `/sdx:next --to <stage>`.

## Механизм перехода этапов (`sdx-stage.sh`)

Единственный детерминированный писатель поля `.stage` в `session_state.json` — CLI-скрипт `sdx/hooks/sdx-stage.sh` (не Hook в терминах `hooks.json`, а самостоятельный скрипт, вызываемый командами через инструмент `Bash`, как уже происходит с `archive-verify.sh`). Скрипт инкапсулирует машиночитаемую таблицу «этап → гейт-артефакт → fail-маркер → fold-credit» (`SDX_STAGE_TABLE`) и выполняет все проверки гейта автоматически. Прежняя модель «трек × этап» и обслуживавшие её отдельные подкоманды смены профиля/отката (`retrack`, `backtrack`) сняты целиком (ADR-020) — единственная оставшаяся навигационная потребность, «вернуться на уже пройденный этап», стала вторым режимом одной подкоманды `next`.

### Две подкоманды

| Подкоманда | Назначение | Вызывается из | Коды возврата |
|---|---|---|---|
| `init <sid> <type> <stage> <gate_mode> <git_branch> <no_code> <no_gates>` | Первичное создание `session_state.json` (REQ-FLAG-1) | `/sdx:start`, `/sdx:import` | `0` успех; `2` ошибка (несовместимые флаги — REQ-FLAG-3, нераспознанный `stage`, `no_gates=true` не на `Execution` — REQ-SCALE-5, `no_code=true` на исключённом этапе — REQ-SCALE-4, файл уже существует) |
| `next <sid> [--to <stage>]` | Без `--to` — forward-переход на следующий активный этап, проверяет гейт уходящего этапа. С `--to` — переход НАЗАД на уже пройденный (или ранее неактивный, но идущий раньше текущего в каноническом порядке) этап, без проверки гейта уходящего этапа, с маркировкой последующих артефактов как устаревших (REQ-NAV-1/2) | `/sdx:next`, `/sdx:next --to <stage>`, `/sdx:archive` (вход в Closeout) | `0` успех/no-op; `1` гейт не пройден (forward) либо цель не распознана/дальше текущего этапа (`--to`); `2` ошибка (нет `session_state.json`, повреждённое/нераспознанное состояние — REQ-COMPAT-3) |

**Приоритет-0: `no_gates == true` (REQ-LEGAL-1).** Прежде чем разбирать `--to` или что-либо ещё, `next` проверяет `no_gates` первым: пока флаг не снят, ЛЮБОЙ вызов (с `--to Execution` или без аргументов) возвращает `OK no-op Execution` и ничего не меняет; вызов `--to <stage>` с целью, отличной от `Execution`, отказывает (`exit 1`) с указанием на `/sdx:proto` как единственный путь наружу. Это единственный механизм, удерживающий инвариант ADR-018 «нет `Closeout` без легализации» без опоры на отсутствующую строку матрицы.

### stdout и stderr (REQ-STAGE-5)

- **Успех (код 0):** stdout содержит одну из строк: `OK <old-stage> -> <new-stage>` или `OK no-op <stage>`. Для `next --to` дополнительно выводятся строки `OUTDATED: <path>` для каждого помеченного артефакта.
- **Отказ (код 1/2):** stderr содержит одну developer-facing строку на русском языке, называющую (а) чего не хватает и (б) какой командой чинить.

### Возврат на более ранний этап (`next --to`, REQ-NAV-1/2)

**Ограничение цели по флагу (REQ-SCALE-4).** `--to` отклоняется (код `1`), если целевой этап
исключён из активного набора флагом `no_code` — то есть для `Task Planning`, `Execution`,
`Documentation`, `Deployment` в сессии с `no_code == true`. Исключение флагом объявлено
безусловным, поэтому оно действует одинаково на всех трёх путях: `init`, форвардный `next` и
`next --to`. Сообщение отказа называет и запрет, и способ его снять — одноразовую эскалацию
`no_code: true -> false`.
Способность «переместить сессию на более ранний, уже пройденный этап, чтобы доработать артефакт» — штатная детерминированная операция без выделенной команды: `sdx-stage.sh next <sid> --to <stage>`. Не проверяет гейт уходящего этапа (симметрично прежнему `backtrack`); не может целить дальше текущего этапа в каноническом порядке — только назад или на месте (форвард мимо гейта делает исключительно обычный `next` без `--to`). Нередеструктивная маркировка «последующие артефакты устарели» (HTML-баннер `<!-- SDX-OUTDATED -->`, вставляемый первой строкой файла) сохраняется как бизнес-требование (REQ-NAV-2): перемещение назад не удаляет и не бэкапит артефакты, лишь сигнализирует человеку/агенту, что содержимое требует пересмотра. Баннер не блокирует ни один гейт — доказательность гейта остаётся фактом наличия файла, не его качеством; помеченный устаревшим артефакт продолжает считаться доказательством пройденного гейта. Маркировка идемпотентна: повторный `--to`, указывающий на тот же файл, не дублирует баннер.

**Границы доказательности.** Доказательством пройденного гейта считается факт существования непустого файла-артефакта (плюс отсутствие маркера `[FAIL]` там, где он применим, плюс fold-credit `change_note.md` для планировочных этапов) — не его содержательное качество. Файл-заглушка в одну строку гейт проходит: механизм отличает «артефакта нет» от «артефакт есть», но не «артефакт осмыслен» — последнее остаётся предметом прозаического суждения оркестратора и fresh-eyes ревью на Verification.

### Источник истины: таблица внутри скрипта

**Машиночитаемый источник истины** канонического порядка этапов и соответствующих гейт-артефактов находится **исключительно** внутри `sdx/hooks/sdx-stage.sh` как heredoc-таблица `SDX_STAGE_TABLE`. Таблица-проекция «Единая шкала этапов и режимы-флаги» выше в этом документе — **человекочитаемая проекция тех же данных** для справки; она **не используется** скриптом. При расхождении между таблицей выше и `SDX_STAGE_TABLE` в скрипте — прав скрипт. Sanity-тест (REQ-TEST-1) сравнивает все четыре столбца таблицы из обоих мест — не только порядок имён — и сигнализирует о любом расхождении (см. `sdx/hooks/test-sdx-stage.sh`).

## Авторежим гейтов (gate_mode, opt-in — ADR-014)
По умолчанию сессия интерактивна: прозаические гейты (аппрувы артефактов, переходы `/sdx:next`, квитирование WARN) требуют подтверждения пользователя на каждом шаге. Для тривиальных задач пользователь может включить **авторежим** — `gate_mode: "auto"` в `session_state.json`: флагом `/sdx:start --auto` либо согласием на предложение оркестратора на Discovery/Business Spec-гейте (там, где согласуются развилки задачи). При `no_gates == true` предложение включить авторежим не делается (см. «`no_gates == true` — прототипирование без церемонии»). Решение per-session; возврат в `interactive` — в любой момент по слову пользователя.

При `gate_mode: "auto"`:
- Прозаические подтверждения и несущественные уточнения по ходу принимают **дефолт без остановки**. Каждый принятый дефолт фиксируется одной строкой в файле сессии `auto_decisions.md` (формат: `развилка → выбранный дефолт → почему несущественно`). Файл универсален для любого объёма дельты (работает и там, где нет `change_note.md`) и версионируется как обычный артефакт сессии.
- Детерминированные хуки НЕ смягчаются: stop-gate, prod-guard и archive-verify работают без изменений. Авторежим касается только прозаического слоя.
- Единственная обязательная точка подтверждения — **дисклоуз** на входе в Closeout (см. `/sdx:archive`): `auto_decisions.md` выводится пользователю одним блоком (автоквитированные WARN — первыми), после чего запрашивается одно явное подтверждение. Несогласие с любым дефолтом → сброс `gate_mode` в `interactive` и пересмотр решения через `/sdx:next --to <stage>` (REQ-NAV-3).

**Стоп-рубрика.** Авторежим ОБЯЗАН остановиться и вернуть решение пользователю на:
- коллизиях триады SPEC ↔ DESIGN ↔ Codebase (CLAUDE.md §4 — без исключений);
- находках FAIL верификации и красном тест-поле stop-gate;
- изменениях внешних контрактов: публичные API, схемы данных, форматы файлов, миграции;
- деструктивных/необратимых операциях и территории prod-guard;
- эскалации объёма: переход к более тяжёлому артефакту (`SPEC.md`/`DESIGN.md`) для уже пройденного этапа, ранее закрытого `change_note.md`, сбрасывает `gate_mode → interactive` (масштаб изменился — исходное решение «задача тривиальна» недействительно); обратное движение (сужение объёма) режим не меняет;
- шагах ручного тестирования (`/sdx:manual` интерактивен по определению, ADR-006).

Критерий по умолчанию для не перечисленного: если цена отката ошибочного дефолта выше цены остановки — остановись.

**Решение на стоп-рубрике идёт не в `auto_decisions.md`.** Стоп-рубрика останавливает
`auto`-сессию точно так же, как `interactive` — на её пунктах решение всегда принимает человек,
а не дефолт модели. Такое решение фиксируется в `decisions_log.md` (см. «Журнал решений
(`decisions_log.md`) — `PROC-019`» ниже), а не в `auto_decisions.md`: последний фиксирует только
то, что было принято дефолтом БЕЗ остановки, то есть по построению никогда не пересекается со
стоп-рубричными решениями ни в одном из двух режимов.

## Enforcement-слой (хуки)
Инварианты, обязанные выполняться всегда, вынесены из прозы в детерминированные хуки.
Скрипты поставляются плагином (`${CLAUDE_PLUGIN_ROOT}/sdx/hooks/`), проводка — `hooks/hooks.json`
плагина. Per-project конфиги слоя (`prod-guard.conf`, `verify-cmd.sh`)
живут в `.claude/sdx/` целевого проекта и разворачиваются `/sdx:init` из шаблонов
`${CLAUDE_PLUGIN_ROOT}/sdx/templates/`. Там же живёт маркер версии плагина
`sdx-version` (не шаблон — пишется исключительно `/sdx:reconcile`, сверяется `/sdx:start`;
см. «Сверка форматов после релиза и миграции» ниже). Все хуки активны только в
SDX-ветке `sdx/<id>` и деградируют в no-op при отсутствии сессии/конфига (safe-by-default).

**Инвариант формы вызова (BUG-008).** Любой скрипт слоя вызывается ТОЛЬКО через интерпретатор —
`bash <путь>` в `hooks/hooks.json`, в командах `/sdx:*` и во внутренних вызовах хук→lib — либо
через `. <путь>` (source). Прямое исполнение файла (`"<путь>"/script.sh`) запрещено: оно требует
бита `x`, а установщики плагина не обязаны сохранять режимы файлов (наблюдено: установка, где все
`sdx/hooks/**/*.sh` разворачиваются с правами `0600`). В такой среде прямой вызов даёт `exit 126`
и `Permission denied`, то есть тихую смерть детерминированного слоя — ровно тот класс невидимой
деградации, что описан в DEBT-010. Инвариант enforced тестом `sdx/hooks/test-hook-wiring.sh`
(сценарий `[2]`), покрывающим проводку `hooks/hooks.json`; для вызовов из прозаических команд
`/sdx:*` он остаётся конвенцией текста.

Механизм блокировки PreToolUse: JSON `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"<причина>"}}` на stdout, exit 0 (НЕ exit 2 — подтверждено на бинарнике Claude Code 2.1.195). Единственный хук слоя, использующий этот механизм сегодня — `prod-guard` (см. ниже); он остаётся частью контракта на случай будущих PreToolUse-хуков.

### Enforcement-окно (REQ-ENF-1) — что перестало проверяться этой поставкой

ADR-020 снимает два хука enforcement'а порядка процесса — `stage-gate.sh` (замораживал запись кода до гейта Execution) и `stage-write-guard.sh` (deny-хук на прямую правку `stage`/`no_code`/`no_gates` в обход `sdx-stage.sh`) — БЕЗ замены, до появления модели полномочий по классу риска (`FEAT-006`, отдельная будущая сессия). Явно, для фиксации принятого пользователем окна, классы, переставшие быть enforced ЛЮБЫМ детерминированным хуком:
1. Запись НЕ-документационного, НЕ-тестового кода реализации ДО прохождения Discovery/Business Spec/Technical Design/Task Planning (при их активности) — механический блок исчезает; становится вопросом прозаической дисциплины оркестратора, того же класса, что сегодня уже составляют смысловые условия гейта («решение согласовано»).
2. Прямая правка `stage` (и полей `no_code`/`no_gates`) в `session_state.json` через `Write`/`Edit`/`MultiEdit`, минуя `sdx-stage.sh` — раньше блокировалось `stage-write-guard.sh`, теперь доступно любому агенту штатными инструментами, не только через `Bash`.
3. Обход через `Bash` (`sed -i`/`jq` in-place и т.п.) — не новая дыра сама по себе (уже была известна как `DEBT-003`, не enforced и раньше), но её относительное значение меняется: то, что раньше было единственным способом обхода, становится единственным способом входа вообще, потому что штатные инструменты (п. 2) больше тоже не проверяются.
4. Ложные срабатывания и пробелы покрытия этих двух хуков (`BUG-001`, `BUG-006`, `DEBT-003`, `DEBT-014`, `DEBT-015`, `DEBT-016`) закрываются симметрично — их предмет исчезает вместе с хуками, не чинится отдельно.

Единственный компенсирующий механизм на время окна — прозаическая дисциплина оркестратора (этот документ) и обязательное fresh-eyes ревью `reviewer` на `Verification`, которое по-прежнему безусловно и не смягчается (рубрика трёх осей ADR-004, REQ-SCALE-8).

### Оставшиеся три хука (плюс self-test — четвёртая запись, см. ниже)

- **stop-gate** (Stop): тест-прогон как пол под Verification; ход не завершается на красном
  (скоуп Execution/Verification или `SDX_STOP_GATE=1`). После 3 красных подряд — возврат
  человеку. Привязан к `Stop` (не `SubagentStop`), чтобы не воевать с TDD red-green developer'а.
  Деградирует в no-op без известной тест-команды (`verify-cmd.sh` — per-project, ADR-4).
  Per-project раннер активируется **наличием** файла, а не битом выполнения (поправка к ADR-4
  от 2026-09-01, DEBT-026); отказ от раннера — отсутствие файла. Бит при этом определяет способ
  вызова: исполняемый раннер запускается напрямую (действует его shebang, язык произволен),
  неисполняемый интерпретируется как bash. Автодетект-строки (`composer test`/`npm test`/`phpunit`) статичны и идут через `bash -c`.
  **Green-run cache (ADR-011):** отпечаток дерева (`HEAD` + хэш `git status --porcelain`)
  последнего зелёного прогона хранится в `.stopgate.ok`; при неизменном дереве повторный `Stop`
  пропускается без перезапуска verify (кэш-хит до инкремента loop-guard). `SDX_STOP_GATE=1`
  кэш обходит; красный прогон кэш не пишет.
  **`no_gates == true` на `stage == "Execution"` — намеренно прозрачен (REQ-ENF-2).** Хук денит
  только по значению `stage` из явного списка (`Execution|Verification`) — а прототипирование
  теперь тоже проходит на `stage == "Execution"` (REQ-SCALE-5 отменяет прежнее отдельное имя
  `Prototype`). Без дополнительного условия коллапс имени этапа побочным эффектом отменил бы
  иммунитет ADR-018 молча — поэтому хук получает ОДНО дополнительное условие внутри уже
  существующей ветки `case`: читает `no_gates` из состояния и остаётся прозрачным (`exit 0`),
  когда `no_gates == true`, даже если верификационная команда сконфигурирована и красна. Это
  единственное исключение из правила «слой необратимого не трогается» — вынужденное коллизией
  имени этапа, а не расширение скоупа правки. Причина механическая, не идейная: тестов на
  прототип нет по построению режима (никакого TDD-цикла, один непрерывный проход), а пол под
  тесты возвращается на `Execution` сразу после легализации (снятие `no_gates`, REQ-VIBE-6).
  `SDX_STOP_GATE=1` форсирует прогон и здесь, как и на любой другой стадии.
- **prod-guard** (PreToolUse `Bash`): прод-команды по `prod-guard.conf` блокируются; пустой
  или отсутствующий conf (нет ни одной активной строки-паттерна) = нет защиты (opt-in
  per-project) — проверка conf выполняется **раньше** проверки `jq`. Прод-деплой — только явное
  действие человека, не агента. **Граница:** покрывает только инструмент `Bash` — деплой
  через иной механизм (MCP-tool, шелл-обёртка) его минует. При отсутствии `jq` prod-guard
  деградирует в **fail-closed** (блокирует команду из осторожности) **только если защита
  сконфигурирована**; без активных паттернов отсутствие `jq` не блокирует команды.
- **preflight** (SessionStart): однократная проверка зависимостей хуков (`jq`). При
  отсутствии `jq` громко предупреждает (prod-guard → fail-closed); опционально может жёстко
  отказывать в сессии (закомментированный `exit 2`).

### self-test (четвёртая запись SessionStart)

Синтетическая проба живости трёх основных хуков enforcement-слоя (`preflight.sh`, `prod-guard.sh`, `stop-gate.sh`) — новая, независимая запись `SessionStart` в `hooks/hooks.json`, выполняется после `preflight.sh` (REQ-ST-1). Не является детектором класса регрессии `BUG-008` (потеря бита `x`) — вызывает хуки через `bash <путь>`, как и правильная штатная проводка, и `bash <путь>` не чувствителен к исполняемому биту; покрытие `BUG-008` остаётся зоной статической проверки `test-hook-wiring.sh`, вне self-test (REQ-LIMIT-1).

**Гард признака SDX-проекта.** Хук молчит в проектах, не проходивших `/sdx:init`: первой операцией после резолва каталога проекта стоит проверка `[ -d "$proj/.claude/sdx" ]`, и при её отказе — `exit 0` без единой записи на диск. Признак тот же, что проверяет `/sdx:start` шагом 1. Причина: `SessionStart` срабатывает в любом проекте, а установка плагина в user-scope не должна оставлять следов там, где SDX не используется — ровно так же ведут себя три соседних хука (`prod-guard` без своего конфига и `stop-gate` без сессии уходят в no-op, `preflight` не пишет вовсе).

**Периметр и исключения.** Три зарегистрированных в `hooks.json` события: `preflight.sh` (SessionStart), `prod-guard.sh` (PreToolUse), `stop-gate.sh` (Stop). `sdx-stage.sh` (CLI-скрипт, не hook в терминах `hooks.json`) — вне периметра (DESIGN.md, развилка 1: его единственный failure-mode без `jq` уже структурно проверяется дважды — диагностически `preflight.sh`'ом и структурно блоком здоровья `/sdx:status`; отдельная поведенческая проба не добавляет сигнал, только стоимость). Статический `test-hook-wiring.sh` — вне периметра (см. REQ-LIMIT-1). Сознательное ограничение периметра фиксируется заголовочным комментарием скрипта, не молчаливый пропуск.

**Кэш и отпечаток.** Вердикт кэшируется по отпечатку в `.claude/sdx/.cache/selftest.json` (нетрекаемое место, gitignored паттерном `.claude/sdx/.cache/` — он входит в канонический список, который `/sdx:init` раскладывает в проект, и в детект `/sdx:reconcile` для проектов, инициализированных до 2.1.0). Отпечаток — конкатенация четырёх компонентов: версия плагина (`plugin.json`, поле `version`), хэш содержимого `prod-guard.conf`, хэш содержимого `verify-cmd.sh`, содержимое `sdx-version` (маркер версии плагина); при отсутствии файла-источника — sentinel `ABSENT`. Изменение любого из этих четырёх компонентов инвалидирует кэш независимо от остальных (REQ-ST-9).

**Чего в отпечатке НЕТ и что из этого следует.** Содержимое самих пробуемых хуков и содержимое `selftest.sh` в отпечаток не входят. В обычной эксплуатации это не создаёт разрыва: хуки приезжают вместе с плагином, и их правка означает новую версию, то есть смену первого компонента. Разрыв возникает в dogfood-режиме — когда хуки правятся в рабочем дереве без бампа версии: кэш продолжит отдавать прежний вердикт, и `/sdx:status` покажет `ok`, полученный до правки. Инвалидировать вручную можно удалением `.claude/sdx/.cache/selftest.json`.

**Частая причина `degraded`, не означающая поломки хука: отсутствие `jq`.** Без `jq` `prod-guard.sh` уходит в fail-closed и отвечает `deny` на любую команду, включая заведомо безопасную. Проба (б) сверяет обе стороны — «паттерн → deny» И «не паттерн → не deny», — поэтому вторая сторона краснеет, и агрегат становится `degraded`, хотя хук ведёт себя ровно так, как спроектирован. Проба (в) без `jq` краснеет по своей причине: `stop-gate.sh` читает `stage` из состояния сессии через `jq` и без него не доходит до ветки enforcement. То есть без `jq` `degraded` даёт не одна проба, а две, и ни одна из них не означает поломки хука. Диагноз в этом случае даёт не self-test, а `preflight.sh`, который отдельно предупреждает об отсутствии `jq`: если сообщения пришли вместе, чинить надо `jq`, а не хуки.

**Бюджет времени.** Суммарное время self-test на `SessionStart` ограничено `2000` мс (переменная окружения `SDX_SELFTEST_BUDGET_MS`, ≈280 мс на референсной машине, 7× запас на медленное железо). Превышение бюджета — информационное (пишется в кэш как `budget_exceeded: true`), не блокирует `SessionStart` (REQ-ST-7). Замер выполняется самим скриптом (`date +%s%N` с делением на 1000000 мс).

**Исходы и коды возврата.** Три пробы возвращают `pass`/`fail`/`skip` (REQ-ST-4): `pass` — ответ хука совпал с ожиданием; `fail` — выполнилась, но расхождение (`REQ-FAIL-1`); `skip` — пробе не удалось подать (собственная поломка self-test, например отказ `mktemp`, `REQ-FAIL-2`). Агрегированный `selftest_status`: `ok` (все три `pass`), `degraded` (минимум одна `fail`, ноль `skip`), `broken` (минимум одна `skip`). Скрипт безусловно завершается `exit 0` (вдвойне: явным `exit 0` в конце + внешним `timeout 10 ... ; exit 0` в `hooks.json` REQ-FAIL-1/REQ-FAIL-2); ни провал пробы, ни поломка self-test не блокируют `SessionStart`.

**Блок здоровья `/sdx:status`** — новый шаг 5 (DESIGN.md, развилка 7): дешёвые структурные проверки (`jq` в `PATH`, `prod-guard.conf` present+non-empty, `verify-cmd.sh` present+executable, ветка ↔ сессия) вычисляются live, поведенческий вердикт self-test читается из кэша **без повторного прогона** (REQ-HEALTH-3 — чисто читающая операция). Возраст кэша (`ts`) выводится явно (REQ-HEALTH-2) — пользователь не спутает закэшировано с проверено прямо сейчас. Формулировки: диагностика, не gate. Провал self-test — только видимость человеку: работа CLI продолжается как обычно, набор доступных классов риска остаётся прежним, записи в журнал прогонов не возникает (этих механизмов в коде нет вовсе: `FEAT-010`/`FEAT-006`/`FEAT-004` — `open`, волны 2–4), и ни к какому реальному ограничению вердикт не подключён (REQ-LIMIT-2). Формулировать иначе — значит обещать то, чего нет. Регрессионный гейт `[T25]` в `test-selftest.sh` — подстраховка от случайно попавшего буквального обещания, а не доказательство его отсутствия: он ищет литеральные биграммы и не видит ни разорванных разметкой (обратные апострофы), ни разницы между утверждением и отрицанием. Строгий вариант пробовался и отвергнут — увидев разметку, гейт начинает краснеть на корректной прозе, включая фразу, описывающую его самого. Гарантией `REQ-LIMIT-2` остаётся fresh-eyes ревью, читающее тексты. Три точки подключения будущих потребителей: (1) `FEAT-010` — читает `selftest_status` как вход `observed` в `effective = min(declared, observed)`; (2) `FEAT-006` — расширит пробу `prod-guard` при появлении классов `ask`/`allow`/`defer`; (3) `FEAT-004` — может дополнительно получать запись при каждом некэшированном прогоне.

**Интеграция.** Запись в `hooks/hooks.json`:
```json
{
  "type": "command",
  "command": "timeout 10 bash \"${CLAUDE_PLUGIN_ROOT}\"/sdx/hooks/selftest.sh; exit 0"
}
```
Регистрируется ОТДЕЛЬНОЙ записью (не расширением `preflight.sh`) — изоляция failure-modes, porядок (preflight first), страховка от зависания внутренним `exit 0`, усиленная внешним `timeout 10` там, где `timeout` есть. **Граница:** в базовой macOS `timeout` отсутствует, и хвост `; exit 0` проглатывает `command not found` — тогда self-test не выполняется вовсе, а `/sdx:status` показывает «ещё не выполнялся». Известное ограничение, вынесено записью бэклога: тихая деградация внутри механизма, построенного ради её обнаружения.

### `archive-verify` (вызов из `/sdx:archive`, не проводка `hooks.json`)

- **archive-verify** (вызов из `/sdx:archive` после мёржа, вариант A): полагается только на
  переданный `$proj` и git. Резолвит основную ветку через `lib/default-branch.sh` (без хардкода
  `main`, ADR-010) — вызовом `bash <путь>`, а не исполнением файла, поэтому резолв не зависит от
  того, сохранил ли установщик плагина бит выполнения (BUG-008); если резолвер не вернул имени,
  скрипт отказывает явно (`[FAIL] не удалось определить основную ветку`) до всех проверок, а не
  отправляет пустой ref в git. Проверяет Closeout-инварианты: 1 (рабочее дерево чистое), 5 (ветка
  `sdx/<id>` доказуемо слита в автоопределённую основную ветку — имя ветки сверяется точно
  `grep -qx`, при отсутствии ветки слияние считается недоказуемым и деструктив отменяется без
  явного подтверждения `SDX_ARCHIVE_NO_BRANCH_OK=1`), 6 (каталог сессии отсутствует/не tracked
  в дереве основной ветки — детектор пропуска коммита `git rm` до мёржа). Деструктив
  (`git branch -d`; условное `git worktree remove --force` — legacy-совместимость с
  worktree-сессиями до ADR-012, при их отсутствии no-op) выполняется ТОЛЬКО после того, как все
  три инварианта доказаны — `rm -rf` каталога сессии остаётся лишь страховкой на остаточный
  физический путь, а не основным механизмом удаления.

## Верификация (этап Verification)
Этап верификации структурирован по **трём осям** и сочетает корректность-исполнением с независимым fresh-eyes ревью. Команда — `/sdx:verify`, артефакт — `verification_report.md` в папке сессии.

### Три оси
- **Полнота (completeness)** — у каждого требования/критерия есть реализация и тест; нет кода без прослеживаемого требования (scope creep). Источник предупреждений вида «сценарий X не имеет тестового покрытия».
- **Корректность (correctness)** — поведение соответствует намерению, граничные случаи из `DESIGN.md` обработаны, тесты не тавтологичны.
- **Когерентность (coherence)** — непротиворечивость триады `SPEC ↔ DESIGN ↔ Codebase`. Это операционализация детектора коллизий из CLAUDE.md §4: проверку ведёт независимая сторона, а не автор изменений.

### Статусы и гейт
- **FAIL** блокирует гейт (возврат к `developer`, либо `/sdx:next --to <stage>` для более раннего этапа) — в любом `gate_mode`.
- **WARN** не блокирует, но требует явного квитирования пользователем. При `gate_mode: "auto"` квитирование **отложенное**: WARN автоквитируются с записью в `auto_decisions.md` и предъявляются первым блоком дисклоуза на входе в Closeout (ADR-014).
- Покрытие, выведенное из чтения diff, — «видимое» (apparent), а не доказанное.

### Ручное тестирование (интерактивно)
Сценарии, которые нельзя покрыть автотестом, исполняются **интерактивно** командой `/sdx:manual`, а не отдаются пользователю как статичный файл. Оркестратор ведёт пользователя по шагам: на каждый шаг даёт детальную инструкцию и ожидаемый результат, затем собирает фактический результат (`Passed/Failed/Blocked` + наблюдение) через `AskUserQuestion`. План шагов готовит `qa` в `MANUAL_TEST.md` (атомарные шаги: действие / предусловия / ожидаемый результат); результаты прогона дописываются туда же одним блоком. Проваленные шаги становятся находками `FAIL` для гейта верификации наравне с автотестами и fresh-eyes ревью.

### Fresh-eyes: контракт изоляции
Статическое ревью поставки выполняет агент `reviewer` и **только через делегирование Task — никогда инлайн основной сессией** (даже для минимальной точечной правки). Цель — стена контекста: ревьюеру передаются ТОЛЬКО артефакты-контракт и diff поставки, но НЕ `session.log`, не история рассуждений и не пояснения «почему так». Отсутствие памяти о решениях — это и есть механизм: автор изменений рационализировал бы несоответствия, ревьюер без памяти — ловит. Решение, отсутствующее в артефактах, но присутствующее в коде, классифицируется как находка (недокументированное решение).

**Кто вычисляет diff и как он подаётся (BUG-004).** Diff вычисляет **оркестратор** в `/sdx:verify` (шаг 4), а не ревьюер: `git diff $(default-branch.sh)...sdx/<id> -- . ':!.claude/sessions/**'` (основная ветка автоопределяется, REQ-BRANCH-3; каталог артефактов сессии исключён из diff — он tracked на ветке `sdx/<id>` и иначе замусорил бы fresh-eyes-обзор). Вывод **материализуется редиректом в файл** `.claude/sessions/<id>/delivery.diff` (эфемерный буфер, gitignored паттерном `.claude/sessions/*/delivery.diff` наравне с `.stopgate.*`, REQ-SESS-2) — так diff не проходит через контекст оркестратора дважды. Ревьюеру передаётся **путь** к этому файлу; он читает его через `Read`. Контракт изоляции здесь — **enforcement, а не договорённость**: у агента `reviewer` в наборе инструментов НЕТ `Bash` (`agents/reviewer.md` frontmatter), поэтому он физически не может ни пересчитать diff (в т.ч. по хардкоженному `main`), ни дотянуться до `session.log`/произвольного git.

**При `no_gates == true` своего этапа Verification нет (REQ-SCALE-5/REQ-LEGAL-1).** Такая сессия обязана сперва легализоваться (`/sdx:proto` — единственный путь, снятие `no_gates`) и наследует полный объём верификации, выбранного НА САМОЙ легализации объёма (лёгкий или полный) — отдельного, суженного прогона для прототипа до легализации не существует (REQ-VIBE-6): этап физически недостижим, пока флаг не снят (`next` безусловно возвращает `OK no-op Execution`). `reviewer` видит код прототипа в диффе ветки сессии наравне с любым другим кодом; специального исключения для него на этой оси нет.

Объём ревью масштабируется объёмом дельты и флагом `no_code` (REQ-SCALE-8), а не бывшим треком: против полноценных `SPEC.md`/`DESIGN.md` — обязательно и полно; против `change_note.md` (небольшая дельта) — суженно; для минимальной точечной правки — **обязательный лёгкий прогон** против `change_note.md` (ADR-014): оси корректности и когерентности, полнота — в границах change_note. Корректность-исполнением (`qa`) в этом случае не требуется — регрессионный тест и stop-gate покрывают; независимо от `gate_mode`. При `no_code == true` — **обязательный лёгкий прогон**, тем же принципом (ADR-017/ADR-019): fresh-eyes `reviewer` против `change_note.md`, оси корректности и когерентности — трёхсторонне: не противоречит ли новая/изменённая запись бэклога уже существующим и не подменяет ли выбранный тип (`intake`/`grooming`/`audit`) операцию, свойственную другому (create/update/verify); для типа `audit` дополнительно три проверки: (а) каждая `source`-ссылка разрешается в реально существующую находку названного отчёта; (б) каждая запись-регресс ссылается на реально закрытую запись; (в) ни одна новая запись не дублирует открытую по смыслу; полнота — в границах change_note. Субагент `qa` не вызывается вовсе (REQ-SCALE-8) — при `no_code == true` нет кода, поэтому регрессионный тест-прогон не имеет предмета проверки. **Уточнение по факту (не по замыслу):** хук `stop-gate` (`sdx/hooks/stop-gate.sh`) остаётся включённым по значению `stage` (`Execution|Verification`) **независимо от флагов**, кроме `no_gates == true` (REQ-ENF-2, см. «Enforcement-слой» выше) — он не знает о `no_code`. В проекте, где настроен `.claude/sdx/verify-cmd.sh`, `stop-gate` фактически прогонит эту команду и при `no_code == true` на этапе `Verification` — флаг здесь не даёт иммунитета. Прозрачность (no-op) возникает только в проектах без известной тест-команды — тот же случай, что и в любой другой конфигурации без неё, а не свойство, специфичное для `no_code`.

## Контракт закрытия сессии (Closeout)
Этап Closeout завершает ЛЮБУЮ сессию. Это самый частый источник пропусков, поэтому он оформлен как **обязательный чек-лист**: оркестратор печатает его пользователю с отметками `[ ]/[x]` и НЕ объявляет сессию закрытой, пока все пункты не отмечены `[x]`. Если пункт неприменим к сессии — он помечается `[x]` с пометкой `(n/a)`.

**Порядок под вариант A: удаление ДО мёржа.** Весь Closeout выполняется последовательно в
ОДНОМ CLI (ADR-012): шаги 1–5 — на ветке сессии `sdx/<id>`, затем checkout основной ветки,
мёрж и enforcement-проверка. Инженерный инвариант сохранён: HEAD-дерево основной ветки не
должно содержать файлы сессии — удаление оформляется коммитом `git rm -r` НА ВЕТКЕ до мёржа.

**Гейт входа в Closeout** (до начала чек-листа, см. `/sdx:archive`):
- при `no_gates == true` — безусловный стоп ДО начала чек-листа (defense-in-depth поверх приоритетной проверки REQ-LEGAL-1 внутри `cmd_next`, ADR-018): такая сессия физически не может достичь `Closeout` (`next` возвращает `OK no-op Execution`), она направляется на `/sdx:proto` — единственный путь, и предъявление результата, и легализация;
- для ЛЮБОЙ сессии — существует `verification_report.md` без находок FAIL (обязательная верификация обобщена на все сессии без исключения, REQ-SCALE-7, ADR-014/ADR-017); отсутствует → стоп и направление на `/sdx:verify`;
- при `gate_mode: "auto"` — выполнен **дисклоуз**: `auto_decisions.md` выведен пользователю одним блоком (автоквитированные WARN первыми) и получено одно явное подтверждение. Это единственная обязательная остановка авторежима; несогласие → сброс `gate_mode` в `interactive` и пересмотр решения через `/sdx:next --to <stage>` (REQ-NAV-3), Closeout прерывается.

Чек-лист закрытия (см. `/sdx:archive`):

**На ветке сессии `sdx/<id>`:**
1. `[ ]` Рабочее дерево чистое, все изменения закоммичены в ветку сессии `sdx/<id>`.
2. `[ ]` Дельты перенесены в постоянные документы: `change_note.md`/`SPEC.md` → `docs/specs/`, `DESIGN.md` → `docs/designs/`, пользовательская и техническая документация актуализированы. Закоммичено на `sdx/<id>`. При `no_code == true` — как правило `(n/a)`: такая сессия не производит `SPEC.md`/`DESIGN.md`. **Исключение** — если сама сессия (типично `postmortem`) приходит к выводу об изменении протокола `sdx/`, `CLAUDE.md` или порождает новый ADR: тогда пункт выполняется штатно, не `(n/a)`.
3. `[ ]` `PLAN.md` (если создавался) заархивирован в `docs/history/plans/`. Закоммичено. При `no_code == true` — всегда `(n/a)`: `Task Planning` безусловно исключён (REQ-SCALE-4).
4. `[ ]` Глобальный лог знаний обновлён (`docs/history/`) и бэклог актуализирован (`docs/backlog/`, ADR-015): закрытые этой сессией записи получили `status: closed` + `session`; отложенные решения и неквитированные WARN-находки верификации оформлены новыми `DEBT-`/`IDEA-`записями; индекс `README.md` обновлён. При `no_code == true` (ADR-017) правки `docs/backlog/` уже выполнены на планировочных этапах (см. «`no_code == true` — процессная работа без кода» выше, «Что производит `change_note.md`») — здесь, на Closeout, этот пункт **финальная сверка/актуализация статусов, не первичная работа**: подтвердить, что минимум одно изменение `docs/backlog/` (новая запись либо правка `status`/`priority`/`wave` существующей) действительно присутствует и помечено `session: <session_id>`. Оговорка: «не первичная работа» относится к продукту разбора, а не к находкам верификации — неквитированные WARN и отложенные решения возникают ПОСЛЕ планировочных этапов и физически не могли быть оформлены на них, поэтому соответствующие `DEBT-`/`IDEA-`записи заводятся здесь, на Closeout, независимо от `no_code`; для типа `intake` минимум одна из таких записей обязана быть НОВОЙ (не правкой существующей) — единственное место чек-листа, где Closeout содержательно различает `intake` и `grooming`. Для сессий типа `retro`/`postmortem`/`intake` этот же пункт включает перенос постоянного документа разбора из каталога сессии в `docs/history/retro/<session_id>.md`, `docs/history/postmortem/<session_id>.md` или `docs/history/intake/<session_id>.md` соответственно (по аналогии с переносом `PLAN.md` в п.3) — для `grooming` и `audit` отдельного документа нет, записи бэклога являются единственным и достаточным выходом (для `audit` — предмет разбора уже является постоянным документом: сам отчёт `docs/history/audit/audit-<дата>[-N].md`, лежащий в репозитории вне сессии, ADR-019). Закоммичено.
5. `[ ]` Файлы сессии удалены коммитом `git rm -r .claude/sessions/<id>` НА ВЕТКЕ `sdx/<id>`, ДО мёржа (вариант A) — отдельный, явно поименованный коммит, не смешанный с коммитом переноса дельт (п.2).
   **REQ-COMPAT-3, разово перед п.6.** Скан ВСЕХ `.claude/sessions/*/session_state.json` в репозитории (не только этой сессии) на предмет `stage`, использующего снятое этой поставкой имя (`Change`/`Update`/`Prototype`, см. «Совместимость с сессиями, начатыми до ADR-020» выше): находка → одноразовый ручной перенос ДО слияния текущей сессии в основную ветку; отсутствие находок фиксируется явно, пункт не пропускается молча.

**На основной ветке (автоопределяется), тот же CLI:**
6. `[ ]` Ветка `sdx/<id>` слита в основную ветку (`git checkout $(default-branch.sh) && git merge --no-ff sdx/<id>`).
7. `[ ]` Enforcement-проверка закрытия (`archive-verify.sh <id>`) пройдена: инварианты 1 (дерево чисто), 5 (ветка слита), 6 (каталог сессии не tracked в дереве основной ветки — подтверждает, что п.5 выполнен). Скрипт сам выполняет `git branch -d` после подтверждения инвариантов (и `git worktree remove --force` для legacy-worktree-сессий, если такая обнаружится).
8. `[ ]` Факт закрытия зафиксирован в глобальном логе (п.4, уже выполнено) — `session.log` отдельной записи не требует, так как удаляется вместе с каталогом сессии в п.5.

Пункт 5 (удаление файлов сессии, коммит ДО мёржа) исторически пропускается чаще всего —
оркестратор обязан выполнить его явно; его пропуск ловится инвариантом 6 хука `archive-verify.sh` в п.7.

## Import / Export (перенос функциональности между SDX-проектами)
Перенос фичи из проекта-источника в целевой проект, где **оба используют SDX**. Перенос triad-aware: бандл несёт нативные дельты `SPEC`/`DESIGN`, а не только код.

### Асимметрия
- **`/sdx:export` — команда** (без сессии, read-only на источнике): извлекает фичу и пакует в переносимый бандл. Источник не модифицируется.
- **`import` — тип сессии** (полный жизненный цикл, крупная дельта по умолчанию): принимает бандл, реконсилирует с целью и интегрирует. Создаётся через `/sdx:import <путь-к-бандлу>`.

### Формат бандла
Самоописательный каталог `.sdx/bundles/<feature>/` с **полным замыканием**:
```
manifest.yaml        # источник, версия SDX, имя фичи, дата, исходная сессия
spec.delta.md        # срез бизнес-требований (Delta-формат)
design.slice.md      # компоненты, схемы данных, API, обработка ошибок
code/                # файлы кода фичи
tests/               # связанные тесты
deps.yaml            # замыкание зависимостей: внешние либы+версии, внутренние модули
assumptions.md       # допущения о среде (рантайм, фреймворк, общие сервисы)
integration_points.md# точки подключения (роуты, DI-регистрации, entrypoints)
```

### Поток import-сессии
1. Валидация `manifest` и **совместимости версии SDX** (предупреждение при расхождении).
2. Discovery по цели + **реконсиляция** (`architect`): каждый компонент бандла классифицируется —
   - `transplant` — чисто ложится в цель (адаптировать пути/нейминг/импорты);
   - `reimplement` — не ложится; реализуется заново по `spec.delta`/`design.slice`, код бандла = референс;
   - `gap` — в цели нет опоры (зависимость/паттерн отсутствует) → стоп и решение пользователя.
   Результат — артефакт сессии `import_map.md` (компонент → решение → место в цели → заметки).
3. Мёрж `spec.delta.md`/`design.slice.md` в `SPEC`/`DESIGN` цели через Delta-формат, адаптированно. Коллизии триады → стоп и решение пользователя (ось когерентности).
4. Далее обычный full-цикл: Task Planning (задачи transplant + reimplement) → Execution → Verification → Closeout. Тесты из бандла переносятся и служат проверкой сохранности поведения; `reviewer` сверяет diff с мёрженым контрактом; недостающие зависимости добавляются (при необходимости — `devops`).

## Аудит проекта (`/sdx:audit`) и его триаж
Второй, наряду со «Сверкой форматов» ниже, механизм **проектного**, а не сессионного уровня:
целостная ревизионная оценка состояния проекта «как есть» — без эталона, без гейта, без
привязки к какой-либо одной сессии (ADR-019).

**Команда и её read-only контракт.** `/sdx:audit` (`commands/audit.md`) исполняется вне сессий:
не создаёт ветку, не читает и не пишет `session_state.json`/`session.log`, не вызывает
`sdx-stage.sh`. Единственная запись в проект — файл отчёта и, при первом прогоне, каталог под
него. Оркестратор вычисляет форму проекта один раз (детерминированный слой) и распределяет
девять векторов рубрики (`ARCH`/`TRIAD`/`TRACE`/`CODE`/`TEST`/`DOCS`/`DEPLOY`/`SEC`/`PROC`,
полное описание — `agents/auditor.md`) параллельным фан-аутом двумя волнами через `Task` агенту
`auditor` (`model: fable`, без `Bash`/`Edit` — read-only здесь enforcement, а не обещание).
Каждый вызов получает общий read-only вход (`manifest.txt`) и собственный write-only выход
(`<CODE>.md`) — общего изменяемого файла между параллельными вызовами нет ни одного, что снимает
класс риска `PROC-010` структурно.

**Хранение и имя отчёта.** Накопительно, `docs/history/audit/audit-<YYYY-MM-DD>[-N].md`
(`-N` начиная с `2` при повторном прогоне в тот же день). Отчёт после записи иммутабелен: ни
триаж, ни повторные прогоны его не правят и не помечают. Каталог содержит ТОЛЬКО отчёты
прогонов — тип сессии `audit` постоянного документа разбора не производит вовсе (второй тип
`no_code`-семейства без него, наравне с `grooming`, см. выше).

**Каталог прогона.** Промежуточные файлы (`manifest.txt` + файл на вектор) живут в
`.sdx/audit-runs/<YYYY-MM-DD-HHMMSS>/`, никогда не версионируются (точечный паттерн
`.gitignore`) и удаляются оркестратором сразу после успешной записи отчёта; при обрыве прогона
каталог остаётся — существование каталога прогона означает «прогон не завершён», и `/sdx:audit`
перечисляет такие каталоги на старте, предлагая пользователю доснять/отбросить/оставить.

**`source` и три слоя дедупликации.** Триаж отчёта (`/sdx:start audit <путь>`) ссылается на
находки полем `source: <run-id> (<CODE><N>)` (аддитивное расширение уже сложившейся де-факто
формы, схема ADR-015 не меняется). Дедупликация — в три слоя: точный (`grep` по `source`, ловит
повторный триаж того же отчёта), смысловой против записей `open`/`in-progress` (не создавать
дубль, при новой детали — дополнить), смысловой против `closed` (совпадение трактуется как
**регресс**: новая запись с `links: [<closed-id>]` и пометкой в `source`, а не тихий дубль и не
пропуск). Разделение слоёв 1 и 2 содержательно — они закрывают два разных сценария
идемпотентности (повторный триаж того же отчёта vs. новый прогон на неизменившемся проекте).

**Отчёт не гейтит ничего.** Гарантия структурная, не соглашение: `docs/history/audit/` не
назван ни в одной строке `SDX_STAGE_TABLE` (см. «Источник истины: таблица внутри скрипта»
выше), а `sdx-stage.sh` грепает исключительно артефакты таблицы внутри каталога сессии — отчёт
аудита физически не способен повлиять на гейт, даже если бы содержал литерал `^### [FAIL]`
(который в нём намеренно не используется). ADR-019 фиксирует это инвариантом.

**Границы.** Вектор `SEC` работает без внешних сканеров безопасности/зависимостей/CVE и без
сети — только то, что видно прозаическому анализу репозитория; недостающее объявляется в разделе
`## Границы прогона` отчёта, а не выдаётся за проверенное. Значение `model: fable` не
валидируется ни одним тестом фреймворка — тот же известный пробел, что и у трёх прежних тиров
(ADR-019, раздел «Границы»; учтено записью `docs/backlog/`).

## Сверка форматов после релиза и миграции
Приведение накопленных в проекте данных к актуальному формату фреймворка — обязательный шаг:
после первого подключения SDX к существующему проекту (`/sdx:init`, особенно `--existing`)
и после каждого обновления версии установленного плагина. Формат данных фреймворка эволюционирует
(ADR-015 ввёл `docs/backlog/`, ADR-017 — `docs/history/retro|postmortem|intake/`, ADR-012 сменил
модель сессий) — без явной сверки проект продолжает жить в старом формате, пока расхождение не
заметят вручную.

**Механизм.** Команда `/sdx:reconcile` (`commands/reconcile.md`) — не требует активной сессии,
работает в любой момент жизненного цикла проекта. Две задачи слиты в одну команду: перенос
незакрытых задач/техдолга/открытых вопросов из легаси-материала проекта (заметки, память,
старые сессии, roadmap-блоки) в `docs/backlog/` (ADR-015), и приведение устаревших структур
хранения к текущей раскладке. Перенесённые источники помечаются на месте маркером
`<!-- SDX-MIGRATED: → <ID> (<дата>) -->`, не удаляются — с единственным именованным
исключением: бандлы `.sdx/bundles/**` сканируются, но НЕ помечаются (см. границы ниже).

**Точки автовызова.** `/sdx:init` вызывает `/sdx:reconcile` автоматически после разворачивания
структуры (и, если применимо, после реверс-инжиниринга `--existing`) — момент, когда легаси-
материал максимально богат, а бэклог пуст. `/sdx:start` сверяет версию плагина с маркером
`.claude/sdx/sdx-version` (пишется исключительно `/sdx:reconcile`, по факту завершённой
сверки — `/sdx:init` сам маркер не пишет, только вызывает `/sdx:reconcile`) и при расхождении **предлагает**
прогнать `/sdx:reconcile` до старта новой сессии — одной строкой, с возможностью отказаться.
У предложения ровно два терминальных исхода: **отказ** не блокирует старт и не запоминается
глобально (предложение повторится при следующей смене версии), **согласие** останавливает
`/sdx:start` без создания сессии — реконсиляция выполняется отдельной командой в своей ветке,
после чего `/sdx:start` повторяется с теми же аргументами. Инлайн `/sdx:start` реконсиляцию не
выполняет и её результат не коммитит: он относится ко всему проекту, а не к задаче сессии, и
идёт обычным путём правок репозитория (branch-first, ADR-009). Выбор точки автопроверки — `/sdx:start`, а не SessionStart-хук: ни одна SDX-сессия
не начинается мимо `/sdx:start`, а хук потребовал бы отдельного скрипта и тест-сьюта ради
напоминания.

**Границы.**
- Скан источников в `/sdx:reconcile` — прозаический (агент читает и судит смысл),
  не детерминированный парсер: полнота не гарантируется, отсюда обязательный отчёт
  `docs/sdx-reconcile-report.md` со списком просканированного и явно исключённого
  (`docs/backlog/`, `docs/history/`, исходный код, `.git/`).
- Скан «файлов памяти» покрывает ТОЛЬКО пути внутри рабочего дерева проекта
  (`.claude/memory/`, `CLAUDE.local.md`). Автономная память Claude Code вне дерева
  (пользовательский каталог `~/.claude/projects/<slug>/memory/`) в скан не входит и требует
  отдельного ручного просмотра пользователем — это осознанная граница (полное покрытие
  потребовало бы доступа вне рабочего дерева проекта, что не согласуется с моделью команды),
  не пробел реализации.
- TODO/FIXME в исходном коде проекта сознательно вне скоупа скана — они разбираются обычным
  код-ревью, а не этим механизмом; иначе бэклог утонул бы в шуме реализации.
- Маркер `SDX-MIGRATED` — конвенция в тексте файла, а не enforced хуком; его ручное удаление
  приведёт к повторному заведению записи при следующем скане.
- Маркер `.claude/sdx/sdx-version` пишет ИСКЛЮЧИТЕЛЬНО `/sdx:reconcile`, и только по факту
  завершённой (не `--scan-only`, не отменённой/отклонённой пользователем) сверки; `/sdx:init`
  сам маркер не пишет — иначе отказ или прерывание реконсиляции внутри `/sdx:init` сделал бы
  состояние «не отреконсилен» неотличимым от «отреконсилен».
- Проверка версии в `/sdx:start` покрывает только момент старта сессии — работу с проектом
  вне команд `/sdx:*` она не видит.
- `--auto` этой команды — НЕ то же самое, что `gate_mode: auto` протокола (ADR-014): у флага
  нет стоп-рубрики, `auto_decisions.md` и обязательного дисклоуза перед Closeout, это буквально
  только «не спрашивать подтверждения по группам находок». Входные предохранители команды
  (чистое рабочее дерево, потолок числа операций за прогон, рекомендация предварительного
  `--scan-only`) частично компенсируют это, но не заменяют гарантии авторежима протокола.
- Дефолт `priority: normal` применяется ко всем записям, перенесённым этим механизмом —
  спросить не у кого в `--auto`, а в интерактиве пользователь подтверждает группу целиком,
  не поле за полем; приоритет уточняется на обычном груминге (`/sdx:backlog`).
- `.sdx/bundles/**` (переносимые бандлы `/sdx:export`) — сканируемый источник с двумя
  оговорками: кандидатами являются только незакрытые/отложенные требования и открытые
  вопросы бандла (roadmap-разделы, `assumptions.md`, отложенные `REQ-*`), но НИКОГДА срезы
  `SPEC`/`DESIGN`, код и тесты — для них штатный путь `/sdx:import`; и маркер `SDX-MIGRATED`
  в тело бандла НЕ ставится — третье поведение источника, отличное и от «сканируется и
  помечается», и от «исключён из скана». Причина исключения из пометки: бандл переносим
  между проектами, скопированный маркер со ссылкой на `DEBT-0NN` ЭТОГО проекта в другом
  проекте ничего не значит и вводит в заблуждение; идемпотентность повторного скана бандлов
  держится на дедупликации по смыслу (шаг 5 команды), а не на маркере.

## Непрерывное улучшение (рекомендации по ходу сессии)
Оркестратор ОБЯЗАН активно озвучивать пользователю замеченные по ходу реальной работы
возможности улучшения фреймворка и процесса, а не молча их обходить. Сигналы: любой workaround
(обход хука через shell, ручная правка состояния), ложное срабатывание enforcement-слоя,
избыточная церемония для объёма задачи, повторяющаяся ручная операция, отсутствующая автоматизация.
Правило: столкнулся с трением → сообщи одной-двумя строками и предложи оформить запись бэклога
(`/sdx:backlog add`) либо, для мета-репозитория SDX, отдельную сессию доработки. Молчаливый
обход запрещён — так теряются дефекты enforcement-слоя (прецедент: BUG-006 — stage-gate на
Windows долго обходили через shell вместо репорта). В авторежиме это не гейт: рекомендация
озвучивается без остановки работы, решение об оформлении — за пользователем (или на дисклоузе
Closeout).

## Журнал решений (`decisions_log.md`) — `PROC-019`

Рядом с `auto_decisions.md` (см. «Авторежим гейтов» выше) вводится второй, дополняющий, не
пересекающийся с ним артефакт сессии — `.claude/sessions/<id>/decisions_log.md`. Оба файла
описывают дополняющие, а не пересекающиеся множества событий одной сессии: `auto_decisions.md`
триггерится фактом, что решение было принято **дефолтом, без остановки**; `decisions_log.md`
триггерится противоположным фактом — **остановкой на стоп-рубрике** (см. список категорий
ниже), причём независимо от `gate_mode` — стоп-рубрика останавливает `auto`-сессию так же, как
`interactive` (см. «Авторежим гейтов»: «Авторежим ОБЯЗАН остановиться…»), и решение, принятое на
этой остановке, человек принимает в обоих режимах одинаково.

**Триггер записи — категории стоп-рубрики плюс явные акты триажа находок.** Семь коротких
тегов, используемых в поле «развилка» записи: `[триада]` (коллизия триады SPEC ↔ DESIGN ↔
Codebase), `[FAIL]` (находка FAIL верификации/красный тест-пол stop-gate), `[контракт]`
(изменение внешнего контракта — публичный API, схема данных, формат файла, миграция),
`[деструктив]` (деструктивная/необратимая операция, территория prod-guard), `[объём]`
(эскалация объёма — переход к более тяжёлому артефакту для уже пройденного этапа), `[ручной-шаг]`
(шаг ручного тестирования `/sdx:manual`), `[триаж]` (явный акт «отложить сейчас» / «принять
сейчас» по находке). **Слово «явный» в определении `[триаж]` несёт нагрузку:** тег покрывает
решение, принятое ЧЕЛОВЕКОМ на остановке. Находка `WARN` при `gate_mode: "auto"` под него не
подпадает — она автоквитируется дефолтом БЕЗ остановки и уходит строкой в `auto_decisions.md`
(`WARN` не входит в стоп-рубрику); тот же `WARN` при `gate_mode: "interactive"` требует явного
квитирования человеком и потому получает запись `[триаж]`. Это не исключение из правила
«стоп-рубрика не зависит от режима», а следствие того, что `WARN` стоп-рубрикой и не является:
от режима зависит, возникает ли акт человека, а не то, фиксируется ли он. Триаж находки `FAIL`
(«исправлять сейчас» / «отложить в бэклог») — стоп-рубрика, и фиксируется в ЛЮБОМ режиме. Первые шесть тегов соответствуют шести пунктам стоп-рубрики дословно; текст
самой стоп-рубрики выше этим не меняется — раздел лишь называет, куда идёт решение, принятое на
ней.

**Формат записи — ровно четыре поля,** Markdown-блок (не однострочник `auto_decisions.md` — поле
«обоснование» не сжимается в одну читаемую строку без потери):

```markdown
### Развилка: [<категория>] <краткое название> (этап: <Stage>)
- Вариант: <что принято — формулировка, которую возобновлённый прогон обязан соблюдать без диалога>
- Обоснование: <почему выбран именно этот вариант — не для повторного обсуждения, а чтобы отличить решение от недосмотра>
```

`<категория>` — один из семи тегов выше; тег живёт внутри поля «развилка», а не отдельным пятым
полем (запись остаётся буквально четырёхпольной). Запись без любого из четырёх полей не считается
корректной. Поля «время»/timestamp сознательно нет — порядок записей уже даёт порядок добавления
в append-only файл, а провенанс по времени даёт метаданные git-коммита, в который запись попадёт.

**Писатель — только оркестратор (модель), безусловно.** Ни один хук, заведённый в `hooks.json`
этого репозитория (`SessionStart`, `PreToolUse`/`Bash`, `Stop`), не имеет доступа к тексту
диалога — содержание решения человека структурно не наблюдаемо ни одним из них, а
`PostToolUse`/`SessionEnd`/`PreCompact`, которые в принципе получали бы больше данных, сегодня не
проводные. **Асимметрия гарантии подлинности, названа явно.** Запись в `decisions_log.md` делает
оркестратор (модель) — тот же агент, чьему самоотчёту не доверяет для остальных категорий событий
наблюдательная часть журнала событий, которые видит хук. Гарантия «журнал недоступен подделке,
потому что пишет не модель» на этот файл НЕ распространяется — независимого наблюдателя решений в
этой поставке нет и не может быть, потому что содержание диалога с человеком не наблюдаемо ни
одним хуком этого репозитория. Любая документация и любые формулировки о `decisions_log.md`
обязаны называть эту асимметрию явно, а не молчаливо переносить гарантию наблюдаемого хуком
журнала.

**Момент записи — деферред-батчинг к ближайшему уже происходящему коммиту, не отдельный ход.**
Запись, принятая на стоп-рубрике, держится в рабочем контексте модели с момента принятия и
физически пишется на диск и коммитится тем же `git add`, что и артефакт/состояние, ради которого
коммит и так должен был случиться — без отдельного, выделенного исключительно под запись решения
хода инструмента. Конкретные точки батчинга: переход этапа (`sdx-stage.sh next` / `next --to`) —
для `[триада]`/`[объём]`; коммит `verification_report.md` — для `[FAIL]`/`[триаж]`; коммит
`SPEC.md`/`DESIGN.md` на Business Spec/Technical Design — для `[контракт]`; коммит блока
результатов в `MANUAL_TEST.md` — для `[ручной-шаг]`; коммиты `/sdx:proto` (легализация/откат) —
для `[деструктив]`. Решение, принятое мид-этапно (не совпадающее ни с каким переходом), остаётся
в контексте до ближайшего коммита, который случится по другой причине — маржинальная стоимость
такого решения равна нулю дополнительных ходов, но ценой такого выбора остаётся то же самое окно
недолговечности, что уже названо ниже границей REQ-BOUND-1(a).

**Файл ленивый и append-only.** `decisions_log.md` НЕ заводится пустым при `/sdx:start` (в
отличие от `auto_decisions.md` при `--auto`) — создаётся при первом решении, достигшем
стоп-рубрики. Отсутствие файла — не ошибка, трактуется как «решений не зафиксировано» тем же
кодом-путём, что и для сессий, начатых до этой поставки. Записи не редактируются и не удаляются
задним числом: если решение впоследствии пересмотрено правкой контракта, пересмотр получает
**новую** запись («пересматривает <предыдущая развилка>»), а не правку старой.
`decisions_log.md` — провенанс истории «почему», а не четвёртый член триады SPEC ↔ DESIGN ↔
Codebase, и не арбитрирует её: если запись противоречит текущему (с тех пор изменённому)
состоянию контракта — это коллизия триады по обычной политике (CLAUDE.md §4), не автоматическое
применение устаревшего варианта. `decisions_log.md` НЕ входит в состав входа `reviewer` на
fresh-eyes ревью (см. «Fresh-eyes: контракт изоляции») — тем же основанием, что и `session.log`:
поле «обоснование» несёт пояснение вида «мы так сделали, потому что…», прямо исключённое
контрактом изоляции.

**Честные границы (REQ-BOUND-1).** Механизм не обещает и не должен создавать впечатление, что
обещает, восстановление: (а) незакоммиченной работы в окне между коммитами (норма REQ-SESS-1
сокращает окно, но не закрывает его); (б) содержания вопроса, заданного, но не отвеченного на
момент смерти CLI (решения ещё не существует — записывать нечего); (в) любого содержимого,
существовавшего только в контексте модели и не осевшего ни в одном файле на диске к моменту
последнего коммита. Ни один пользовательский текст (сообщения, документация) не должен
утверждать или подразумевать восстановление сверх этой границы.

## `/sdx:resume` — durable-возобновление прогона (`PROC-019`)

Команда `/sdx:resume` восстанавливает прогон **на момент последнего зафиксированного
(закоммиченного) состояния**, включая все решения, записанные в журнал решений
(`decisions_log.md`) до этой точки, без участия человека и без чтения истории чата — и, в
отличие от `/sdx:status`, не просто предъявляет прочитанное человеку, а внедряет его в рабочий
контекст возобновлённого агента и продолжает исполнение прогона (переходит к следующему шагу
активного плана/этапа). Это категорическое отличие от `/sdx:status`: **`/sdx:status` показывает
прочитанное, `/sdx:resume` внедряет прочитанное в контекст и продолжает исполнение** — инвариант
`/sdx:status` «просмотр статуса не мутирует сессию» этой командой не затрагивается и не
отменяется, `/sdx:resume` — мутирующая операция по построению.

**Композиция чтения** (без обращения к истории чата) — `session_state.json` (этап, флаги,
`gate_mode`), прогресс `PLAN.md` (доля отмеченных задач и первая незавершённая), последняя строка
`[STAGE_CHANGE]` `session.log`, содержимое `decisions_log.md` (если файл есть — иначе «журнал
решений пуст/отсутствует», не ошибка), состав `git`. Каждый источник — независимо проверяемая
команда.

**Гард чистого рабочего дерева.** Перед чтением `/sdx:resume` обязана проверить `git status
--porcelain`: если рабочее дерево не чистое — жёсткий стоп с инструкцией разобраться вручную, без
чтения/интерпретации грязных файлов как части восстановленного состояния — единственный способ
удержать формулировку выше буквально верной (незакоммиченная правка не является частью
«последнего зафиксированного (закоммиченного) состояния»).

**Соблюдение записанных решений (REQ-RESUME-3).** Перед любым `AskUserQuestion`/аналогичным
запросом по развилке из состава стоп-рубрики — продолженное исполнение обязано свериться с
`decisions_log.md`: развилка найдена (текстовое сопоставление по ключевым терминам) → применить
зафиксированный вариант молча и продолжать, без повторного `AskUserQuestion` по этой же развилке;
не найдено → вести себя как обычно (задать вопрос). Тот же алгоритм применим и вне `/sdx:resume`,
для живого хода сессии с памятью, при переходах `/sdx:next`.

## Checkpoint и сброс контекста
Команда `/sdx:checkpoint` записывает суммаризацию состояния в `.claude/sessions/<id>/checkpoint.md`. После этого пользователь может выполнить `/clear`; восстановление контекста происходит чтением файлов сессии (`/sdx:status`, `checkpoint.md`). Менять системный промпт или очищать контекст программно невозможно.
