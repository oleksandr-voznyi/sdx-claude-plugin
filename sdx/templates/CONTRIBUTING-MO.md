# Как сдать изменение узлу мета-оркестратора (МО)

Этот документ — для исполнителя, который делает изменение по заказу узла МО и не пользуется
конкретным инструментом сдачи. Нужны только `git`, `sha256sum` и текстовый редактор. Любой харнес,
который пишет те же файлы, сдаёт изменение так же.

Формальная форма манифеста — шаблон `CHANGE.template.yaml` (sim-kit; в плагине SDX он лежит в
`sdx/mo/CHANGE.template.yaml`, а не рядом с этим документом — при передаче документа приложите шаблон). Этот документ его не заменяет, а поясняет, как заполнить поля.

## 1. Что такое пакет изменения

Пакет — одна git-ветка в репозитории проекта, которую узел МО принимает на аудит. Узел сам проверяет
формальные признаки пакета (формат манифеста, область, сумма архива, реестр решений), сам гоняет
тесты на своём стенде, сам решает о слиянии. Пакет отдают узлу, а не заказчику: заказчик получает
результат после решения узла.

Пакет состоит из ровно двух слоёв:

1. **Код** — один squash-коммит (`head`) над актуальной базовой веткой проекта (`base`).
2. **Манифест** — файл `CHANGE.yaml` в корне, отдельным **последним** коммитом поверх `head`.
   Манифест не может входить в `head`: в нём записана сумма архива `head`, а архив не может
   содержать собственную сумму.

Ветка называется `change/<C>-<executor>`, где `<C>` — идентификатор обязательства узла (из заказа),
`<executor>` — ваш идентификатор исполнителя из мандата (`change/<C>-<executor>` должна попадать
под маски `scope.branches` мандата). Оба идентификатора — символы `A-Z a-z 0-9 . _ -`, начало —
буква или цифра, длина до 64; двоеточия, пробелы и `..` недопустимы.

## 2. Порядок сдачи

```
git fetch
git switch -c change/<C>-<executor> <base-ветка-проекта>
# ... работа; внутри пакета остаётся только то, что идёт в проект ...
git reset --soft <base-ветка-проекта>          # свести историю в один коммит
git commit -m "<C>: <название изменения>"      # head
# заполнить CHANGE.yaml (раздел 3), затем отдельным коммитом:
git add CHANGE.yaml && git commit -m "<C>: manifest"
git push origin change/<C>-<executor>
```

Правила порядка:

- Манифест — **последний** коммит; между `head` и вершиной ветки нет ничего, а разница между ними —
  ровно файл `CHANGE.yaml`.
- В коде (в `head`) не должно быть файла `CHANGE.yaml`.
- Рабочие записи сессии исполнителя (журналы, отчёты, заметки) в пакет не входят: итог, который нужен
  проекту, — это изменённый код, документация «как стало» и запись решения.
- Если пакет нужно переделать, соберите новый `head` поверх прежнего (родитель нового `head` — прежняя
  вершина ветки), чтобы история обсуждения не пропала, и пересчитайте поля манифеста. Если за это время
  базовая ветка ушла вперёд, у нового `head` два родителя: прежняя вершина и новая база — тогда
  `merge-base(head, dev)` равен новой базе, а между `head` и вершиной ветки по-прежнему только `CHANGE.yaml`.
  Поэтому при повторной сдаче `head` — merge-коммит, а не squash: это ожидаемо, узел сливает пакет
  через `merge --squash`, и в базу он попадает одним коммитом.

## 3. Манифест `CHANGE.yaml` (формат 1)

Все строки пишите в двойных кавычках: 12-значный `mandate_digest` из одних цифр голый YAML прочтёт как
число.

| Поле | Что значит | Как получить |
|---|---|---|
| `format` | версия формата, сейчас `1` | константа |
| `commitment` | обязательство узла, по которому сделано изменение | из заказа |
| `executor` | ваш идентификатор в мандате | из заказа/мандата |
| `mandate_digest` | какой мандат вы считаете действующим | поле `digest` в `.mesh/mandate.yaml` |
| `base` | от какого коммита базовой ветки сделан пакет | `git merge-base <head> <base-ветка>` |
| `head` | голова кода | `git rev-parse HEAD` (до коммита манифеста) |
| `archive_sha256` | тождество поставки: узел пересчитывает его сам | `git archive --format=tar <head> \| sha256sum` |
| `scope_touched` | какие файлы изменены (включая сгенерированные: lock-файлы, сборки) | `git diff --name-only <base>..<head>` |
| `touches_shared` | `true`, если правятся общие пути из `scope.shared_paths` мандата | пересечение `scope_touched` с `shared_paths` |
| `spec` | `docs/specs/<module>.md@<sha>`, если у вас была спецификация | необязательно; ключ опускается, если её нет |
| `verify` | что вы проверили сами: `tests: pass` или `unknown`, `report` — где отчёт | честно; узел перепроверит |
| `adr` | запись решения: `<файл реестра>#<якорь>` | файл реестра обязан быть **изменён в этом пакете** |
| `docs` | итоговая документация «как стало», вошедшая в пакет | файлы из `scope_touched` под `docs_paths` |
| `history_ref` | где лежит история работы, если не в репозитории | например `executor:<id сессии>` |
| `notes` | свободный текст | без секретов |

Пояснения:

- **`touches_shared: true`** означает, что слияние — решение человека. Не декларировать при пересечении
  с общими путями — ошибка, узел вернёт пакет.
- **`adr`** обязателен, если `docs_in_repo` мандата равен `final` (значение по умолчанию): реестр
  решений проекта (например `docs/DECISIONS.md`) должен быть изменён в пакете, а `adr` — указывать на
  этот файл (часть после `#` узел отбрасывает).
- **`docs`** — файлы документации «как стало»; при `docs_in_repo: none` список пуст.
- Секреты (пароли, токены, ключи) в изменении и в `notes` недопустимы.

## 4. Область и срок мандата

Всё, что вы меняете, должно лежать в области мандата (`.mesh/mandate.yaml`):

- `scope.paths` — где вы пишете;
- `scope.shared_paths` — общие пути: правка допустима, но слияние решает человек (`touches_shared`);
- `scope.docs_paths` — итоговая документация и записи решений: допустимы всегда;
- `scope.branches` — маски имён веток, которые вы вправе сдавать;
- `valid_until` — срок мандата: просроченный мандат узел не принимает.

Файл вне области — основание отклонить пакет целиком, поэтому перед сдачей сверьте `scope_touched` с
областью.

## 5. Протокол решений `protocol.yaml`

Если узел просит протокол работы, положите файл `protocol.yaml` рядом с заказом (в каталог, который
указал узел; в пакет он не входит). Пять ключей-списков присутствуют всегда, пустой раздел — `[]`:

```yaml
done:        # что сделано
  - "…"
decisions:   # принятые решения; у каждого непустые id, what, why
  - id: "D-1"
    what: "…"
    why: "…"
    alternatives: []
    adr: false
questions:   # открытые вопросы
  - "…"
verified:    # что проверено
  - "…"
deltas:      # изменения требований
  - "[ADDED] REQ-1"
```

## 6. Что делает узел и чего не делаете вы

Узел сам: проверяет формальные признаки пакета, запускает наборы тестов на своём стенде, ведёт ревью,
решает о слиянии, ставит теги, продвигает изменение по контурам.

Вы **не**: сливаете пакет в защищённые ветки (`dev`, `stage`, `main`), ставите теги, пушите куда-либо,
кроме ветки `change/<C>-<executor>`, и не правите чужие пакеты.

## 7. Чек-лист самопроверки

- [ ] Имя ветки `change/<C>-<executor>`, оба идентификатора допустимы и совпадают с заказом.
- [ ] `head` — один squash-коммит над актуальной базой; `CHANGE.yaml` в нём нет.
- [ ] `CHANGE.yaml` — отдельный последний коммит; `git diff --name-only <head> <tip>` печатает ровно `CHANGE.yaml`.
- [ ] `archive_sha256` пересчитан от `head` командой из раздела 3.
- [ ] Все файлы из `scope_touched` лежат в области мандата, срок мандата не истёк.
- [ ] `touches_shared` совпадает с пересечением `shared_paths`.
- [ ] Реестр решений изменён в пакете, `adr` указывает на него (при `docs_in_repo: final`).
- [ ] В изменении и в `notes` нет секретов.
- [ ] `mandate_digest` равен `digest` из актуального `.mesh/mandate.yaml`.
